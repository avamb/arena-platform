# Локальная сборка табличного исходника

Это ограниченная реализация для явно нумерованных таблиц. Она пока не является
универсальным распознавателем произвольного PDF/JPEG.

1. Профиль указывает конкретный исходник и SHA-256, область мест, область подписей
   рядов, параметры измерения и происхождение названия секции. Ручной SVG не читается.
2. Для PDF извлекаются слова и прямоугольники. Номер сопоставляется только с реальной
   замкнутой ячейкой, затем с единственной подписью ряда. Нет границы/номера/подписи —
   quarantine, а не заполнение последовательности.
3. Для JPEG используется source-bound проверенная разметка ячеек и напечатанных
   номеров. Есть проверка границ изображения и наличия чернил в каждой ячейке.
   Это ручная аннотация источника, НЕ автоматическое подтверждение цифр OCR.
4. Покрытие всех исходных чисел проверяется отдельно от смысла мест. Надписи вроде
   «ненумерованные», смешанные конфигурации или неполные правила блокируют экспорт,
   пока semantic review не станет PASS. До этого места имеют QUARANTINE.
5. После независимой проверки создаётся seating-json-v1. Исходные координаты не
   изменяются. Подгонка осей и шага — отдельный presentation profile с provenance.
6. Общий exporter создаёт venue_Bil24.svg и venue_Arena.svg, 15 категорий без цен.
   Их байты могут совпадать: общий authoring grammar поддерживается обоими парсерами.
   Это не доказывает одинаковое отображение в Arena Widget.
7. Проверяются identities, дубли, координаты, пересечения, XML и бюджет байтов.
   Проверка браузера и настоящий локальный Arena ImportSVG выполняются отдельно.
   Сервер BIL24 и Arena Admin/Widget требуют отдельной UI-проверки.

Запуск из feature worktree:

    python -m venue_generator.table_pipeline SOURCE_PROFILE.json --output-dir NEW_DIRECTORY

Выходная директория должна быть новой. manifest.json остаётся INCOMPLETE при
неполном результате; готовые SVG не публикуются. Повторный запуск не переписывает
старый пакет. CLI не вызывает API. Расходы Claude относятся к предыдущему анализу,
а elapsed_local_seconds — только к локальной сборке, не к полному времени работы.

Файлы источников, профили клиентских площадок и результаты остаются в локальных
игнорируемых каталогах. В Git попадают только общий код, документация и тесты.


## Комментарии организатора

Исходный комментарий хранится целиком с evidence ID, SHA-256 текста и явной
областью действия (идентификаторы выделенных регионов). Поддерживаемые фразы
обрабатывает organizer_comments.py. «Предполагаю» сохраняется как tentative,
а не превращается в подтверждённый факт. Роль, видимость и доступность продажи
разделены: service + visible=true + bookable=false.

Служебные обозначения находятся в отдельном декоративном слое ServiceMarkers.
У них нет официального номера и функциональной записи места. Поэтому они
не попадают в выбираемые кресла при локальном импорте. Предположительный статус
подписывается на схеме. Проверка реального frontend остаётся отдельной.

Противоречивый текст, разные указания группам, вопрос вместо инструкции или
неподдерживаемая формулировка дают NEEDS_CLARIFICATION. Свободный текст никогда
не увеличивает продаваемый инвентарь. Будущая LLM-интерпретация тоже должна
проходить эти структурные ограничения; универсальное понимание русского
языка текущим правиловым интерпретатором не заявляется.

## Векторные примитивы, подписи столбцов и вертикальные ряды

`pdf_numbered_regions` использует исходные PDF rects/curves заданного размера.
Каждый номер должен находиться в единственном выбранном примитиве; подпись ряда
сопоставляется по явно заданной оси X либо Y. Отсутствующие подписи, неразобранные
числа, пересекающиеся области и повторные identities блокируют экспорт.
Это не распознавание текста, превращённого в кривые, и не OCR растрового PDF.

Для проверенной растровой таблицы допускается `identity_mode=column_header`:
номер связан с bbox напечатанного заголовка того же столбца. Требуются отдельное
source review и evidence правила. Сейчас этот режим проверяет только явно
подтверждённые голубые ячейки: белые пробелы и малиновые ячейки не проходят.
Он не выводит последовательность из желаемой вместимости. Порог чернил для
светлых подписей на сером фоне задаётся в проверенной аннотации и ограничен 230;
белый фон остаётся исключённым. Автоматическая точность OCR не заявляется.

Секторы одной схемы имеют отдельные профили и identities. Одинаковые ряд/место
в разных секторах не объединяются. Один физический source bbox не может создать
два места. `row_label_positions` позволяет подписывать концы вертикальных рядов:
нужны две позиции для каждого ряда, evidence, проверка границ и пересечений
с местами. Это presentation-разметка, исходные координаты кресел не меняются.

## Явное правило организатора и неактивные номерные места

`organizer_inventory.apply_numbering` принимает отдельно сохранённое, подтверждённое
решение с SHA исходника, evidence ID и оригинальным ответом владельца. Сейчас
поддерживается последовательность от1 по явно указанному направлению через проход.
Число реально измеренных мест каждого ряда должно точно совпасть с разрешённым;
пропуски не заполняются. Существующие исходные номера не перезаписываются.
Это структурированное решение после проверки ответа человеком, а не универсальный
NLU-парсер и не доказательство, что номера напечатаны на изображении.

В master Seating JSON сохраняются ВСЕ места и их identities: VALID или UNAVAILABLE.
Неактивные номера входят в последовательность. Для текущего общего authoring
экспорта UNAVAILABLE рисуются только в декоре с серыми обозначениями и номерами;
они не создают выбираемые билеты. Этот декоративный вариант пригоден только для статического просмотра;
он не удовлетворяет требованию редактировать недоступность места в событии. Роль
«служебное», «продано» или «отсутствует» из одного серого цвета не выводится.
Геометрия выравнивается до разделения активных/неактивных, поэтому зазоры
и оси не меняются при наличии серых мест. Общий лимит SVG проверяется повторно
после добавления декора по числу функционально импортируемых мест.

## Поправка: продажи исходного события и схема площадки

Если исходник показывает уже проданные места, перед экспортом обязателен вопрос:
«Создаём чистую схему для нового события или переносим недоступность проданных
мест с возможностью последующего редактирования?» Ответ «серые неактивны»
не выбирает сценарий события автоматически. Решение хранит `event_intent`:
`new_event` либо `carry_source_sales`; отсутствие выбора блокирует обработку.

В обоих сценариях сохраняются все физические места и номера. `source_event_state`
хранит наблюдение о старом событии отдельно от `target_event_availability`.
Для нового события все места доступны; перенос требует применения изменяемых
блокировок в целевой системе. SVG-декор не является заменой такой операции.
Прежний `append_unavailable` разрешён только для явно помеченного
`static_preview_only`; это иллюстрация, не готовый импорт статусов события.
Готовность сценария переноса нельзя объявлять без проверки целевого механизма
блокировки/разблокировки. Никакие реальные заказы, покупатели или оплаты
из цвета кресла не создаются.


## Подписи рядов соседних секций

Presentation profile поддерживает `visible_row_label_sides`: `["left", "right"]`
по умолчанию, одна сторона или пустой список. Изменение требует явного
`row_label_visibility_evidence`. Для непрерывного ряда, пересекающего границу
секций, подписи можно оставить только на внешних краях, чтобы они не попадали
на соседние кресла. Вспомогательная группа мест для колясок может не повторять
визуальные подписи ряда. Функциональные row title, номера и исходные координаты
при этом сохраняются; меняются только декоративные подписи. Выбор сторон требует
визуальной проверки составной схемы, локальная проверка одной секции не доказывает
отсутствие наложений на другую секцию.
