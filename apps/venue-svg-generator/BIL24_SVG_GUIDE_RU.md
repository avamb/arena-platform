## 2. Авторский SVG: требования Bil24

Краткий пересказ [инструкции по созданию](https://bil24.pro/create_schemes.html):

1. Перед работой нужны данные о расположении мест, категориях и квотах. Геометрия должна соответствовать реальному залу; удобно рисовать отдельным слоем поверх актуального растрового плана.
2. Документ — не более **2000 × 2000 px**; для стадиона рекомендован полный этот размер.
3. Место — только `circle`, с контуром **3 px**. Иные формы мест не допускаются.
4. Последовательность: нарисовать места и декор → категории → легенду → раскрасить → сгруппировать ряды → назначить сектор, ряд и номер.
5. Группа категорий имеет `id="PriceCategory"`; круг категории — метку `#Название`. Текст названий — `id="PriceCategoryText"`; текст цены отмечается меткой соответствующей категории. Метки круга и текста нельзя перепутать.
6. Группа `Legend` содержит обозначения `Sold`, `None`, `Reserved`, `MyTickets` для проданных, отсутствующих в продаже, забронированных и собственных билетов.
7. Цвет места точно совпадает с соответствующей категорией либо статусом легенды.
8. Ряд объединяется в группу: метка — `#Сектор`, название — ряд. У круга название — номер места, метка — необязательный штрихкод. Название и ID не взаимозаменяемы. Для синхронизации с ВБС начальное слово «Сектор» убирается: `Сектор А1` → `#А1`.
9. Сохранить SVG и загрузить в Редактор событий. Он проверяет схему, формирует отчёт, оптимизирует файл, проверяет относительный размер и преобразует в BSS.

## 3. Практическая работа в Inkscape

### Подложка

Через **File → Import** импортировать изображение. Редактор предлагает встроить его или оставить ссылкой. Ссылка может сломаться при переносе файлов; встраивание сохраняет изображение внутри SVG, увеличивая размер файла. См. [руководство по импорту](https://inkscape-manuals.readthedocs.io/en/latest/import-pictures.html).

Правило проекта: исходник хранить неизменным, подложку размещать в отдельном слое и блокировать от случайных перемещений. Для итоговой схемы удалить рабочую подложку; в проекте отдельно сохранить исходный файл и сведения о масштабе/выравнивании. PDF сначала обследовать: текст и векторные объекты извлекать, когда они доступны; растр использовать, когда структурированного представления нет. Одна лишь трассировка изображения не создаёт семантику мест.

### Группы и свойства

**Object → Group / Ctrl+G** объединяет выбранные объекты. Группы могут быть вложенными. Двойной щелчок позволяет войти в группу; `Ctrl+Enter` — альтернативный способ. Отдельный объект можно выбрать с удержанием `Ctrl`. Изменения группы действуют на её содержимое. См. [руководство по группировке](https://inkscape-manuals.readthedocs.io/en/latest/grouping.html).

Правило проекта: проверять фактический XML, а не только визуальную подпись в интерфейсе. Не превращать круги мест в paths и не оставлять клоны `use` вместо отдельных кругов. Нумерация берётся из источника, включая буквенные значения и намеренные пропуски.

Пример структуры одного ряда по соглашениям существующего импортёра Arena; **это фрагмент, не готовая схема**:

```xml
<g xmlns="http://www.w3.org/2000/svg"
   xmlns:inkscape="http://www.inkscape.org/namespaces/inkscape"
   id="row-parter-1" inkscape:label="#Партер">
  <title>1</title>
  <circle id="seat-parter-1-1" cx="100" cy="100" r="6"
          fill="#e53935" stroke="#000000" stroke-width="3">
    <title>1</title>
  </circle>
</g>
```

Координаты, радиус и цвет в примере условные. Полный документ дополнительно требует холст, категории и служебные группы. Читаемое XML `id` в примере — правило проекта; оно не является идентификатором места в билетной платформе.

## 4. BSS: результат обработки Bil24

Краткий пересказ [спецификации BSS](https://bil24.pro/BSS.html):

Авторский SVG и BSS — разные представления. В BSS место определяется наличием `sbt:seat` на элементе; обычно это круг.

У места:

- `id` — уникальный XML-идентификатор элемента;
- `sbt:id` — идентификатор места в платформе;
- `sbt:seat` — номер, например `2A`;
- `sbt:cat` — индекс категории;
- `sbt:state` — состояние.

Родительская группа `g` несёт `sbt:sect` и `sbt:row`, задающие сектор и ряд.

В `metadata` контейнер `sbt:categories` задаёт валюту ISO 4217 через `sbt:currency` и признак отсутствия свободных мест через `sbt:sold` (0/1). Категория `sbt:category` содержит цвет `sbt:color`, системный ID `sbt:id`, индекс `sbt:index`, имя `sbt:name`, цену `sbt:price`, доступность `sbt:used`. Вложенные `sbt:tariff` содержат ID, название и цену тарифа. Индекс категории и её системный ID различаются.

Состояния `sbt:state`:

- `0` — недоступно;
- `1` — доступно;
- `2` — предбронировано;
- `3` — бронировано;
- `4` — занято;
- `5` — снято с продажи.

Номер, XML ID и системный ID нельзя подменять друг другом. Отсутствующее место не следует автоматически объявлять свободным.

### Существенные различия

1. Авторский импорт Arena связывает место с категорией по цвету. Цвета статусов, допустимые инструкцией Bil24, могут не совпасть ни с одной категорией и вызвать ошибку. Состояние и категорию необходимо сохранять отдельно; не перекрашивать неизвестные места автоматически.
2. `ImportSBTSVG` рассчитан на конкретный диалект: требует круги, системные ID/состояния и `viewBox`. Поэтому он не является универсальным импортёром всех документов, допустимых описанием BSS.
3. Экспорт `layout_svg.go` использует namespace `http://bil24.pro/sbt` и состояния 0–5; `sbt10_svg.go` — `http://www.w3.org/2015/sbt/1.0`, состояния 1/4 и другую структуру metadata. Эти адреса взяты из кода Arena: страница BSS не задаёт URI namespace в приведённых фрагментах. Выбор формата требует проверки конкретного клиента.
4. `#GA <name>` с ёмкостью в `title`, лимит 15 категорий, предупреждение об отсутствии Legend, JSON-канонизация и SHA-256 — соглашения Arena. Не выдавать их за универсальные правила опубликованных страниц Bil24.
5. Ключ места Arena — `section|row|number`. Он сохраняется при неизменных составляющих; переименование сектора/ряда меняет ключ. Внешние ID хранить отдельно.
6. Неизвестные/некорректные трансформации текущий код пропускает. Радиус масштабирует через определитель матрицы: при неравномерном масштабе или skew круг может геометрически стать эллипсом. Такие случаи требуют предупреждения и ручной проверки.
7. Виджет фильтрует декор; административный preview его не отображает. Проверка только preview не подтверждает сохранность сцены, подписей и проходов.

## 6. Правила надёжного генератора

Это дополнительные требования проекта:

- Для каждого извлечённого утверждения фиксировать файл, страницу/область, способ получения и состояние: подтверждено источником, требует проверки либо предположено. Это будущая модель отчёта, не существующие поля `Geometry`.
- Разделять физическую рассадку, ценовые категории, квоты и динамические статусы продаж. Не назначать цены и ёмкости по догадке.
- AI использовать для интерпретации и обнаружения спорных мест. Координаты, преобразования, ID, подсчёт и SVG строить детерминированно.
- Не исправлять намеренные пропуски номеров. Проверять одинаковые `(сектор, ряд, место)`, коллизии XML ID и внешних ID.
- Проверять конечность координат, положительный радиус, выход за холст, подозрительные наложения, соответствие количества мест по рядам и секторам.
- Сохранять связь координат со страницей источника. Перевод в общий холст должен быть явным и воспроизводимым; размер в единицах `viewBox` сам по себе не доказывает размер страницы в px.
- Не включать скрипты, внешние ресурсы и рабочую растровую подложку в итоговый экспорт.
- Держать редактируемый авторский SVG отдельно от платформенного экспорта. До проверки потребителем не заявлять полную совместимость.

## 7. Проверка перед приёмкой

1. Открыть исходник и результат рядом; проверить сцену, FOH, проходы, балконы и ориентацию.
2. Сверить каждый ряд и его номера с источником; общий итог не заменяет построчную проверку.
3. Проверить XML-структуру, идентификаторы, категории и преобразования через подходящий существующий импортёр.
4. Повторить обработку: канонический JSON и checksum должны совпасть.
5. Проверить отображение в целевом виджете, включая декор и кликабельность мест.
6. Сохранить отчёт расхождений. Если используется Bil24, отдельно проверить отчёт Редактора; успешный локальный импорт не заменяет его.
7. Не публиковать схему, пока критические расхождения не разрешены человеком.
