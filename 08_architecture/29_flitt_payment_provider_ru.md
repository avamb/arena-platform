# Платёжный провайдер Flitt — спецификация

Статус: реализовано 2026-10-01 (миграция 0120). Первая организация — MyEventsArt,
продажи во Франции (EUR) и в Грузии (GEL); интеграция общая — подключается любой
организацией со своими ключами.

Документация Flitt: https://docs.flitt.com (Payment API).

## 1. Что это и зачем

Flitt — карточный шлюз с **redirect-оплатой**, как Stripe Checkout: arena создаёт
заказ, получает `checkout_url`, отправляет покупателя на страницу Flitt, а итог
узнаёт из подписанного callback. Данные карты в arena не попадают.

Встраивается в уже существующий путь виджета
(`POST /v1/public/feeds/{token}/checkout/start`) — тот же интерфейс
`payments.HostedCheckoutProvider`, что и у Stripe. Отдельного платёжного
маршрута нет.

Не входит в эту версию: встроенная (embedded) форма, Apple Pay / Google Pay,
рекуррентные платежи, выплаты, предавторизация, возврат из arena (см. §9).

## 2. Мультитенантность — «несколько организаций на одной интеграции»

Одна организация = одна строка `payment_provider_configs` (`provider='flitt'`,
режим `test`/`live`) со **своими** `merchant_id` и `payment_key` в `secrets`.
Подключить новую организацию — добавить такую строку и назначить каналу
`sales_channels.provider='flitt'`. Кода и конфигурации процесса для этого
не нужно.

- Адаптер строится **на каждый запрос** из строки конфигурации организации.
  Общего ключа процесса нет и не будет.
- Callback приходит на `POST /v1/payment-intents/webhook/{config_id}`: путь
  называет конфигурацию, а значит и ключ, которым проверяется подпись.
- Изоляция проверена тестом `TestFlitt_TwoOrganizationsAreIsolated`:
  корректно подписанный callback организации B про заказ организации A **не
  двигает** платёж A.

## 3. Секреты конфигурации

| Поле | Что это | Где взять |
|------|---------|-----------|
| `merchant_id` | числовой идентификатор продавца | Flitt Portal → Merchant settings |
| `payment_key` | «платёжный ключ» (Payment key): подписывает запросы **и** callback | Portal → Technical settings |

«Закрытый ключ» / «credit key» из портала — для выплат на карты. arena его не
использует и не хранит; вводить его в конфигурацию не нужно.

Отдельного `webhook_secret` у Flitt нет: callback подписан тем же платёжным
ключом. Статус конфигурации становится `configured`, когда заполнены оба поля.

**Тест и бой.** Адрес API один (`https://pay.flitt.com/api`); режим решают
ключи. Общий песочный продавец из документации: `merchant_id 1549901`, ключ
`test`. Поле `mode` конфигурации — только пометка arena (и условие KYB для
`live`), на запросы к Flitt оно не влияет.

## 4. Создание платежа

`POST https://pay.flitt.com/api/checkout/url`, тело `{"request": {...}}`.

| Поле Flitt | Значение arena |
|-----------|----------------|
| `merchant_id` | из конфигурации |
| `order_id` | id checkout-сессии arena (UUID) — он же `payment_intents.provider_payment_id` |
| `order_desc` | название события (до 1024 символов) |
| `amount` | `checkout_sessions.total` в минорных единицах, как есть |
| `currency` | валюта сеанса, верхний регистр, **без списка разрешённых в arena** |
| `response_url` / `cancel_url` | страница покупателя + `?checkout_token=…` |
| `server_callback_url` | `<API_PUBLIC_URL>/v1/payment-intents/webhook/{config_id}` |
| `lifetime` | секунды до конца окна оплаты (минимум 60) |
| `sender_email` | e-mail покупателя |
| `lang` | язык покупателя, если он среди 20 языков Flitt |
| `merchant_data` | JSON с `arena_checkout_session_id`, `arena_org_id`, `arena_order_id` |
| `signature` | см. §5 |

Ответ: `response.checkout_url` (редирект) и `response.payment_id`. Любой
`response_status: failure` — ошибка старта (HTTP 503 `checkout.payment_start_failed`,
место удержания освобождают обычные свипы).

**Окно оплаты.** `lifetime` ≈ `WIDGET_PAYMENT_WINDOW_SECONDS` (1860 с): страница
Flitt умирает раньше, чем arena отпускает места (окно + 120 с «грации») —
покупатель не может оплатить уже проданные места.

**Дубликат.** `order_id` уникален у продавца (ошибка 1013). arena стартует
оплату один раз на checkout; возврат покупателя на страницу оплаты использует
сохранённый `hosted_checkout_url`, а не новый заказ.

## 5. Подпись

`SHA1( payment_key | значения непустых параметров, отсортированных по имени,
через "|" )`, нижний регистр hex. Правила (подтверждены на живой песочнице
2026-10-01):

- `signature` и `response_signature_string` в расчёт не входят;
- пустые значения и `null` пропускаются вместе с разделителем;
- **ноль не пустое значение**;
- числа подписываются как есть (`805243692`, не `8.05e+08`) — тело callback
  читается с `json.Number`;
- UTF-8.

Сравнение подписи — за постоянное время. Пример из самой документации Flitt
не воспроизводится (подпись там посчитана на других данных), поэтому
алгоритм сверен с эталонным Python-кодом из документации и **с живым API**:
верная подпись принимается, неверный ключ даёт 1014.

## 6. Валюты

arena **ничего не фильтрует**: валюта сеанса уходит во Flitt как есть, а
решает Flitt — если валюта не разрешена продавцу, он отвечает ошибкой
(1012/1007), и покупатель видит `checkout.payment_start_failed` **до** того,
как места удержаны надолго (пре-флайт проверяет только конфигурацию, поэтому
неподдерживаемая валюта вскрывается на старте, а места освобождает свип).

- EUR, GEL, USD проверены интеграционным тестом `TestFlitt_…_EveryCurrency`.
- Сумма в минорных единицах (центы, тетри); для валют без дробной части Flitt
  принимает «как есть, без разделителей» — arena в этом случае не пересчитывает.
- Включение валюты — на стороне Flitt (настройки продавца / договор), не arena.

## 7. Callback

`POST /v1/payment-intents/webhook/{config_id}`, плоский JSON, подпись в теле.
Порядок проверок (все до любых записей):

1. тело читаемо, `config_id` — UUID, конфигурация существует, активна, `configured`
   (иначе 404 без деталей);
2. у конфигурации есть `payment_key` (иначе 401);
3. `merchant_id` из тела **равен** `merchant_id` конфигурации (дёшево, до хеша);
4. подпись верна под ключом этой конфигурации (иначе 401);
5. платёж найден по `order_id`; чужой организации, чужого провайдера
   или неизвестный — «не наш»: **200** `processed:false`, чтобы Flitt не
   ретраил сутками.

Маппинг статусов (`order_status`):

| Статус | Действие |
|--------|----------|
| `approved` | платёж `succeeded`, checkout завершается, заказ `paid`, выпуск билетов |
| `expired` | платёж `failed` (`failure_code` из `response_code`) |
| `declined` | **ничего** — карта отклонена, но заказ жив: покупатель может заплатить другой картой на той же странице; закрыть платёж значило бы потерять последующий `approved` |
| `processing`, `created`, `reversed` | подтверждается без перехода (`reversed` — это возврат, он идёт через поток возвратов) |

Идемпотентность — прежняя: `(provider_payment_id, event_type)` в
`payment_intent_events`; повтор callback = 200 и без повторной выдачи билетов.
Flitt ретраит через 2, 60, 300, 600, 3600, 86400 с до ответа HTTP 200.

Flitt-тело на **старом** маршруте `/v1/payment-intents/webhook` отвергается
(`400 webhook.flitt_requires_config_route`): там нет конфигурации, которая
поручилась бы за подпись.

Закрыть доступ по IP не нужно, но Flitt шлёт callback с `54.154.216.60` и
`3.75.125.89` — при необходимости их можно внести в allow-list на прокси.

## 8. Проверка ключей

При сохранении конфигурации и по кнопке «Check again» arena делает
`POST /status/order_id` для заведомо несуществующего заказа:

- ответ `1018 Order not found` → ключи верны (подпись и продавец приняты) → `ok`;
- `1014` (неверная подпись) или `1016` (нет такого продавца) → `failed`;
- сеть, 5xx, прочие коды → `unverified` (это не вердикт о ключе).

Деньги не двигаются и ничего не создаётся.

## 9. Возвраты — как сейчас у Stripe

В arena поток «возврат через провайдера» пока не вызывает API провайдеров
(для Stripe тоже: возврат делается в кабинете провайдера, дальше arena
принимает событие). Для Flitt так же: возврат — в кабинете Flitt
(`POST /api/reverse/order_id` существует и описан в документации), callback со
статусом `reversed` подтверждается и не меняет платёж. Автоматический вызов
reverse из arena — отдельная работа вместе с общим потоком возвратов.

## 10. Настройка организации (чек-лист)

1. Admin → организация → Payment configs → `flitt`, mode `test` (или `live`
   после KYB): `merchant_id` и `payment_key` из портала Flitt. Дождаться
   зелёного бейджа проверки.
2. Admin → Channels → канал сайта: provider `flitt`, `provider_account_id` =
   `merchant_id` (если режим direct_merchant).
3. **Портал Flitt → Настройки продавца → Настройки оплаты:**
   - «Срок действия заказа по умолчанию» — только запасное значение, arena
     присылает `lifetime` сама;
   - «Метод перенаправления на страницу результатов» — **GET**. При POST
     браузер покупателя шлёт POST на страницу сайта с виджетом; статичная
     страница ответит 405. На сайте WordPress POST обычно допустим, но GET
     надёжнее; исход оплаты arena берёт из callback, а не из редиректа.
4. Включить в Flitt нужные валюты для продавца (EUR, GEL, …).
5. Тест: карта `4444 5555 6666 1111` (3-D Secure, одобряется) на песочном
   продавце; полный список тестовых карт — https://docs.flitt.com/api/testing/.

## 11. Известные ограничения

- Язык страницы Flitt и язык письма определяются `checkout_sessions.buyer_locale`,
  а он принимает только `cs, de, en, es, he, ru` (`templates.SupportedLocales`).
  Для покупателя из Франции (`fr`) виджет-локаль отбрасывается ещё до адаптера:
  страница Flitt откроется на языке по умолчанию, а письмо — на английском.
  Исправление — французские шаблоны писем и добавление `fr` в этот список.
- Нет автоматического reverse (§9).
- Одна ставка комиссии площадки — процентная (`sales_channels.fee_percent`),
  как у Stripe; фиксированного сбора нет.
