# Платёжные модули, возвраты через Арену и тип приёма оплаты — спецификация

Статус: решения владельца приняты 2026-10-09. Бэклог — раздел 12 (префикс PAY). Связанные документы:
`29_flitt_payment_provider_ru.md` (Flitt), `32_organization_onboarding_ru.md` (что платформа не держит деньги),
`35_telegram_event_center_full_ru.md` (экраны бота), `docs/plans/telegram_event_center_full_plan_2026-10-09_ru.md`.

Повод: организатор в Telegram-боте должен вернуть деньги покупателю. Сегодня Арена возвраты через провайдера
не проводит: переход в `provider_pending` только имитируется (`hcheckout/refunds.go`, «simulating provider submission»),
событий возврата от Stripe и Flitt она не разбирает.

## 1. Решения владельца (2026-10-09)

1. **Вариант B:** организатор без своего сайта принимает оплату через эквайринг, подключённый в Арене. Возврат делает Арена
   через провайдера. Первый провайдер — Stripe, следующим шагом Flitt, затем AllPay.
2. **Платёжные модули независимы.** Подключить нового провайдера значит добавить один модуль, не трогая остальные и общий код.
3. **Организации делятся по эквайрингу, как в Bil24 по типу подключения:** эквайринг, подключённый через Арену, или
   собственный эквайринг на сайте организатора. Тип подключения — флаг организации (§2), известен боту с регистрации.
   Владелец сайта получает в боте те же экраны; денежные операции по его заказам (возврат, повторная отправка,
   письмо о переносе) идут **через его сайт** — вариант A, волна «сайт как продавец» (PAY-15, EC-00). До неё бот
   объясняет, что сделать на сайте, и ничего не блокирует. Проектируем так, чтобы вариант A ничего не переписывал.
4. **Тип приёма оплаты** вводится сразу как данные (организация и канал) и как единая точка выбора
   маршрута возврата по платежу заказа, чтобы не переделывать позже.
5. Менеджер видит и делает возвраты сразу, как и владелец.
6. Деньги платформа по-прежнему не держит: каждый организатор подключает свой ключ провайдера (direct merchant).
   `merchant_of_record` остаётся только для суперадмина.
7. **Тарификация возвращённых билетов — переключатель суперадмина:** на всю платформу и отдельно на организацию
   (§7.1). Политика гибкая, по умолчанию возвращённые билеты тарифицируются как проданные.

## 2. Термины и тип приёма оплаты

Название оси, предлагается (владелец просил подумать): **`acquiring_mode`** — на организации (тип подключения,
то, что организатор выбирает при регистрации) и на каждом торговом канале (`sales_channels`, по умолчанию наследует
организацию).

| Значение | Смысл | Кто принимает деньги | Кто возвращает | Примеры |
|---|---|---|---|---|
| `arena` | оплата через Арену | эквайринг организатора, подключённый в Арене (`payment_provider_configs`); платёж создаёт Арена (hosted checkout) | Арена через модуль провайдера | страница продаж, виджет, ивенты из бота |
| `seller` | оплата у продавца | собственный эквайринг на сайте организатора; Арена узнаёт об оплате (PAY_ORDER, webhook) | сайт (вариант A, позже) | WordPress-сайты Lampyris и Vino&Co |

Важно:
- Ось называется по тому, **чей эквайринг**, а не по наличию сайта. Организатор с сайтом, который платит через Арену, будет `arena`.
- Это не то же самое, что Bil24 «билетная система» и «билетный агент». Там различаются роли в цепочке продажи, а здесь деньги.
  Совпадение условное: фронтенд типа «Ticketing system» у Bil24 соответствует нашему `seller`.
- Организация может иметь каналы обоих значений (Lampyris: сайт `seller` и hosted-страница `arena` для ивентов из бота).
  Поэтому маршрут возврата выбирается **по платежу заказа**, а не по организации (§6). Флаг организации — это
  значение по умолчанию для новых каналов и режим экранов бота (§6.1), не маршрут.
- «Эквайринг платформы» в словах владельца = эквайринг, подключённый через Арену. Собственного эквайринга у платформы нет.
- Не путать с `sales_channels.payment_mode` (`direct_merchant` / `merchant_of_record`, кто продавец по документам).
  Это другая ось: `merchant_of_record` возможен только при `acquiring_mode='arena'` (CHECK), `direct_merchant` — при любом.

Соответствие Bil24, для ориентира: «билетная система» (сайт продаёт и принимает деньги сам) ≈ `seller`; «билетный агент»
(продаёт через чужой эквайринг) ≈ `arena`. Внутри Арены используем только `arena` / `seller`; в интерфейсах — «оплата
через Арену» / «собственный эквайринг».

## 3. Что есть сейчас (разведка 2026-10-09, код на master)

Модули провайдеров:
- В `domain/payments` есть интерфейсы `PaymentProvider` (CreateIntent, CapturePayment, **RefundPayment**, HandleWebhook), `HostedCheckoutProvider` (отдельно, потому что у AllPay такого нет) и `CredentialVerifier`, а также реестр `PaymentRoutingPolicy`. **Реестр в боевом коде не используется.**
- Реальный выбор жёстко прошит `switch` и `if` по имени провайдера в пяти местах: `hfeed/payment_start.go`, `hpayments/payment_config_verify.go`, `hcheckout/provider_config.go`, `payment_webhook_config_route.go`, `payment_intents.go`; список провайдеров и обязательных полей в `hpayments/payment_configs_types.go`.
- `sales_channels_provider_check` перечисляет провайдеров (`stripe`, `allpay`, `flitt`), поэтому каждый новый требует миграции.
- Stripe-адаптер полный, включая `RefundPayment` (POST /refunds по `pi_…`). Flitt-адаптер умеет только checkout и проверку ключей, не `RefundPayment` и не разбор событий. AllPay существует в **двух копиях** (`domain/payments/allpay.go` и `adapters/allpay`), в hosted checkout не подключён.

Возвраты:
- Состояния `requested → approved → provider_pending → succeeded | failed | manual_review`. На approve **провайдер не вызывается**, записи зависают в `provider_pending`.
- Вебхук `/v1/refunds/webhook` принимает только нормализованное тело Арены с её `refund_id`. Настоящие `refund.updated`, `charge.refunded` от Stripe и Flitt `reversed` не обрабатываются.
- Возврат, созданный в кабинете провайдера, не виден Арене.
- Платёж шлюза Bil24 (`provider='manual'`) принимает запись возврата и повисает: гарда нет.
- Маршруты возврата плоские (`/v1/refunds/...`), проверки организации в хендлерах не было — подтверждённая дыра: владелец или API-ключ любой организации с `refund.*` мог читать, создавать и одобрять возвраты по чужому платежу. Закрыто 09.10 (PAY-00, §8).
- Организационного списка возвратов нет, только `/v1/admin/refunds` для суперадмина.
- `settlement` бывает `provider` и `external` (миграция 0102). Внешние возвраты Bil24 уже пишутся как `external`.

Кто принимал деньги:
- Различитель уже есть: `payment_intents.provider` (`stripe`, `flitt` — через Арену; `manual` — у продавца, шлюз Bil24) и `orders.source` (`bil24_gateway` против `public_feed`/`checkout_api`).
- В `sales_channels` и `organizations` поля «кто принимает оплату» нет.

## 4. Принципы

1. Деньги идут напрямую на аккаунт организатора, Арена комиссию с возврата не берёт и не держит остатков.
2. Вызов провайдера никогда не внутри транзакции БД (как создание hosted checkout). Строка возврата сначала фиксируется, потом идёт вызов, потом результат.
3. Каждый вызов идемпотентен: ключ идемпотентности = id возврата. Повтор безопасен.
4. Билет гасится, **только когда провайдер принял возврат** (деньги сначала, потом билет; решение владельца 2026-09-20). Отказ провайдера оставляет билет рабочим.
5. Ничего не знает о конкретном провайдере общий код. `switch provider` вне модулей запрещён статической проверкой.
6. Возврат необратим, и в интерфейсах это говорится прямо (подтверждение словом, суммы, срок).

## 5. Контракт платёжного модуля

Один пакет на провайдера: `adapters/<provider>`. Общее ядро знает только интерфейсы из `domain/payments`.

```go
// Descriptor: статические данные модуля (без сети).
type Descriptor struct {
    Name         string        // "stripe", "flitt", "allpay"
    Title        string
    Secrets      []SecretField // ключ, подпись, обязательность, формат (regexp), скрытость
    Capabilities Capabilities
}
type Capabilities struct {
    HostedCheckout bool
    Refund         bool
    PartialRefund  bool
    AsyncRefund    bool // подтверждение возврата приходит позже вебхуком
    RefundLookup   bool // умеет прочитать статус возврата по id
}

type Module interface{ Descriptor() Descriptor }

// Необязательные возможности (type assertion, как существующие узкие интерфейсы):
type HostedCheckoutProvider interface{ CreateCheckoutSession(...) }          // уже есть
type CredentialVerifier     interface{ VerifyCredentials(ctx) error }        // уже есть
type WebhookParser interface {
    // Проверяет подпись по секретам конфига и приводит тело к нормализованному событию.
    VerifyAndParse(ctx, in WebhookInput) (NormalizedEvent, error)
}
type Refunder interface {
    Refund(ctx, RefundRequest) (RefundResult, error)
}
type RefundLookup interface {
    RefundStatus(ctx, providerRefundID string) (RefundResult, error)
}
```

`RefundRequest`: учётные данные конфига, ссылка на платёж у провайдера (`provider_charge_ref`, для Stripe `pi_…`),
сумма в **младших единицах Арены** (модуль сам переводит в единицы провайдера, нулевые знаки после запятой для JPY и подобных),
валюта, причина, ключ идемпотентности, метаданные (`refund_id`, `order_id`).
`RefundResult`: `ProviderRefundID`, `Status` (`pending` | `succeeded` | `failed`), `FailureCode`, `FailureMessage`.
`NormalizedEvent`: вид (`payment_succeeded`, `payment_failed`, `payment_expired`, `refund_updated`, `dispute_opened`),
идентификаторы платежа и возврата, статус, сумма, сырое тело для аудита.

Реестр:
- Один файл `domain/payments/modules.go` перечисляет подключённые модули (фабрики с конфигом). Это единственное место, где названия провайдеров встречаются в списке.
- Реестр заменяет неиспользуемый `PaymentRoutingPolicy`. Ядро спрашивает `registry.Get(name)` и проверяет возможности.
- Валидация провайдера канала и обязательных секретов идёт через `Descriptor`, не через `switch`. `sales_channels_provider_check` снимается (остаётся непустое значение), новый провайдер миграции не требует.
- Статическая проверка (`tests/staticanalysis`) падает, если в `hcheckout`, `hfeed`, `hpayments`, `htickets`, `eventbot` встречается литерал имени провайдера вне тестов и `modules.go`. Разрешённый список: `manual` (платёж у продавца, шлюз Bil24) и `none` (бесплатный заказ) — это не модули, а признаки отсутствия провайдера. `webhookRoute.ExpectedProvider="flitt"` в конфигурационном маршруте уходит в PAY-01: маршрут спрашивает модуль по `payment_provider_configs.provider`.

Что это даёт: новый провайдер = пакет с `Descriptor` + нужными интерфейсами + строка в `modules.go` + контрактный тест. Остальное код не трогает.

Контрактные тесты (`payments/contracttest`): набор, который запускается на каждый модуль: дескриптор корректен; подпись вебхука неверная даёт ошибку; нормализация события; идемпотентность повтора Refund; частичная сумма; нулевая сумма и сумма больше платежа отвергаются.

## 6. Маршрут возврата и тип приёма оплаты

Единая функция `refunds.RouteForOrder(order)` возвращает один из:

| Маршрут | Условие | Что делает Арена |
|---|---|---|
| `arena_provider` | у заказа платёж `stripe`/`flitt`/… (успешный `payment_intents`) и модуль провайдера умеет `Refund` | возвращает через модуль |
| `seller_site` | `payment_intents.provider='manual'` или `orders.source='bil24_gateway'` | сейчас отказ `409 refund.seller_site_order`; позже вариант A |
| `none` | бесплатный или пригласительный заказ | аннулирование без денег |
| `unsupported` | провайдер без возможности `Refund` | `422 refund.provider_not_supported`, подсказка «верните в кабинете провайдера» |

### 6.1. Тип подключения организации и канала (`acquiring_mode`)

`organizations.acquiring_mode` (`arena` | `seller`) — тип подключения организации, аналог типа фронтенда в Bil24:
- миграция: колонка `text NOT NULL DEFAULT 'arena'` с CHECK; заполнение: организация, у которой есть хотя бы один канал с включённым шлюзом (`settings.gateway.enabled` или хэш токена) или активный `webhook_subscribers` вида `bil24_wp`, получает `seller`; остальные `arena`;
- **откуда берётся:** вопрос онбординг-анкеты `acquiring` (select: «оплата через Арену» / «собственный эквайринг на сайте»; рядом с `has_website` и `payment_provider` в `onboarding.Fields`, метки en/ru/es), при одобрении `provisioning.CreateWorkspace` переносит ответ в организацию; суперадмин меняет в карточке организации (`PATCH /v1/organizations/{id}`, только суперадмин — как `kyb_status`, потому что флаг решает, кто возвращает деньги); владелец видит, не меняет;
- отдаётся в `GET /v1/organizations/{id}`, `/v1/me` (по организациям членства) и в `GET …/bot-team`-подобных ответах, чтобы бот знал режим с первого экрана;
- смена пишется в аудит.

`sales_channels.acquiring_mode` (`arena` | `seller`) — то же на канале:
- миграция: колонка `text NOT NULL DEFAULT 'arena'` с CHECK; заполнение: каналы с включённым шлюзом или активным `bil24_wp`-подписчиком получают `seller`; CHECK: `payment_mode='merchant_of_record'` только при `acquiring_mode='arena'`;
- новый канал наследует флаг организации; `provisioning.CreateWorkspace` ставит значение организации; `PUT .../channels/{id}/gateway-credential` ставит `seller`; смена значения пишется в аудит;
- проверка согласованности: канал `arena` обязан иметь рабочую конфигурацию провайдера, иначе платная покупка отвергается заранее (как `payment pre-flight`); канал `seller` не создаёт hosted-платежей;
- **ни одно из полей не решает маршрут возврата** (его решает платёж заказа, §6), они нужны для интерфейсов, онбординга, режима бота и отчётов.

### 6.2. Что это значит для бота

Бот **даётся организациям обоих типов**. Режим экранов — по флагу организации, действия по заказу — по `refund-options` заказа:

| | `arena` | `seller` (сайт) |
|---|---|---|
| Меню | «Оплата через Арену» и состояние подключения провайдера | «Собственный эквайринг: сайт <домен канала>» |
| Возврат заказа, оплаченного через Арену | экран возврата (EC-21) | то же — такие заказы есть и у `seller`-организации (hosted-страница) |
| Возврат заказа сайта (`seller_site`) | — | до PAY-15: экран «Возврат делается на сайте» с номером заказа WooCommerce; после PAY-15: тот же экран возврата, Арена шлёт сайту `order.refund_requested`, сайт отвечает вебхуком |
| Повторная отправка билетов заказа сайта | — | до EC-00: «письмо шлёт сайт»; после: событие сайту |
| Перенос и отмена сеанса с заказами сайта | — | до EC-00 (SCN-05/06): отказ `session.change_site_unsupported` с объяснением; после: письмо шлёт сайт |

Никаких отказов `bot.not_available_for_seller_organization`: прежняя идея ограничения снята. Вариант A потом = ещё одна реализация маршрута `seller_site` (событие `order.refund_requested`, ответ сайта), остальной код (экран бота, API, таблица возвратов) не меняется, потому что опирается на `RouteForOrder` и `GET .../refund-options` (§8).

## 7. Движок возврата

Состояния те же (`requested → approved → provider_pending → succeeded | failed | manual_review`), но теперь они настоящие.

Данные (миграция данных, следующая по порядку на момент работы; права — в единой миграции прав `EC-17` из `35_…` §3, сюда не входят):
- `refund_batches`: `id`, `org_id`, `order_id`, `idempotency_key` (уникален в организации — это и есть хранилище заголовка `Idempotency-Key`), `reason`, `notify_buyer`, `cancel_tickets`, `created_by`, `via`, `created_at`. Одна операция «вернуть эти билеты» = одна строка;
- `refunds.provider text`, `provider_status text`, `origin text` (`arena` | `provider_dashboard`), `batch_id uuid → refund_batches`, `cancel_ticket boolean`, `order_id`/`ticket_id` разрешены и для `settlement='provider'` (меняется `refunds_settlement_shape_check`; `payment_intent_id` для `provider` остаётся обязательным);
- уникальный индекс `(provider, provider_refund_id) WHERE provider_refund_id IS NOT NULL`; уникальность «не более одного живого **гасящего** возврата на билет»: `(ticket_id) WHERE cancel_ticket AND state NOT IN ('failed','rejected')` — частичные возвраты без гашения (`cancel_tickets=false`) могут повторяться, пока есть остаток;
- `usage_records.tickets_refunded` (§7.1);
- `organizations.acquiring_mode`, `sales_channels.acquiring_mode` (§6.1), снятие `sales_channels_provider_check`.

Последовательность одной операции (`POST …/orders/{order_id}/refunds`):
1. **Проверки** (транзакция; первым оператором `pg_advisory_xact_lock` по `payment_intent_id`, потому что вызовы идут из `arena-api`, а повторы — из `arena-worker`, и блокировка в памяти процесса их не сериализует): организация совпадает, маршрут `arena_provider`, билеты принадлежат заказу и не погашены, сумма каждого ≤ остатку (`order_items.total` минус уже возвращённое по билету, считая `provider_pending`), причина не пустая, `Idempotency-Key` не встречался (повтор отвечает прежним `batch_id` и состоянием, ничего не создавая).
2. **Фиксация:** строка `refund_batches` и по строке `refunds` на билет, сразу `approved → provider_pending` (у всех ролей бота есть `refund.approve`; `requested` остаётся только для API-ключей без него — экрана одобрения в боте нет). Транзакция закрывается.
3. **Вызов провайдера** `Refunder.Refund` с ключом идемпотентности = id возврата. По одному платежу — один вызов за раз: та же `pg_advisory_xact_lock` в короткой транзакции-«замке» вокруг вызова (или строка `refunds` в `provider_pending` без `provider_refund_id` как признак «идёт вызов» для сметателя — не трогать моложе минуты). Ссылка на платёж у провайдера — `payment_intents.provider_charge_ref` (`pi_…`); если поле пустое (оплата до миграции 0103 или вебхук без `payment_intent`), модуль Stripe сам дочитывает Checkout Session по `provider_payment_id` (`cs_…` → `payment_intent`) и записывает его в `provider_charge_ref` перед возвратом.
4. **Результат** (новая транзакция):
   - `succeeded` → состояние `succeeded`, билет гасится (`CancelTicketTx` с новым параметром `RefundID`, освобождение места, отзыв QR);
   - `pending` → остаётся `provider_pending`, **билет гасится сразу** (провайдер возврат принял; если позже `failed`, возврат попадёт в очередь «деньги не вернулись»);
   - ошибка отказа (карта закрыта, суммa больше остатка, нет средств) → `failed`, билет остаётся рабочим, пользователю читаемая причина;
   - неизвестный исход (таймаут, обрыв) → остаётся `provider_pending` без `provider_refund_id`; доработка сметателем (ниже).
5. **Письмо покупателю** (`kind=refund`, 7 языков, одно на операцию): билеты, сумма, срок «обычно 5–10 рабочих дней», без обещаний сверх этого. Отключается `notify_buyer=false`.
6. **Событие** `v1.ticket.refunded` и аудит: кто, какая сумма, с какого канала (`via=telegram_bot` через заголовок клиента).

Фоновая задача `refund.sweep` (самопланирующаяся, как `order.expire_sweep`, раз в минуту):
- строки `provider_pending` без `provider_refund_id` старше минуты: повторить вызов с тем же ключом;
- строки с `provider_refund_id`, где модуль умеет `RefundLookup`, старше 10 минут: прочитать статус и применить результат;
- строки старше 24 часов в `provider_pending` → `manual_review` и тревога в ops-бот (`opswatchdog`, без данных покупателя).

Вебхуки возвратов:
- Организатор регистрирует endpoint в кабинете провайдера сам, поэтому события возвратов приходят, только если он их включил. Инструкция подключения Stripe (админка и письмо об одобрении) называет события `checkout.session.completed`, `checkout.session.expired`, `refund.updated`, `charge.refunded`; `POST …/payment-configs/{id}/verify` для Stripe дополнительно читает `GET /v1/webhook_endpoints` и предупреждает (`payment_config.webhook_events_missing`), если endpoint Арены не подписан на события возвратов. Без вебхуков состояние всё равно доедет через сметатель и `RefundLookup`, но с задержкой до 10 минут.
- Конфигурационный маршрут `POST /v1/payment-intents/webhook/{config_id}` передаёт тело `WebhookParser` модуля. Нормализованное `refund_updated` находит возврат по `(provider, provider_refund_id)`; найден — применяется результат (идемпотентно, повтор ничего не делает); не найден — см. возврат из кабинета.
- Старый маршрут `/v1/refunds/webhook` остаётся для mock-провайдера и тестов, но под настоящие вебхуки провайдеров не переделывается.
- **Возврат из кабинета провайдера** (организатор вернул в Stripe руками): `refund_updated` без нашей строки создаёт запись `origin='provider_dashboard'`; полный возврат платежа гасит билеты (существующая `applyFullInboundRefundCancellation`), частичный ставит билеты на проверку и попадает в очередь «Возвраты». До сих пор такие события игнорировались.

Правила сумм:
- по умолчанию возвращается `order_items.total` билета (то, что покупатель заплатил за него, включая долю сервисного сбора и минус долю скидки);
- частичная сумма разрешена, если `Capabilities.PartialRefund`; погашать ли билет при частичной сумме выбирает пользователь (`cancel_tickets`);
- сумма больше остатка — `409 refund.amount_exceeds_refundable`;
- возврат на заказ с промокодом считает скидку так же, как билет оплачивался.

### 7.1. Тарификация возвращённых билетов (решение владельца 7)

Биллинг платформы уже версионный: `tariffs` (глобальный при `org_id IS NULL`, переопределение на организацию) и
`usage_records.tickets_sold` за период `YYYY-MM`, из которых `hbilling` строит строки счёта. Переключатель ложится туда:
- `tariffs.bill_refunded_tickets boolean NOT NULL DEFAULT true` — тарифицировать ли возвращённые билеты. Глобальный тариф задаёт политику платформы, тариф организации её переопределяет; значение видно и меняется там же, где тариф (`billing.admin`, суперадминка, карточка тарифа);
- `usage_records.tickets_refunded bigint NOT NULL DEFAULT 0` — счётчик всегда ведётся (и `provider`, и `external`, и `provider_dashboard`), увеличивается в транзакции результата `succeeded` за период **возврата**, не продажи;
- строка счёта «Билеты»: количество = `tickets_sold`, а при `bill_refunded_tickets=false` — `tickets_sold − tickets_refunded` (не ниже 0); отдельная информационная строка «из них возвращено N» печатается всегда;
- уже выставленный счёт не пересчитывается: возврат билета, проданного в закрытом периоде, уменьшает текущий период;
- админка: в карточке тарифа флажок «Тарифицировать возвращённые билеты», в сводке организации — продано / возвращено / к оплате.

## 8. API (организационные, с изоляцией по организации)

Все маршруты под `/v1/organizations/{org_id}/` и проверяют членство через `requireOrgMembership`; суперадмин только с `X-Admin-Reason`.

| Маршрут | Право | Назначение |
|---|---|---|
| `GET …/orders/{order_id}/refund-options` | `refund.read` | маршрут (`arena_provider`/`seller_site`/`none`/`unsupported`), провайдер, возможности (частичный возврат), по каждому билету: оплачено, уже возвращено, можно вернуть, статус; активные возвраты |
| `POST …/orders/{order_id}/refunds` | `refund.create` | создать операцию: `items[{ticket_id, amount?}]`, `reason` (обязательно), `cancel_tickets` (по умолчанию true), `notify_buyer` (true); заголовок `Idempotency-Key`; ответ 202 с `batch_id` и состоянием по билетам |
| `GET …/refunds` | `refund.read` | очередь: фильтры состояния и ивента, постранично |
| `GET …/refunds/{refund_id}` | `refund.read` | деталь с событиями |
| `POST …/refunds/{refund_id}/retry` | `refund.approve` | повтор вызова провайдера для `failed`/`manual_review` по решению пользователя (новый ключ идемпотентности только если провайдер ответил отказом) |
| `POST …/refunds/{refund_id}/resolve` | суперадмин | закрыть `manual_review` вручную с заметкой |

Коды ошибок: `refund.seller_site_order` (409), `refund.provider_not_supported` (422), `refund.nothing_to_refund` (409),
`refund.amount_exceeds_refundable` (409), `refund.ticket_not_refundable` (409), `refund.provider_rejected` (422, с `failure_message`),
`refund.provider_unavailable` (**503**, не 502: Cloudflare подменяет 502), `refund.in_progress` (409).

Старые плоские маршруты `/v1/refunds/*`, `/v1/tickets/{id}/cancel`, `/v1/complimentary/{id}/revoke`: аудит изоляции (PAY-00); те,
что остаются, получают проверку организации по строке (через `orgread`) и тесты «чужая организация получает 404».

## 9. Экраны бота

Описаны в `35_telegram_event_center_full_ru.md`, раздел «Деньги». Они читают только `refund-options` и создают операцию.
