# Площадка как общий ресурс платформы — спецификация (отложена)

Статус: **отложена, в работу не запущена.** Дата: 2026-09-21. Запись в бэклоге: `docs/backlog_ru.md` B-11.
Решение владельца 21.09.2026: оформить и вернуться, когда станет актуально — у двух клиентов,
которых переносим сейчас, площадки в разных странах и не пересекаются.

**Когда станет актуально (любое из трёх):**
1. перенос из Bil24 второго организатора, у которого есть площадка с тем же `venueId`, что уже
   импортирована другим. По выгрузке заказов Bil24 (2023–09.2026) 23 площадки из 136 встречаются
   больше чем у одного `actionLegalOwner`; часть — разные написания одного организатора, но есть и
   настоящие пересечения: Futurum Music Bar, Прага (Somewhere Show и Lampyris); La Octava и
   Santander 10, Торревьеха (Teatro Vega и Actorre); Espacio Ronda, Мадрид (Viva Ballet и La Cuna);
2. запуск маркетплейса arenasoldout.com — одна площадка должна быть одной страницей, а не N дублями;
3. первый живой случай, когда два организатора Arena работают в одном зале.

## 1. Замысел и факт

Замысел (`00_backend_architecture_brief_ru.md` п. 12, `03_platform_management_api_and_permissions_ru.md`
раздел Venue): площадка — переиспользуемый ресурс платформы со статусом проверки
(`draft / pending_review / verified / merged / archived`), видимостью (`public / restricted / private`),
алиасами (включая «название из импортированной Bil24») и правилом «несколько организаторов по одному
адресу ссылаются на один `venue.id`». Схемы залов — отдельные защищённые ресурсы со своим владельцем.

Факт (проверено по коду 21.09.2026, head ef8fe74):

## 2. Целевая модель

Площадка принадлежит платформе; организация — её **создатель и куратор**, а не владелец.

Новые поля `venues`:
- `created_by_org_id uuid NULL` — кто завёл (бывший `org_id`); `NULL` — заведена оператором платформы;
- `visibility text NOT NULL` — `public` (видна и доступна всем организациям) / `private` (только создателю);
  значение `restricted` из замысла не вводим, пока нет сценария;
- `review_status text NOT NULL` — `unverified` / `verified` / `merged`;
- `merged_into_venue_id uuid NULL` — куда слита запись-дубль.

`org_id` остаётся в таблице на время перехода как зеркало `created_by_org_id` (его читают десятки
запросов и сид-скрипты); удаляется отдельной миграцией после того, как все читатели переведены.

Правила:
1. **Использовать** (привязать сеанс) можно любую площадку с `visibility='public'` и любую свою.
   `session.venue_org_mismatch` остаётся только для чужой `private`.
2. **Править** площадку может создатель, пока она `unverified`; после `verified` — только оператор
   платформы (право `venue.curate`). Причина: правка адреса или часового пояса общей площадки меняет
   билеты и письма чужих мероприятий.
3. **Часовой пояс** общей площадки менять нельзя, если на ней есть сеансы других организаций с продажами
   (сейчас импорт уже держит сохранённый пояс: предупреждение `import.venue_timezone_kept`).
4. **Удаление** — только мягкое и только если нет сеансов других организаций; иначе 409.
5. **Схемы залов не меняются**: остаются у владельцев, делятся через `visibility` схемы, как сейчас.
   Общая площадка не даёт доступа к чужой схеме.
6. **Создание с проверкой на дубль**: при создании площадки API ищет кандидатов (тот же город +
   похожее имя или координаты ближе 100 м) и отвечает 409 `venue.possible_duplicate` со списком, если
   вызов не подтверждён флагом `confirm_new=true`. Админка показывает «возможно, это она».

## 3. Импорт Bil24

- `external_bil24_id` остаётся уникальным на платформу — это и есть правильная семантика: один
  `venueId` Bil24 = одна площадка Arena = один целочисленный ID в `compatids.KindVenue`.
- `resolveVenue`: найдена площадка с этим `venueId`, созданная другой организацией →
  **использовать её**, а не отвечать 409. Географию и адрес чужой площадки импорт НЕ переписывает
  (сейчас `UpdateImportedVenueGeography` вызывается безусловно) — только предупреждение
  `import.venue_shared_kept`. Площадка, найденная импортом у другой организации, автоматически
  считается `public` (она пришла из общего справочника Bil24).
- Код `import.venue_owned_by_other_org` удаляется из API (openapi, спека 19).
- Staging-организации на той же инсталляции больше не нужен сдвиг ID.

## 4. Слияние дублей (оператор платформы)

`POST /v1/admin/venues/{id}/merge` `{ "into_venue_id": … }` — в одной транзакции перевешивает
`sessions.venue_id`, `seating_plans.venue_id`, алиасы и `external_bil24_id` (если у цели его нет),
помечает источник `review_status='merged'`, `merged_into_venue_id`, мягко удаляет. Отказ, если у
обеих записей разные непустые `external_bil24_id` или разные часовые пояса при наличии продаж.
Аудит обязателен. Чтение слитой площадки по старому `id` отдаёт 301-подобный указатель на цель
(поле `merged_into`), чтобы сохранённые ссылки сайтов не ломались.

## 5. Порядок работ (фичи для AutoForge, когда запустим)

1. Миграция: новые поля, бэкфилл (`created_by_org_id = org_id`, `visibility='private'` для всех
   существующих, кроме имеющих `external_bil24_id` → `public`; `review_status='unverified'`).
   Гардрейл-тест на пару «CHECK в миграции ↔ Go-список значений» по образцу
   `TestAllowedOwnerTypes_MatchMigrationCheckConstraint`.
2. Правила использования и правки (п. 2.1–2.4), право `venue.curate` — **выдать `platform_superadmin`
   в той же миграции** (правило AGENTS.md, гардрейл `TestSuperadminPermissionParity532`).
3. Импорт (раздел 3) + интеграционный тест «две организации импортируют один `venueId`».
4. Проверка на дубль при создании (п. 2.6) + админка: поиск общей площадки в форме сеанса, бейджи
   «общая / проверена», очередь проверки для оператора.
5. Слияние (раздел 4).
6. Шлюз Bil24 и выгрузка MACS: убедиться, что `venueId` в `GET_ALL_ACTIONS` и в `actionEvent`
   билета не зависит от организации-создателя (должно быть так уже сейчас — закрепить тестом).
7. Удаление `venues.org_id` — отдельной фичей после того, как `rg "venues.*org_id|\.OrgID"` по
   читателям площадок пуст; обновить `cmd/arena-seed`, `cmd/arena-bil24-import`, фикстуры.

## 6. Проверить перед запуском

- Полный список читателей `venues.org_id` (запросы `gen/venues.sql.go`, `VenueSessionContextRow`,
  сиды, импорт-CLI `arena-bil24-import --venues`, который пишет площадки на одну организацию).
- Кто сейчас вызывает кросс-организационный `GET /v1/venues` и не утекают ли через него контакты
  площадки (`contact_phone`, `contact_email`) — для `private` они не должны быть видны чужим.
- Лимиты тарифа, считающие площадки на организацию (если есть в `hbilling`).
- Что делать с Lucerna Music Bar (`external_bil24_id` 6967), занятой `lampyris-staging`: после п. 3
  проблема исчезает сама; до него — ручная правка `external_bil24_id` и строки `compatids`.

## 7. Временный обход, если второй перенос придёт раньше волны

Сделать `external_bil24_id` уникальным внутри организации (индекс `(org_id, external_bil24_id)`,
поиск в `resolveVenue` по организации). **Осторожно:** `compatids.KindVenue` общий на платформу —
одно число Bil24 не может указывать на две площадки, поэтому вторая копия получит новый ID ≥ 1e9, и
сайт второго клиента увидит другой `venueId`, чем был у него в Bil24. Перед применением проверить,
как `bil24-acf-sync` сопоставляет площадки (по ID или по имени). Обход плодит дубли — использовать
только как костыль и убрать слиянием из раздела 4.
