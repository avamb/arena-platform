# 61. Магазин как платный модуль и управление магазином из Telegram-бота

Дата: 2026-11-05. Статус: согласована, решения владельца от 05.11 в §9, открытых
вопросов нет. База: `origin/master` 404171e5, голова миграций 0197.
Связано: спека 47 (магазин), 53 (white label: образец платного модуля),
37 §4.3 (вход в веб из бота), 35 §4 (диалоги бота).

## 1. Что меняется

1. Магазин становится **модулем организации**. Подключает и отключает его только
   суперадмин в админке. Без подключения магазина у организации нет нигде: ни в
   веб-ивент-центре, ни в боте, ни на витрине.
2. Модуль **платный**. Цену в месяц задаёт суперадмин, он же может сделать модуль
   бесплатным для организации (цена 0).
3. **Витрину открывает и закрывает сама организация** (владелец или менеджер), а не
   оператор, как сейчас. Домен витрины по-прежнему задаёт только суперадмин.
4. В главном меню бота появляется кнопка **«🛍 Магазин»**. Через неё идёт работа с
   заказами и простыми товарами. Всё, что плохо ложится на Telegram, бот открывает
   ссылкой в веб-ивент-центр, уже со входом под этим человеком.

## 2. Как сейчас (проверено по коду 05.11)

- `shop_settings.enabled` (0172) значит «витрина открыта и принимает заказы». Меняет его
  только суперадмин (`shop.enabled_superadmin_only`), через ручной вызов `PUT
  .../shop/settings`: экрана в админке нет.
- Раздел «Магазин» веб-ивент-центра проверяет только право `shop.read`
  (`OrgLayout.tsx`). Права выданы владельцу и менеджеру любой организации, поэтому раздел
  сегодня видят все.
- В боте нет ни одной строки про магазин. Организации бот берёт из `/v1/me`: id, название,
  роль, архив. Признаков модулей там нет.
- Возврат и отмена заказа в вебе требуют пароль ещё раз (`requireWebStepUp`). Для бота эта
  проверка не действует, у него деньги подтверждаются набранным словом.
- Сообщения о заказах магазина уходят через бота продаж (`salesnotify`, подписки с
  `kinds '{shop}'`). Любой чат с `shop` получает полный текст для курьера: имя, телефон,
  e-mail, адрес, состав. Короткого сообщения «была продажа в магазине» для чата продаж нет:
  чат с одним `tickets` о магазине не слышит ничего. Меняем в §7a.
- Подписки заводятся только SQL-строкой (`docs/ops/shop_notifications_ru.md`): ни API, ни
  экрана нет.

## 3. Данные (миграция 0198 или следующая свободная)

### 3.1 Периоды модуля

Общая таблица для модулей организации, по образцу `white_label_periods`. Сейчас в ней один
модуль `shop`. White label в неё не переносим.

```
org_module_periods
  id                  uuid PK DEFAULT uuidv7()
  org_id              uuid NOT NULL REFERENCES organizations(id)
  module              text NOT NULL CHECK (module IN ('shop'))
  starts_on           date NOT NULL           -- UTC, включительно
  ends_on             date NULL               -- UTC, включительно; NULL = бессрочно
  monthly_price_minor bigint NULL CHECK (>= 0) -- NULL = прайс-лист, 0 = бесплатно
  currency            text NULL CHECK (~ '^[A-Z]{3}$')
  reason              text NOT NULL CHECK (btrim(reason) <> '')
  created_by, created_at, ended_by, ended_at
  CHECK ((monthly_price_minor IS NULL) = (currency IS NULL))
  CHECK (ends_on IS NULL OR ends_on >= starts_on - 1)
```

- Пишет только суперадмин. Период закрывают датой `ends_on`, строку не удаляют. Два периода
  одного модуля одной организации не пересекаются (409).
- Модуль подключён сегодня, если есть период, в который входит сегодняшний UTC-день.
  Функция `modules.Active(ctx, q, orgID, "shop")` — одна на всех.
- Сменить цену = закончить период вчерашним днём и открыть новый с сегодняшнего.
  В админке это одно действие «Изменить цену».
- Даты только вперёд, как у white label: начало и смена цены не раньше сегодняшнего
  UTC-дня, конец не раньше вчерашнего. Так уже начисленный месяц никогда не
  переписывается: нет ни двойного, ни задним числом начисления. Нарушение даёт 422
  (`org_module.starts_on_in_past`, `org_module.from_in_past`,
  `org_module.ends_on_in_past`). Прошлые периоды создают только тесты, напрямую в базе.

### 3.2 Начисление

Как у white label (спека 53 §3.4):

- новый вид `billable_events.kind = 'shop_module_month'`;
- задача `billing.org_modules` (раз в 6 часов) пишет одно событие на период и
  законченный месяц UTC, неполный месяц по дням с округлением вниз, subject = id периода
  и месяц (повтор ничего не добавляет), учитывает `BILLING_COLLECT_SINCE`;
- `billing.rate` превращает событие в начисление по правилу `subscription`
  (`event_kind = 'shop_module_month'`), индивидуальная цена с причиной `individual_price`;
- в месячном счёте отдельная строка «Shop: N months»;
- кредиты пакетов модуль не оплачивают;
- цена прайс-листа — правило `subscription` с `monthly_minor = 0` в каждой валюте
  `standard-2026` (В-9): пока модуль бесплатный для всех. Суперадмин задаёт организации
  индивидуальную цену (§4.4), общая цена меняется новой версией прайс-листа.

### 3.3 Существующие магазины

Миграция открывает период `shop` для каждой организации, у которой уже есть строка
`shop_settings`, со дня её создания, с причиной `migration 0198: shop existed before
modules` и индивидуальной ценой 0 (В-10). Без этого шага действующий
клиент магазина потеряет раздел в момент выката.

### 3.4 Витрина

`shop_settings.enabled` остаётся флагом «витрина открыта». Меняется правило записи:
менять его может держатель `shop.manage` в организации с подключённым модулем
(владелец, менеджер, суперадмин). `shop_domain` — по-прежнему только суперадмин.

Открыть витрину можно, только если (иначе 422 с перечнем, чего не хватает; В-11):

- настройки магазина сохранены;
- у канала магазина есть активный и проверенный платёжный конфиг;
- есть хотя бы один активный товар.

## 4. Сервер

### 4.1 Проверка модуля

- Все маршруты `/v1/organizations/{org_id}/shop/*` проходят middleware
  `requireOrgModule("shop")`. Модуль не подключён → **404 `shop.module_not_enabled`**
  (404, а не 403: для организации без модуля магазина не существует). Суперадмин тоже
  получает 404, кроме маршрутов админки.
- После отключения (§4.2) остаётся **режим «только заказы»**. Он бессрочный: заказы
  магазина (список, карточка, возврат, отправка, заметка, письмо, решение по ручной
  проверке) доступны всегда после отключения, если у организации есть хотя бы один
  оплаченный (`paid_at` заполнено) или открытый заказ (`pending_payment`, `manual_review`,
  `paid` без отправки). Так владелец может вернуть деньги по спору или по поздней просьбе
  покупателя. Каталог, настройки, страницы и витрина закрыты, отвечают 404. Раздел
  исчезает, только если у организации нет ни одного оплаченного или открытого заказа
  (например, все заказы истекли неоплаченными).
  Запрос режима для `/v1/me` использует частичные индексы `shop_orders_open_idx` и
  `shop_orders_paid_idx` (миграция 0198).
- Публичная витрина (`/v1/public/shop/*`) и оформление заказа работают только при
  подключённом модуле И `enabled = true`. Иначе витрина отвечает так же, как закрытая
  сейчас.

### 4.2 Отключение модуля

Суперадмин ставит `ends_on`. Со следующего UTC-дня:

- витрина закрыта, новых заказов нет. При подключении модуля суперадмином `enabled`
  ставится в `false` в той же транзакции, если за день до `starts_on` у организации
  не было периода (первое подключение или возврат после перерыва). Тогда организация
  сама открывает витрину через обычные проверки. Период, который продолжает
  предыдущий, `enabled` не трогает;
- неоплаченные заказы истекают как обычно, по `expires_at`;
- оплаченные заказы можно читать, отправить и вернуть всегда (режим «только заказы»,
  бессрочный, §4.1);
- товары, картинки, страницы и покупатели сохраняются; повторное подключение
  возвращает всё как было;
- начисление идёт по последний день периода включительно.

### 4.3 Признак модуля для клиентов

- `/v1/me`: у каждого членства поле `modules: ["shop"]` и `shop_mode: "full" |
  "orders_only" | null`. Для суперадмина то же в списке всех организаций.
- `GET /v1/organizations/{org_id}/shop/settings` отдаёт `module_active`, `can_open`
  и `open_blockers[]` (что мешает открыть витрину).

### 4.4 Админка (суперадмин)

- `GET /v1/admin/organizations/{org_id}/modules` — периоды и действующая цена.
- `POST /v1/admin/organizations/{org_id}/modules/shop` {starts_on, monthly_price_minor?,
  currency?, reason} — подключить. `starts_on` не раньше сегодня.
- `POST /v1/admin/org-modules/{id}/end` {ends_on, reason} — отключить. `ends_on` не
  раньше вчера.
- `POST /v1/admin/org-modules/{id}/reprice` {from, monthly_price_minor, currency, reason}
  — закрыть и открыть с новой ценой одним запросом. `from` не раньше сегодня.
- Домен — существующий `PUT .../shop/settings` с полем `shop_domain`, теперь из экрана.

Все изменения с `X-Admin-Reason` и в аудите.

### 4.5 Вход в веб с нужного экрана

`POST /v1/bot/web-login-codes` получает необязательный `target`: относительный путь
ивент-центра. Принимаем только `/o/{org_id}/shop`, `/o/{org_id}/shop/...` и пути, которые
уже открывает бот; всё остальное отбрасываем, вход ведёт на главную. После входа
ивент-центр открывает `target`. Ссылка одноразовая и уходит только в личный чат, как сейчас.

### 4.6 Права

Права не меняются. Менеджер (`organizer`) уже имеет `shop.read`, `shop.manage`,
`refund.create`, `refund.approve` — в боте ему доступно всё. Добавлять и удалять
участников может только владелец (`membership.grant/revoke`), так и остаётся.

## 5. Веб-ивент-центр

- Пункт «Магазин» показываем, если `modules` содержит `shop` (или `shop_mode =
  orders_only`) и есть `shop.read`. Иначе пункта нет, прямой адрес даёт экран «Магазин не
  подключён — напишите в поддержку».
- В режиме «только заказы» видны только «Заказы», сверху плашка: «Магазин отключён.
  Витрина закрыта. Заказы и возвраты доступны».
- В «Настройках» кнопка «Открыть витрину» / «Закрыть витрину» для `shop.manage` с
  перечнем `open_blockers`. Текст `shop.settings.operatorOnly` меняется: оператор задаёт
  только домен.
- На экране «Биллинг» строка модуля «Магазин»: с какого дня, цена в месяц (только чтение).

## 6. Админка

На карточке организации блок «Модули → Магазин»:

- состояние: подключён с … / отключён с … / не подключался; витрина открыта или закрыта;
  домен;
- «Подключить»: дата начала (по умолчанию сегодня), цена — «по прайс-листу» /
  «индивидуальная» / «бесплатно», причина;
- «Изменить цену», «Отключить» (дата последнего дня, причина), «Домен»;
- история периодов.

Плюс общий список «Прайс-листы и ставки → Модули» по образцу вкладки «White label».

## 7. Бот

### 7.1 Кнопка и права

- В `homeKeyboard` строка «🛍 Магазин» (`sh:home`), если у текущей организации
  `modules` содержит `shop` или `shop_mode = orders_only`, и роль владелец или менеджер
  (`canViewSales`). Место — после «Заказы».
- Суперадмин видит кнопку в организациях с модулем, как и прочие разделы.
- Каждое нажатие `sh:*` перепроверяет модуль по свежему `/v1/me`: старая кнопка после
  отключения отвечает «Магазин не подключён» и ведёт в главное меню.

### 7.2 Экран «Магазин»

```
🛍 Магазин · <организация>
Витрина: открыта / закрыта · <ссылка на витрину>
К отправке: 3 · На проверке: 1 · Ждут оплаты: 2

[📦 Заказы] [🏷 Товары]
[➕ Новый товар]
[🔓 Открыть витрину] или [🔒 Закрыть витрину]
[⚙️ Настройки] [🌐 Открыть в браузере]
[⬅️ Меню]
```

В режиме «только заказы» — только «Заказы», «Открыть в браузере» и плашка §5.

### 7.3 Заказы

- Вкладки: «К отправке» (по умолчанию), «На проверке», «Ждут оплаты», «Все». По 10 на
  страницу. Строка: номер, дата (в поясе организации), сумма, имя, статус.
- Поиск: набранный текст на экране заказов ищет по номеру, e-mail, имени
  (`POST .../orders/search`).
- Карточка: номер, статус, покупатель (имя, телефон, e-mail), доставка (адрес по строкам или
  «Без доставки»), состав, сумма, оплата, заметка, история.
- Действия:
  - «Отправлен» — трек-номер или «без номера» → `POST .../ship`;
  - «Текст для курьера» — отдельным сообщением в блоке кода, чтобы скопировать целиком;
  - «Заметка» — набранный текст → `PATCH`;
  - «Письмо ещё раз» — выбор письма (получен / отправлен / возврат);
  - «Отменить» (неоплаченный) и «Возврат» (сумма: вся или своя; причина) —
    подтверждение **набранным словом**, как при отмене сеанса; `Idempotency-Key` создаётся в
    начале диалога и хранится в нём, так что повтор после сбоя не вернёт деньги дважды;
    состояние в `bot_dialogs` (kind `shop_refund`);
  - «Решить» для заказа на ручной проверке — те же варианты, что в вебе, деньги тоже через
    набранное слово;
  - «Вернуть на склад» после возврата.

### 7.4 Товары

- Список: активные, черновики, архив; строка — название, цена, остаток. Кнопка товара —
  карточка.
- Карточка простого товара (один вариант): название, цена, остаток, статус, вид, фото.
  Кнопки: «Цена», «Остаток», «Название», «Описание», «Фото», «Опубликовать» / «В черновик» /
  «В архив», «Открыть в браузере».
- Товар с несколькими вариантами: в боте меняются только цена и остаток каждого варианта и
  статус товара. Состав вариантов, опции и цифровые файлы — кнопкой «Открыть в браузере»
  сразу на этот товар.
- Все записи несут `expected_stock` / `expected_variant_ids` / `expected_updated_at`.
  409 → «Пока вы правили, товар изменили» и свежая карточка.

### 7.5 Новый товар (мастер)

Только простой товар, один вариант:

1. Вид: «Товар с доставкой» / «Услуга». Цифровой товар — через веб (файл до 20 МБ
   Telegram, а поддержка и счётчики скачиваний есть только в вебе).
2. Название.
3. Цена в валюте магазина (`FormatMoney` по языку бота).
4. Остаток: число или «Не считать остаток».
5. Фото: одно или несколько, фото или файлом, как афиша; «Пропустить».
6. Описание: текстом или в редакторе мини-приложения; «Пропустить».
7. Итог: «Опубликовать» / «Сохранить черновиком».

Состояние в `bot_dialogs` (kind `shop_product`), переживает перезапуск. Слаг товара
сервер делает из названия.

### 7.6 Витрина и настройки

- «Открыть витрину» → показываем `open_blockers`, если есть; иначе одно нажатие
  «Да, открыть». «Закрыть витрину» — тоже подтверждение, предупреждаем, что неоплаченные
  заказы остаются.
- «Настройки» — только просмотр: валюта, доставка (цена, подпись), страна, 18+,
  контактный e-mail, канал и платёжный провайдер, домен. Правка — «Открыть в браузере» на
  экран настроек.

### 7.7 Что только в вебе

Варианты с опциями, цифровые файлы, страницы витрины, настройки магазина, реферальная
программа магазина, порядок товаров, импорт. Везде в боте — кнопка «Открыть в браузере» с
`target` (§4.5).

### 7.8 Тексты и прочее

- Ключи `bot.sh.*` в `en`, `ru`, `es`, список в `shop_keys.go`, под тестом полноты.
- События аналитики бота: открытие раздела, отправка, возврат, новый товар.
- Новых уведомлений в боте ивент-центра нет (§9, В-6).

## 7a. Уведомления магазина: чат продаж и группа доставки (В-13)

Все сообщения по-прежнему шлёт бот продаж (`SALES_TELEGRAM_BOT_TOKEN`). В боте ивент-центра
уведомлений магазина нет (В-6).

### 7a.1 Два вида подписки вместо одного

`sales_notification_subscriptions.kinds`: вместо `shop` два значения.

- `shop_sale` — **чат продаж**. Только факт: «🛍 Продажа в магазине · заказ № N · сумма ·
  2 позиции: Название ×1, Название ×1». Ни имени, ни телефона, ни e-mail, ни адреса.
- `shop_delivery` — **группа доставки** (комплектовщики, курьерская служба). Полная карточка,
  как сейчас: покупатель, адрес по полям курьера, состав, доставка, заметка покупателя.

Чат с обоими значениями получает только полную карточку (одно сообщение, не два).

### 7a.2 Что куда уходит

| Событие | `shop_sale` (продажи) | `shop_delivery` (доставка) |
| --- | --- | --- |
| Заказ оплачен | факт: номер, сумма, позиции | полная карточка с адресом |
| Возврат | факт: номер, сумма возврата, «возвращён полностью / частично» | сообщение о возврате с номером и составом: не отправлять / остановить |
| Заказ на ручной проверке | «нужно решение в ивент-центре», номер, сумма | ничего: заказ не оплачен, отправлять нечего |
| Ручная проверка решена в пользу отправки | ничего нового: чат уже получил уведомление о проверке | полная карточка (решение пишет `v1.shop.order.paid` с `after_review: true`, `resolve.go`) |

Цифровой товар и услуга (`delivery_kind = none`): в группу доставки не уходят, отправлять
нечего. В чат продаж — факт, как обычно.

### 7a.3 Миграция подписок

- Каждое `shop` в `kinds` становится `shop_delivery`: существующие группы логиста работают
  как сейчас.
- Каждой подписке организации, у которой есть `tickets`, добавляется `shop_sale`: чаты
  продаж начинают слышать факт продажи в магазине. Операторская строка (`org_id NULL`)
  тоже получает `shop_sale`.
- CHECK: `kinds <@ {tickets, shop_sale, shop_delivery}`.
- Сообщения магазина идут только организациям с подключённым модулем или в режиме
  «только заказы» (§4.1).

### 7a.4 Как подключить группу доставки: экран в админке (В-14)

Админка, карточка организации → «Telegram-чаты». Только суперадмин, каждое изменение с
причиной и в аудите.

- Список чатов организации: название, что слышит (билеты / факт продаж магазина /
  доставка), включён ли, последняя ошибка доставки, когда подключён.
- «Добавить чат»: название и что слышит → админка показывает код, например
  `/connect 7KQ2-M9`, срок 30 минут. Оператор добавляет бота продаж в группу и пишет туда
  этот код. Бот отвечает «Чат подключён: <организация>, <что слышит>» и сам записывает
  `chat_id`. Вводить номер чата руками не нужно.
- Правка «что слышит», выключение, удаление (строка помечается удалённой, история
  доставок остаётся).
- Бота удалили из группы — Telegram присылает `my_chat_member`, чат помечается
  «бот удалён из группы», сообщения в него больше не идут.
- Операторские чаты (`org_id NULL`) — там же, во вкладке «Платформа».

Для этого бот продаж начинает принимать сообщения и нажатия, см. §7b.3.

## 7b. Обратная связь из группы доставки (В-15)

Сейчас у заказа магазина один шаг доставки — «Отправлен» (`shipped_at`, `tracking_note`),
и ставит его только организатор в ивент-центре. Группа доставки ничего не может ответить.
Здесь же делается пункт SHOP-B2 бэклога спеки 47.

### 7b.1 Шаги доставки

Новое поле `shop_orders.fulfillment_step`, отдельно от денежного статуса (`status`):
возврат денег не стирает шаг доставки, и наоборот (так было с M-10).

| Шаг | Что значит | Кто ставит |
| --- | --- | --- |
| `waiting` | оплачен, ждёт сборки | сам, при оплате |
| `packed` | собран | группа доставки, ивент-центр, бот |
| `handed_over` | передан курьеру (номер отправления по желанию) | группа, ивент-центр, бот |
| `delivered` | доставлен | группа, ивент-центр, бот |
| `failed` | не доставлен (причина) | группа, ивент-центр, бот |

- `handed_over` — это нынешнее «Отправлен»: статус `shipped`, `shipped_at`, номер
  отправления, письмо покупателю `shop_order_shipped`. Повторное нажатие письма не шлёт.
- После `failed` можно снова `handed_over` (повторная попытка).
- У цифровых товаров и услуг (`delivery_kind = none`) шагов нет.
- Существующие заказы: `shipped` → `handed_over`, оплаченные без отправки → `waiting`.

История — новая таблица `shop_order_events`: заказ, шаг, номер отправления, причина,
кто (пользователь платформы или Telegram-аккаунт: id и имя), откуда (`delivery_group`,
`telegram_bot`, `admin_web`), когда. Пишется на каждый шаг, ничего не удаляется.

### 7b.2 Кнопки под карточкой в группе доставки

Под полной карточкой заказа (§7a.2) — кнопки следующего шага:

```
[📦 Собран] [🚚 Передан курьеру]
[❌ Не доставлен]
```

После нажатия бот правит то же сообщение: строка «📦 Собран · Иван · 14:20 (по поясу
организации)» и кнопки следующего шага. Карточка всегда показывает текущий шаг, лента
группы не засоряется.

- **Передан курьеру** → бот спрашивает номер отправления: ответить на сообщение бота
  текстом или нажать «Без номера».
  Сделано так (М5): вопрос — отдельное сообщение бота с force reply, ответом на карточку, а «Без номера»
  и «Назад» стоят под самой карточкой: у одного сообщения Telegram бывает либо force reply, либо кнопки.
- **Не доставлен** → причина кнопкой: «Не дозвонились», «Нет дома», «Неверный адрес»,
  «Отказ от получения», «Другое» (тогда текстом ответом на сообщение).
- **Доставлен** — появляется после «Передан курьеру».
- Если заказ тем временем вернули или отменили, нажатие отвечает «Заказ возвращён, не
  отправлять», кнопки снимаются.
- Если шаг уже поставил кто-то другой (в группе или в ивент-центре), нажатие отвечает,
  какой шаг сейчас, и обновляет карточку.

Нажимать может любой участник группы, подключённой к этой организации как
`shop_delivery`. В истории записываются его Telegram-имя и id.

### 7b.3 Как бот продаж получает нажатия

- Бот продаж сейчас только отправляет сообщения (из `arena-worker`). Принимать нажатия,
  ответы и `/connect` будет процесс `arena-bot`: второй опрос Telegram (`getUpdates`) с
  токеном `SALES_TELEGRAM_BOT_TOKEN`, рядом с ботом ивент-центра. `arena-bot` и так
  работает в одном экземпляре, а отправка из воркера опросу не мешает.
- Нажатие уходит в API под сервисным токеном бота:
  `POST /v1/bot/shop-delivery/steps` {chat_id, telegram_user_id, telegram_name, order_id,
  step, tracking?, reason?}. Сервер проверяет, что `chat_id` — включённая группа
  `shop_delivery` организации этого заказа; иначе 404.
- Шаг из группы, из ивент-центра и из бота ставится одной функцией
  `shop.SetFulfillmentStep` с блокировкой строки заказа: два одновременных нажатия не
  поставят шаг дважды и не отправят два письма.
- После шага, поставленного НЕ из группы, бот продаж обновляет карточку в группе: группа
  всегда видит актуальный шаг. Для этого при отправке карточки запоминаем `message_id`
  (в `sales_notification_deliveries`).

### 7b.4 Где это видно организатору

- **Веб-ивент-центр.** В списке заказов колонка «Доставка» и фильтр по шагу; бейдж «ждёт
  больше N дней» для `waiting`/`packed`; в карточке — история шагов с именами.
- **Бот ивент-центра.** Вкладка «К отправке» = `waiting` и `packed`, новая вкладка «Не
  доставлены» = `failed`. В карточке — текущий шаг и история; те же кнопки шагов.
- **Чат продаж (`shop_sale`).** Только «Не доставлен: заказ № N, причина»: организатору
  решать, что дальше (повторная доставка или возврат). Остальные шаги туда не идут.
- **Покупатель.** Письмо при «Передан курьеру» (уже есть) и письмо **всегда** при
  «Доставлен» (В-17): новый вид `shop_order_delivered` задания `shop.order_email`, шаблоны на
  семи языках в оформлении `shop_order_shipped`, одно письмо на заказ (отметка в
  `shop_orders.metadata`, как у остальных писем), «Отправить письмо ещё раз» получает вид
  `delivered`. Повторное «Доставлен» после «Не доставлен» и новой передачи курьеру шлёт
  письмо, только если его ещё не было.

## 8. Этапы

1. **М1. Модуль.** Миграция, `modules.Active`, middleware, режим «только заказы»,
   `/v1/me`, перенос права на `enabled`, `open_blockers`, админские маршруты, начисление,
   уведомления §7a (виды подписки, короткое сообщение, миграция подписок), OpenAPI +
   клиенты, интеграционные тесты.
2. **М2. Админка и веб.** Блок модуля в карточке организации, вкладка «Модули», скрытие
   раздела, режим «только заказы», кнопки витрины, строка в «Биллинге», парная матрица.
3. **М3. Бот: заказы.** Кнопка, экран магазина, заказы, карточка, все действия, вход в веб
   с `target`.
4. **М4. Бот: товары.** Список, карточка, быстрая правка, мастер нового товара, витрина.
5. **М5. Доставка.** Шаги доставки и история (§7b.1), опрос бота продаж в `arena-bot`,
   `/connect`, кнопки в группе, обновление карточки, сервисный маршрут; экран
   «Telegram-чаты» в админке (§7a.4); шаги в веб-ивент-центре и в боте.

М1 нужен всем остальным. После М1 параллельно идут М2, М3 и М5. М4 — после М3. Шаги
доставки в карточке заказа бота (М3) появляются вместе с М5.

## 9. Решения владельца (05.11.2026)

- **В-1.** Витрину открывает и закрывает владелец или менеджер организации.
- **В-2.** У организации без подключения магазин скрыт везде, включая веб-ивент-центр.
- **В-3.** При отключении витрина закрывается, оплаченные заказы доводятся до конца.
- **В-4.** В боте: работа с заказами и добавление простых товаров. Остальное —
  ссылкой в веб-ивент-центр со входом под этим человеком.
- **В-5.** Менеджеру в боте разрешено всё. Добавлять и удалять участников — только
  владелец.
- **В-6.** Уведомления о заказах магазина — только в боте продаж.
- **В-7.** Модуль платный. Цену задаёт суперадмин, он же может сделать модуль бесплатным.
- **В-8.** Подключается только из админки, не из бота.

- **В-9.** Цена модуля по прайс-листу 0. Суперадмин задаёт цену организации сам.
- **В-10.** Действующие магазины получают модуль с ценой 0.
- **В-11.** Витрину без активного товара и проверенного платёжного конфига открыть нельзя.
- **В-12.** Режим «только заказы» после отключения бессрочный: заказы магазина (список,
  карточка, возврат, отправка) доступны всегда, если у организации есть хотя бы один
  оплаченный или открытый заказ. Каталог, настройки, страницы и витрина закрыты
  (§4.1, §4.2).
- **В-13.** Заказы магазина с адресом уходят только в отдельную группу доставки. В чат
  продаж — только факт продажи, без данных покупателя (§7a).

- **В-14.** Чаты бота продаж (включая группу доставки) подключаются экраном в админке, не
  SQL (§7a.4).
- **В-15.** Информация о доставке возвращается из группы доставки и учитывается в заказе
  (§7b).

- **В-16.** Кнопки в группе доставки нажимает любой участник группы; имя и Telegram-id
  нажавшего пишутся в историю (§7b.2).
- **В-17.** Письмо покупателю «Заказ доставлен» уходит всегда (§7b.4).
- **В-18.** Причины «Не доставлен» — список §7b.2.
- **В-19.** Старые заказы доступны для возврата всегда (решение 05.11): после отключения
  модуля владелец читает заказы и возвращает деньги по спорам и поздним просьбам, срока
  нет (§4.1).
