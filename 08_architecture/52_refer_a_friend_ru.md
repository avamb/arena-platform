# 52. «Приведи друга»: скидка другу, кэшбэк приводящему (01.11.2026)

Статус: **черновик, ждёт ответов владельца (§9)**. Код не начат.

Источник: решение владельца Р-4 (спека 51 §4.3), решение 16.10 «при возврате плата платформы
остаётся». Опирается на промокоды (спека 25, `hcheckout.ValidatePromoForLines` +
`CheckPromoLimits`), отслеживаемые ссылки (спека 43), движок возвратов (спека 36, пакет
`internal/platform/refunds`).

## 1. Что строим

1. Покупатель оплатил заказ на мероприятие, где организатор включил программу.
2. Он получает **личный код** и ссылку с ним: на странице «спасибо» и в письме с билетами.
3. Друг открывает ссылку (или вводит код) и получает **процентную скидку** на свой заказ.
4. Когда заказ друга «состоялся» (правило §5), приводящему возвращается **часть его
   исходного платежа** через провайдера организатора — частичный возврат без гашения билета.
5. Приводящий получает от Arena письмо о кэшбэке. Организатор видит начисления и выплаты в
   ивент-центре и боте.

Деньги за кэшбэк платит организатор: возврат уходит с его счёта у провайдера. Платформа
кэшбэк не финансирует.

## 2. Что уже есть и что подходит (проверено на master 23b7d49)

| Нужно | Есть | Вывод |
|---|---|---|
| Скидка по коду | `promo_codes`, проверка `ValidatePromoForLines` + `CheckPromoLimits` на всех поверхностях, учёт `promo_code_redemptions` по заказу | Личный код = строка `promo_codes`. Скидка, лимиты, журнал попыток и сводки работают без изменений |
| Ссылка | `sales_links` (спека 43): редирект `/go/{code}`, QR, атрибуция `ref`, последнее касание 7 дней | Использовать как **канал**, но не как ключ программы: последнее касание затирается другим QR, и скидка пропала бы. Ключ — код (§3.2) |
| Частичный возврат без гашения | `refunds.CreateBatch` с `CancelTickets=false`, явная сумма на билет, ключ идемпотентности, очередь «Возвраты», письмо, sweep | Кэшбэк = возврат движка с новым `origin`. Сам движок не меняется, кроме двух исключений (§6.3) |

## 3. Модель (предложение)

### 3.1 Программа

```sql
CREATE TABLE referral_programs (
    id                   uuid PRIMARY KEY DEFAULT uuidv7(),
    org_id               uuid NOT NULL REFERENCES organizations(id),
    event_id             uuid NOT NULL,                 -- (event_id, org_id) -> events, как у материалов
    status               text NOT NULL DEFAULT 'active' CHECK (status IN ('active','paused','ended')),
    friend_discount_pct  smallint NOT NULL CHECK (friend_discount_pct BETWEEN 1 AND 100),
    cashback_pct         smallint NOT NULL CHECK (cashback_pct BETWEEN 1 AND 100),  -- от чего — В-3
    cashback_cap_pct     smallint NOT NULL DEFAULT 100 CHECK (cashback_cap_pct BETWEEN 1 AND 100), -- от исходного платежа
    max_friends          smallint,                      -- NULL = без предела
    payout_mode          text NOT NULL DEFAULT 'auto' CHECK (payout_mode IN ('auto','approve')),   -- В-6
    starts_at, ends_at   timestamptz,                   -- по умолчанию: с включения до конца продаж
    created_by, created_via, created_at, updated_at ...
);
-- одна живая программа на мероприятие
```

Изменение процентов действует на **новые** коды и заказы. У уже выданного кода проценты
записаны в нём (снимок), чтобы покупатель получил обещанное.

### 3.2 Личный код

Строка `promo_codes` с новыми колонками `origin` и `referral_program_id`, `referrer_order_id`:

- `origin`: `manual` (по умолчанию) / `referral`. Колонку вводит та из двух сессий («Приведи друга»,
  «Брошенная корзина»), что вливается первой; корзине своё значение не нужно: её код «за подписку» — обычный `manual`, связь хранится в `org_growth_settings`.
- Списки промокодов ивент-центра и бота показывают только `origin='manual'`. Личные коды
  видны в карточке программы.
- Код: префикс из имени приводящего латиницей плюс 4 символа алфавита спеки 43
  (`ANNA-7K2Q`); без имени — 8 символов. Уникален в организации (`promo_codes_unique_per_org`).
- Скидка: `percent`, `friend_discount_pct`; сеансы = сеансы мероприятия; срок = срок
  программы; `max_uses` = `max_friends`; `max_uses_per_customer = 1`.
- Выдаётся лениво и идемпотентно по `referrer_order_id` (уникальный частичный индекс): первый,
  кто попросит (страница «спасибо», письмо), создаёт код; повтор возвращает тот же. Выдача —
  вне денежной транзакции оплаты (письмо собирает воркер, страница — свой запрос).

### 3.3 Ссылка

`<страница мероприятия>?promo=ANNA-7K2Q&utm_source=referral&utm_medium=friend&utm_campaign=<slug>`.
Страница и виджет читают `promo`, подставляют код и применяют его (сегодня такого параметра
нет — добавить). Короткая ссылка `/go/…` и QR — по В-2.

### 3.4 Начисление

```sql
CREATE TABLE referral_rewards (
    id                uuid PRIMARY KEY DEFAULT uuidv7(),
    org_id            uuid NOT NULL,
    program_id        uuid NOT NULL REFERENCES referral_programs(id),
    promo_code_id     uuid NOT NULL REFERENCES promo_codes(id),
    referrer_order_id uuid NOT NULL REFERENCES orders(id),
    friend_order_id   uuid NOT NULL REFERENCES orders(id) UNIQUE,   -- один заказ друга = одно начисление
    amount_minor      bigint NOT NULL CHECK (amount_minor >= 0),
    currency          text NOT NULL,
    state             text NOT NULL CHECK (state IN
        ('waiting','due','awaiting_approval','sent','paid','capped','cancelled','failed','not_possible')),
    reason            text,           -- self_referral, friend_refunded, dispute_open, provider_unsupported, cap_reached ...
    refund_id         uuid REFERENCES refunds(id),
    due_at            timestamptz,    -- когда можно платить (§5)
    created_at, updated_at ...
);
```

Строка пишется в транзакции оплаты друга (`FulfillCompletedCheckoutTx`, рядом с
`recordPromoRedemptionTx`) — одна вставка, её отказ под SAVEPOINT не ломает оплату
(правило AGENTS «best effort внутри денежной транзакции»).

## 4. Расчёт кэшбэка

- Сумма = `cashback_pct` от базы (В-3), округление вниз в младших единицах.
- Предел: сумма всех `sent`+`paid` начислений по одному `referrer_order_id` не больше
  `cashback_cap_pct` от оплаченного итога его заказа минус уже вернувшиеся деньги.
  Излишек — `capped`.
- Валюта кэшбэка = валюта заказа приводящего. Заказ друга в другой валюте (другое мероприятие
  программы быть не может, но сеансы мероприятия могут продаваться в разных валютах) —
  `not_possible` (курсов в коде нет, решение биллинга R-B5).
- Возврат раскладывается по живым билетам заказа приводящего (у движка бюджет на билет —
  `order_items.total`), от дорогого к дешёвому, явными суммами, `CancelTickets=false`.

## 5. Когда платить

Предложение (В-4): **после окончания сеанса друга + 3 дня**, и только если заказ друга
по-прежнему оплачен (не возвращён, не отменён, нет спора) и заказ приводящего тоже.

Почему не сразу после оплаты друга: иначе друг может вернуть билет, а кэшбэк уже ушёл —
организатор платит за отменённую продажу. Минус: приводящий ждёт. Сеанс друга почти всегда
в пределах окна возврата провайдера (§6.2).

Воркер `referral.payout_sweep` (раз в 10 минут, самопланирующийся):
`waiting` → `due` по правилу; `due` → создаёт возврат движка (`auto`) или `awaiting_approval`
(`approve`); после ответа движка → `paid` / `failed`; повторная проверка условий прямо перед
созданием возврата, под `refunds.LockPayment` заказа приводящего.

## 6. Деньги и провайдеры

### 6.1 Как уходит возврат

Через движок, как любой возврат: `refunds.origin='referral_cashback'`, причина
«Кэшбэк по программе «Приведи друга», заказ друга №…», ключ идемпотентности
`referral-<reward id>`. У Stripe движок уже шлёт `metadata.arena_refund_id`; добавим
`metadata.arena_referral_reward_id`, `reason=requested_by_customer` (никогда `fraudulent`).
AllPay — `amount` с проверкой `paymentstatus` (уже в модуле), PayPlus —
`RefundByTransactionUID` с меткой `more_info` (уже в модуле).

### 6.2 Что может помешать

| Случай | Что делаем |
|---|---|
| По платежу приводящего открыт спор (Stripe не возвращает) | держим `due`, повторяем; если спор проигран или срок вышел — `not_possible`, организатору в очередь |
| У организатора нет баланса (Stripe ставит возврат `pending`) | движок уже держит такой возврат и дочитывает; `sent` до подтверждения |
| Провайдер отказал | `failed`, видно в очереди «Возвраты», есть «Повторить» (правило движка: только если деньги точно не ушли) |
| Провайдер не умеет частичный возврат (Flitt сейчас), заказ с сайта, бесплатный заказ | `not_possible` сразу; при включении программы ивент-центр предупреждает, если канал продаж на таком провайдере |
| Платёж старше окна возврата провайдера (Stripe: карточные возвраты обычно до ~180 дней; AllPay, PayPlus — уточнить) | `not_possible` с причиной; альтернатива — В-7 |

Комиссия провайдера с исходного платежа не возвращается (Stripe её удерживает) — это
расход организатора, говорим об этом в настройке программы.

### 6.3 Два исключения в движке

1. **Сканированный билет.** Сейчас возврат по отсканированному билету запрещён везде
   (`refunds/scanned.go`). Кэшбэк платится ПОСЛЕ мероприятия, билет приводящего почти всегда
   отсканирован. Предложение: правило не касается `origin='referral_cashback'` с
   `cancel_ticket=false` — билет остаётся действительным, деньги не за билет. Нужно решение
   владельца (В-5), правило «отсканированный билет не возвращаем» было его решением 12.10.
2. **Письмо покупателю.** Обычное письмо о возврате («билет больше не действует» и т. п.) не
   подходит. Для кэшбэка — своё письмо (§7.3), обычное не шлём (`notify_buyer=false` у пакета).

## 7. Экраны и письма

### 7.1 Организатор (веб-ивент-центр и бот)

- Карточка мероприятия → «Приведи друга»: включить, проценты, предел, число друзей, режим
  выплаты, срок; предупреждение о провайдере; пауза; итоги (кодов выдано, друзей пришло,
  скидка дана, кэшбэк начислен/выплачен/не выплачен).
- Список начислений с фильтром по состоянию; в режиме `approve` — «Выплатить» (одно
  нажатие + повтор пароля в вебе, как у возвратов) и «Не выплачивать» с причиной.
- Права: настройка — `promo.update` (+ `refund.create`); выплата — `refund.create` +
  `refund.approve`. У владельца и менеджера они есть (0129), у агента нет.

### 7.2 Покупатель

- Страница «спасибо» и письмо с билетами: блок «Пригласите друга: скидка N % другу, вам
  вернётся до M % стоимости» + код + ссылка + «Поделиться» (Web Share API на телефоне).
- Только если программа активна и заказ оплачен деньгами (не приглашение, не 0).

### 7.3 Письма Arena (7 языков)

- `referral_cashback_sent` — приводящему: «Друг купил билет по вашему коду. Мы вернули X на
  карту, которой вы платили. Банку обычно нужно 5–10 рабочих дней». Stripe сам не пишет.
- `referral_friend_used` — по В-8 (письмо приводящему сразу, когда друг оплатил).
- Уведомление организатору в Telegram — через продажного бота, по В-9.

## 8. Защита от накрутки

1. Код не применяется, если покупатель = приводящий: тот же `customer_id`, e-mail или телефон
   (идентичности `customer_identities`). Проверка — при применении кода (понятная ошибка) и
   ещё раз при создании начисления (`self_referral`).
2. `max_uses_per_customer = 1`: один друг — одна скидка.
3. `max_friends` и предел кэшбэка (§4) ограничивают сумму сверху.
4. Начисление только после «состоялся» (§5) — купить и вернуть не выгодно.
5. Опционально: тот же отпечаток карты Stripe у друга и приводящего → `self_referral`
   (нужно читать charge; В-10).
6. Код приводящего не даёт скидку на его же повторный заказ.

## 10. Отчёты и биллинг

- Сводка мероприятия/сеанса: новые числа «по коду друга» (заказы, билеты, скидка) и
  «кэшбэк выплачен» отдельно от «возвратов» — иначе возвраты выглядят выше, чем есть.
- `billing.collect` сегодня пишет `ticket_refunded` по каждому успешному возврату.
  Кэшбэк — не возврат билета: источник пропускает `origin='referral_cashback'`, либо пишет
  отдельный вид без платы (журнал). Плата за билет друга и приводящего остаётся.
- CSV продаж: колонка «Код друга».
