# 52. «Приведи друга»: скидка другу, кэшбэк приводящему (01–02.11.2026)

Статус: **реализовано в ветке `claude/refer-a-friend-644918` (PR #348), 03.11.2026.** Решения
владельца 02.11 — §0; владелец 02.11 принял предложения §9 (В-1, В-2, В-8–В-15). Отличия реализации
от текста ниже: личный код — 6 случайных символов (`ANNA-7K2QX9`); проценты кэшбэка и предела
снимаются в код при выдаче; код выдаётся только покупателю, чей платёж провайдер умеет вернуть
частично; остановка кода после двух отмен у друзей окончательная; реферальный код не действует в
шлюзе сайтов, REST-checkout и promo-validate.

03.11.2026 (ветка `claude/referral-payout-after-event`): выплата после мероприятия, проверка
баланса Stripe перед выплатой и слежение за статусом возврата — Р-RF2, §5.1, §5.2 п. 5, §6.2.

Источник: решение владельца Р-4 (спека 51 §4.3), решение 16.10 «при возврате плата платформы
остаётся». Опирается на промокоды (спека 25, `hcheckout.ValidatePromoForLines` +
`CheckPromoLimits`), отслеживаемые ссылки (спека 43), движок возвратов (спека 36, пакет
`internal/platform/refunds`), магазин (спека 47).

## 1. Что строим

1. Покупатель оплатил заказ — билеты на мероприятие или покупку в магазине, где организатор
   включил программу.
2. Он получает **личный код** и ссылку с ним: на странице «спасибо» и в письме о заказе.
3. Друг открывает ссылку (или вводит код) и получает **процентную скидку** на свой заказ.
4. После мероприятия друга (Р-RF2, решение 03.11) приводящему возвращается **процент от
   стоимости билетов друга после скидки** (без сборов), — частичный возврат на его исходный
   платёж через провайдера организатора. Билет приводящего не гасится. В магазине — сразу
   после оплаты друга (§5.1, открытый вопрос).
5. Приводящий получает от Arena письмо о кэшбэке. Организатор видит начисления и выплаты в
   ивент-центре и боте.

Деньги за кэшбэк платит организатор: возврат уходит с его счёта у провайдера. Платформа
кэшбэк не финансирует.

## 3. Модель

### 3.1 Программа

```sql
CREATE TABLE referral_programs (
    id                   uuid PRIMARY KEY DEFAULT uuidv7(),
    org_id               uuid NOT NULL REFERENCES organizations(id),
    scope                text NOT NULL CHECK (scope IN ('event','shop')),
    event_id             uuid,                          -- для scope='event'; (event_id, org_id) -> events
    status               text NOT NULL DEFAULT 'active' CHECK (status IN ('active','paused','ended')),
    friend_discount_pct  smallint NOT NULL CHECK (friend_discount_pct BETWEEN 1 AND 100),
    cashback_pct         smallint NOT NULL CHECK (cashback_pct BETWEEN 1 AND 100),  -- от суммы друга (Р-RF1)
    cashback_cap_pct     smallint NOT NULL DEFAULT 100 CHECK (cashback_cap_pct BETWEEN 1 AND 100), -- от исходного платежа
    max_friends          smallint,                      -- NULL = без предела
    starts_at, ends_at   timestamptz,                   -- мероприятие: по умолчанию до конца продаж
    terms_accepted_at    timestamptz NOT NULL,          -- организатор прочитал подсказку Р-RF5
    created_by, created_via, created_at, updated_at ...,
    CHECK ((scope = 'event') = (event_id IS NOT NULL))
);
-- одна живая программа на мероприятие и одна на магазин организации
```

Изменение процентов действует на **новые** коды. У выданного кода проценты записаны в нём
(снимок), чтобы покупатель получил обещанное. Пауза и выключение останавливают **новые**
скидки и начисления; начисление по уже оплаченному заказу друга выплачивается.

### 3.2 Личный код

Строка `promo_codes` с новыми колонками `origin`, `referral_program_id`, `referrer_order_id`
(или `referrer_shop_order_id`):

- `origin`: `manual` (по умолчанию) / `referral`. Колонку вводит та из двух сессий («Приведи
  друга», «Брошенная корзина»), что вливается первой; корзине своё значение не нужно: её код
  «за подписку» — обычный `manual`, связь хранится в `org_growth_settings`.
- Списки промокодов ивент-центра и бота показывают только `origin='manual'`. Личные коды
  видны в карточке программы.
- Код: префикс из имени приводящего латиницей плюс 4 символа алфавита спеки 43
  (`ANNA-7K2Q`); без имени — 8 символов. Уникален в организации (`promo_codes_unique_per_org`).
- Скидка: `percent`, `friend_discount_pct`; сеансы = сеансы мероприятия; срок = срок
  программы; `max_uses` = `max_friends`; `max_uses_per_customer = 1`.
- Выдаётся лениво и идемпотентно по заказу приводящего (уникальный частичный индекс): первый,
  кто попросит (страница «спасибо», письмо), создаёт код; повтор возвращает тот же. Выдача —
  вне денежной транзакции оплаты.
- Код перестаёт действовать (`status='inactive'`), когда заказ приводящего полностью
  возвращён или отменён: кэшбэк больше некуда вернуть, а скидка без кэшбэка — уже не программа.

### 3.3 Ссылка

`<страница мероприятия или магазина>?promo=ANNA-7K2Q&utm_source=referral&utm_medium=friend&utm_campaign=<slug>`.
Страница, виджет и витрина магазина читают `promo`, подставляют код и применяют его (сегодня
такого параметра нет — добавить). Короткая ссылка `/go/…` и QR — по В-2.

### 3.4 Начисление

```sql
CREATE TABLE referral_rewards (
    id                     uuid PRIMARY KEY DEFAULT uuidv7(),
    org_id                 uuid NOT NULL,
    program_id             uuid NOT NULL REFERENCES referral_programs(id),
    promo_code_id          uuid NOT NULL REFERENCES promo_codes(id),
    referrer_order_id      uuid REFERENCES orders(id),
    referrer_shop_order_id uuid REFERENCES shop_orders(id),
    friend_order_id        uuid REFERENCES orders(id) UNIQUE,
    friend_shop_order_id   uuid REFERENCES shop_orders(id) UNIQUE,
    amount_minor           bigint NOT NULL CHECK (amount_minor >= 0),
    currency               text NOT NULL,
    state                  text NOT NULL CHECK (state IN
        ('due','sent','paid','capped','not_possible','failed','cancelled')),
    reason                 text,      -- self_referral, cap_reached, dispute_open, card_unavailable, provider_declined, program_off ...
    friend_reversal        text,      -- NULL / refunded / partially_refunded / disputed — для §5.2
    refund_id              uuid REFERENCES refunds(id),
    created_at, updated_at ...
);
```

Строка `due` пишется в транзакции оплаты друга (`FulfillCompletedCheckoutTx` рядом с
`recordPromoRedemptionTx`; в магазине — `markPaidTx`) под SAVEPOINT: её отказ не ломает
оплату (правило AGENTS «best effort внутри денежной транзакции»). Выплату делает воркер после
мероприятия друга (§5.1, решение 03.11).

### 3.5 Промокод в магазине (минимум для программы)

В магазине промокодов нет. Для программы добавляем только личный код программы магазина:
поле `promo_code` в `POST .../shop/checkout`, проверка «код программы этого магазина, активен,
не свой, один раз на покупателя», скидка процентом на товары (без доставки), снимок в
`shop_orders` (`discount_minor`, `promo_code_id`). Обычные промокоды магазина — отдельная
задача, не в этой волне.

## 4. Расчёт кэшбэка

- База — **стоимость билетов друга после всех скидок** (Р-RF1, решение 03.11):
  `subtotal − discount` заказа, без `charge` (сервисный сбор), налогов и сборов провайдера.
  В магазине — товары после скидки, без доставки. Сумма = `cashback_pct` от базы,
  округление вниз в младших единицах. Пример: 2 билета по 250 CZK, скидка 10 % → 450,
  сбор 4,50 → друг платит 454,50; кэшбэк 10 % = 45,00.
- Предел: сумма всех `sent`+`paid` начислений по одному заказу приводящего не больше
  `cashback_cap_pct` от его билетов (товаров) после скидки, без сборов, минус деньги, уже вернувшиеся ему по любым
  возвратам. Излишек — `capped` (начисление видно, денег нет).
- Валюта: кэшбэк в валюте заказа приводящего. Заказ друга в другой валюте — `not_possible`
  (курсов в коде нет, решение биллинга R-B5).
- Билеты: возврат раскладывается по живым билетам заказа приводящего (бюджет на билет —
  `order_items.total`), от дорогого к дешёвому, явными суммами, `CancelTickets=false`.
  Магазин: возврат на платёж заказа магазина, без строк товара.

## 5. Когда платить и что с отменой у друга

### 5.1 Выплата (Р-RF2, Р-RF4; изменено 03.11.2026)

Начисление `due` пишется, как и прежде, в транзакции оплаты друга, и в ней же ставится
задача `referral.payout`. Платит она **после мероприятия** (код — `referral/wait.go`):

- **Срок** — конец сеанса заказа друга (`sessions.end_at`; если сеансов в заказе несколько —
  самый поздний из неотменённых) **плюс сутки** (`PayoutGrace`). Сутки — вечер мероприятия и
  следующий день, когда приходит большинство просьб «не смог прийти, верните». До срока
  начисление стоит `due` с `wait_reason='waiting_event'` и `next_attempt_at` = срок;
  `referral.payout_sweep` ставит задачу снова, когда срок наступил. Ожидание не считается
  попыткой (`attempts` не растёт).
- **Друг вернул деньги или открыл спор до срока** → начисление `cancelled`
  (`friend_refunded`, `friend_disputed`), денег нет. Sweep отменяет такие начисления сразу,
  не дожидаясь срока, если по ним ещё нет пакета возврата. Ради этого правило и введено:
  организатор не теряет кэшбэк, когда друг возвращает свой билет.
- **Отсканированный билет друга** кэшбэк не отменяет: друг пришёл.
- **Сеанс перенесён** — срок считается заново при каждой попытке, выплата едет вместе с
  датой. Если сеанс перенесли раньше, выплата уйдёт не раньше старого срока (позже — не
  страшно).
- **Сеанс отменён** (`status='cancelled'` или удалён) — отмена не выплата: начисление ждёт
  (`wait_reason='session_cancelled'`, проверка раз в 6 часов). Вернули другу деньги →
  `cancelled` (`friend_refunded`). Если за 60 дней после запланированного конца другу так и
  не вернули деньги, начисление закрывается `cancelled` с причиной `session_cancelled`, без
  письма.
- **Магазин** не меняется: у заказа магазина нет сеанса, кэшбэк уходит сразу после оплаты
  друга. Открытый вопрос владельцу — В-16 (§9).

Причина ожидания хранится отдельно от `reason` (`referral_rewards.wait_reason`, миграция
0196): выплаченное начисление сохраняет свою причину (`cap_reduced`).

Когда срок наступил, воркер (`referral.payout_sweep` раз в 10 минут — подстраховка):
1. Под `refunds.LockPayment` платежа приводящего ещё раз проверяет: программа включена,
   заказ друга оплачен, не самоприглашение (§8), предел не превышен.
1а. Читает баланс Stripe организатора (§6.2): не хватает — ждём, возврат не создаём.
2. Создаёт возврат движка с ключом `referral-<reward id>` и `Approved=true` (подтверждения
   организатора нет — Р-RF4).
3. По ответу движка: `sent` → `paid`; отказ — §6.2.

### 5.2 Друг вернул деньги или открыл спор (коллизия Р-RF2) — предложение

Кэшбэк уже ушёл на карту приводящего, забрать его обратно нельзя: списать деньги с чужой
карты без согласия мы не можем. Значит, это расход организатора. Предлагаю:

1. **Предупреждение до возврата.** Экран возврата в ивент-центре и боте (`refund-options`)
   по заказу друга показывает: «По этому заказу приводящему уже вернули X. Возврат другу эти
   деньги не вернёт». Возврат не блокируем.
2. **Уведомление после.** Когда заказ друга возвращён (любым путём: ивент-центр, бот,
   кабинет провайдера) или по нему открыт спор, начислению ставится `friend_reversal`, а организатору уходит сообщение в
   продажный Telegram-чат и письмо владельцам: «Друг по коду ANNA-7K2Q вернул деньги / открыл
   спор. Кэшбэк X уже выплачен приводящему, вернуть его нельзя».
   Споры: одно место — таблица `payment_disputes` сессии «Чарджбэки» (миграция 0189,
   PR #360; в неё пишут и вебхук провайдера, и ручное внесение). Outbox-события у неё нет.
   `referral.payout_sweep` сам проверяет `EXISTS (… WHERE order_id = <заказ друга> AND NOT
   is_inquiry)` по начислениям последних 120 дней без `friend_reversal`; запрос
   (`is_inquiry`) спором не считается. Та же проверка перед выплатой: спор по заказу друга
   до выплаты → `cancelled`, причина `friend_disputed`.
3. **Защита от повторов.** Если у одного кода два таких случая — код ставится на паузу, и
   организатор получает об этом отдельную строку в том же сообщении. Включить обратно может
   организатор в карточке программы.
4. Пока выплата не ушла (`due`, `failed`), а друг уже вернул деньги — начисление
   `cancelled` с причиной `friend_refunded`, выплаты не будет. С 03.11 выплата ждёт конца
   мероприятия (§5.1), так что этот случай — основной, а уведомление п. 2 остаётся для
   возврата или спора уже после выплаты.
5. В условиях продажи и в подсказке при включении (решение 03.11.2026): «кэшбэк
   выплачивается после мероприятия, через сутки после окончания сеанса друга. Если друг до
   этого вернёт деньги, кэшбэка не будет; выплаченный кэшбэк не отзывается. Он платится с
   вашего баланса Stripe: если денег не хватает, Arena сообщит и подождёт до 30 дней, потом
   кэшбэк не выплачивается, и рассчитаться с покупателем нужно вам». Покупателю в блоке
   «Пригласите друга» — «вернётся на карту после мероприятия». В магазине — по-прежнему
   «сразу после оплаты друга».

## 6. Деньги и провайдеры

### 6.1 Как уходит возврат

Через движок, как любой возврат: `refunds.origin='referral_cashback'`, причина
«Кэшбэк по программе «Приведи друга», заказ друга №…». У Stripe движок уже шлёт
`metadata.arena_refund_id`; добавим `metadata.arena_referral_reward_id`,
`reason=requested_by_customer` (никогда `fraudulent`). AllPay — `amount` с проверкой
`paymentstatus` (уже в модуле), PayPlus — `RefundByTransactionUID` с меткой `more_info`
(уже в модуле).

### 6.2 Что может помешать

| Случай | Что делаем |
|---|---|
| Провайдер канала не умеет частичный возврат (Flitt сейчас), продажи только через сайт | Программу **нельзя включить**: ивент-центр объясняет почему. Иначе каждый кэшбэк был бы «не выплачен» |
| На балансе Stripe организатора не хватает денег (решение 03.11.2026) | **До возврата**: воркер читает `GET /v1/balance` ключом организатора (тот же модуль и ключ, что для возврата; `payments.BalanceReader`, есть только у Stripe — у AllPay и PayPlus такого API нет, для них проверка пропускается). Смотрим `available` в валюте заказа. Меньше суммы кэшбэка → возврат не создаём, начисление `due`, `wait_reason='waiting_balance'`, повтор раз в 6 часов. Организатору **один раз** — сообщение в продажный Telegram-чат и письмо владельцам `referral_payout_organizer`: «Для выплаты кэшбэка N покупателям нужно X на балансе Stripe» (новое ожидающее начисление шлёт новое сообщение с новыми итогами, повторные попытки — нет). Баланс не прочитался — «неизвестно» (`balance_unknown`), повтор через час, это не отказ. Ждём дольше **30 дней** → `not_possible`, причина `balance_timeout`: приводящему письмо `referral_cashback_unavailable` («обратитесь к организатору»), организатору — «кэшбэк не выплачен, рассчитайтесь с покупателем сами, например дайте ему промокод». Запасного кэшбэка промокодом от Arena нет (решение владельца) |
| Stripe принял возврат, но держит его `pending` (`pending_reason: insufficient_funds`) | Начисление `sent`, пока возврат `provider_pending`. Через час ожидания организатору один раз: «Stripe держит кэшбэк, пополните баланс». Движок ждёт такой (денежный, без гашения) возврат **50 дней**, а не 7 (`CashbackPendingParkAfter`), и дочитывает его раз в 6 часов после первых суток: Stripe держит возврат до 45 дней. Если Stripe за это время списал недостачу с банка организатора — возврат `succeeded`, начисление `paid` |
| Stripe отменил возврат после 45 дней (`failure_reason: insufficient_funds`) | Вебхук `refund.updated`/`refund.failed` или дочитывание → возврат кэшбэка сразу `failed` (не `manual_review`: билет не гасился, исправлять человеку нечего) → начисление `not_possible` с причиной `insufficient_funds`, письмо приводящему `referral_cashback_unavailable` и сообщение организатору «кэшбэк не выплачен» |
| По платежу приводящего открыт спор (Stripe не возвращает) | повторяем 7 дней; потом `not_possible` по Р-RF5 |
| Карта приводящего недоступна, платёж старше окна возврата провайдера, провайдер отказал | `not_possible`, деньги остаются у организатора (Р-RF5), приводящему письмо `referral_cashback_unavailable` («обратитесь к организатору») |
| Ответ провайдера потерян | правило движка: неизвестный исход не считается отказом, sweep повторяет с тем же ключом |

Комиссия провайдера с исходного платежа не возвращается (Stripe её удерживает) — это
расход организатора, говорим об этом в подсказке при включении.

### 6.3 Исключения в движке

1. **Сканированный билет (Р-RF3).** Правило `refunds/scanned.go` не применяется к
   `origin='referral_cashback'` с `cancel_ticket=false`. Остальные возвраты — как прежде.
2. **Письмо покупателю.** Обычное письмо о возврате не шлём (`notify_buyer=false` у пакета);
   у кэшбэка своё письмо (§7.3).
3. **Повтор.** «Повторить» из очереди «Возвраты» для кэшбэка не нужно: при отказе действует
   Р-RF5. Очередь показывает такие возвраты с меткой «кэшбэк».

## 7. Экраны и письма

### 7.1 Организатор (веб-ивент-центр и бот)

- Карточка мероприятия → «Приведи друга»; магазин → свой раздел «Приведи друга» (Р-RF6).
- Поля: скидка другу %, кэшбэк % от стоимости билетов друга, предел кэшбэка % от билетов приводящего,
  число друзей на код, срок. Перед включением — подсказка с правилами Р-RF2, Р-RF5 и про
  комиссию провайдера; включение = согласие (`terms_accepted_at`).
- Пауза и выключение — одним нажатием.
- Итоги: кодов выдано, друзей пришло, скидка дана, кэшбэк выплачен / не выплачен / в пути,
  отмены у друзей. Список начислений с фильтром по состоянию.
- Права: настройка — `promo.update` + `refund.create` + `refund.approve` (включая, организатор
  разрешает возвраты от своего имени). Есть у владельца и менеджера (0129), у агента нет.

### 7.2 Покупатель

- Страница «спасибо» и письмо о заказе: блок «Пригласите друга: скидка N % другу, вам
  вернётся M % от стоимости его билетов» + код + ссылка + «Поделиться» (Web Share API на телефоне).
- Только если программа активна и заказ оплачен деньгами (не приглашение, не 0).

### 7.3 Письма Arena (7 языков)

- `referral_cashback_sent` — приводящему: «Друг купил по вашему коду. Мы вернули X на карту,
  которой вы платили. Банку обычно нужно 5–10 рабочих дней». Stripe сам не пишет.
- `referral_cashback_unavailable` — приводящему: «Вернуть X на вашу карту не удалось. По
  условиям сервиса обратитесь к организатору» + контакт организатора (форма, правило HP-4b).
- Организатору — сообщение о `friend_reversal` (§5.2).
- Организатору (решение 03.11.2026) — `referral_payout_organizer` (7 языков) и то же в
  продажный Telegram-чат: «кэшбэк ждёт баланса Stripe», «Stripe держит кэшбэк», «кэшбэк не
  выплачен, рассчитайтесь с покупателем сами». Каждое — один раз (`balance_notice_at`,
  `pending_notice_at`, `unpaid_notice_at`, миграция 0196).

## 8. Защита от накрутки

1. Код не применяется, если покупатель = приводящий: тот же `customer_id`, e-mail или телефон
   (идентичности `customer_identities`). Проверка — при применении кода (понятная ошибка) и
   ещё раз перед выплатой (`self_referral`).
2. `max_uses_per_customer = 1`: один друг — одна скидка.
3. `max_friends` и предел кэшбэка (§4) ограничивают сумму сверху.
4. Код приводящего не даёт скидку на его же повторный заказ.
5. Два возврата или спора у друзей одного кода — код на паузе (§5.2 п. 3).
6. Код гаснет, когда заказ приводящего полностью возвращён (§3.2).

## 10. Отчёты и биллинг

- Сводка мероприятия/сеанса и магазина: «по коду друга» (заказы, билеты/товары, скидка) и
  «кэшбэк выплачен» **отдельно** от «возвратов» — иначе возвраты выглядят выше, чем есть.
- `billing.collect` пишет `ticket_refunded` по каждому успешному возврату. Кэшбэк — не возврат
  билета: источник пропускает `origin='referral_cashback'`. Плата за билеты друга и
  приводящего остаётся.
- CSV продаж: колонка «Код друга».
