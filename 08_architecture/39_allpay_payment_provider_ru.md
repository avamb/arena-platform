# Платёжный провайдер AllPay — спецификация

Статус: код готов к ревью 2026-10-13 (PAY-14 из спецификации 36). Миграции нет. На проде ничего не настроено.
Проверено: юнит-тесты, интеграционные тесты с заглушкой AllPay на чистой базе, эталонный пример подписи из документации AllPay.
Не проверено: живая тестовая зона AllPay. Ключи тестовой интеграции владелец ещё не передал (раздел 11).

**Рамки работы (решение владельца 2026-10-13).** Разработка и проверка идут ТОЛЬКО на тестовом аккаунте AllPay Vino&Co (ключи тестовой зоны dev-сайта). Настоящие аккаунты AllPay других организаторов подключаем позже, когда интеграция закончена и проверена полностью, включая возвраты. Код рассчитан на много организаторов: у каждого свой аккаунт AllPay в своей конфигурации оплаты.

Документация AllPay: https://allpay.to/docs/api-reference.htm (API v15).
Как AllPay вызывают сегодня: плагин WooCommerce `allpay-payment-gateway` 1.1.3 и mu-плагины Vino&Co (`allpay-webhook-bridge.php`, `allpay-status-sync.php`) в репозитории `vinoandco`.

## 1. Что это и зачем

AllPay — израильский платёжный шлюз. На своей странице оплаты он принимает израильские и иностранные карты, Bit, Apple Pay, Google Pay и рассрочку (תשלומים).

Схема та же, что у Flitt:

1. arena создаёт заказ в AllPay и получает `payment_url`.
2. Покупатель платит на странице AllPay.
3. AllPay присылает подписанный вебхук. arena проводит оплату.

Данные карты в arena не попадают. Отдельного платёжного маршрута нет. AllPay встроен в путь виджета `POST /v1/public/feeds/{token}/checkout/start` через тот же интерфейс `payments.HostedCheckoutProvider`, что Stripe и Flitt.

Возврат из arena входит в эту версию (раздел 8).

Не входит в эту версию:

- рассрочка с фиксированным числом платежей, токены карт, подписки, предавторизация J5.
- приём сведений о чарджбэках (раздел 7, только подтверждение получения).

## 2. Несколько организаций на одной интеграции

Одна организация — одна строка `payment_provider_configs` (`provider='allpay'`, режим `test` или `live`) со своими ключами в `secrets`.

- Модуль AllPay строится на каждый запрос из строки конфигурации организации. Общего ключа процесса нет.
- Вебхук приходит на `POST /v1/payment-intents/webhook/{config_id}`. Адрес называет конфигурацию, а значит и ключ проверки подписи.
- Вебхук организации B про заказ организации A не двигает платёж A. Это проверяет тест `TestAllPay_TwoOrganizationsAreIsolated`.
- AllPay работает только с бизнесами, зарегистрированными в Израиле (включая ИП, «осек»). Организатор из другой страны не откроет аккаунт AllPay.

## 3. Ключи конфигурации

| Поле | Что это | Где взять |
|------|---------|-----------|
| `merchant_id` | API login интеграции | Кабинет AllPay → Settings → API Integrations |
| `secret_key` | API key той же интеграции. Подписывает запросы и вебхуки. | Там же |
| `vat` (необязательно) | Код НДС строки в чеке: `0` без НДС (по умолчанию), `1` НДС включён в цену, `3` НДС 0 % | Решение организатора и его бухгалтера |
| `max_installments` (необязательно) | Наибольшее число платежей рассрочки, от 2 до 12. Только для ILS. | Решение организатора |
| `installments_min_amount` (необязательно) | Наименьшая сумма заказа в шекелях, с которой покупателю предлагается рассрочка, например `300`. Пусто — рассрочка для любой суммы. | Решение организатора |

Имена `merchant_id` и `secret_key` остались от прежней заготовки AllPay. Так форма в админке и уже сохранённые строки продолжают работать.

Отдельного секрета вебхука у AllPay нет. Вебхук подписан тем же API key.

Статус конфигурации `configured` наступает, когда заполнены `merchant_id` и `secret_key`. Неверные `vat`, `max_installments` и `installments_min_amount` отклоняются при сохранении.

**Тест и бой.** Адрес API один. Тестовый режим включают в кабинете AllPay для каждой интеграции. Запрос может включить его сам: `test_mode=1`.

arena отправляет `test_mode=1` для каждой конфигурации с режимом `test`. Ключ, сохранённый как тестовый, не может списать деньги с настоящей карты, даже если интеграция в кабинете переключена в бой.

Для режима `live` arena отправляет `test_mode=0`. Проверено 2026-10-13 на тестовой интеграции Vino&Co: AllPay принимает `test_mode=0` без ошибки, и страница открывается без пометки тестового режима, хотя в кабинете тестовый режим включён. Значит, `test_mode` запроса сильнее настройки кабинета. Без этого боевая конфигурация на интеграции, которую забыли переключить в кабинете, выдавала бы настоящие билеты за тестовую карту: ни вебхук, ни `paymentstatus` не говорят, была ли оплата тестовой.

Конфигурация без режима не отправляет `test_mode`, тогда режим решает кабинет.

## 4. Создание платежа

`POST https://allpay.to/app/?show=getpayment&mode=api15`, тело JSON.

| Поле AllPay | Значение arena |
|-------------|----------------|
| `login` | `merchant_id` конфигурации |
| `order_id` | id checkout-сессии arena (UUID). Он же `payment_intents.provider_payment_id`. |
| `items` | одна строка на всю корзину: `name` (название мероприятия, до 200 символов), `qty` 1, `price`, `vat` |
| `price` | итог checkout-сессии в **основных** единицах (`123.5`, а не `12350`) |
| `currency` | валюта сеанса: только `ILS`, `USD` или `EUR` (раздел 6) |
| `webhook_url` | `<API_PUBLIC_URL>/v1/payment-intents/webhook/{config_id}` |
| `success_url` и `backlink_url` | маршрут arena `/v1/public/payment-return?r=<страница покупателя>&checkout_token=…` (раздел 4.1) |
| `expire` | Unix-время конца окна оплаты, не раньше чем через 60 с |
| `client_email` | e-mail покупателя |
| `client_name` | имя покупателя, если он его ввёл |
| `client_phone` | телефон покупателя, если он его ввёл |
| `client_tehudat` | `000000000`, если телефон записан в международном виде (`+` или `00`) и код страны не 972. Это значение AllPay документирует: поле номера удостоверения скрыто, иностранцу его не вводить. Израильский, местный или пустой телефон: поле не отправляется, и AllPay спрашивает номер на странице. |
| `lang` | язык покупателя, если AllPay его знает: EN, HE, RU, AR, ES, IT, DE, FR. Иначе поле не отправляется, и AllPay берёт язык браузера. |
| `inst` | `max_installments`, только если больше 1, валюта ILS и итог заказа не меньше `installments_min_amount` |
| `test_mode` | `1` для конфигурации в режиме `test`, `0` для режима `live` |
| `sign` | раздел 5 |

Ответ: `payment_url` для редиректа. Ошибка приходит с HTTP 200 и полями `error_code`, `error_msg`. Любая ошибка старта — это HTTP 503 `checkout.payment_start_failed`. Бронь освобождают обычные свипы.

Одна строка корзины выбрана намеренно. Скидки, промокоды и сервисный сбор arena уже посчитала. AllPay получает итог, который покупатель видел в корзине.

### 4.1 Возврат покупателя идёт через arena

AllPay не описывает, каким методом (GET или POST) страница оплаты отправляет покупателя на `success_url`. Поэтому `success_url` и `backlink_url` указывают на маршрут arena `GET|POST /v1/public/payment-return`. Он на любой метод отвечает 303 на страницу покупателя. Так сделано и для Flitt.

У AllPay нет адреса неудачи. При отказе карты страница показывает ошибку и предлагает другую карту. `backlink_url` — это кнопка «Вернуться на сайт».

**Окно оплаты.** `expire` равен концу `WIDGET_PAYMENT_WINDOW_SECONDS` (1860 с). Бронь arena живёт на 120 с дольше. Страница AllPay закрывается раньше, чем arena отпускает места.

## 5. Подпись

SHA-256 (hex, нижний регистр) от строки: значения параметров через `:`, в конце `:` и API key.

Правила (из раздела «Signature Algorithm» документации):

- Поле `sign` в расчёт не входит.
- `""` и `null` пропускаются, как будто поля нет.
- `0`, `"0"` и `false` — это значения, они входят в строку.
- Ключи сортируются по алфавиту на каждом уровне: верхний уровень, поля каждого объекта в `items`, поля объекта `subscription`. Порядок элементов массива сохраняется.
- Число пишется в кратчайшей точной форме: `100.00` → `100`, `100.50` → `100.5`. Строка остаётся как есть: `"100.00"` → `100.00`.
- `true` → `1`, `false` → `0`.
- Значения не обрезаются и не меняют регистр.

Подпись считается по значениям так, как они пришли в JSON. Поэтому тело вебхука читается с `json.Number`, а запрос собирается из `json.Number`.

Эталон: пример из документации AllPay даёт `c3c5458724d88837bd60879b5130c860589e42248360b4ca42c2539ebf8a7803`. Тест `TestSign_DocumentedWorkedExample` проверяет этот пример. В HTML документации адрес в примере скрыт защитой Cloudflare. Настоящий адрес — `jason@company.io`, с ним хеш совпадает.

Сравнение подписи — за постоянное время.

## 6. Валюты

AllPay списывает деньги только в ILS, USD или EUR. Если у аккаунта нет права на USD или EUR, AllPay **молча** пересчитывает сумму в шекели по курсу Google Finance. Тогда arena записала бы одну валюту, а AllPay списал бы другую.

Поэтому модуль отказывает в любой другой валюте до запроса к AllPay. Покупатель получает `checkout.payment_start_failed`. Тест: `TestAllPay_UnsupportedCurrencyTakesNoPage`.

Минимальная сумма в ILS — 5 шекелей (ошибка AllPay 21).

Рассрочка разрешена только в ILS (код отказа 312). Для USD и EUR arena не отправляет `inst`.

## 7. Вебхук

`POST /v1/payment-intents/webhook/{config_id}`, JSON, подпись в теле (`sign`). Заголовка подписи нет. Поля продавца в теле нет.

Порядок проверок (все до любых записей):

1. Тело читается, `config_id` — UUID, конфигурация существует, активна, `configured`. Иначе 404 без подробностей.
2. У конфигурации есть `secret_key`. Иначе 401.
3. Подпись верна под ключом этой конфигурации. Иначе 401.
4. Платёж найден по `order_id`. Платёж другой организации, другого провайдера или неизвестный считается «не нашим»: ответ **200** `processed:false`, чтобы AllPay не повторял доставку.

Как arena понимает вебхук:

| Вебхук | Действие |
|--------|----------|
| `status` 1, без `type` | сначала сверка с AllPay (ниже). Потом платёж `succeeded`, checkout завершается, заказ `paid`, выпуск билетов |
| `status` 0 | **ничего не меняется.** Это одна неудачная попытка. Страница AllPay остаётся открытой для другой карты. Если закрыть платёж, следующая успешная оплата потеряется. |
| есть `subscription_create` или `preauth=authorized` | ничего не меняется: деньги не списаны (arena такого не запрашивает) |
| `type=chargeback` | подтверждается, платёж не меняется (чарджбэки — PAY-16) |
| `type=chargeback_revert` | подтверждается, платёж не меняется |

**Сверка оплаты.** Подпись доказывает только то, что вебхук прислал AllPay. Поэтому перед выпуском билетов модуль читает заказ через `?show=paymentstatus` и берёт сумму и валюту из этого ответа, а не из вебхука. Списано = `amount` минус `discount`.

| Ответ `paymentstatus` | Что делает arena |
|------------------------|------------------|
| `status` 1 с суммой и валютой | сумма и валюта идут в общую проверку ядра (ниже) |
| `status` 1 без суммы или без валюты | ответ **503**, ничего не записано: такой ответ нечем сверить |
| ответ про другой `order_id` | ответ **503**, ничего не записано |
| `status` 0 или `preauth=authorized` | ответ **503**. AllPay доставит вебхук ещё раз. Документация просит читать статус не раньше чем через 2 с после попытки, поэтому первый ответ может отстать. |
| `status` 3 или 4 | деньги уже частично или полностью вернули (например, в кабинете). Платёж уходит в `manual_review`, билетов нет. |
| ошибка 6 (нет такого заказа у этого login) | платёж уходит в `manual_review`. Если заказ чужой организации, проверка организации раньше отвечает 200 «не наш». |
| сеть, 5xx, другая ошибка | ответ **503**, ничего не записано. AllPay повторит доставку. |

**Проверка ядра (для всех модулей с `WebhookConfigRouteOnly`: Flitt и AllPay).** Если сумма или валюта оплаты не совпадает с платежом arena или событие об оплате пришло без суммы или без валюты, платёж переходит в `manual_review` с причиной `paid_amount_mismatch`. Checkout не завершается, билеты не выпускаются. Сторож (`ops.watchdog`) присылает оператору оповещение о платеже в `manual_review`. Причина хранится в `payment_intents.failure_code` и `failure_message`.

Тип события для идемпотентности: `allpay.payment.paid`, `allpay.payment.declined`, `allpay.payment.not_charged`, `allpay.chargeback`, `allpay.chargeback_revert`. Повтор вебхука даёт 200 и не выпускает билеты второй раз.

`order_id` записывается и в `provider_charge_ref`: AllPay возвращает деньги и читает статус по `order_id`.

AllPay повторяет вебхук до 10 раз за сутки, пока не получит HTTP 200.

Вебхук AllPay на **старом** маршруте `/v1/payment-intents/webhook` отклоняется: `400 webhook.allpay_requires_config_route`.

Повтор вебхука после 503 обрабатывается как первый: 503 ничего не записывает. Повтор уже записанного события, пока платёж ещё не завершён (две доставки одновременно), получает **200** `processed:false`, а не 204: AllPay повторяет доставку, пока не увидит 200.

## 8. Возвраты

Возврат из arena работает (PAY-14b): полный и частичный, из бота и через API организатора. Модуль заявляет `Capabilities.Refund` и `PartialRefund`.

Метод AllPay: `POST ?show=refund&mode=api15` с `order_id` и `amount` в основных единицах. Ответ: `status` 3 (возвращено полностью) или 4 (частично).

**Почему нужна сверка.** У метода `refund` нет ключа идемпотентности, и он не возвращает id возврата. Если ответ потерялся, повтор с теми же данными вернёт деньги второй раз. Поэтому модуль **никогда** не вызывает `refund`, не прочитав заказ.

Перед каждым вызовом модуль читает `paymentstatus` и сравнивает:

- P — сколько AllPay уже вернул по заказу (`refunded` при статусе 4, вся оплаченная сумма при статусе 3, 0 при статусе 1);
- K — сколько вернули другие возвраты arena по этому платежу, которые провайдер принял;
- U — сколько могли вернуть другие возвраты arena, у которых вызов закончился без ответа;
- A — сумма этого возврата.

| Условие | Что делает модуль |
|---------|-------------------|
| P < K | ничего не отправляет. Возврат уходит на ручную проверку (`allpay_refunded_less_than_known`). |
| P − K = 0 | отправляет `refund`. |
| P − K = A и U = 0, повторный вызов (номер попытки не 1) | ничего не отправляет. Значит, прошлый вызов этого же возврата дошёл до AllPay, а ответ потерялся. Возврат считается выполненным. |
| P − K = A и U = 0, первый вызов | ничего не отправляет, нужна ручная проверка. Прошлого вызова не было, поэтому эти деньги вернули в другом месте, например в кабинете AllPay. |
| любое другое | ничего не отправляет. Ручная проверка (`allpay_refund_unexplained`). Так выглядит возврат, сделанный в кабинете AllPay, о котором arena не знает. |
| A больше остатка заказа | ничего не отправляет. Ручная проверка (`allpay_amount_over_remaining`). |
| статус 4, но `refunded` нет, или он не меньше оплаченного | ничего не отправляет. Ручная проверка (`allpay_partial_refund_unclear`). |
| в ответе нет суммы или валюты, или ответ про другой заказ | ничего не отправляет. Исход неизвестен, движок повторит позже. |
| повторный вызов того же возврата, P − K = 0, с первого вызова прошло меньше 10 минут | ничего не отправляет. Исход неизвестен, движок повторит позже. Прошлый вызов мог ещё обрабатываться в AllPay и не попасть в `paymentstatus`. |

K и U движок возвратов считает под блокировкой платежа. Движок не допускает двух вызовов по одному платежу одновременно. Поэтому за время сверки суммы на стороне arena не меняются.

Другие ответы:

- статус 0, ошибка 6, другая валюта → ручная проверка, ничего не отправлено;
- `paymentstatus` не прочитан (сеть, 5xx) → исход неизвестен, движок повторит позже, `refund` не отправлялся;
- `refund` ответил ошибкой AllPay: 17 (процессор отказал) и 2 (неверная сумма) → отказ, билет остаётся действительным; 16 (неверный статус заказа) → ручная проверка;
- `refund` без ответа (сеть, 502) → исход неизвестен. Следующий вызов сначала прочитает заказ и увидит, дошёл ли возврат.

Id возврата у AllPay нет. arena хранит `<order_id>/<id возврата arena>` в `refunds.provider_refund_id`.

**Возврат в кабинете AllPay.** Вебхука о возврате AllPay не описывает. arena не узнаёт о таком возврате сама. Первый же возврат arena по этому заказу остановится на ручной проверке и не вернёт деньги второй раз. Как действовать:

1. Если вернули в кабинете полностью: в arena отмените билеты с `refund_mode=none`.
2. Возвраты из кабинета и из arena по одному заказу не смешивайте.

Периодическое чтение статуса всех платежей AllPay (аналог `allpay-status-sync.php`) не сделано. Оно нужно, чтобы arena сама замечала возвраты из кабинета. Это следующая задача (раздел 12).

## 9. Проверка ключей

При сохранении конфигурации и по кнопке «Check again» arena вызывает `?show=checkkeys` с `login` и `sign`. Деньги не двигаются, ничего не создаётся.

- Ответ без `error_code` → ключи верны → `ok`.
- `error_code` 3 (неверная подпись, то есть неверный ключ) или 5 (неизвестный login) → `failed`.
- Сеть, 5xx, другие коды → `unverified`. Это не вердикт о ключе.

## 10. Что изменилось в старом коде

- Прежний адаптер `internal/adapters/allpay` описывал выдуманный API (`api.allpay.co.il/v1`, Bearer-токен, заголовок `X-AllPay-Signature`). AllPay так не работает. Адаптер переписан по документации.
- Вторая копия `internal/domain/payments/allpay.go` удалена. Её ничего не использовало. Так закрыт вопрос 5 спецификации 36 «какая копия каноническая».

## 11. Сквозная проверка на тестовом аккаунте Vino&Co

Тест `internal/adapters/allpay/live_test.go` (тег сборки `allpaylive`, в CI не запускается) проверяет ключи, создаёт страницу оплаты на 10 ILS с `test_mode=1` и читает статус заказа. Ключи берутся только из переменных окружения и не печатаются.

Ключи тестовой интеграции Vino&Co владелец положил в локальный файл вне git (2026-10-13). Интеграция в кабинете AllPay — в тестовом режиме.

План проверки. Каждый шаг — на тестовом аккаунте Vino&Co, с локальной arena или стендом, никогда на проде.

**A. Ключи и страница**

1. Запустить `live_test.go`: `checkkeys` принимает ключи, неверный ключ даёт отказ.
2. Создать страницу оплаты на 10 ILS. Ожидается `payment_url`, статус заказа 0.

**B. Оплата через виджет**

Вебхук нужен публичный адрес arena: AllPay не доставит его на `localhost`. Поэтому шаги B и C идут на стенде (`api-staging`) с конфигурацией в режиме `test`, либо локально через туннель.

1. Канал стенда с провайдером `allpay`, конфигурация `test` с ключами Vino&Co.
2. Купить билет в виджете, оплатить картой `4557430402053431`.
3. Ожидается: вебхук `status` 1, заказ `paid`, билет выпущен, `paymentstatus` = 1.
4. Попытка с картой отказа `4000000000000002`, затем успешной картой на той же странице. Ожидается: первая попытка ничего не меняет, вторая проводит оплату.
5. Повтор того же вебхука из истории транзакции в кабинете AllPay. Ожидается: 200, второй выдачи билета нет.

**C. Возвраты (обязательная часть плана)**

1. Возврат одного билета из бота. Ожидается: `paymentstatus` = 4, `refunded` равен цене билета, билет отменён, письмо покупателю.
2. Возврат второго билета того же заказа. Ожидается: `paymentstatus` = 3, заказ `refunded`.
3. Новый заказ. Частичный возврат в кабинете AllPay, затем возврат билета из бота. Ожидается: arena ничего не отправляет, возврат на ручной проверке (`allpay_refund_unexplained`), билет действителен. Проверить, присылает ли AllPay вебхук о возврате из кабинета (документация молчит). Если присылает, записать тело в спецификацию.
4. Обрыв ответа на возврат проверен заглушкой (`TestAllPayRefund_LostAnswerSecondTicketAndDashboardRefund`, `TestRefund_LostAnswerIsNotRefundedTwice`). На настоящем AllPay его не воспроизвести.

Готовность к подключению настоящих организаторов: все шаги A–C пройдены, включая C.3.

## 15. MCP-сервер AllPay

Источник: страница https://www.allpay.co.il/en/integrations/mcp и новость https://www.allpay.co.il/en/news/allpay-mcp-chatgpt-claude-gemini (прочитаны 2026-10-13). AllPay пишет, что интеграция ещё в разработке.

**Что это.** Удалённый MCP-сервер `https://allpay.to/mcp`. Его подключают в ChatGPT, Claude (раздел Connectors) и других ассистентах.

**Вход.** Человек входит в свою учётную запись AllPay и разрешает доступ. Это вход аккаунта, а не API login и key интеграции. Отдельных прав (scopes) нет: ассистент видит всё, что доступно через MCP по этому аккаунту. Сотрудник из раздела Team может подключить ассистента сам, без подтверждения владельца аккаунта. Секретный ключ API-интеграции ассистенту не выдаётся.

**Что умеет**

| Чтение | Запись |
|--------|--------|
| сводки платежей, сравнение периодов, крупные покупатели, разбивка по валютам | запрос оплаты для конкретного покупателя |
| платёж: детали, плательщик, чек | многоразовые платёжные ссылки (в том числе рассрочка и ежемесячная подписка) |
| баланс, график и история выплат | создание API-интеграции |
| документы о комиссии, подключённые сервисы, тариф | |
| подписки покупателей, статусы, даты списаний | |

Чего нет: возвраты, выплаты, подключение платных услуг. Это только в кабинете AllPay. Отдельного тестового режима нет, в отчётах тестовые платежи можно отфильтровать.

**Где хранятся данные.** AllPay хранит запросы и ответы MCP не больше 30 дней. Данные аккаунта (платежи, покупатели) уходят в выбранный ИИ-сервис и живут по его правилам. Удаление истории MCP в AllPay не удаляет переписку в ИИ-сервисе.

**Для чего можно использовать (после решения владельца)**

1. Поддержка и сверка у оператора: «оплачен ли заказ X», «что вернули за неделю», сверка выплат AllPay с продажами arena.
2. Отчёты для организатора в его собственном ассистенте, под его собственным аккаунтом AllPay.
3. Ручная проверка тестов: посмотреть платёж и чек тестового заказа Vino&Co.

**Для чего использовать нельзя**

1. Ничего, что двигает деньги или создаёт платёж мимо движка arena. Платёжная ссылка, созданная через MCP, не связана с заказом arena: оплата по ней не выпустит билет и не попадёт в учёт.
2. Создание API-интеграций и любые записи из бота arena или автоматики.
3. Проверка статуса для выпуска билетов. Источник правды — подписанный вебхук и `paymentstatus` через ключ конфигурации организатора.
4. Бот ивент-центра и ИИ-помощник arena не подключаются к MCP. Им хватает API AllPay под ключом организатора, в своих границах.

**Безопасность**

1. Доступ привязан к человеку и его аккаунту AllPay, а не к организации в arena. Подключение даёт ассистенту все данные аккаунта, включая покупателей. Подключать только своим аккаунтом, только в своём ассистенте.
2. Чужие аккаунты организаторов через MCP не подключаем: это передача их данных о покупателях третьей стороне.
3. Сервер arena к MCP не подключается. Ключи организаторов в MCP не передаются.
4. Отозвать доступ: кабинет AllPay → Settings → Integrations → MCP, и отключить коннектор в ассистенте.
5. Права «только чтение» нет. Поэтому даже пробное подключение даёт ассистенту возможность создавать ссылки и интеграции. Пробное подключение к аккаунту Vino&Co делает только владелец, сам, в своём ассистенте. Эта сессия его не делала.
