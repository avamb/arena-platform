## 0. Задача и решения владельца

Владелец и менеджер организации выдают **пригласительные** на сеанс так же, как покупатель
покупает билет: выбирают места на схеме, заполняют данные гостя, получают билеты. Оплаты нет.
Выбирать можно и **закрытые места** (`unavailable` — резерв организатора).

Повод: Actorre, «Сердце на поводке», 27.10. Ряды 1–3 (60 мест) закрыты под резерв, гости пишут
организатору напрямую, а выдать гостю конкретное место нечем: нынешний `POST …/complimentary`
на рассадочном сеансе место не выбирает.

| № | Вопрос | Решение 2026-10-28 |
|---|---|---|
| Р-1 | Модель | Пригласительный = **заказ на 0** с `orders.source='complimentary'`, тот же путь, что у покупки. `complimentary_issuances` для новых выдач не используется |

## 2. Главный принцип: место не открывается ни на миг

Закрытое место нельзя делать «доступным только для роли» через `available` и бронь сотрудника:
истечёт бронь или упадёт запрос — место уйдёт в открытую продажу на сайтах и в виджете.

**Публичная бронь берёт только `available`. Выдача пригласительного берёт `available` и
`unavailable` и продаёт место (`sold`) в той же транзакции, где создан заказ.** Бронь внутри
выдачи живёт миллисекунды и конвертируется в той же транзакции, поэтому протухание брони
(`reservation.expire_sweep`) к пригласительным неприменимо.

Тело выдачи:

```json
{
  "request_id": "uuid — повтор с тем же id возвращает тот же заказ (200, replay=true)",
  "seats":  [{"seat_key": "sala|3|12"}],
  "ga":     [{"tier_id": "uuid", "qty": 2}],
  "guest":  {"name": "Ana López", "email": null, "phone": "+34…", "locale": "es"},
  "delivery": "guest_email | my_email | pdf_only",
  "note": "внутренняя заметка"
```

- `guest.name` обязателен (печатается в билете). `email` обязателен только при `guest_email`.
  `my_email` = `users.email` вошедшего; в заказ как адрес гостя он не пишется (3.4).
- Ответ 201: `order_id`, `system_id`, места (`seat_key`, сектор/ряд/место, категория, номинал,
  `origin`), `tickets_status: issuing`, `charge` (3.6).
- Ошибки: `409 invitation.seats_taken` + `details.seat_keys` (места `held`/`sold`, в том числе
  проданные в старой системе — `sold` без брони); `422 invitation.session_cancelled`;
  `422 invitation.guest_email_required`; `400 invitation.empty`; `400 invitation.unknown_seat`;
  `400 invitation.too_many` (больше 50 мест в одной выдаче — для большего есть CSV).
- Список: заказы `source='complimentary'` сеанса **всех** выдавших (Р-5): гость, места, доставка,
  кто выдал (`issued_by` → имя/e-mail), когда, статус, CSV-пакет.

### 3.2 Транзакция выдачи (одна; `retryOnSerializationFailure`)

1. `IncrementSessionSeatStatusVersion` — первым оператором (порядок блокировок AGENTS.md).
2. Сеанс существует, не `cancelled`, не удалён. Окно продаж, `is_open`, `sales_end_at`,
   время начала **не проверяются** (Р-3).
3. Места `FOR UPDATE` по `(session_id, seat_key)`: допустимы `available` и `unavailable`,
   исходный статус запоминается. GA: `AllocateGAUnitsTx`-подобная аллокация по категории,
   допускающая `unavailable` единицы категории после `available` (сначала свободные).
4. `ReserveCapacity` + `ConfirmCapacity` на уровне сеанса.
5. Бронь (`reservations`) + `reservation_seats`, `checkout_sessions` в `pricing_confirmed`
   с ценами из `hcheckout.ComplimentaryBreakdown` (вынесенная `complimentaryBreakdown`),
   заказ через `ordering.CreateOrderFromCheckout`: `source='complimentary'`, `total=0`,
   канал — внутренний (3.3), `issued_via='staff'`, `issued_by`, `buyer_*` по 3.4.
6. `order_items.seat_origin` = исходный статус места.
7. Места → `sold` **в этой же транзакции** (`sellReservationSeatsTx`, он идемпотентен к
   `alreadySold`, так что последующее задание `checkout.convert_reservation` безвредно).
8. `CompleteFreeCheckoutTx` — задания выпуска билетов и конвертации, отметка «оплачен».
9. `customers.Resolve` по e-mail/телефону гостя в SAVEPOINT (правило best-effort AGENTS.md).
10. Аудит `v1.invitation.issue` (места, сколько из резерва, доставка; `via` ставится сам).

Публичные `CreateSeatedHold`, `hfeed`, шлюз — без изменений поведения.

### 3.3 Миграция (одна на весь прогон, INV-01)

- `order_items.seat_origin text NULL CHECK (seat_origin IN ('available','unavailable'))`.
- `orders.issued_via text NULL CHECK (issued_via IN ('staff','staff_bulk'))`,
  `orders.issued_by uuid NULL REFERENCES users(id)`, `orders.invitation_batch_id uuid NULL`.
- `invitation_batches (id, org_id, session_id, created_by, file_sha256, request_id UNIQUE per org,
  rows, seats, from_reserve, status, error_report jsonb, created_at)`.
- `billing_account_terms.complimentary_billing text NOT NULL DEFAULT 'free'
  CHECK (complimentary_billing IN ('free','standard'))`.
- Внутренний канал: признак `sales_channels` для канала «Пригласительные» (на разведке INV-01
  выбрать — столбец `kind`/`is_internal` или ключ `settings.internal=true`). Канал создаётся
  лениво при первой выдаче, без провайдера, без вебхуков, без hosted-страницы, **не виден** в
  публичных фидах и списках каналов организации для привязки ключей и публикаций.
- `role_permissions`: `organizer` ← `complimentary.revoke` (новых прав нет, guard паритета 532
  молчит).
- Пин головы миграций и `lock_timeout_test.go` обновить.

Освобождение места: `ReleaseCancelledTicketInventoryTx` получает целевой статус из
`order_items.seat_origin` (через `tickets.order_item_id` или по `seat_key` в заказе):
`unavailable` → место снова в резерве; иначе `available`. Изменение SQL: новые запросы
`ReleaseSoldSessionSeatTo(…, target)` / `ReleaseSoldGAUnitBySeatKeyTo`, старые остаются
обёртками с `available` — у всех прочих путей поведение не меняется.

### 3.4 Доставка

| `delivery` | Письмо | Кому | `orders.buyer_email` |
|---|---|---|---|
| `guest_email` | одно письмо на заказ, шаблон приглашения, PDF всех мест | гость | гостя |
| `my_email` | то же | выдавший | пусто; адрес только в задании доставки и `orders.delivery_email` (столбец 3.3, если нужен) |

- «Скачать PDF» есть всегда: `tickets.pdf` — один файл на все билеты заказа (склейка

- Цены в письме и PDF нет (`pdf.priceValue` уже скрывает 0).

### 3.5 Массовая выдача из CSV (только веб)

```
guest,name,email,phone,locale,sector,row,seat,category,qty,note
1,Ana López,ana@x.es,,es,Sala,3,12,,,
1,Ana López,,,,Sala,3,13,,,
2,Press ABC,press@abc.com,,en,,,,Invitado,4,пресса
```

- UTF-8 (с BOM или без), разделитель `,` или `;`, заголовки обязательны, порядок свободный;
  вместо `sector,row,seat` допустим `seat_key`.
- `guest` — номер гостя: его строки дают один заказ и одно письмо; имя/e-mail/телефон/язык
  берутся из первой строки гостя.
- `dry_run=true`: ничего не пишет; отчёт по строкам (неизвестное место, занято, дважды в файле,
  нет имени, нет e-mail при «гостю на e-mail»), итог: гостей, мест, из резерва, стоимость (3.6).
- Выдача: **одна транзакция на файл** (всё или ничего), лимит 1 000 мест и 2 МБ; строка
  `invitation_batches`, заказы с `issued_via='staff_bulk'`, `invitation_batch_id`; результат —
  CSV с номерами заказов. Доставка: колонка `email` → гостю, иначе общая настройка пакета
  «письма мне» / «только PDF».

### 3.6 Биллинг

- Событие остаётся `ticket_complimentary`. `ListCollectOrderItems` дополнительно отдаёт
  `orders.issued_via`; в `billing.Event` — признак `Bulk`.
- `Rate` для `ticket_complimentary`:
  1. `Bulk` → стандартная ставка;
  2. `terms.ComplimentaryBilling == standard` → стандартная ставка;
  3. иначе бесплатно до `free_tickets_annual_limit`, сверх — как сейчас.
- **Стандартная ставка** = фиксированная ставка за билет: индивидуальная (`org_rate_overrides`,
  `seated_minor` для места на схеме, `unseated_minor` для GA), иначе `fixed_per_ticket`
  стандартной строки прайс-листа (с местом / без). Процентные и low-price правила к
  пригласительным **не применяются**. `fee_mode=buyer_pays` не влияет: платит организатор.
- Отмена пригласительного начисление не сторнирует (Р-10).
- Предпросмотр для интерфейса: `charge` в ответе выдачи и в `dry_run` CSV — «12 × 0,50 € =
  6,00 €» либо «бесплатно, осталось N из годового лимита»; функция расчёта — та же `Rate`.
- Суперадмин: переключатель на карточке биллинга организации в admin-web (`billingPrices*`
  или вкладка организации), маршрут `PATCH /v1/admin/billing/accounts/{id}/terms`
  (`billing.admin`, `X-Admin-Reason`) — точное место по разведке INV-07.

### 3.7 Telegram-бот продаж (Р-11)

Выдача пригласительного уже поднимает `v1.order.paid`, и `salesnotify` объявляет его
обычным сообщением о продаже (`FormatSale`: «Order #N · invitation (Invitations)», 0, контакты
гостя из `orders.buyer_*`). Это остаётся. Добавляется блок «кто выдал»:

```
🎟 New sale — Actorre
…
🧾 Order #1000000512 · invitation (Invitations)
🎫 2 × Партер
💰 Total: 0.00 EUR

👤 Иван Петров
✉️ ivan@example.com
📞 +34 600 000 000

🙋 Issued by: Manager · anna@actorre.es
```

- Источник — `orders.issued_by` (0174) → `users.email`; роль — членство выдавшего в
  организации заказа: `org_admin` → Owner, `organizer` → Manager; пользователь с правом
  суперадмина без членства → Platform operator; `issued_by IS NULL` (выдача API-ключом) →
  `API key` + `api_keys.name`, если его можно достать из `orders.metadata.invitation`
  (INV-02 кладёт туда метку ключа; если не кладёт — дописать там же).
- Блок печатается только для `source='complimentary'` с `issued_via` (staff/staff_bulk);
  старые заказы шлюза и обычные продажи не меняются. `FormatSale` получает поле
  `IssuedBy{Role, Email, Label}`, запрос `store.go` (продажа) — `LEFT JOIN users` по
  `issued_by` и роль из `memberships`.
- **Отмена пригласительного** (`v1.ticket.cancelled`, сообщение `FormatRefund` с суммой 0)
  получает такую же строку «🙋 Cancelled by: роль · e-mail». Кто отменил — записать при отмене
  в `orders.metadata.invitation.cancelled_by` (user id или метка ключа) в той же транзакции
  `HandleCancel`; сообщение читает оттуда.
- Тексты бота продаж английские (как остальные сообщения `salesnotify`), без новых ключей i18n.
- Кому: тем же подпискам, что и продажи (`kinds` содержит `tickets`, `on_order_paid` /
  `on_ticket_refunded`) — группе организации и операторскому чату. Никакого нового флажка.

## 4. Интерфейс

### 4.1 Веб-ивент-центр

Маршрут `/o/$orgId/events/$eventId/sessions/$sessionId/invitations` (`InvitationsScreen`),
ссылка-секция «Пригласительные» на `SessionScreen`.

```
 ┌ схема (SeatMapCanvas, tool="seat", look=invite) ─────┐  ┌ Выбрано (3) ───────────┐
 │ свободные — как у покупателя                          │  │ Sala · ряд 3 · место 12│
 │ закрытые — штриховка + метка «резерв», выбираются     │  │   Партер · 25 € → 0 €  │
 │ проданные / в брони / проданные в старой системе — нет│  │ GA «Invitado»  − 2 +   │
 └───────────────────────────────────────────────────────┘  └────────────────────────┘
 Гость: имя* · e-mail · телефон · язык письма · заметка
 Доставка: (•) гостю на e-mail  ( ) мне на e-mail  ( ) только PDF
 Стоимость: бесплатно / 1,50 € по тарифу
 [Выдать 3 пригласительных]
 → заказ 1000001234 · Скачать PDF · Отправить ещё раз · Отменить
 Список выдач сеанса (все сотрудники) · [Загрузить CSV]
```

- Конфликт при отправке: форма сохраняется, схема перечитывается, занятые места снимаются из
  выбора и подсвечиваются. Брони сотрудника с таймером нет.
- Отмена: весь заказ или отдельный билет; текст подтверждения «места вернутся в резерв» /
  «в продажу» по `origin`; флажок «сообщить гостю» включён.
- CSV: загрузка → таблица проверки с ошибками по строкам и стоимостью → «Выдать N» → ссылка на
  CSV-результат.
- Тексты en/ru/es, стандарт текстов (бронь = «бронь», без запрещённых слов).

### 4.2 Бот + Mini App

- Карточка сеанса в боте → «Пригласительные» → по нажатию код и `web_app`-кнопка на
  `/tg/invitations?session=…` (приём `textfmt_miniapp.go`); флаг `BOT_MINIAPP_INVITES_ENABLED`.
- Экран мини-приложения = `InvitationsScreen` в мобильной раскладке без CSV (CSV — ссылка
  «открыть в браузере»).
- Выдача — не денежный маршрут: повторный пароль не нужен.
- Сеанс без схемы — можно и в чате: категория → количество → имя → доставка (через тот же
  маршрут `POST …/invitations` с `ga`). Тексты `bot.inv.*` en/ru/es.

## 6. Протокол прогона (оркестратор)

**Волны.**

```
Волна 1 (последовательно):  INV-01 → INV-02 → INV-R1 → слияние
Волна 2 (параллельно, после слияния INV-02):
    INV-03 (sonnet)   INV-04 (sonnet, Ф-L)   INV-06 (sonnet)   INV-07 (opus)   INV-08 (sonnet)
    INV-12 (sonnet)
Волна 3: INV-05 (после 03+04), INV-06b (после 04+06), INV-07b (после 07)
Волна 4: INV-09, INV-10, финальное opus-ревью всей фичи на стенде, INV-11
```

INV-01 и INV-02 делает **один opus-агент** в одной ветке двумя коммитами (меньше передачи
контекста), PR один.

**Правила для каждого агента** (бриф оркестратора включает их выдержкой, не весь AGENTS.md):

- Ветка `feat/inv-XX-<slug>` от свежего `origin/master`, отдельный worktree; коммит по шагам,
  `git push origin HEAD:refs/heads/feat/inv-XX-…`, PR сразу (draft до зелёного CI); при
  нехватке бюджета — draft-PR со списком незавершённого.
- Файлы стейджить по путям, никогда `git add .`; gofmt всех Go-файлов, включая `integration`.
- Любое касание `openapi.yaml` → `make gen-openapi`-эквивалент и `node scripts/gen-ts-client.mjs`;
  проверить, что `git diff types_gen.go` не удаляет строк (ловушка enum). Конфликты кодгена
  при слиянии волны 2: сливать по одному PR, остальные rebase + перегенерация.
- Живые тесты — под тегом `integration`, на свежей базе `arena_ci_inv` (рецепт AGENTS.md),
  `arena_worker` остановлен на время тестов outbox.
- Только одна миграция в прогоне (INV-01). Если задаче волны 2 понадобился столбец —
  стоп, «Развилка» в журнал, оркестратор решает (новая миграция или правка INV-01 до слияния).
- Sonnet не решает архитектурные развилки: пишет «Развилка» в описание PR и останавливается.
- Журнал прогона — `docs/runs/inv_2026-10_ru.md` (агенты дописывают свою строку: PR, итог,
  развилки).

**Оркестратор** ставит задачи, читает дифф и CI каждого PR, заказывает ревью, сливает в master
по порядку волн, перед волной 4 выкатывает на стенд (ABH TEAM, сеанс со схемой и закрытыми
рядами) и проходит сценарий руками: выдача из резерва → письмо → скан на входе → отмена →
место снова закрыто → начисление в биллинге. **Прод не трогает** без слова владельца.

**Владельца зовут** только по стоп-условиям таблицы 5 или при неразрешимом противоречии.
