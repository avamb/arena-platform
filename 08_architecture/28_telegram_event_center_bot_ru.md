# Telegram-бот ивент-центра: архитектура и план (28.09.2026)

Назначение: организатор заводит и правит ивенты, видит список и сводку продаж и подключает
сотрудников — из Telegram, с телефона. Платформа Arena — единственный источник; сайты
организаторов (Vino&Co, Lampyris) получают всё из платформы и про бота не знают.

Исходная логика мастера (вопросы, поля, проверки, тексты, пакет event-bundle, правила
правки): `docs/plans/event_center_logic_for_bot_2026-09-28_ru.md`. Здесь она не повторяется,
здесь — где бот живёт, от чьего имени работает, как хранит диалог, какие эндпоинты и таблицы
нужны и в каком порядке всё делать.

## 2. Сервис `arena-bot`

### 2.1 Процесс и деплой

- `apps/backend/cmd/arena-bot` — четвёртый бинарник в существующем `Dockerfile` рядом с
  `arena-api`, `arena-worker`, `arena-migrate`; тот же `config.Load`, тот же тег образа.
- Compose (локально и Dokploy `backend-prod`): сервис `bot`, `entrypoint: /app/arena-bot`,
  без публичного порта, `replicas: 1` (long polling допускает ровно один экземпляр — второй
  получает 409 от Telegram и должен завершиться, не «бороться»).
- Обновления — **long polling** (`getUpdates`, таймаут 50 с), не webhook: нет публичного URL,
  Cloudflare и подписи; переезд на webhook возможен позже без смены остального.
- Внутри compose бот ходит в `http://api:8080` (переменная `BOT_ARENA_API_URL`); снаружи сети
  compose он ничего не открывает.
- Переменные: `EVENTS_TELEGRAM_BOT_TOKEN` (новый бот), `BOT_ARENA_API_URL`,
  `JWT_SIGNING_SECRET` (общий с api — см. §3), `DATABASE_URL` (только свои таблицы `bot_*`),
  `OPS_TELEGRAM_*` (уведомления владельцу платформы, уже есть у worker), `APP_PUBLIC_URL`.
- Библиотека Bot API: `github.com/go-telegram/bot` (чистый Go, без зависимостей, long polling
  и webhook, inline-клавиатуры, скачивание файлов). Существующие `salesnotify`/`opsalert` на
  голом `net/http` остаются как есть — им нужен только `sendMessage`.
- Метрики на `:9092` (как у worker `:9091`): обновлений/с, время ответа, ошибок API по коду,
  открытых черновиков. Падение бота не влияет на продажи: он не в цепочке оплаты.

### 2.2 Граница доверия

Бот — **внешний клиент API**, как плагин сайта: он не видит бизнес-таблицы (`events`,
`orders`, `organizations`…) и не вызывает обработчики напрямую. Изоляцию организаций, права и
аудит обеспечивает API. Единственные два допущения внутри trust-boundary compose:

1. бот знает `JWT_SIGNING_SECRET` и чеканит короткоживущие токены для привязанного
   пользователя (§3.1);
2. бот пишет свои таблицы `bot_*` в той же базе (§6) — привязки, приглашения, черновики.

Если позже бот вынести на другой хост, пункт 1 заменяется эндпоинтом обмена
(`POST /v1/auth/bot-token` под сервисным ключом) без изменения остального кода.

## 3. Кто говорит с API: личность, роли, приглашения

### 3.1 Личность

Таблица `bot_telegram_links` (§6): `telegram_user_id → users.id`, язык, дата привязки,
`revoked_at`. Каждый запрос бота в API идёт с JWT, выпущенным `auth.IssueJWT(secret, userID,
nil, nil, issuer, "arena-api", 5*time.Minute)` — ровно так, как `hauth/login.go`, без ролей в
клейме; права API берёт из БД (`GetActiveRolesForUser` объединяет активные `memberships`).
В аудите действие принадлежит человеку, а не «боту» и не ключу организации.

Ловушка из AGENTS.md: org-scoped `user_roles` до реальных JWT не доходят. Поэтому онбординг
пишет **только `memberships`** (`status='active'`), никогда `user_roles`.

### 3.2 Роли

| Роль бота | `memberships.role` | Что может |
|---|---|---|
| Владелец | `org_admin` (роль уже есть в `roles`, миграция 0009; в `memberships_role_check` её **нет** — расширить CHECK в миграции 0115) | всё по организации: реквизиты, платёжные конфиги (через веб-страницу), сотрудники, ивенты, площадки, промоутеры, сводка |
| Менеджер | `organizer` | ивенты, площадки, промоутеры, города, сводка; без денег, ключей и сотрудников |

`organizer` сегодня имеет `venue.read, channel.read, event.*, media.*` (0074); для мастера
ему нужны ещё `import.bil24_session, venue.create, city.create, promoter.read,
promoter.manage, order.read` (сводка) — грант в той же миграции 0115 (и `platform_superadmin`
получает всё новое там же, правило AGENTS.md).

### 3.3 Приглашения (волна 1 — уже заведённые организации)

Реализовано 29.09 (миграция 0115, пакет `httpserver/hbot`, письмо
`authemail.HandleBotInvitationEmail`):

1. **Один маршрут для всех:** `POST /v1/organizations/{org_id}/bot-invitations
   {email, role: owner|manager, locale?}` (право `membership.grant`; вызывающий —
   член организации, её ключ API или платформенный суперадмин с `X-Admin-Reason`).
   В одной транзакции: пользователь находится или создаётся по e-mail (без пароля —
   пароль для веба потом через «забыли пароль»), членство создаётся сразу
   (owner → `org_admin`, manager → `organizer`; уже существующее членство роль **не
   меняет**, ответ сообщает фактическую), в `bot_invitations` пишется SHA-256
   одноразового кода (32 байта base64url, 7 дней), в `worker_jobs` ставится
   `bot.invitation_email`. Ответ 201 — приглашение без кода; **только суперадмин**
   получает `deep_link` = `https://t.me/ArenaEventsCentrBot?start=inv_<код>` — для
   ручной передачи владельцам уже заведённых организаций.
2. Письмо (en/ru) строит ссылку из `EVENTS_TELEGRAM_BOT_USERNAME` в arena-worker;
   без этой переменной задача падает и повторяется, мёртвая ссылка не уходит.
3. Бот получает `/start inv_<код>` → спрашивает e-mail → `POST /v1/bot/invitations/accept
   {code, email, telegram_user_id, telegram_username?, locale?}` под
   `Authorization: Bearer <BOT_SERVICE_TOKEN>` — единственный вызов бота вне личности
   пользователя; без настроенного токена маршрут отвечает 503, никогда не открыт.
   Неизвестный, просроченный и использованный код отвечают одинаковым 404 (перебор
   невозможен), чужой e-mail — 422, Telegram-аккаунт, уже привязанный к другому
   пользователю, — 409. Успех = строка `bot_telegram_links` (язык, текущая организация)
   и `accepted_at` у приглашения, в одной транзакции.
4. Владелец организации приглашает сотрудников из бота тем же маршрутом (JWT
   пользователя). Отзыв — `DELETE /v1/organizations/{org_id}/members/{user_id}`; бот при
   следующем обновлении получает 403/404 и снимает привязку к этой организации.
   Один Telegram-аккаунт может состоять в нескольких организациях — бот спрашивает
   организацию при входе и помнит выбор (`current_org_id`).

Тесты: `hbot/*_test.go` (роли, сервисный токен, код), `authemail/bot_invitation_test.go`
(письмо), `httpserver/bot_invitations_integration_test.go` (полный путь приглашение →
письмо → приём → повтор/кража/чужой e-mail).

### 3.4 Канал публикации

При вызове от пользователя (JWT), а не по ключу API, импорт event-bundle **не
публиковал ивент ни в один канал** — `ensureChannelPublication`
(`himports/import_publication.go`) брал канал только из `api_keys.channel_id`.
Реализовано 29.09: поле пакета `channelIds: [uuid…]` — API проверяет ДО транзакции,
что каждый канал принадлежит организации (422 `import.invalid_channel`, ничего не
записано), и публикует во все; ключ API со своим каналом публикует в свой плюс
названные; ответ несёт `publications[]` (всегда массив) и прежний `publication`
(первый). Бот: если у организации один активный канал — молча в него; если
несколько (Lampyris: сайт + витрина) — шаг «Где продавать» с галочками **один раз**,
ответ запоминается в `defaults` и дальше не спрашивается (решение владельца 29.09).
Так ивент из бота попадает и в товар сайта (вебхук `event.created`), и на страницу
промоутера. Тест: `himports/event_bundle_channel_ids_integration_test.go`.

## 4. Онбординг новой организации (волна 2, модель Stripe)

Stripe: аккаунт мгновенно и полностью рабочий в тестовом режиме; «активация» — чек-лист, а
не стена; требования — данные (`currently_due` / `eventually_due` / `past_due` +
`disabled_reason`), интерфейс их только рисует; санкции ступенчатые. Перенос:

| Ступень | Что открыто | Требования |
|---|---|---|
| 0. Регистрация (1 минута в боте) | организация создана, звонящий — владелец; площадки, промоутеры, ивенты, черновик витрины | название, страна, валюта, e-mail + код из письма |
| 1. Открыть продажи (`currently_due`) | «Опубликовать» публикует, витрина продаёт | юрлицо, ИНН/IČO, телефон; платёжный провайдер подключён и проверен (`payment-configs/{id}/verify` = ok); подписка на тариф оформлена (карта в Stripe Billing, при необходимости разовая плата за подключение). **Открывается автоматически**, владелец платформы получает сообщение в ops-чат с кнопкой «Заблокировать» |
| 2. Работать дальше (`eventually_due`, 30 дней после первой продажи) | ничего не отключается до срока | адрес, логотип, домен отправителя писем (sender identity) |
| Просрочка (`past_due`) | новые ивенты не публикуются, текущие продажи не трогаем | пока чек-лист не закрыт |
| Блокировка (`disabled_reason=platform_review`) | публикация закрыта, витрина показывает «скоро» | снимает владелец платформы |

- Хранение: `organizations.activation` (jsonb: `status`, `disabled_reason`,
  `blocked_at/by`, `first_sale_at`) — а списки требований **вычисляются** API из реальных
  данных (заполнены ли `legal_name`, `tax_id`, есть ли проверенный платёжный конфиг, активная
  подписка) и отдаются в `GET /v1/organizations/{org_id}/activation`. Ничего не дублируется.
- Точка принуждения одна: публикация (`event.publish`, `publish:true` в пакете,
  `/publications`) → 422 `org.activation_required` со списком `currently_due`. Бот показывает
  список кнопками «Заполнить».
- Регистрация: `POST /v1/auth/register-organization` (публичный, rate-limit по IP и e-mail,
  код подтверждения на e-mail) создаёт `users` + `organizations` (slug из названия через
  `geoslug`) + `memberships(org_admin)` + канал продаж «Витрина» с feed-токеном; ответ — ссылка
  на страницу промоутера `tickets.arenasoldout.com/<slug>`. Уведомление владельцу платформы —
  сразу при регистрации (а не только при открытии продаж), чтобы задать вопросы заранее.
- Платёжные ключи: бот даёт ссылку на страницу `APP_PUBLIC_URL/setup/payments?token=…`
  (одноразовый токен на 30 минут, `purpose=payment_setup`), где ключ вводится в поле
  `readOnly` + «Replace» (урок 21.09 с автозаполнением) и тут же проверяется запросом к
  провайдеру. Второй путь — владелец платформы вводит сам из суперадминки.
- Подписка: `GET /v1/billing/tariffs/active` → бот показывает тариф → ссылка на Stripe
  Checkout платформенного аккаунта (подписка; `hbilling` уже умеет клиентов и счета, нужен
  режим подписки и вебхук `customer.subscription.*`) → `organizations.billing_status`.

## 5. Диалог

### 5.0 Принципы интерфейса (владелец, 29.09)

Аудитория — организаторы без сайта и без привычки к системам. Бот должен вести их к
правильно заведённому ивенту без ошибок, поэтому:

- **Один вопрос за раз.** Каждое сообщение бота — одна тема, одна подсказка в одну-две
  строки простым языком и пример ответа («например, 199»). Никаких терминов платформы
  (tier, feed, channel, bundle) — только слова мастера: категория, сеанс, площадка.
- **Кнопки везде, где есть выбор.** Возраст, режим билетов, «да/нет», страна, город,
  площадка, промоутер, валюта, канал — inline-кнопки. Свободный ввод только для названия,
  цены, даты, времени, описания, e-mail. У каждого ввода — образец формата в подсказке.
- **Умолчания вместо вопросов.** Всё, что можно взять из прошлых ответов (страна, город,
  площадка, возраст, промоутер, валюта, время 20:00), предлагается кнопкой «Оставить …»
  первым пунктом.
- **Ошибка = что сделать.** Текст ошибки говорит, что исправить и как («Цена — число,
  например 199 или 99,90»), и повторяет вопрос; ввод пользователя не теряется.
- **Всегда виден путь.** Заголовок шага «Шаг 3 из 6 · Билеты», кнопки «← Назад» и
  «Отмена» на каждом шаге; из итога — «Изменить …» в любой раздел.
- **Итог перед публикацией — человеческим языком**, та же одна фраза, что на сайте
  (документ §2.6), плюс что произойдёт после нажатия («появится на вашей странице
  продаж, ссылку пришлю сюда»).
- **После публикации — что дальше.** Ссылка на продажу, как ею поделиться, где смотреть
  продажи, и что предупреждения импорта значат по-русски.
- **Нельзя сделать неправильно.** Проверки мастера (даты по возрастанию, минимум две
  категории, дубли названий) срабатывают в момент ввода, а не при сохранении.

### 5.1 Машина состояний

Мастер из документа ложится на шаги как есть: `event` → `sessions[]` → `tickets` (ветка по
режиму) → `extra` (описание, валюта, канал) → `summary` → `publish`. Каждый шаг — функция
`(draft, input) → (draft', reply)`, чистая, покрытая тестами на текстах документа.

- **Черновик** — одна строка `bot_drafts` (jsonb, версия схемы, шаг, значения, время). Любое
  сообщение обновляет черновик до ответа, так что перезапуск бота ничего не теряет.
- **Клавиатуры**: выбор из списка — inline-кнопки (страны, города, площадки, промоутеры,
  режимы); свободный ввод — текст. Списки длиннее 8 — постранично и поиск по подстроке.
- **Навигация**: «← Назад» на каждом шаге, «Отмена» (черновик удаляется после
  подтверждения), из итога — «Изменить …» в любой раздел. Один активный черновик на
  пользователя и организацию; новый «+ Ивент» при открытом — предложить продолжить или
  начать заново.
- **Память ответов** (страна, город, площадка, возраст, промоутер, валюта, канал) —
  `bot_telegram_links.defaults` jsonb, как в мастере сайта.
- **Таймаут**: черновик живёт 7 дней; через 24 часа тишины — одно напоминание.
- **Афиша**: только как **документ** (Telegram сжимает «фото»; ширина ≥ 1080 проверяется
  по байтам). Бот скачивает файл (`getFile`, лимит 20 МБ), проверяет формат/размер/пропорции
  теми же правилами и текстами, что сайт, загружает `POST /v1/media` (`owner_type=event_poster`)
  и передаёт подписанный `GET /v1/media-files/{id}` как `bigPosterUrl`. Импорт по-прежнему
  скачивает по URL (`sideLoadPoster`) — для него это просто ещё один источник.
- **Описание**: одно сообщение ≤ 4 000 знаков, разметка снимается.
- **Сохранение** не атомарно (N сеансов = N запросов): бот пишет в черновик `actionId` после
  первого сеанса и `externalRef`/`session_id` после каждого; повтор «Опубликовать» после ошибки
  досылает только несохранённые сеансы. `externalRef = tg:<org_slug>:<draft_id>:<n>` —
  идемпотентен, как `wp:<site>:product:<id>`.
- **Правка**: «Мои ивенты → ивент → Изменить» читает состояние из Arena (те же GET, что в
  разделе 5 документа), строит черновик режима `edit` сразу на итоге; сохранение адресует
  ивент, сеансы и категории их UUID (`arenaEventId` / `arenaSessionId` / `arenaTierId` в
  event-bundle), так что ключ `externalRef` боту знать не нужно. Перед отправкой бот
  сравнивает `updated_at` ивента с моментом загрузки: если ивент менялся (сайт, админка) —
  предупреждает и просит подтвердить. Волна 1 не меняет уже созданные даты и каналы
  продаж (см. §9a, шаг 4).
- **Список и сводка**: «Мои ивенты» — `GET /v1/organizations/{org_id}/events` (предстоящие
  первыми, по 5, поиск по названию); карточка ивента — сеансы с продано/осталось из
  `GET …/sessions/{session_id}/summary` (деньги по валютам, по категориям), ссылка на витрину
  (`/v1/public/pages/{org_slug}/{event_slug}`), кнопки «Изменить», «Повторить как новый»
  (копия черновика с очищенными датами — самая частая операция организатора).

### 5.2 Что бот отвечает после публикации

Ссылка на продажу — сразу: страница промоутера/ивента на tickets.arenasoldout.com. Для
организаций с сайтом — плюс фраза «на сайте появится через минуту-две» (товар создаёт
сайт, §7). Предупреждения импорта (`warnings[]`) переводятся теми же текстами, что на сайте.

## 7. Сайты-ведомые (репозитории `lampyrisevents`, `vinoandco`)

Плагин `lampyris-ops` учится принимать ивенты, которых он не создавал:

1. по вебхуку `event.created` / при синхронизации каталога (`GET_ALL_ACTIONS`) сеанс с
   `externalRef` не своего сайта (`tg:` или любой не `wp:<этот сайт>:…`) → создать товар
   WooCommerce (Lampyris — и страницу `past-event`), записать `_lops_arena_event_id`,
   `_lops_arena_session_id`, `bil24_action_id`, `bil24_action_event_id`;
2. картинку товара забрать с афиши Arena (`bigPosterUrl` в каталоге / медиа ивента);
3. «Изменить» на сайте открывается для таких ивентов так же (форма читает Arena);
   `externalRef` при пересохранении с сайта **не меняется** (иначе Arena заведёт копию) —
   плагин хранит чужой `externalRef` в мете и отправляет его.
4. Материалы, письма, тур — по-прежнему только на сайте; бот про них не спрашивает, карточка
   ивента в боте даёт ссылку «Дополнить на сайте» (URL карточки ивент-центра).

Это отдельная работа в двух репозиториях сайтов, до неё ивент из бота у Vino/Lampyris
появится в витрине Arena, но не в товаре сайта.

## 8. Языки

- Тексты бота — в существующем бандле `internal/platform/i18n/locales/{en,ru,cs,he}.toml`
  под префиксом `bot.*`; тест полноты по образцу `bil24.*` (ключ есть во всех файлах).
  Русские тексты мастера переносятся из документа дословно, английские пишутся сразу;
  cs/he получают английский по fallback go-i18n, пока не переведены.
- Язык пользователя: `bot_telegram_links.locale`, по умолчанию `language_code` Telegram,
  команда «Язык». Даты/деньги — через те же helpers, что письма (`templates`).
- Клавиатуры и команды бота (`setMyCommands`) — тоже из бандла, по языку.

## 9. Безопасность

- Токен бота и `BOT_SERVICE_TOKEN` — только в Environment Dokploy, как `SALES_TELEGRAM_BOT_TOKEN`.
- Сервисный ключ бота умеет **одно**: принять приглашение по коду. Ничего платформенного.
- Никаких секретов в чате: платёжные ключи только через веб-страницу; бот отвечает отказом и
  подсказкой, если пользователь присылает `sk_live_…`.
- `/start` без кода — «вас ещё не пригласили»; неизвестные пользователи не могут вызвать
  ничего, что ходит в API. Rate-limit на пользователя: 30 сообщений/мин.
- Данные покупателей в боте волны 1 не появляются (сводка — числа и суммы).
- В логах бота — `telegram_user_id`, `org_id`, шаг, код ошибки API; никогда текст ввода.
