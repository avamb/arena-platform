# 42. Исполнительная спецификация биллинга: кредиты, счета, акции (16.10.2026)

Статус: **черновик, блоки Б1–Б2 готовы к прогону, Б3–Б6 — по мере подхода.** Источник правды по
архитектуре — `41_billing_credits_architecture_ru.md` (§6 модель, §8.1 решения владельца 16.10); по цифрам —
`docs/pricing/pricing_policy_2026-10-16_ru.md` (семь пунктов её §12 ещё не подтверждены основателями). Протокол
прогона, классы сложности, общие правила и стоп-условия — те же, что в `40_event_center_execution_spec_ru.md`
(разделы 1–4), здесь только дополнения для денег. Оркестратор — Claude-сессия; исполнители по классам (haiku /
sonnet / opus); ревью и разведка до 24.10 — через `ops/claude-sdk-runner` на API-кредитах.

## 1. Как читать

- **Блоки** = разделы 6.12 документа 41: Б1 основание (счета, условия, прайс-листы), Б2 сбор и тарификация
  («только копим и сверяем»), Б3 кредиты и покупка пакета, Б4 счета и налоги, Б5 кампании и офферы, Б6
  организации-инструменты и договоры. Волны прогона совпадают с блоками: Б-A = Б1 + Б2, Б-B = Б3, Б-C = Б4,
  Б-D = Б5, Б-E = Б6.
- **Что можно делать без утверждения цен.** Все таблицы, джобы, API и экраны Б1–Б3 не зависят от конкретных
  чисел: ставки, лестницы, пороги и сроки — строки прайс-листа и параметры, которые заводятся сидом. Сид
  `standard-2026` пишется по политике как есть и помечается в миграции комментарием «цифры ждут подтверждения
  §12»; изменить число = новая версия прайс-листа, не правка кода. Б4 (тексты счетов, налоги) и Б5 (тексты
  офферов) ждут ответов В-14 и правок §12 — их карточки описаны на уровне плана.
- **Нумерация миграций** — правило 40 §1: следующий свободный номер на `origin/master` в момент вливания
  (голова на 16.10 — 0156). Две миграции одного PR идут подряд.
- **Детализация по мере подхода.** Карточки Б1–Б2 содержат файлы по коду master на 16.10; Б3 — файлы по
  разведке перед стартом волны Б-B; Б4–Б6 — только цели и приёмка.

## 2. Классы и модели

Как в 40 §2, с уточнением: **всё, что пишет в `credit_ledger`, `charges`, `invoices` или меняет сумму счёта —
класс L (opus), с независимым opus-ревью до слияния.** Джоб сбора (`collect`) — L: он решает, что вообще
подлежит оплате. Проекции, экраны чтения, статические защиты — S/M (sonnet). Разведка — haiku через раннер.

## 3. Правила прогона, добавленные для денег

К пунктам 1–7 из 40 §3:

8. Деньги — `bigint` минорных единиц с валютой рядом; никаких `float`/`numeric` в Go-типах (в SQL `numeric`
   допустим только для процентов правил).
9. `billable_events`, `charges`, `credit_ledger`, `campaign_grants` — только INSERT. Исправление —
   компенсирующая запись с причиной и актором. Статическая защита (Б1-3) запрещает `UPDATE`/`DELETE` по этим
   таблицам вне миграций и allowlist.
10. Всякая запись в `credit_ledger` — под `SELECT … FOR UPDATE` строки `billing_accounts`; лоты обрабатываются
    по возрастанию `(expires_at NULLS LAST, purchased_at, id)`; `CHECK (remaining_minor >= 0)`.
11. Внутри открытой транзакции не звать `*gen.Queries`, привязанный к пулу (AGENTS.md); джобы биллинга берут
    `WithTx`.
12. Нога outbox для биллинга только ускоряет сбор и всегда возвращает nil; источник истины — таблицы продаж
    (41 §6.2). Тест, который доказывает начисление, ждёт `collect`, а не событие.
13. Новое право сеется с грантом `platform_superadmin` в той же миграции (парность 532); `billing.admin`
    остаётся платформенным и в `apikeys.IsForbiddenScope`; новые org-права `billing.purchase`,
    `billing.payer_manage` — в `IsForbiddenScope` НЕ попадают (организация может выдать их своему ключу — нет,
    решение прогона: **попадают**, покупка пакета ключом API запрещена, только человеком).
14. Любое число, которого нет в `docs/pricing/pricing_policy_2026-10-16_ru.md` или в 41 §8.1, — стоп-условие
    ST-2, не «решение прогона».

## 4. Стоп-условия, добавленные для денег

| Код | Условие |
|---|---|
| ST-2 (уточнение) | Любая ставка, порог, срок, потолок или получатель денег, не названный политикой или 41 §8.1; любое изменение того, что уже названо |
| ST-3 (уточнение) | Тексты счёта, налоговые формулировки, тексты офферов и писем о бонусах — только после ответа консультанта (В-14) и подтверждения §12 |
| ST-Б1 | Сверка Б2-5 нашла оплаченные заказы ЖИВЫХ организаций без `billable_event` или с начислением, которое отличается от выставленного вручную счёта за тот же период, — до любого автоматического счёта |
| ST-Б2 | На проде обнаружены `tickets.order_id IS NULL` после даты X (билеты без заказа у живых продаж) — правило бэкфилла меняет поведение |
