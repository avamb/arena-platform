# Платёжный провайдер AllPay — спецификация

Статус: код готов к ревью 2026-10-13 (PAY-14 из спецификации 36). Миграции нет. На проде ничего не настроено.
Проверено: юнит-тесты, интеграционные тесты с заглушкой AllPay на чистой базе, эталонный пример подписи из документации AllPay.
Не проверено: живая тестовая зона AllPay. Ключи тестовой интеграции владелец ещё не передал (раздел 11).

Документация AllPay: https://allpay.to/docs/api-reference.htm (API v15).
Как AllPay вызывают сегодня: плагин WooCommerce `allpay-payment-gateway` 1.1.3 и mu-плагины Vino&Co (`allpay-webhook-bridge.php`, `allpay-status-sync.php`) в репозитории `vinoandco`.

## 1. Что это и зачем

AllPay — израильский платёжный шлюз. На своей странице оплаты он принимает израильские и иностранные карты, Bit, Apple Pay, Google Pay и рассрочку (תשלומים).

Схема та же, что у Flitt:

1. arena создаёт заказ в AllPay и получает `payment_url`.
2. Покупатель платит на странице AllPay.
3. AllPay присылает подписанный вебхук. arena проводит оплату.

Данные карты в arena не попадают. Отдельного платёжного маршрута нет. AllPay встроен в путь виджета `POST /v1/public/feeds/{token}/checkout/start` через тот же интерфейс `payments.HostedCheckoutProvider`, что Stripe и Flitt.

Не входит в эту версию:

- возврат из arena (раздел 8).
- рассрочка с фиксированным числом платежей, токены карт, подписки, предавторизация J5.
- приём сведений о чарджбэках (раздел 7, только подтверждение получения).

## 2. Несколько организаций на одной интеграции

Одна организация — одна строка `payment_provider_configs` (`provider='allpay'`, режим `test` или `live`) со своими ключами в `secrets`.

- Модуль AllPay строится на каждый запрос из строки конфигурации организации. Общего ключа процесса нет.
- Вебхук приходит на `POST /v1/payment-intents/webhook/{config_id}`. Адрес называет конфигурацию, а значит и ключ проверки подписи.
- Вебхук организации B про заказ организации A не двигает платёж A. Это проверяет тест `TestAllPay_TwoOrganizationsAreIsolated`.

## 3. Ключи конфигурации

| Поле | Что это | Где взять |
|------|---------|-----------|
| `merchant_id` | API login интеграции | Кабинет AllPay → Settings → API Integrations |
| `secret_key` | API key той же интеграции. Подписывает запросы и вебхуки. | Там же |
| `vat` (необязательно) | Код НДС строки в чеке: `0` без НДС (по умолчанию), `1` НДС включён в цену, `3` НДС 0 % | Решение организатора и его бухгалтера |
| `max_installments` (необязательно) | Наибольшее число платежей рассрочки, от 2 до 12. Только для ILS. | Решение организатора |

Имена `merchant_id` и `secret_key` остались от прежней заготовки AllPay. Так форма в админке и уже сохранённые строки продолжают работать.

Отдельного секрета вебхука у AllPay нет. Вебхук подписан тем же API key.

Статус конфигурации `configured` наступает, когда заполнены `merchant_id` и `secret_key`. Неверные `vat` и `max_installments` отклоняются при сохранении.

**Тест и бой.** Адрес API один. Тестовый режим включают в кабинете AllPay для каждой интеграции. Запрос может включить его сам: `test_mode=1`.

arena отправляет `test_mode=1` для каждой конфигурации с режимом `test`. Ключ, сохранённый как тестовый, не может списать деньги с настоящей карты, даже если интеграция в кабинете переключена в бой. Для режима `live` arena не отправляет `test_mode`, и режим решает настройка интеграции.

## 4. Создание платежа

`POST https://allpay.to/app/?show=getpayment&mode=api15`, тело JSON.

| Поле AllPay | Значение arena |
|-------------|----------------|
| `login` | `merchant_id` конфигурации |
| `order_id` | id checkout-сессии arena (UUID). Он же `payment_intents.provider_payment_id`. |
| `items` | одна строка на всю корзину: `name` (название мероприятия, до 200 символов), `qty` 1, `price`, `vat` |
| `price` | итог checkout-сессии в **основных** единицах (`123.5`, а не `12350`) |
| `currency` | валюта сеанса: только `ILS`, `USD` или `EUR` (раздел 6) |
| `webhook_url` | `<API_PUBLIC_URL>/v1/payment-intents/webhook/{config_id}` |
| `success_url` и `backlink_url` | маршрут arena `/v1/public/payment-return?r=<страница покупателя>&checkout_token=…` (раздел 4.1) |
| `expire` | Unix-время конца окна оплаты, не раньше чем через 60 с |
| `client_email` | e-mail покупателя |
| `lang` | язык покупателя, если AllPay его знает: EN, HE, RU, AR, ES, IT, DE, FR. Иначе поле не отправляется, и AllPay берёт язык браузера. |
| `inst` | `max_installments`, только если больше 1 и валюта ILS |
| `test_mode` | `1` для конфигурации в режиме `test` |
| `sign` | раздел 5 |

Ответ: `payment_url` для редиректа. Ошибка приходит с HTTP 200 и полями `error_code`, `error_msg`. Любая ошибка старта — это HTTP 503 `checkout.payment_start_failed`. Бронь освобождают обычные свипы.

Одна строка корзины выбрана намеренно. Скидки, промокоды и сервисный сбор arena уже посчитала. AllPay получает итог, который покупатель видел в корзине.

### 4.1 Возврат покупателя идёт через arena

AllPay не описывает, каким методом (GET или POST) страница оплаты отправляет покупателя на `success_url`. Поэтому `success_url` и `backlink_url` указывают на маршрут arena `GET|POST /v1/public/payment-return`. Он на любой метод отвечает 303 на страницу покупателя. Так сделано и для Flitt.

У AllPay нет адреса неудачи. При отказе карты страница показывает ошибку и предлагает другую карту. `backlink_url` — это кнопка «Вернуться на сайт».

**Окно оплаты.** `expire` равен концу `WIDGET_PAYMENT_WINDOW_SECONDS` (1860 с). Бронь arena живёт на 120 с дольше. Страница AllPay закрывается раньше, чем arena отпускает места.

## 5. Подпись

SHA-256 (hex, нижний регистр) от строки: значения параметров через `:`, в конце `:` и API key.

Правила (из раздела «Signature Algorithm» документации):

- Поле `sign` в расчёт не входит.
- `""` и `null` пропускаются, как будто поля нет.
- `0`, `"0"` и `false` — это значения, они входят в строку.
- Ключи сортируются по алфавиту на каждом уровне: верхний уровень, поля каждого объекта в `items`, поля объекта `subscription`. Порядок элементов массива сохраняется.
- Число пишется в кратчайшей точной форме: `100.00` → `100`, `100.50` → `100.5`. Строка остаётся как есть: `"100.00"` → `100.00`.
- `true` → `1`, `false` → `0`.
- Значения не обрезаются и не меняют регистр.

Подпись считается по значениям так, как они пришли в JSON. Поэтому тело вебхука читается с `json.Number`, а запрос собирается из `json.Number`.

Эталон: пример из документации AllPay даёт `c3c5458724d88837bd60879b5130c860589e42248360b4ca42c2539ebf8a7803`. Тест `TestSign_DocumentedWorkedExample` проверяет этот пример. В HTML документации адрес в примере скрыт защитой Cloudflare. Настоящий адрес — `jason@company.io`, с ним хеш совпадает.

Сравнение подписи — за постоянное время.

## 6. Валюты

AllPay списывает деньги только в ILS, USD или EUR. Если у аккаунта нет права на USD или EUR, AllPay **молча** пересчитывает сумму в шекели по курсу Google Finance. Тогда arena записала бы одну валюту, а AllPay списал бы другую.

Поэтому модуль отказывает в любой другой валюте до запроса к AllPay. Покупатель получает `checkout.payment_start_failed`. Тест: `TestAllPay_UnsupportedCurrencyTakesNoPage`.

Минимальная сумма в ILS — 5 шекелей (ошибка AllPay 21).

Рассрочка разрешена только в ILS (код отказа 312). Для USD и EUR arena не отправляет `inst`.

## 7. Вебхук

`POST /v1/payment-intents/webhook/{config_id}`, JSON, подпись в теле (`sign`). Заголовка подписи нет. Поля продавца в теле нет.

Порядок проверок (все до любых записей):

1. Тело читается, `config_id` — UUID, конфигурация существует, активна, `configured`. Иначе 404 без подробностей.
2. У конфигурации есть `secret_key`. Иначе 401.
3. Подпись верна под ключом этой конфигурации. Иначе 401.
4. Платёж найден по `order_id`. Платёж другой организации, другого провайдера или неизвестный считается «не нашим»: ответ **200** `processed:false`, чтобы AllPay не повторял доставку.

Как arena понимает вебхук:

| Вебхук | Действие |
|--------|----------|
| `status` 1, без `type` | платёж `succeeded`, checkout завершается, заказ `paid`, выпуск билетов |
| `status` 0 | **ничего не меняется.** Это одна неудачная попытка. Страница AllPay остаётся открытой для другой карты. Если закрыть платёж, следующая успешная оплата потеряется. |
| есть `subscription_create` или `preauth=authorized` | ничего не меняется: деньги не списаны (arena такого не запрашивает) |
| `type=chargeback` | подтверждается, платёж не меняется (чарджбэки — PAY-16) |
| `type=chargeback_revert` | подтверждается, платёж не меняется |

Тип события для идемпотентности: `allpay.payment.paid`, `allpay.payment.declined`, `allpay.payment.not_charged`, `allpay.chargeback`, `allpay.chargeback_revert`. Повтор вебхука даёт 200 и не выпускает билеты второй раз.

`order_id` записывается и в `provider_charge_ref`: AllPay возвращает деньги и читает статус по `order_id`.

AllPay повторяет вебхук до 10 раз за сутки, пока не получит HTTP 200.

Вебхук AllPay на **старом** маршруте `/v1/payment-intents/webhook` отклоняется: `400 webhook.allpay_requires_config_route`.

**Сумма в вебхуке не сверяется с заказом.** Подпись делает только AllPay ключом организатора, а сумму задаёт arena при создании страницы. Сверку можно добавить вместе с чтением статуса (раздел 12).

## 8. Возвраты

**В этой версии возврат из arena не работает.** Модуль не заявляет `Capabilities.Refund`. Бот и API отвечают `refund.provider_not_supported` (422), как сейчас для Flitt.

Почему. У AllPay есть метод `?show=refund`, но:

1. У него нет ключа идемпотентности.
2. Он не возвращает id возврата.
3. Документация не описывает вебхук о возврате.

Движок возвратов arena повторяет вызов с неизвестным исходом (таймаут, обрыв связи) с тем же ключом. У AllPay повтор после потерянного ответа может вернуть деньги второй раз. Частичный возврат AllPay ограничивает только остатком заказа, так что второй возврат одного билета пройдёт.

Как делать возврат сейчас:

1. Верните деньги в кабинете AllPay (полностью или частично).
2. В arena отмените билет с `refund_mode=none`.

Предложение для PAY-14b (нужно решение владельца):

1. Перед каждым вызовом `refund` модуль читает `paymentstatus` и сравнивает `refunded` с суммой возвратов, которые arena уже знает по этому платежу.
2. Если AllPay вернул больше, чем знает arena, повторный вызов не делается. Возврат считается принятым.
3. Движок уже не допускает двух вызовов по одному платежу одновременно (`LockPayment`, claim). Этого достаточно для одного повтора.
4. Для этого нужно поле в `payments.RefundRequest` с суммой уже известных возвратов. Это правка движка возвратов, её надо делать отдельно и с отдельным ревью.
5. Чтение статуса для сверки возвратов из кабинета: опрос `paymentstatus`, как в mu-плагине Vino&Co `allpay-status-sync.php`.

## 9. Проверка ключей

При сохранении конфигурации и по кнопке «Check again» arena вызывает `?show=checkkeys` с `login` и `sign`. Деньги не двигаются, ничего не создаётся.

- Ответ без `error_code` → ключи верны → `ok`.
- `error_code` 3 (неверная подпись, то есть неверный ключ) или 5 (неизвестный login) → `failed`.
- Сеть, 5xx, другие коды → `unverified`. Это не вердикт о ключе.

## 10. Что изменилось в старом коде

- Прежний адаптер `internal/adapters/allpay` описывал выдуманный API (`api.allpay.co.il/v1`, Bearer-токен, заголовок `X-AllPay-Signature`). AllPay так не работает. Адаптер переписан по документации.
- Вторая копия `internal/domain/payments/allpay.go` удалена. Её ничего не использовало. Так закрыт вопрос 5 спецификации 36 «какая копия каноническая».
- Функция `payments.VerifyAllPaySignature` удалена.
- `ALLPAY_WEBHOOK_SECRET` больше ничего не проверяет. Переменная читается, чтобы старый деплой запускался. В production теперь обязателен `STRIPE_WEBHOOK_SECRET`: одного `ALLPAY_WEBHOOK_SECRET` недостаточно. На проде задан `STRIPE_WEBHOOK_SECRET` (проверено 2026-10-13), поэтому деплой не сломается.
- `SecretField.Pattern` теперь проверяется при сохранении ключей. До этого поле было в описании модуля, но ничего не проверяло.
- Тестовая подмена адреса: `ALLPAY_API_BASE_URL`. В production её запрещает `config.Validate`.

## 12. Решения и вопросы для владельца

1. Код НДС по умолчанию — `0` (без НДС), как в плагине WooCommerce Vino&Co без налогов. Подходит ли это израильским организаторам? Организатор-плательщик НДС должен выбрать `1`.
2. Рассрочка: включать её только по полю `max_installments` организатора? Или задать порог суммы, как в плагине (`installment_min_order`)?
3. Возвраты через arena (раздел 8, PAY-14b): делать сейчас или после первых продаж? До этого возврат — только в кабинете AllPay.
4. `client_tehudat` (номер удостоверения). arena его не отправляет, и AllPay спрашивает номер на странице. Скрывать поле для иностранных покупателей (`000000000`)?
5. Сверка суммы вебхука с заказом и периодическое чтение статуса (аналог `allpay-status-sync.php`): нужно ли сразу?
6. У AllPay есть MCP-сервер. Подключать его к работе поддержки и сверки — отдельное решение, к проду не подключено.

## 13. Настройка организации (чек-лист)

1. Кабинет AllPay → Settings → API Integrations: создайте интеграцию для arena. Для проверки включите в ней Test Mode.
2. Admin → организация → Payment configs → `allpay`, режим `test` (или `live` после KYB): `merchant_id` = API login, `secret_key` = API key. Дождитесь зелёного бейджа проверки.
3. Admin → Channels → канал: provider `allpay`.
4. Вебхук в кабинете AllPay настраивать не нужно. arena присылает `webhook_url` с каждым заказом.
5. Валюта сеансов — ILS (или USD/EUR, если AllPay разрешил их аккаунту).
