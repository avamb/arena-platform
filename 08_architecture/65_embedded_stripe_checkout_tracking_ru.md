# 65. Встроенный чекаут Stripe с отслеживанием каждого шага

Статус: v3, 22.11.2026. Спека прошла проверку двумя независимыми критиками и судьёй (§12). Решения владельца внесены (§11).

## 0. Цель

Покупатель платит прямо на нашей странице: в виджете на сайте организатора и на странице билетов tickets.arenasoldout.com. Сейчас его уводят на checkout.stripe.com.

Каждый шаг оплаты становится событием:
- в нашей воронке (спека 50);
- по выбору организатора — в его Meta Pixel и GA4.

Организатор видит, на каком шаге теряет покупателей. По оплате и по отслеживанию чекаут должен быть сильнее, чем у Ticket Tailor и других. Где это доказано источником, а где нет, сказано в §2.

**Решения владельца (22.11):**
- своя форма на Elements, не Embedded Checkout;
- первая версия: виджет и страница билетов;
- карта, Apple Pay и Google Pay сразу;
- пиксели Meta и GA4 нужны;
- новый чекаут включается на каналах сразу, а не по согласию каждого организатора;
- форма выглядит так же, как у Stripe, без нашей темы;
- баннер согласия — общий текст платформы;
- отказы банка показываем организатору группами;
- TikTok добавим позже, поэтому пиксели устроены так, чтобы новый пиксель добавлялся одним модулем (§6.5).

**Вне рамок первой версии:**
- магазин;
- Flitt (остаётся на хостовой странице);
- асинхронные способы оплаты: SEPA, Klarna, банковские редиректы (§3.3);
- серверный CAPI и GA4 Measurement Protocol. Сейчас закладываем только детерминированный `event_id` (§6.6).

## 1. Как сейчас (master)

- **Виджет.** `apps/widget/src/ArenaTickets.svelte` → `handleCheckout`: форма покупателя (`BuyerForm`: e-mail, имя, телефон по `session.buyer_fields`, согласие, галочка рассылки) → `POST /v1/public/feeds/{token}/checkout/start` → `window.location.href = redirect_url`. После возврата `checkout_token` берётся из URL или sessionStorage, статус опрашивается через `GET /v1/public/checkout/{token}` (`OrderStatus.svelte`).
- **Страница билетов** (`apps/tickets-page`) ставит `<arena-tickets>` (`src/lib/render.ts`), своего чекаута у неё нет.
- **Бэкенд.**
  - `hfeed/payment_start.go`: холд коммитится, потом вызывается `StripePaymentStarter.StartHostedCheckout`.
  - `adapters/stripe/adapter.go` `CreateCheckoutSession`: `mode=payment`, **только карта** (комментарий около строки 340: асинхронные способы дали бы «completed» после истечения холда), одна строка на всю сумму, `success_url`/`cancel_url`, `customer_email`, `expires_at` (окно 1860 с), `locale`, metadata `arena_*`.
  - `cs_…` хранится в `payment_intents.provider_payment_id`, `pi_…` в `provider_charge_ref`.
- **Вебхуки.** `checkout.session.*` находят строку по `cs_…`. События `payment_intent.*` несут `pi_…`, поэтому `GetPaymentIntentByProviderID` строку не находит (`stripe/module.go:196`, `hcheckout/payment_intents.go:1210`). Отказ сейчас не делает intent терминальным **случайно**, правила для этого нет (§3.6).
- **Ключи.** У Stripe хранятся только sk (`secrets.api_key`) и `webhook_secret`. Publishable key нет нигде; место под него есть в `payment_provider_configs.public_config` (0046).
- **Воронка.**
  - `lib/funnel.ts`: шаги `view | session_open | seats_chosen`.
  - Маяк `POST /v1/public/funnel` (`hfeed/public_sales_funnel.go:80-87`) не принимает `checkout_token`, дедуп идёт в памяти процесса (`salesfunnel.go:117-148`).
  - `sales_funnel_daily` (0193): CHECK на шаги, ключ `(event_id, day, step, surface, session_key, utm_source, utm_campaign)`.
  - Серверные `checkout_start`, `payment_open`, `paid` считаются из таблиц заказа.
- **Маркетинг.**
  - `fbq`, `gtag`, `dataLayer` и GTM в `apps/` нет.
  - Атрибуция `ref` и `utm_*` есть (`lib/attribution.ts`, спека 43).
  - Баннера согласия для аналитики нет.
- **Уже есть в чекауте:** таймер холда, промокод и quote, строка сервисного сбора, напоминание о брошенной корзине (51-1), add-on категории, реферальный код.
- **Кэш.** У `GET /v1/public/checkout/{token}` (`hfeed/public_checkout_status.go`) не задан `Cache-Control`. Остальные публичные маршруты отдают `public, max-age=30`.
- **CSP страницы билетов** не разрешает Stripe, Meta и Google.

## 3. Как устроена оплата

### 3.1. Объект Stripe

Checkout Session с `ui_mode=elements`; в Stripe.js — `initCheckoutElementsSdk`. Источник: docs.stripe.com/js/custom_checkout. Версию API Stripe и Stripe.js закрепляем; параметры сверяем с API reference именно этой версии.

Что не меняется:
- `cs_…` в `provider_payment_id`;
- `checkout.session.completed` с `payment_status=paid` как единственный источник «оплачено»;
- окно оплаты и `expires_at` (минимум 30 минут у Stripe);
- metadata `arena_*`;
- «провайдер вызывается после коммита холда».

### 3.2. Подтверждение и возврат

- Браузер вызывает `checkout.confirm({redirect: 'if_required'})`. Без этой опции Stripe **всегда** уводит покупателя на `return_url`, даже после успешной оплаты картой.
- `return_url` в сессии передаём всегда, хотя для одних карт он формально не обязателен. Он нужен 3-D Secure, если банк открывает отдельную страницу. Ведёт он через `/v1/public/payment-return` (как у Flitt) обратно на страницу покупателя с `checkout_token`; виджет возобновляет опрос статуса, как сейчас.
- `success_url`/`cancel_url` для `elements` не передаём.

### 3.3. Способы оплаты

- Только карта и Link. Apple Pay и Google Pay — это кошельки поверх карты, отдельного типа им не нужно.
- Набор задаём явно через параметр сессии, который в выбранной версии API ограничивает способы (`allowed_payment_method_types` или `payment_method_configuration`; судья не нашёл в reference `payment_method_types` для этого режима). **Перед E2 проверить на тестовом аккаунте, что при таком ограничении видны Apple Pay, Google Pay и Link.**
- Асинхронные способы не включаем, пока не спроектировано окно для денег, пришедших после холда. Возвраты у Stripe сейчас только симулируются, так что вернуть такие деньги автоматически нечем.

### 3.4. Ответ `checkout/start` и publishable key

- Ответ получает поле `payment: {provider: "stripe", mode: "elements", client_secret, publishable_key}`. `redirect_url` остаётся для hosted и Flitt.
- `publishable_key` — новое необязательное поле в описании модуля Stripe (`payments.SecretField` без `Hidden`, поэтому его можно показать владельцу). Так оно проходит ту же проверку префикса и режима, что и sk: `pk_test_` только в режиме test, `pk_live_` только в live. Принадлежность pk тому же аккаунту сервер проверить не может. Первая ошибка инициализации Stripe.js в браузере уходит ops-алертом, а виджет переключается на hosted (§3.5).
- Конфигурация без pk работает как сейчас, через hosted.

### 3.5. Флаг, совместимость и запасной путь

- Настройка канала `settings.checkout.stripe_ui = auto | hosted`, по умолчанию `auto` (решение владельца: включаем сразу). `auto` — это `elements`, если в конфигурации Stripe есть pk, иначе `hosted`. `hosted` ставит оператор, если у канала проблема.
- Глобальный выключатель `STRIPE_ELEMENTS_ENABLED` в arena-api (по умолчанию включён) возвращает все каналы на hosted без выката, если что-то пошло не так.
- Виджет шлёт `capabilities: ["stripe_elements"]`. Старый виджет без этого поля получает hosted-сессию.
- Запасной путь `POST /v1/public/checkout/{token}/hosted` срабатывает, если:
  - Stripe.js не загрузился за 5 секунд;
  - CSP хоста его запретил;
  - инициализация упала.

  Порядок действий сервера:
  1. Истечь старую `elements`-сессию (`ExpireCheckoutSession`). Если Stripe отказал, потому что сессия уже оплачена или обрабатывается, hosted не создаём и отвечаем «оплата уже идёт», виджет опрашивает статус.
  2. Создать hosted-сессию на тот же холд. Новая строка `payment_intents`, старая помечается `superseded`.
- **`superseded` не исключает строку из поиска по `cs_…`.** Вебхук `completed` по старой сессии всё равно оплачивает заказ, а новая сессия тут же истекает.
- Если оплачены обе сессии, вторая оплата идёт в ops-алерт как двойное списание и возвращается вручную, пока нет автоматического возврата. Обязательный интеграционный тест: «старая сессия оплачена после создания новой».

### 3.6. Отказ банка

- Отказ возвращается в `confirm()` и показывается в форме. Сессия остаётся открытой, покупатель пробует другую карту, холд и таймер не трогаются.
- **Явное правило:** для строк, созданных Checkout Session, события `payment_intent.*` не меняют состояние intent. Состояние меняют только `checkout.session.completed`, `.expired`, `.async_payment_*`. Сейчас это выполняется случайно, потому что поиск идёт по `cs_…`.
- Тест: сначала `payment_intent.payment_failed` по `pi_…`, потом `checkout.session.completed` по `cs_…`. Заказ должен оказаться оплаченным.

### 3.7. `client_secret`

- Отдаётся в `checkout/start` и в `GET /v1/public/checkout/{token}`, но только пока заказ `pending` и холд жив. После `paid`, после истечения и после `superseded` секрета в ответе нет.
- У `GET /v1/public/checkout/{token}` выставляется `Cache-Control: no-store`. Это нужно и сейчас, независимо от спеки.
- Секрет не хранится в базе: при повторном запросе сервер берёт его у Stripe (`GET /v1/checkout/sessions/{id}` с sk организатора). В логи и в URL он не попадает.

## 4. Форма оплаты (UX)

Два экрана внутри `CartSheet`, как сейчас, но второй — на нашей странице.

**Экран 1, «Контакты»** (уже есть, `BuyerForm`):
- **e-mail первым полем**, `autocomplete="email"`; имя и телефон только если организатор их требует (`buyer_fields`), телефон с `inputmode="tel"`;
- согласие с условиями и галочка рассылки;
- кнопка ведёт к `checkout/start`.

E-mail уходит в сессию (`customer_email`), поэтому Link его узнаёт. Изменить e-mail на втором экране нельзя: вернуться назад можно, холд при этом сохраняется. Можно ли менять e-mail через `updateEmail` при заданном `customer_email`, в справке не нашлось; на E2 проверить на тестовом аккаунте.

**Экран 2, «Оплата»:**
1. Короткий итог: сумма к оплате вместе с сервисным сбором, ссылка «подробнее» раскрывает строки.
2. Кнопки Express Checkout (Apple Pay, Google Pay, Link), только если устройство их поддерживает. Сумма в окне кошелька та же.
3. Payment Element.
4. Кнопка «Оплатить 52,50 €» (сумма на кнопке). На телефоне кнопка прилипает к низу экрана, чтобы блок организатора её не скрывал. Пока идёт подтверждение, она заблокирована.
5. Под кнопкой — «Организатор: …» и контакт.

Правила:
- **Таймер:** спокойная строка «Места за вами до 21:45». В последние 5 минут она становится заметной. Когда время вышло, кнопка и кошельки отключаются, секрет больше не отдаётся (§3.7), покупатель видит, что делать дальше.
- **Язык:** `locale` Stripe совпадает с языком виджета. Для иврита `locale: 'he'` и `dir=rtl` у нашей обёртки. Номер карты и CVC остаются слева направо — это норма для иврита. Проверяем на стенде.
- **Оформление как у Stripe** (решение владельца): `appearance: {theme: 'stripe'}` без наших цветов и шрифтов. Наша обёртка экрана оплаты (итог, кнопка, строка организатора) повторяет вид Stripe Checkout: белый фон, системный шрифт, синяя кнопка Stripe. Тема виджета на этот экран не действует.
- **Ошибки:** тексты отказа Stripe уже локализованы. После отказа ниже подсказка: «Заказ держится до 21:45, попробуйте другую карту».
- **Успех:** «Добавить в календарь» (ICS) и ссылка на билеты рядом со статусом. Истина — вебхук: экран опрашивает статус, как сейчас.
- **Встроенные браузеры** Instagram и Facebook: Apple Pay там обычно недоступен, Stripe сам скрывает кнопку. Проверяем, что оплата картой работает.

## 5. Apple Pay и Google Pay

- Кнопки показываются только на доменах, зарегистрированных в аккаунте продавца, то есть организатора (`payment_method_domains`). Его sk у нас есть, поэтому регистрируем сами (`POST /v1/payment_method_domains`):
  - `tickets.arenasoldout.com` — при сохранении или проверке конфигурации;
  - домены сайтов из `allowed_origins` каналов — при сохранении канала и ночной сверкой. Регистрируем и `example.com`, и `www.example.com`: регистрация дешёвая, а точное правило по поддоменам источником не подтверждено.
- Статус каждого домена (`apple_pay.status`, `google_pay.status`) виден в ивент-центре рядом с платёжной конфигурацией. Неудача не блокирует оплату картой.
- Виджет — web component на странице хоста, не iframe, поэтому проверяется домен верхней страницы. Если организатор сам вставил виджет в свой `<iframe>`, Safari 17+ требует у этого iframe `allow="payment"` (docs.stripe.com/elements/express-checkout-element). Это пишем в памятку.
- Виджет на домене, которого нет в `allowed_origins`, принимает карту без кошельков. `checkout_form_view` передаёт `wallets_available`, такие домены видны в отчёте.

## 6. Отслеживание

### 6.1. Словарь шагов

| Шаг | Когда | Источник |
|---|---|---|
| `checkout_start` | холд и сессия созданы | сервер (есть) |
| `checkout_form_view` | Payment Element готов (`ready`) | виджет |
| `payment_method_selected` | выбран способ: `card`, `apple_pay`, `google_pay`, `link`, `other` | виджет |
| `payment_details_complete` | Payment Element сообщил `complete=true` | виджет |
| `pay_clicked` | нажата «Оплатить» или кнопка кошелька | виджет |
| `payment_3ds` | `confirm` потребовал проверку банка на нашей странице. Банк, уведший на свою страницу, сюда не попадает | виджет |
| `payment_declined` | отказ, группа причины (решение владельца): `no_funds` («нет средств»: `insufficient_funds`), `bank_declined` («банк отклонил»: `card_declined`, `do_not_honor`, `fraudulent`, `lost_card`, `stolen_card`), `input_error` («ошибка ввода»: `expired_card`, `incorrect_cvc`, `incorrect_number`, `invalid_expiry_*`), `auth_failed` («не прошла проверка банка»: `authentication_required`, `authentication_failed`), `other` (всё остальное). Коды Stripe переводятся в группу в виджете, на сервер уходит только группа | виджет |
| `paid` | вебхук подтвердил оплату | сервер (есть) |
| `abandoned` | холд истёк без оплаты | сервер, считается |

Шаг «контакты заполнены» не нужен: экран 1 заканчивается `checkout_start`, который считает сервер.

### 6.2. Хранение (наша воронка)

**Однократность — на клиенте.** Виджет отмечает отправленные шаги в sessionStorage по `checkout_token` и не шлёт их повторно. Сервер `checkout_token` не получает и id покупателя не хранит (спека 50 §1.2, §11). Счётчики клиентских шагов приближённые: другая вкладка или очищенное хранилище дадут лишний счёт. Экран так и говорит.

**Повторные отказы.** `payment_declined` идёт с номером попытки `attempt` из закрытого списка `1`, `2`, `3+`. Тогда серверный Deduper не склеивает разные попытки одного дня.

**Миграция:**
- расширить `CHECK step`;
- добавить `detail text NOT NULL DEFAULT ''` с CHECK по закрытому списку (способ оплаты, причина, попытка);
- пересобрать первичный ключ вместе с `detail`;
- проверить, что лимит `MaxUTMPairsPerDay` не раздует таблицу: `detail` ставится только на шаги `payment_method_selected` и `payment_declined`.

Маяк принимает новые шаги и `detail` только из списков, неизвестное молча отбрасывает.

**Экран воронки** в ивент-центре: новые ступени между `payment_open` и `paid`, разбивка по способу оплаты, «почему не прошла оплата», доля посетителей с доступными кошельками.

**Малые числа.** Разбивка по причинам и способам скрывается, если в ячейке меньше 5 случаев. Причина отказа одного покупателя на маленьком мероприятии иначе почти указывает на человека.

### 6.3. Внешние системы: события

| Наш шаг | GA4 | Meta |
|---|---|---|
| `view` | `view_item` | `ViewContent` |
| `seats_chosen` | `add_to_cart` | `AddToCart` |
| `checkout_form_view` | `begin_checkout` | `InitiateCheckout` |
| `payment_details_complete` или выбран кошелёк | `add_payment_info` (`payment_type`) | `AddPaymentInfo` |
| `paid` (экран успеха) | `purchase` (`transaction_id` = номер заказа) | `Purchase` |
| прочие шаги | `arena_checkout_step` (`step`, `detail`) | не отправляем |

Параметры:
- **GA4:** `value`, `currency`, `items[]` с `item_id` = id категории, `item_name`, `quantity`.
- **Meta:** `value`, `currency`, `content_ids`, `content_type: 'product'`, `num_items`. `eventID` передаётся четвёртым аргументом: `fbq('track', 'Purchase', {...}, {eventID})`.
- **`event_id`** детерминированный. Для Purchase — `order-<system_id>`, как в магазине Einat; его же потом возьмёт CAPI. Для остальных шагов — `ck-<хеш checkout_token>-<шаг>`.

Purchase из браузера отправляется только с экрана успеха после `paid` и не повторяется при перезагрузке (метка в sessionStorage). Это нижняя оценка: закрытая вкладка или блокировщик её теряют. В отчёте организатора истиной считается наш `paid`, а не цифры Meta или GA. Экран объясняет разницу; закроет её CAPI.

### 6.4. Где что запускается

**Страница билетов (наш домен):**
- в настройках организации: Meta Pixel ID и GA4 Measurement ID;
- скрипты грузим мы и только после согласия в новом баннере страницы билетов; для GA — Consent Mode v2;
- текст баннера общий для платформы (решение владельца), на всех языках страницы билетов; в нём перечислены категории («аналитика», «реклама») и ссылка на политику платформы. Организатор текст не меняет;
- организатор здесь контролёр данных, мы обработчик. Это вносится в DPA и в политику;
- **GTM на этой странице не ставим.** На странице с платёжной формой нужен контроль всех скриптов (PCI DSS 4.0, требования 6.4.3 и 11.6.1); GTM исполняет произвольный код организатора.

**Виджет (сайт организатора):**
- своих скриптов не грузит и согласие сайта не обходит;
- `settings.tracking.forward_to_host` **по умолчанию выключен**, организатор включает его в ивент-центре сам. Варианты:
  - `datalayer_arena`: в `window.dataLayer` уходят только события `arena_*` (`arena_view_item`, `arena_begin_checkout`, `arena_add_payment_info`, `arena_purchase`, `arena_checkout_step`) с теми же параметрами. Теги на них организатор настраивает в своём GTM, и его согласие действует там. Своих `purchase` или `begin_checkout` (например, от WooCommerce) это не задвоит;
  - `datalayer_ga4`: стандартные ecommerce-имена GA4. Только для сайтов, где своих таких событий нет; в настройке это написано;
  - `direct_pixels`: прямые вызовы `fbq`/`gtag`, если они есть на странице. В настройке предупреждение: мы не видим, получил ли сайт согласие, и ответственность на сайте.
- независимо от настройки виджет шлёт `CustomEvent('arena:checkout', {detail})` на свой элемент — для разработчиков сайтов. Он ничего никуда не отправляет.

### 6.5. Новый пиксель — один модуль

TikTok и любой следующий пиксель (решение владельца: позже, но легко) добавляются без правок в чекауте.

- **Одна точка отправки.** Виджет и страница билетов зовут только `track(step, payload)` из общего пакета `packages/arena-track` (он уже есть со спеки 50). Шаги чекаута не знают, какие пиксели подключены.
- **Модуль назначения** — один файл `destinations/<name>.ts` с интерфейсом:
  `{ id, consentCategory: 'analytics' | 'ads', scriptUrl(config), init(config), map(step, payload) → вызов или null }`.
  В первой версии модулей три: `ga4`, `meta`, `datalayer` (для виджета).
- **Таблица соответствия** «наш шаг → событие назначения» живёт внутри модуля (у TikTok — `ViewContent`, `AddToCart`, `InitiateCheckout`, `AddPaymentInfo`, `CompletePayment`). Общий словарь шагов (§6.1) не меняется.
- **Настройки организации** — список `tracking.destinations: [{type, id}]`, а не отдельная колонка на каждый пиксель. Новый тип проверяется закрытым списком на сервере и регулярным выражением для его ID.
- **CSP** собирается из `scriptUrl`/`connect` всех модулей одним списком.
- **Баннер** включает модуль по его `consentCategory`, поэтому новый пиксель автоматически попадает под существующую категорию.

Добавить TikTok = новый модуль + значение в закрытом списке + поле в ивент-центре + домены в CSP + тест соответствия шагов.

### 6.6. Основа под CAPI

Сейчас храним только детерминированный `event_id`. `_fbp`, `_fbc` и `client_id` GA — устойчивые идентификаторы устройства; хранить их без CAPI незачем, а спека 50 этого не допускает. Этап CAPI сам решит, где их хранить: отдельно от воронки, только при записанном согласии, с коротким сроком хранения и с записью в DPA.

## 7. Безопасность

- Данные карты не касаются нашей страницы, поля Stripe живут в iframe. sk в браузер не попадает. `client_secret` — по правилам §3.7.
- CSP страницы билетов:
  - `script-src`: `js.stripe.com`, а также `connect.facebook.net` и `www.googletagmanager.com` (последние два — только вместе с баннером);
  - `frame-src`: `js.stripe.com`, `hooks.stripe.com`;
  - `connect-src`: `api.stripe.com`, `*.stripe.network`, Google Analytics, Facebook.

  Полный список Stripe зависит от версии Stripe.js. **Приёмка:** на стенде с включённым CSP пройти карту, 3-D Secure, Link, Apple Pay и Google Pay без единой ошибки CSP в консоли.
- Хостам виджета публикуем памятку: адреса Stripe для их CSP и `allow="payment"` для iframe. Без этого сработает hosted-путь.
- Ошибки новых публичных маршрутов (`/hosted`, создание сессии) — 503, не 502 (правило Cloudflare из AGENTS.md).

## 8. Тесты и проверка

**Go integration:**
- elements-сессия возвращает `client_secret` и pk; `completed` платит заказ;

**`stripe-stub.cjs`:** ответы `ui_mode=elements`, `payment_method_domains`, истечение уже оплаченной сессии.

**Vitest:**

## 10. Риски

- CSP чужих сайтов, блокировщики и медленная загрузка Stripe.js → переход на hosted по таймауту и счётчик таких случаев.
- Неверный pk → проверка префикса, алерт, hosted.
- Две оплаченные сессии на один заказ → истечь до создания, оплата по любой `cs_…`, алерт и ручной возврат (§3.5).
- Кто-то добавит поиск intent по `pi_…`, и отказ станет терминальным → явное правило и тест (§3.6).
- Асинхронные способы, включённые организатором в Dashboard, → явное ограничение способов в сессии (§3.3).
- Цифры Meta и GA ниже наших → экран объясняет; CAPI следующим этапом.
- Параметры Stripe для elements менялись в 2025 (`custom` → `elements`, имена методов) → закрепить версии.

## 12. Проверка спеки (22.11)

Два критика (платёжная часть; отслеживание и конкуренты) и судья по первоисточникам.

**Принято и внесено:**
- `confirm({redirect:'if_required'})`;
- явное ограничение способов оплаты;
- правило для `payment_intent.*`;
- гонка `/hosted`;
- `client_secret` и `no-store`;
- однократность шагов на клиенте и `attempt` у отказов;
- ключ таблицы с `detail`;
- порог 5;
- `_fbp`/`_fbc` не храним до CAPI;
- `forward_to_host` выключен по умолчанию и пишет `arena_*`;
- Purchase — нижняя оценка;
- параметры `content_ids`/`items`;
- e-mail первым полем;
- кнопка с суммой, прилипающая на телефоне;
- `locale 'he'`;
- `allow="payment"`;
- переход на hosted по таймауту;
- ICS;
- этапы E5/E6 с ревью opus.

**Отклонено судьёй:**
- «у Ticket Tailor есть AddPaymentInfo»: у них его нет (статья 5560643);
- «события Tito называются `tito:registration:*`»: это слушатели JS-API, аналитические события — `tito_widget_*`;
- «`return_url` обязателен без `redirect_on_completion=never`»: этот параметр относится к `embedded_page`.

**Не подтверждено источником, проверяется на тестовом аккаунте перед E2:**
- блокирует ли `customer_email` изменение e-mail;
- какой параметр ограничивает способы в режиме `elements`;
- нужна ли отдельная регистрация `www`.
