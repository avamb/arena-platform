# 45. Перенос билета на другой сеанс того же мероприятия (обмен без возврата)

Статус: черновик для решения владельца, 2026-10-27. Кода нет.
Связанные спеки: 30 (перенос и отмена сеанса, письма), 36 (возвраты), 35 (бот ивент-центра), 37 (веб-ивент-центр), 23 (квоты GA-категорий), 26 (места на схеме), 41 (биллинг), 15 (каталог событий outbox), 17 (MACS).

## 1. Зачем

Покупатель оплатил билет на один сеанс и хочет прийти на другой сеанс того же мероприятия. Деньги он назад не просит.

Живой случай (прод, организатор «Учебный театр», мероприятие «Серебряное копытце»):

- куплено: пятница 18 декабря, 18:00, категория «Ребёнок 4–9 лет + взрослый», 50 EUR;
- нужно: суббота 19 декабря, 12:30, категория «Ребёнок от 6 лет + взрослый», 50 EUR.

Сегодня платформа так не умеет. Обходной путь один: выдать приглашение на новый сеанс (бот, `invite.go`) и отменить старый билет (`POST /v1/tickets/{id}/cancel`, `refund_mode=none`). У обхода четыре проблемы:

1. Приглашение — это не продажа. Отчёт о продажах субботы не видит денег, заказ остаётся на пятнице с отменённым билетом.
2. Покупатель получает два несвязанных письма: «ваш билет отменён» и «вас пригласили».
3. Связи «старый билет → новый билет» нет. Через месяц никто не объяснит, откуда приглашение.
4. Возврат нового билета невозможен: у приглашения нет заказа и оплаты.

## 2. Что делаем (коротко)

Новая операция **«Перенос на другой сеанс»** (обмен). Она работает над оплаченным заказом:

- выбранные билеты заказа переходят на другой сеанс того же мероприятия, в выбранную категорию;
- заказ, его номер, оплата и сумма остаются прежними;
- старый билет перестаёт пускать на вход, у нового — новый штрихкод;
- место в старом сеансе освобождается, место в новом сеансе занимается — в одной транзакции;
- покупатель получает одно письмо «ваш билет перенесён» с новым PDF;
- каждая операция записана в журнал: кто, когда, что на что поменял и почему.

Рекомендация: этап 1 — только **весь заказ целиком** и **только при равной цене** (или если организатор явно отказался от доплаты). Это закрывает живой случай и почти все похожие. Частичный перенос и доплата — отдельные этапы (раздел 13).

## 3. Термины

- **Перенос** (exchange) — операция над заказом: билеты сеанса A становятся билетами сеанса B. Не путать с «переносом сеанса» из спеки 30: там двигается сам сеанс, а здесь — билеты покупателя.
- **Исходный билет** — билет до переноса. После переноса у него статус `transferred`.
- **Новый билет** — билет, выпущенный переносом. Статус `active`.
- **Разница в цене** — цена новой категории на момент переноса минус то, что покупатель заплатил за строку заказа (`order_items.total`).

## 4. Модель данных

### 4.1. Варианты

**Вариант A. Поменять билет «на месте».** У того же `tickets.id` меняем `session_id`, `tier_id`, `seat_key`. Плюсы: мало строк. Минусы, из-за которых вариант отклонён:

- штрихкод EAN-13 и `system_ticket_id` (идентификатор билета в MACS) остаются прежними. MACS уже держит этот билет на сеанс A, и сайт со старым PDF тоже. Старый PDF продолжит сканироваться;
- исчезает история: нельзя показать «был на пятницу»;
- весь код считает, что сеанс билета не меняется (MACS-экспорт, `scan_events`, письма, биллинг).

**Вариант B. Отменить и выпустить заново, со связью (рекомендуется).** Исходный билет получает статус `transferred` (он есть в `tickets_status_check` с миграции 0026, но пока не используется). Новый билет создаётся в том же `checkout_session_id` со следующим `ordinal`. Строка заказа (`order_items`) переставляется на новый билет, новое место и новую категорию. Деньги строки (`unit_price`, `discount`, `charge`, `total`) не меняются.

### 4.2. Новые таблицы (миграция, номер — следующий свободный после 0170)

```sql
-- Одна операция переноса: один запрос организатора над одним заказом.
CREATE TABLE ticket_exchanges (
  id               uuid PRIMARY KEY,
  org_id           uuid NOT NULL REFERENCES organizations(id),
  order_id         uuid NOT NULL REFERENCES orders(id),
  event_id         uuid NOT NULL,
  from_session_id  uuid NOT NULL REFERENCES sessions(id),
  to_session_id    uuid NOT NULL REFERENCES sessions(id),
  reservation_id   uuid NOT NULL REFERENCES reservations(id), -- техническая бронь в сеансе B, см. 5.2
  price_policy     text NOT NULL CHECK (price_policy IN ('equal','waived','keep_difference')),
  difference_minor bigint NOT NULL,  -- сумма разниц по строкам, со знаком
  currency         text NOT NULL,
  reason           text NOT NULL CHECK (char_length(reason) BETWEEN 1 AND 500),
  notify_buyer     boolean NOT NULL,
  idempotency_key  text NOT NULL,
  actor_type       text NOT NULL,
  actor_id         uuid,
  via              text,             -- telegram_bot / event_center_web / admin_web
  letter_state     text NOT NULL DEFAULT 'pending'
                   CHECK (letter_state IN ('pending','sent','failed','skipped','off')),
  email_letter_id  uuid,             -- письмо, привязанное к этой операции (правило 0149)
  created_at       timestamptz NOT NULL DEFAULT now(),
  UNIQUE (org_id, idempotency_key),
  CHECK (from_session_id <> to_session_id)
);

-- Одна строка на каждый перенесённый билет.
CREATE TABLE ticket_exchange_items (
  exchange_id     uuid NOT NULL REFERENCES ticket_exchanges(id),
  order_item_id   uuid NOT NULL REFERENCES order_items(id),
  old_ticket_id   uuid NOT NULL UNIQUE REFERENCES tickets(id),
  new_ticket_id   uuid NOT NULL UNIQUE REFERENCES tickets(id),
  from_tier_id    uuid NOT NULL,
  to_tier_id      uuid NOT NULL,
  from_seat_key   text,
  to_seat_key     text,
  paid_minor      bigint NOT NULL,   -- order_items.total на момент переноса
  new_price_minor bigint NOT NULL,   -- цена категории B на момент переноса
  PRIMARY KEY (exchange_id, old_ticket_id)
);
```

Обе таблицы только пополняются (`UPDATE` разрешён только для `letter_state`/`email_letter_id`). Статический тест по образцу `email_letters_retention_test.go` запрещает `DELETE`. Билет может переноситься несколько раз: тогда цепочка `old → new → newer` читается по `ticket_exchange_items`.

Поле `tickets.exchanged_from_ticket_id` не добавляем: `scanTicketRow` кормят десятки запросов, расширение строки — известная ловушка (AGENTS.md, «hand-written gen wrappers share scan helpers»). Связь читается из `ticket_exchange_items`.

### 4.3. Что меняется в существующих строках

| Строка | Что делает перенос |
|---|---|
| `tickets` (исходный) | `status = 'transferred'`, `cancelled_at = now()`, `cancellation_reason = 'exchanged'`. Возвратные поля не трогаем. |
| `tickets` (новый) | Новая строка: тот же `checkout_session_id`, `order_id`, `holder_email`, `holder_name`, `vip`; новый `session_id`, `tier_id`, `seat_*`, `ordinal = max+1`, новый `system_ticket_id`. |
| `order_items` | `ticket_id`, `session_seat_id`, `tier_id` → новые. Деньги строки не меняются. |
| `orders` | Этап 1 (весь заказ): `session_id` → B. `event_id` тот же. `status`, суммы, `paid_at` не меняются. |
| `ticket_credentials`, `barcodes` | У исходного билета отзываются (`RevokeTicketArtifactsTx`). Новому выпускается EAN-13 через `mint.EAN13` (`mintTicketEAN13s`). |
| `delivery_jobs` | Новая строка для нового билета через обычный `InsertDeliveryJob`; письмо собирает операция (раздел 8). |

## 5. Места и квоты

### 5.1. Порядок блокировок

Одна транзакция. Порядок обязателен (AGENTS.md: сначала `sessions`, потом `inventory_ledger`):

1. `IncrementSessionSeatStatusVersion` для обоих сеансов **в порядке возрастания `session_id`**. Иначе два встречных переноса (A→B и B→A) дадут взаимную блокировку (40P01).
2. `LockOrderForUpdate` заказа — вторым шагом. Два переноса одного заказа выстраиваются в очередь, повторное решение читается под блокировкой.
3. Освобождение мест в A, затем занятие мест в B, затем `inventory_ledger` обоих сеансов.

Всё тело оборачивается в `txretry` (как `retryOnSerializationFailure`): при 40P01/40001 транзакция начинается заново целиком.

### 5.2. Сеанс A (освобождение)

Тот же код, что у отмены: `ReleaseCancelledTicketInventoryTx` (GA-место возвращается в свою категорию по `seat_key` вида `ga|t…`, место на схеме — через `ReleaseSoldSessionSeat`) и `RestoreSoldCapacity`. Новый код не пишем — выносим из `CancelTicketTx` общую часть.

### 5.3. Сеанс B (занятие)

Проданное место без брони (`reservation_id IS NULL`) платформа считает «проданным во внешней системе» (`sold_upstream`, AGENTS.md). Поэтому перенос создаёт **техническую бронь** в сеансе B: `reservations` с `channel_id` и `org_id` заказа, `state = 'converted'` сразу. Места выделяются через существующие примитивы:

- GA: `AllocateGAUnitsTx` по категории B (в нём проверка «места есть»; категория владеет местами, NULL-категория не продаётся), затем перевод `held → sold` тем же запросом, что использует конвертация брони. `seat_key` нового билета — ключ выделенного места.
- Схема зала: место выбирает организатор (раздел 9). Проверка «место свободно», захват `FOR UPDATE` в порядке `seat_key` (как `CreateSeatedHold`), перевод в `sold`.
- `inventory_ledger` B: `capacity_sold + n` на уровне сеанса (как при конвертации брони с местами).

### 5.4. Ворота продаж

Ворота категории (`CheckCategorySellable`: открыта, окно продаж, конец продаж сеанса, сеанс не отменён) **проверяются, но организатор может их обойти**. Причина: перенос часто нужен, когда продажи на сеанс B уже закрыты для покупателей («продажи закрыты за час, а покупатель просит на завтра»). Правила:

- сеанс B `cancelled` — всегда отказ (`409 exchange.target_session_cancelled`);
- сеанс B уже начался — отказ (`409 exchange.target_session_started`);
- категория B закрыта или вне окна продаж, или прошёл конец продаж — ответ `409 exchange.target_not_on_sale` с `details.reason`; повтор с `override_sales_gate: true` проходит. Бот показывает это как вопрос «Продажи на этот сеанс закрыты. Всё равно перенести?»;
- мест нет — отказ всегда (`409 exchange.target_sold_out`). Перенос не создаёт мест.

### 5.5. Валюта

Валюта категории B должна совпадать с `orders.currency`. Иначе отказ `422 exchange.currency_mismatch`. Обмен валют не делаем.

## 6. Разница в цене

`paid` = `order_items.total` строки (то, что покупатель заплатил с учётом промокода и сервисного сбора). `new` = текущая цена категории B (`priceresolve`, с учётом окна цены), без промокода.

### 6.1. Варианты

| Случай | Вариант 1 | Вариант 2 | Вариант 3 |
|---|---|---|---|
| `new == paid` | Переносим, денег нет. | — | — |
| `new > paid` (дороже) | Организатор явно отказывается от доплаты (`waived`) и переносит. | Покупатель доплачивает по ссылке на оплату (новая hosted-оплата «доплата к заказу»). Перенос выполняется после оплаты. | Отказ: «выберите категорию той же цены». |
| `new < paid` (дешевле) | Переносим, разницу не возвращаем (`keep_difference`), письмо об этом не пишет. | Переносим и сразу запускаем частичный возврат разницы через движок возвратов (спека 36), билет остаётся действительным. | Отказ. |

### 6.2. Рекомендация

- **Этап 1:** равная цена — без вопросов. Дороже — только с явным `waived` (в боте: «Покупатель доплачивать не будет. Перенести бесплатно?»). Дешевле — `keep_difference` с явным подтверждением («Разница 10 EUR останется у вас. Если хотите вернуть её — сделайте возврат части суммы после переноса»).
- **Не сравниваем с ценой «сейчас», если она ниже из-за скидки покупателя.** Сравниваем с `order_items.total`: так 50 EUR со скидкой 10 % при переносе на категорию за 50 EUR — это «дороже на 5 EUR», и организатор видит это и решает сам.
- **Этап 3 (по решению владельца):** доплата по ссылке. Нужен новый платёжный поток «дополнительный платёж к заказу» (`payment_intents` с ролью `supplement`, отдельное письмо со ссылкой, бронь места B на время оплаты, сумма в `orders.total` растёт). Это большая работа и отдельная спека.
- **Возврат разницы при «дешевле».** Движок возвратов уже умеет возврат части суммы без отмены билета (`cancel_tickets=false`), но бот и веб такого режима не показывают (они всегда отменяют билеты). Этап 2 добавляет кнопку «Вернуть разницу» прямо в итог переноса и вызывает `CreateBatch` с `cancel_tickets=false` и суммой разницы. Возврат идёт по НОВОМУ билету (после переноса `order_items.ticket_id` указывает на него).

Биллинг платформы при переносе не меняется: за продажу уже начислено (раздел 10.3).

## 7. Штрихкод, вход, MACS, сайты

### 7.1. Штрихкод

Исходный билет: отзываем учётные данные и штрихкоды (`RevokeTicketArtifactsTx`). Сканер arena отвечает «билет недействителен». Новый билет: новый EAN-13 через `mint.EAN13` (уникален по всем источникам штрихкодов).

### 7.2. Что нельзя перенести

- Билет, по которому уже был вход (то же правило, что в `refunds/scanned.go`: `used_at`, принятый скан, отсканированный штрихкод). Отказ `409 exchange.ticket_scanned`. Без исключений на этапе 1.
- Билет на удержании проверки (`review_hold`), билет не `active`, билет с возвратом в работе (живая строка `refunds` с `cancel_ticket`). Отказ `409 exchange.ticket_not_exchangeable` с причиной.
- Заказ не `paid` / `partially_refunded`. Приглашение без заказа — этап 4 (у приглашения нет денег, его проще отозвать и выдать заново).
- Сеанс B другого мероприятия — `422 exchange.other_event`. Перенос на другое мероприятие — не в этой спеке.

### 7.3. События outbox и MACS

После коммита пишем одно новое событие на билет: `v1.ticket.exchanged` (ресурс `ticket`, id исходного билета; `data`: `old_ticket_id`, `new_ticket_id`, `order_id`, `from_session_id`, `to_session_id`, `exchange_id`). Событие добавляется в спеку 15 в том же PR (правило каталога).

MACS (`internal/platform/macs`):

- исходный билет → `ticket.refunded` (MACS знает только «действителен / возвращён»; `TicketStatus` уже отдаёт 3 для любого не-`active`, комментарий упоминает `transferred`);
- новый билет → `order.paid` с одним билетом (тот же синтетический конверт, что сейчас для приглашений через `v1.scanner.ticket.issued`).

Порядок важен: сначала старый закрывается, потом новый открывается. Проверить на заглушке MACS (`macs/stub`) и с живым MACS Vino (решение В-1).

### 7.4. Заказы, проданные сайтом (WordPress, шлюз Bil24)

Сайт хранит свою копию билетов и пишет покупателю сам. Правило то же, что у переноса сеанса и повторной отправки: заказ с `orders.source = 'bil24_gateway'` или канал с активным подписчиком `bil24_wp` (`sessionchange.ChannelHasSite`) → `409 exchange.seller_site_order`, ничего не меняется. Текст: «Этот заказ продал сайт. Перенос делается на сайте». Протокол Bil24 обмена не знает. Поддержка сайтов — отдельный этап после плагинов (спека 31).

## 8. Письмо покупателю

Новый вид письма `exchange` (по образцу `change` из спеки 30, все 7 языков: en, ru, cs, he, es, de, fr). Одно письмо на операцию:

- «Ваш билет перенесён»: было — сеанс, время, категория; стало — сеанс, время, категория, место; номер заказа;
- новый PDF во вложении (тот же рендер, что у `ticket.deliver`, со всеми подсказками презентации);
- строка «старый билет больше не действует»;
- текст организатора (необязательно), формат как у сообщения переноса сеанса (`session_message`, `richtext`);
- блок «вход с», контакты организатора и примечание про «Отписаться» — по общим правилам писем.

Механика: worker-задача `ticket.exchange_email` ставится в той же транзакции (`worker.EnqueueInTx`). Письмо отправляется через `delivery.sendRecorded` и записывается в `email_letters` с источником операции (`ticket_exchanges.email_letter_id`, правило 0149: подтверждает письмо только его собственный источник). `delivery_jobs` нового билета помечается отправленным этим же письмом, чтобы `ticket.deliver` не прислал второй, отдельный билет. В карточке заказа письмо видно в `letters[]` (вид `exchange`).

`notify_buyer = false` — письма нет (`letter_state = 'off'`), PDF доступен для повторной отправки (EC-13).

## 9. Интерфейс в боте

На карточке заказа (`eventbot/order_card.go`), только в личном чате, для владельца и менеджера (право `ticket.update`, оба его имеют с миграции 0129), только для оплаченного заказа, у мероприятия которого больше одного живого сеанса. Кнопка «🔁 Перенести на другой сеанс». Нажатия `or:m:*` (префикс свободен, внутри Orders — диалог заказов не закрывается). Состояние — `bot_dialogs` вида `exchange`, шаг сохраняется до ответа (`withSaveBeforeReply`), запись в `dialogOwners`.

Шаги:

1. **Какие билеты.** Этап 1: все действующие билеты заказа (экран показывает список, выбора нет). Этап 2: отметки, по умолчанию ничего не отмечено.
2. **Сеанс.** Список будущих живых сеансов того же мероприятия, кроме текущего, с датой по часам площадки и числом свободных мест. Пагинация через `paging.go`.
3. **Категория.** Для каждого билета (этап 1 — одна категория на все, если все билеты одной категории; иначе по билету): категории сеанса B той же валюты, с ценой и свободными местами. Совпадение по имени помечено «как было».
4. **Место** — только для зала со схемой: ряд и место текстом или кнопкой «любое свободное» (этап 1 допускает только «любое свободное» в той же зоне; выбор на схеме — веб, этап 2).
5. **Разница в цене** (если есть) — вопрос из раздела 6.2.
6. **Письмо** — флажок по образцу возвратов: «☑ Отправить письмо покупателю» / «☐ Не отправлять письмо покупателю».
7. **Причина** — обязательный текст, до 500 символов.
8. **Итог** — было → стало по каждому билету, разница и что с ней, письмо. Кнопки «Перенести» и «Отмена».

Подтверждение — **одно нажатие** итоговой кнопки, без набираемого слова. Почему: деньги не двигаются, операцию можно повторить в обратную сторону, итог показан целиком. Ключ идемпотентности (`tg-<uuid>`) создаётся при первом показе итога и меняется при любой правке выбора — как у возврата. Кнопка «Перенести» несёт первые 12 символов ключа и срабатывает только на том итоге, который она называет. Если сервер отвечает, что продажи на сеанс закрыты (раздел 5.4), бот показывает вопрос и повторяет с `override_sales_gate`.

Ответ: «Готово. Билет №… перенесён на суббота, 19 декабря, 12:30. Новый номер билета №…. Письмо покупателю отправлено». Карточка заказа после переноса показывает новые билеты и строку «Перенесён с …» (из `ticket_exchange_items`).

Веб-ивент-центр (спека 37): тот же поток на карточке заказа, строка в матрице паритета, «двойник» в `tests/smoke/live`. Шаг выбора места на схеме — в вебе.

## 10. Отчёты и биллинг

### 10.1. Сводка сеанса и мероприятия

- Продажа остаётся продажей: число заказов и сумма мероприятия не меняются.
- Этап 1 переносит весь заказ, поэтому `orders.session_id` = B. Деньги и заказ в сводках сеанса (`session_summary.sql` считает по `o.session_id`) **переезжают** на сеанс B. Это честно: место в B занято платным покупателем. Сводка категорий (`order_items.total` по `tier_id`) тоже переезжает.
- Посещаемость (`tickets.session_id`, вход) — на B.
- В сводке сеанса добавляется строка «Перенесено: сюда N, отсюда M» (из `ticket_exchange_items`), чтобы организатор понял, почему у пятницы стало меньше денег, чем было вчера.
- CSV продаж: исходный билет в выгрузке не появляется (он не `active`); у нового билета колонка «Перенесён с» (дата исходного сеанса). Колонку добавить в конец (потребители читают по заголовку, но не ломаем порядок).

**Решение владельца (Р-1):** деньги следуют за заказом (рекомендация) или остаются на исходном сеансе, а на B переезжает только посещаемость. Второй вариант требует переписать запросы сводки с `o.session_id` на `tickets.session_id` — больше работы.

### 10.2. Перенос сеанса и отмена сеанса (спека 30)

- Запрос «заказы сеанса для писем» (`sessionchange.go`, строка с `JOIN tickets t ON t.order_id = o.id AND t.session_id = o.session_id`) на этапе 1 работает без правок: у перенесённого заказа `orders.session_id` = B. **На этапе 2 (частичный перенос) его надо перевести на `tickets.session_id`**, иначе отмена сеанса B не напишет владельцу перенесённого билета. Это блокер этапа 2.
- Отмена сеанса A после переноса: у исходного билета статус `transferred`, письма нет. Правильно.

### 10.3. Биллинг платформы (спека 41)

- Новое событие `ticket_sold` не появляется: продажа одна. `billable_events` пополняются только, правок нет.
- **Проблема:** при отмене сеанса A движок `billing.rate` сторнирует все `ticket_sold` сеанса A, включая проданный там, но перенесённый билет. Платформа вернула бы организатору сбор за билет, который использован на сеансе B. Решение: новый вид биллингового события `ticket_exchanged` (журнальное, 0 EUR) с `from_session_id`/`to_session_id`, а сторно при отмене сеанса пропускает продажи, по которым есть `ticket_exchanged` с уходом из этого сеанса. Сборщик `billing.collect` получает восьмой источник (`ticket_exchange_items`).
- Сверка `billing.reconcile`: проверка «действующий билет без события» должна находить продажу по `order_items.ticket_id` (новый билет), а не по исходному билету. Добавить тест.

### 10.4. Уведомления о продажах (Telegram, salesnotify)

Новое сообщение не обязательно. Этап 1: не отправляем. По желанию владельца — короткое «🔁 Заказ №… перенесён с … на …» в группу организации.

## 11. API

```
GET  /v1/organizations/{org_id}/orders/{order_id}/exchange-options
POST /v1/organizations/{org_id}/orders/{order_id}/exchanges        (Idempotency-Key обязателен)
GET  /v1/organizations/{org_id}/orders/{order_id}/exchanges        (история операций заказа)
```

Право `ticket.update`, заказ загружается внутри организации пути (чужой — `404 orders.not_found`), ключ API организации допускается (как у повторной отправки), суперадмин — с `X-Admin-Reason`. Маршруты имеют `{org_id}` плюс дочерний id → строка в таблице org-isolation sweep.

`exchange-options` отвечает: `route` (`arena` / `seller_site` / `not_paid`), билеты заказа с признаком `exchangeable` и причиной, список сеансов того же мероприятия (без текущего, будущие, не отменённые) с категориями: цена сейчас, валюта, свободно мест, `on_sale`, причина закрытия, `seated`. Для каждого билета — `paid_minor`. Деньги клиент не считает: разницу по паре (билет, категория) отдаёт сервер.

`POST .../exchanges`:

```json
{
  "to_session_id": "uuid",
  "items": [{"ticket_id": "uuid", "to_tier_id": "uuid", "seat_key": "необязательно"}],
  "price_policy": "equal | waived | keep_difference",
  "override_sales_gate": false,
  "notify_buyer": true,
  "reason": "Покупатель попросил субботу",
  "message": "необязательно", "message_format": "text | art"
}
```

Ответ 201: операция с `items` (старый → новый билет, номера, места) и `letter_state`. Повтор с тем же ключом и тем же телом → 200 с первым ответом, `replayed: true`; тот же ключ с другим телом → `409 exchange.idempotency_key_reused`.

Коды отказов (все в `API_ERROR_STEMS` веба и в каталогах бота): `exchange.seller_site_order`, `exchange.order_not_paid`, `exchange.ticket_scanned`, `exchange.ticket_not_exchangeable`, `exchange.other_event`, `exchange.same_session`, `exchange.target_session_cancelled`, `exchange.target_session_started`, `exchange.target_not_on_sale`, `exchange.target_sold_out`, `exchange.seat_taken`, `exchange.currency_mismatch`, `exchange.price_policy_required` (цена отличается, а политика `equal`), `exchange.partial_not_supported` (этап 1, не все билеты заказа), `exchange.idempotency_key_reused`.

`openapi.yaml` + `types_gen.go` + TS-клиент в том же PR. `price_policy` и `route` — простые строки с перечнем значений в описании, без inline `enum` (ловушка переименования констант, AGENTS.md).

`GET /v1/organizations/{org_id}/orders/{order_id}` (карточка) получает `exchanges[]`: кратко, по операциям (дата, было → стало, кто). Поле аддитивное.

## 14. Тесты

Интеграционные (тег `integration`, своя организация, уникальные значения для глобальных индексов):

1. GA, равная цена, весь заказ из одного билета (живой случай «Копытца»): заказ тот же, сумма та же; старый билет `transferred`, штрихкод отозван; новый `active` с новым EAN-13; место A свободно и в своей категории, место B продано и принадлежит категории B с бронью-операцией; `inventory_ledger` обоих сеансов сходится; `order_items` указывает на новый билет; одно письмо в очереди.
2. Повтор с тем же ключом — `replayed`, ничего не записано второй раз; тот же ключ с другим телом — 409.
3. Два встречных переноса A→B и B→A в 16 горутинах — нет 40P01 наружу, все места сходятся.
4. Перенос против покупки последнего места B — ровно один выигрывает, второй получает `target_sold_out` / 409 продажи.
5. Отказы: отсканированный билет, заказ сайта, неоплаченный заказ, отменённый сеанс B, начавшийся сеанс B, другая валюта, другое мероприятие, «дороже» без `waived`, частичный выбор на этапе 1.
6. Ворота: закрытая категория → 409 `target_not_on_sale`; с `override_sales_gate` → проходит.
7. Зал со схемой: место B выбрано, занято другим — `seat_taken`, ничего не изменено.
8. Чужая организация (владелец, менеджер, ключ API организации B) — 404 на всех трёх маршрутах, строки A не изменились. Агент — 403.
9. Возврат после переноса: `refund-options` показывает новый билет с `paid_minor` исходной строки; возврат отменяет новый билет и освобождает место B.
10. Отмена сеанса A после переноса — письма перенесённому покупателю нет; отмена сеанса B — письмо есть.
11. Биллинг: отмена сеанса A не сторнирует сбор перенесённой продажи; сверка чистая.
12. MACS: заглушка получает `ticket.refunded` старого и `order.paid` нового, в этом порядке.
13. Письмо: 7 языков рендерятся, PDF нового билета во вложении, `email_letters` привязано к операции, `ticket.deliver` второго письма не шлёт.

Модульные: `Plan` (таблица случаев цены и проверок), тексты бота en/ru/es (`TestEventBot_LocaleBundleHasEveryKey`, стиль текстов), шаблоны письма (`templates_*_test.go`, без ссылки отписки).
