## 1. Что строим и почему так

Три задачи с разными зрителями и разными правилами по личным данным:

| № | Задача | Кто смотрит | Чьи действия | Личность |
|---|---|---|---|---|
| 1 | **Воронка продаж мероприятия**: от просмотра до оплаты, по источникам | организатор в ивент-центре | покупатели | никакой: только дневные счётчики |
| 2 | **Путь лида до организатора**: письмо или органика → сайт (страницы, статьи, время) → заявка → одобрение → первая продажа → оборот; активность видна в карточке CRM | владелец и Марина в Twenty | посетители arenasoldout.com, заявители, организаторы | контакт CRM / пользователь платформы |
| 3 | **Где спотыкаются в ивент-центре и боте** — для постоянного улучшения UX | команда | организаторы и их менеджеры | пользователь платформы |

Три решения, которые нельзя переигрывать в прогоне:

1. **Всё у нас.** Сбор, хранение и обработка — в арене (Go + Postgres), без сторонних трекеров и без передачи
   событий третьим лицам. Витрины: экран ивент-центра (задача 1), поля и хроника Twenty через n8n (задача 2),
   дашборды и недельная сводка (задача 3).
2. **Покупатель не получает никакого идентификатора.** Задача 1 — только агрегаты по дню, без cookie и без
   хранения на устройстве, по той же формуле, что маяк hosted-страницы (`pagestats`). Наш скрипт в виджете на
   чужих сайтах не узнаёт людей, поэтому не меняет баннеры согласия клиентов.
3. **Вехи организатора выводятся из бизнес-таблиц, а не дописываются в денежные пути.** «Первое мероприятие»,
   «подключил оплату», «первая продажа», оборот считаются фоновой обработкой из `events`, `orders`,
   `payment_provider_configs`, `onboarding_*`. В транзакции оплаты, заказа и выпуска билетов аналитика ничего не
   пишет. Скрипты и приёмники пишут только поведение (просмотры, шаги, ошибки, время).

## 3. Модель личности и согласие

| Поверхность | Идентификатор | Где хранится на устройстве | Нужно согласие |
|---|---|---|---|
| Виджет, страница билетов, hosted-страница | нет | ничего | нет |
| arenasoldout.com без согласия | одноразовый id просмотра страницы (только в памяти вкладки, для подсчёта времени) | ничего | нет |
| arenasoldout.com после согласия «Аналитика» | `aid` — случайный id посетителя | first-party cookie `aso_aid`, 13 месяцев | да |
| Переход из нашего письма | `cid` — код контакта CRM в ссылке | — (только сам заход) | нет для записи клика, да для дальнейшего пути |
| Ивент-центр | `user_id` из JWT, сервер берёт его из токена, не из тела | ничего | нет; пункт в политике и условиях, отказ в профиле (вопрос 4) |
| Бот | `user_id` связанного пользователя; незнакомцу (заявка через бота) — `tg:` + sha256 от Telegram id с секретом | — | нет; пункт в политике |

**Склейка.** Таблица `analytics_identities` хранит пары «вид → значение» (`aid`, `cid`, `email_sha256`, `user`,
`tg`) и человека, которому они принадлежат. События пишутся с тем идентификатором, который был у источника, а
человек определяется при обработке через эту таблицу, поэтому слияние двух людей — одна строка UPDATE, без
перезаписи событий. Склейка происходит:

- `cid` + `aid` на одном заходе: клик из письма у посетителя с согласием, либо новый посетитель, принявший
  баннер на той же странице (сайт держит `cid` в памяти страницы и повторяет его один раз в первой пачке с `aid`).
  Сервер пишет `email_click` с `props.aid` (ставит сам, от клиента не принимает), не чаще одного на пару (`cid`, `pv`).
- `aid` + e-mail при старте заявки на сайте (заявка получает `aid` в теле, сервер добавляет `email_sha256`);
- e-mail заявки + `user` при одобрении (`provisioning.CreateWorkspace` знает обоих);
- `tg` + e-mail при подтверждении кода в боте (APP-11).

**Коды контактов.** `analytics_contact_codes (code, twenty_person_id, created_at)`: 10 символов из алфавита спеки 43
(`abcdefghjkmnpqrstuvwxyz23456789`), `crypto/rand`, идиома «INSERT … ON CONFLICT DO NOTHING, перерисуй». n8n
запрашивает коды пачкой перед отправкой рассылки и дописывает `?cid=<code>` к ссылкам на наш сайт. Ссылка остаётся
на нашем домене, без переписывания через Brevo, поэтому не выдаёт массовую рассылку (совет спеки 44 §5 выключать
трекинг кликов Brevo в «личных» письмах остаётся в силе). Сайт после чтения убирает `cid` из адресной строки
(`history.replaceState`), чтобы его не пересылали дальше.

**Без согласия на сайте** записывается только факт захода по `cid` (контакт кликнул по письму, страница входа,
время). Дальнейший путь такого посетителя считается анонимно и к контакту не привязывается.

## 4. Сбор

### 4.1 Скрипт `arena-track` (около 2 КБ, без зависимостей)

Один пакет для сайта и ивент-центра (`packages/arena-track` в монорепозитории, копия собирается в arena-site).
Возможности:

- просмотр страницы или экрана: путь (для ивент-центра — шаблон маршрута `/events/:id`, никогда не сами id),
  заголовок, язык, домен перехода, UTM;
- **активное время**: идёт, пока вкладка видна и была активность за последние 30 секунд; отправляется при
  `pagehide`/`visibilitychange` через `navigator.sendBeacon`;
- глубина прокрутки 25/50/75/100 % (только сайт);
- клики по элементам с атрибутом `data-track="<имя>"`; без атрибута клики не пишутся;
- ошибки, показанные пользователю (ивент-центр: код ошибки API и экран);
- «яростный клик»: три и больше кликов по одному элементу за секунду (ивент-центр);
- шаги сценариев: `flow_step` с именем сценария и шага, которые размечает код экрана.

Очередь в памяти, отправка пачкой раз в 5 секунд и при уходе со страницы. Никаких значений полей ввода, текстов,
e-mail и id сущностей в свойствах.

### 4.2 Приёмники

| Маршрут | Кто шлёт | Аутентификация | Лимиты |
|---|---|---|---|
| `POST /v1/t` | arenasoldout.com | нет; CORS только для origin сайта | тело ≤ 16 КБ, ≤ 50 событий, 120 запросов/мин с IP |
| `POST /v1/me/t` | ивент-центр | JWT; `user_id` и `org_id` берутся из токена и пути экрана, тело их не задаёт | то же, 300/мин на пользователя |
| `POST /v1/public/funnel` | виджет, страница билетов, hosted-страница | нет; контекст — `feed_token` + `event_id` (виджет) или slug-пара (страница), проверяется, что мероприятие опубликовано | как у маяка `pagestats` |

**Контракт тела (общий для скрипта и приёмников, менять только вместе):**

```jsonc
// POST /v1/t  (сайт)
{
  "aid": "a_7Hk2…",          // необязательно: только после согласия; 8–40 символов [A-Za-z0-9_-]
  "cid": "x7k2qpm3ab",       // необязательно: только в первой пачке после захода по ссылке из письма
  "pv":  "p_Q9…",            // id текущего просмотра страницы, живёт в памяти вкладки
  "events": [
    { "name": "page_view", "at": "2026-11-01T10:00:00Z", "props": { "path": "/pricing", "lang": "ru" } }
  ]
}
// POST /v1/me/t  (ивент-центр; пользователь — из JWT)
{
  "org_id": "uuid",          // необязательно: организация текущего экрана; сервер берёт её, только если
                             // пользователь в ней состоит (или суперадмин), иначе пишет NULL
  "pv": "p_…",
  "events": [ { "name": "flow_step", "at": "…", "props": { "flow": "event_create", "step": "venue" } } ]
}
// POST /v1/public/funnel  (виджет, страницы; без личности)
{
  "feed_token": "…", "event_id": "uuid",          // виджет
  // или "page": { "slug": "…", "event_slug": "…" } // hosted-страница / страница билетов
  "session_id": "uuid",                            // необязательно
  "step": "view",                                  // view | session_open | seats_chosen
  "surface": "widget",                             // widget | hosted_page | tickets_page
  "utm_source": "…", "utm_campaign": "…"
}
```

Скрипт без настроенного адреса приёмника (`endpoint` пуст) ничего не шлёт и не падает: фронтенды можно
сливать раньше бэкенда.

Общие правила приёмников: имя события и его свойства проверяются по словарю (раздел 5), неизвестное событие
отбрасывается целиком, неизвестное свойство — молча; строки обрезаются до 200 символов; время события берётся
сервером (клиентское хранится отдельно для порядка внутри пачки и отбрасывается, если расходится больше чем на
сутки). Ответ всегда `204` и без тела, кроме `400` на нечитаемый JSON, — приёмник ничего не рассказывает о
причинах отказа. Подозрительные User-Agent помечаются флагом `suspect` по правилу `pagestats`.

Публичные маршруты за Cloudflare: при отказе — `503`, никогда `502` (правило AGENTS.md).

### 4.3 Серверная запись

Пакет `internal/platform/analytics`: `Track(ctx, Event)` кладёт событие в буферизованный канал (10 000 событий),
фоновый писатель сбрасывает пачку `COPY`-ом раз в 2 секунды или по 500 событий. Переполнение — событие
отбрасывается и считается в `arena_analytics_dropped_total`; запрос пользователя никогда не ждёт аналитику и не
падает из-за неё. Писатель живёт в процессах arena-api и arena-bot (бот уже держит пул БД для `bot_dialogs`).
Внутри открытой транзакции `Track` не обращается к пулу: он только кладёт в канал.

### 4.4 Бот

В `handleUpdate` после ограничителя частоты — одно событие `bot_update` (вид: сообщение / нажатие / команда;
префикс callback до первого `:`; текущий шаг мастера или диалога). В мастере (`Wizard.Apply`) — `wizard_step` при
каждом переходе (откуда, куда, сколько секунд на шаге) и `wizard_input_error` с кодом причины (например,
`date_unparsed`, `price_invalid`), без введённого текста. «Назад», «Отмена», выбор «удалить черновик»,
напоминание и удаление брошенного черновика (`draft_sweep.go`) — отдельные события.

## 6. Хранение (одна миграция на этап A1, вторая на A7)

Схема `analytics` в той же базе, а не отдельная база: миграции goose, бэкапы (`ops/backup`) и восстановление
работают без изменений, а с денежными таблицами она не пересекается. Объёмы малые (тысячи визитов на сайт,
десятки пользователей ивент-центра), разбиение по месяцам — ради дешёвого удаления старого, не ради скорости.

```sql
CREATE SCHEMA analytics;

CREATE TABLE analytics.events (            -- сырые события, разделы по месяцам
    id          bigint GENERATED ALWAYS AS IDENTITY,
    at          timestamptz NOT NULL,
    surface     text NOT NULL,             -- site | event_center | bot
    name        text NOT NULL,
    id_kind     text NOT NULL,             -- aid | cid | user | tg | anon
    id_value    text NOT NULL,             -- для anon: id просмотра страницы
    org_id      uuid,                      -- ивент-центр и бот: текущая организация
    props       jsonb NOT NULL DEFAULT '{}',
    suspect     boolean NOT NULL DEFAULT false,
    PRIMARY KEY (at, id)
) PARTITION BY RANGE (at);

CREATE TABLE analytics.people (
    id              uuid PRIMARY KEY,
    twenty_person_id text UNIQUE,
    user_id         uuid UNIQUE REFERENCES public.users(id) ON DELETE SET NULL,
    first_touch     jsonb NOT NULL DEFAULT '{}',   -- source, medium, campaign, ref_host, at
    last_touch      jsonb NOT NULL DEFAULT '{}',
    created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE analytics.identities (
    kind      text NOT NULL,               -- aid | cid | email_sha256 | user | tg
    value     text NOT NULL,
    person_id uuid NOT NULL REFERENCES analytics.people(id) ON DELETE CASCADE,
    seen_at   timestamptz NOT NULL,
    PRIMARY KEY (kind, value)
);

CREATE TABLE analytics.contact_codes (
    code             text PRIMARY KEY,
    twenty_person_id text NOT NULL,
    created_at       timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX contact_codes_person_idx ON analytics.contact_codes (twenty_person_id);

CREATE TABLE analytics.sessions (          -- строит обработка
    id              uuid PRIMARY KEY,
    person_id       uuid REFERENCES analytics.people(id) ON DELETE CASCADE,
    surface         text NOT NULL,
    started_at      timestamptz NOT NULL,
    ended_at        timestamptz NOT NULL,
    pages           int NOT NULL,
    engaged_seconds int NOT NULL,
    entry           jsonb NOT NULL DEFAULT '{}'   -- путь входа и источник
);

CREATE TABLE analytics.profiles (          -- строит обработка, читает n8n
    person_id          uuid PRIMARY KEY REFERENCES analytics.people(id) ON DELETE CASCADE,
    stage              text NOT NULL,      -- lead | applicant | organizer | selling
    last_seen_at       timestamptz,
    visits_30d         int NOT NULL DEFAULT 0,
    engaged_minutes_30d int NOT NULL DEFAULT 0,
    articles           jsonb NOT NULL DEFAULT '[]',  -- прочитанные статьи, последние 20
    milestones         jsonb NOT NULL DEFAULT '{}',  -- веха -> время
    activity_score     int NOT NULL DEFAULT 0,
    changed_at         timestamptz NOT NULL
);
CREATE INDEX profiles_changed_idx ON analytics.profiles (changed_at);

CREATE TABLE analytics.flow_daily (        -- шаги сценариев ивент-центра и бота
    day date NOT NULL, surface text NOT NULL, flow text NOT NULL, step text NOT NULL,
    entered int NOT NULL, left_here int NOT NULL, errors int NOT NULL,
    median_seconds int,
    PRIMARY KEY (day, surface, flow, step)
);

CREATE TABLE analytics.state (             -- курсоры обработки, как ops_watchdog_state
    key text PRIMARY KEY, value jsonb NOT NULL, updated_at timestamptz NOT NULL
);
```

Хранение: сырые события 13 месяцев (раздел удаляется целиком), сессии 25 месяцев, профили — пока жив контакт или
пользователь, счётчики воронки покупателей 24 месяца (как `event_page_stats`).

`analytics.people.user_id` — единственная ссылка из схемы `analytics` в бизнес-таблицы; бизнес-таблицы на схему
`analytics` не ссылаются никогда.

### 6.1 Счётчики воронки покупателей (этап A7)

```sql
CREATE TABLE public.sales_funnel_daily (
    org_id       uuid NOT NULL,
    event_id     uuid NOT NULL,
    session_id   uuid,                     -- NULL для шагов до выбора сеанса
    day          date NOT NULL,
    step         text NOT NULL,            -- view | session_open | seats_chosen
    surface      text NOT NULL,            -- widget | hosted_page | tickets_page
    utm_source   text NOT NULL DEFAULT '',
    utm_campaign text NOT NULL DEFAULT '',
    hits         bigint NOT NULL DEFAULT 0,
    suspect_hits bigint NOT NULL DEFAULT 0,
    PRIMARY KEY (event_id, day, step, surface, utm_source, utm_campaign, session_id) -- через COALESCE-индекс
);
```

Точное выражение первичного ключа с nullable `session_id` (уникальный индекс по `COALESCE`) решает исполнитель A7.
Таблица в схеме `public`, рядом с `event_page_stats`, со ссылкой на `events (id, org_id)` и `ON DELETE CASCADE`;
правила очистки UTM, потолок пар в день и дедупликация — из `pagestats`. Серверные шаги (`checkout_start`,
`payment_open`, `paid`) не пишутся сюда: их считает запрос по `checkout_sessions`, `payment_intents`, `orders` и
`attribution` в момент показа.

## 7. Обработка: задача `analytics.rollup`

Самопланирующаяся задача arena-worker, раз в час (курсор в `analytics.state`):

1. **Склейка**: новые пары из событий (`cid`+`aid`, e-mail заявки, одобрение, подтверждение в боте) →
   `identities`; слияние людей — перенос идентичностей на старшего, младший удаляется.
2. **Сессии**: события одного идентификатора с разрывом больше 30 минут — новая сессия.
3. **Касания**: первое и последнее по `utm_*`, `ref_host`, `email_click`; органика — заход без UTM с поисковика или
   без домена перехода.
4. **Вехи** из бизнес-таблиц по `user_id` и организации пользователя (раздел 1, решение 3).
5. **Профили**: `last_seen_at`, визиты и минуты за 30 дней, прочитанные статьи (страница раздела статей, где
   `engaged ≥ 30 с` и прокрутка ≥ 75 %), этап, индекс активности; `changed_at` обновляется только при
   изменении, чтобы n8n забирал разницу.
6. **Сценарии**: `flow_daily` по `flow_step` / `wizard_step` / `wizard_exit` / `ui_error`.

**Индекс активности (v1, веса настраиваются в Go-таблице):** визит 1, прочитанная статья 3, страница цен или
калькулятор 5, клик из письма 2, начатая заявка 10, отправленная заявка 20; затухание вдвое за 14 дней. Формула
видна в карточке как «почему такая цифра» — индекс должен объясняться одной строкой.

## 11. Приватность и защита

- В событиях нет e-mail, телефонов, имён, текстов сообщений, значений полей и id сущностей. Тест словаря
  проверяет, что ни одно разрешённое свойство не называется `email`, `phone`, `text`, `value`, а `name` разрешён
  только у `click` и `rage_click` (метка `data-track` из кода, не имя человека, `[a-z0-9_.-]`, ≤ 64).
- IP и User-Agent читаются только для решения «подозрительный» и для дневного хеша счётчиков; не хранятся и не
  пишутся в лог.
- Удаление по запросу: `DELETE /v1/admin/analytics/people/{id}` удаляет человека, его идентичности, сессии,
  профиль и сырые события (просмотр разделов допустим при наших объёмах). Отклонённые и просроченные заявки,
  чьи данные стирает `onboarding.sweep`, теряют и `email_sha256` в `identities`.
- Изоляция организаций: витрина 1 — только через маршрут с `{org_id}` и проверку мероприятия; витрины 2 и 3 —
  только суперадмин.
- Документы: пункт об аналитике в политике конфиденциальности сайта, в условиях для организаторов и в баннере
  сайта (категория «Аналитика»).
