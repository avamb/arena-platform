# 63. Замена билета, отправленного не тому покупателю

Статус: все решения владельца приняты 07.11.2026 (раздел 9). Кода и миграций нет. Спека готова к этапам раздела 10.
Связанные спеки: 45 (перенос билета на другой сеанс, черновик в ветке `docs/spec-45-ticket-exchange`), 35 (бот ивент-центра, повторная отправка EC-13), 37 (веб-ивент-центр), 17 (MACS), 18 (шлюз Bil24), 30 (перенос и отмена сеанса), 51 (доказательства для спора), 62 (уход Vino&Co с WordPress).

## 1. Зачем

Покупатель опечатался в адресе и купил билет. Письмо со штрихкодом ушло на чужой ящик. Потом покупатель пишет с настоящего адреса и называет имя и телефон. Администратор организации сверяет данные и решает, что это тот самый покупатель.

Сейчас администратор может только переслать письмо на верный адрес. Штрихкод при этом тот же. Значит, оба письма дают проход: кто первый пришёл, тот и прошёл.

Нужно действие **«Заменить билет»**:

- выпустить новый штрихкод и отправить новое письмо на настоящий адрес;
- старый штрихкод перестаёт пускать на вход, причина — «отправлен по ошибке»;
- место, заказ и деньги не меняются. Возврата нет, место не освобождается.

### 1.1. Случай, с которого всё началось (ноябрь 2026)

Заказ сайта WordPress одного из организаторов: один билет. Письмо ушло на адрес с опечаткой. Покупательница написала через форму контактов с настоящего адреса и назвала имя и телефон. Администратор переотправил письмо в ивент-центре WordPress на верный адрес. Штрихкод остался тем же, поэтому оба письма дают проход. Штрихкод вручную не отзывали: он у настоящей покупательницы.

Решение по этому заказу (Р-15): ничего не делаем. Вероятность, что ошибочный ящик окажется рядом с мероприятием, очень мала.

### 1.2. Два случая: опечатка или просьба переслать

Перед любым действием администратор отвечает на вопрос: **с какого адреса пишет покупатель?**

| Случай | Признак | Действие |
|---|---|---|
| **Опечатка.** В заказе чужой или несуществующий адрес | Покупатель пишет с другого адреса. Администратор сверяет имя и телефон | **Заменить билеты** (эта спека): новые штрихкоды, письмо на верный адрес, адрес заказа меняется |
| **Просьба переслать.** Адрес в заказе верный | Покупатель пишет **с адреса заказа** и просит отправить билеты на другой ящик | **Отправить повторно** на другой адрес (EC-13, уже есть): тот же штрихкод, разовый адрес на 24 часа, адрес заказа не меняется |

Во втором случае человек опознан однозначно: он пишет с адреса, на который оформлен заказ. Новый ящик — его выбор, второй действующий экземпляр того же кода у него же. Поэтому штрихкод не меняем.

Экран и бот задают этот вопрос первым шагом (раздел 7) и ведут в нужное действие. Кнопки «сделать новый адрес основным» без замены штрихкодов нет (Р-18).

## 2. Как устроено сейчас

### 2.1. Повторная отправка в arena

- `POST /v1/admin/tickets/{id}/delivery/resend` (`htickets/admin_ticket_delivery.go`) — консоль поддержки, один билет. Вызывает `RequeueDeliveryJob(ticket, tickets.holder_email)`. Адрес сменить нельзя.
- `POST /v1/organizations/{org_id}/orders/{order_id}/resend-tickets` (`htickets/order_resend.go`, EC-13) — весь заказ, бот и веб. Можно указать **разовый** адрес: он живёт 24 часа на задаче доставки, `orders.buyer_email` и `tickets.holder_email` не меняются.
- Обе отправляют **тот же** штрихкод. Поэтому после пересылки действуют оба письма.
- `resend-tickets` отказывает `409 order.seller_site_order`, если `orders.source = 'bil24_gateway'` **или** у канала есть активный подписчик `bil24_wp` (`sessionchange.ChannelHasSite`). Проверка по `source` отказывает и после остановки WordPress: заказы эпохи WordPress так и останутся «заказами сайта».

### 2.2. Штрихкод и учётные данные билета

- `barcodes` (миграция 0029): строка на значение штрихкода, `status` = `active` / `scanned` / `revoked`, `ticket_id`. У одного билета может быть несколько строк (индекс не уникальный). Причины отзыва нет.
- `ticket_credentials` (0027): одна строка на пару (билет, тип), `UNIQUE (ticket_id, type)`. Типы `static_qr`, `pdf`, `ean13`. `InsertTicketCredential` — upsert: новый код **затирает** старый и сбрасывает `revoked_at`.
- Выпуск — только `mintTicketEAN13s` → `mint.EAN13` (уникальность по всем источникам штрихкодов), затем upsert `ean13`.
- Отзыв — `RevokeTicketArtifactsTx` (`htickets/cancel.go`): все строки `barcodes` билета → `revoked`, учётные данные `static_qr`, `pdf`, `ean13` → `revoked_at`. Ошибки только пишутся в лог. Событий не пишет: их пишет вызывающий код.
- `RevokeBarcode` (`hbarcode/barcodes.go`) — ручной отзыв одной строки.

### 2.3. Проверка на входе

| Проверка | Что смотрит | Отозванный штрихкод |
|---|---|---|
| Bil24 SCAN_TICKET (`hbil24/cmd_tickets.go`) | `barcodes.status` по `external_ref` во всех authority | отказ `-2` «revoked». Статус билета **не** смотрит |
| Сканер arena, `POST /v1/scanner/validate` | `barcodes.status` + статус билета | отказ `barcode_revoked` |
| `scanner_callback` (только `static_qr`, служебный) | статус билета | отказ для `cancelled`, `revoked`, `transferred` |
| Офлайн-снимок `GET /v1/scanner/snapshot` | список штрихкодов сеанса | полный снимок без отозванных, дельта отдаёт их со статусом `revoked` (R-1) |
| MACS (вход Vino) | своя копия билетов из выгрузки arena | решает сам MACS, см. 2.5 |
| Приём сканов MACS `POST /v1/macs/scan-events` | `ResolveMACSScanTicketByBarcode` | скан сохраняется как факт MACS, `used_at` не ставится, в событии `barcode_revoked: true` (R-1) |

### 2.4. Письмо с билетами

- `delivery/handler.go`: адрес берётся из `delivery_jobs.recipient_email`, иначе из `tickets.holder_email`.
- `delivery/order_letter.go`: одно письмо на заказ и адрес. Штрихкод берётся из учётных данных `ean13` в момент отправки.
- PDF билета хранится в учётных данных `pdf` (`ticketPDFBytes`). Смена штрихкода должна сбросить этот PDF. Отозванный PDF не прикладывается и не отдаётся (R-1).
- В письме есть ссылки «Скачать PDF» (`delivery/download_links.go`): `/v1/public/checkout/{checkout_token}/tickets/{ticket_id}/pdf`. По токену покупки открываются страница статуса заказа, PDF каждого билета и страница «Приведи друга». Токен лежит и в первом письме, поэтому замена меняет токен (Р-12).
- «Мои билеты по ссылке» (`mytickets`, спека 62 §7) ищет заказы по `orders.buyer_email`. Поэтому замена меняет адрес заказа (Р-2), иначе настоящий покупатель не увидит заказ в «Моих билетах».

### 2.5. Две дороги письма

**Arena пишет сама** (виджет, hosted-страница, будущий статический сайт Vino). Всё под нашим контролем: адрес, штрихкод, письмо.

**Письмо пишет сайт** (WordPress, плагин bil24-ticket-mailer, заказы `source = 'bil24_gateway'`). Факты:

- Сайт хранит снимок `ticketList` со штрихкодами из вебхука `order.paid` (мета заказа `bil24_tickets`, спека 30, раздел о сайтах). Его кнопка «Отправить повторно» собирает PDF из этого снимка. Новый штрихкод в снимок сам не попадёт.
- `GET_TICKETS_BY_ORDER` отдаёт штрихкод из `ticket_credentials` типа `ean13` и статуса билета не отдаёт. Билеты `cancelled` и `revoked` возвращаются со своим кодом, `transferred` — не возвращаются.
- Вебхуки сайту (`bil24wire`): `v1.ticket.cancelled|refunded|revoked` → `ticket.refunded` с `holderStatus: REFUND`. Сайт склеивает повторы по номеру билета (`data.id`). События «у действующего билета сменился штрихкод» **нет**.
- Код плагина bil24-ticket-mailer живёт в репозиториях сайтов клиентов, не здесь. Плагин `apps/wp-plugin/arena-events` — другой, `ticket.refunded` не обрабатывает.

**MACS** (`internal/platform/macs`):

- `v1.order.paid` → `order.paid` со всем заказом и штрихкодами.
- `v1.scanner.ticket.issued` → `order.paid` с одним билетом (так сейчас уходят приглашения).
- `v1.ticket.{refunded,cancelled,revoked}` → `ticket.refunded`, `holderStatus = 3` (не пускать).
- MACS ведёт билет по номеру (`system_ticket_id`). Сообщения «смени штрихкод у действующего билета» в протоколе **нет**.

Вывод: чтобы закрыть старый код в MACS и на сайте, есть надёжное сообщение только одно — «этот билет больше не действует». Оно говорит про **номер билета**, а не про код.

### 2.6. Статус `transferred`

Есть в `tickets_status_check` с миграции 0026. Ничто его не пишет. Его уже понимают: сканеры arena (отказ), MACS (`holderStatus = 3`), вебхук сайту (как REFUND), сводки сеанса (отдельный счётчик), бот (`orders_format.go`). Спека 45 занимает его для переноса на другой сеанс.

## 3. Варианты (выбран B, решение Р-7)

### 3.1. Вариант A. Новый штрихкод на том же билете

Тот же `tickets.id`, номер, место, строка заказа. Отзываем старую строку `barcodes`, выпускаем новую через `mint.EAN13`, upsert `ean13`, сбрасываем кэш PDF, меняем адрес, отправляем письмо.

Плюсы:

- в базе меняется меньше всего: заказ, строка заказа, место, деньги, возвраты, биллинг, отчёты не трогаем;
- номер билета у покупателя прежний.

Риски:

- **MACS.** Старый код надо закрыть, а номер билета оставить открытым. `ticket.refunded` закроет весь билет вместе с новым кодом. Остаётся повторный `order.paid` с новым кодом под тем же номером. Как MACS его обработает (заменит код, добавит второй, проигнорирует повтор), мы не знаем. Нужна проверка с MACS Vino или новое сообщение протокола.
- **Сайт.** Аналогично: `ticket.refunded` пометит билет возвращённым навсегда.
- Приём сканов MACS находит билет по отозванному коду и ставит `used_at` у активного билета. Надо чинить в любом варианте (раздел 5.6), но здесь это бьёт по действующему билету.
- `ticket_credentials` хранит один код на билет: старый код остаётся только в `barcodes` без причины. Нужна новая таблица журнала (она нужна и в B).
- Правило «билет уже был на входе» смотрит все `barcodes` билета. Если старый код отсканирован после замены, «вошёл» станет новый билет. Возвраты по нему закроются.

### 3.2. Вариант B. Старый билет закрываем, новый выпускаем на то же место (выбран)

Старый билет → `status = 'transferred'`, причина `reissued`, учётные данные и штрихкоды отозваны (`RevokeTicketArtifactsTx`). Новый билет — новая строка: тот же заказ, `checkout_session_id`, сеанс, категория, `seat_key`, место, `vip`; новый `system_ticket_id`, `ordinal = max + 1`, новый EAN-13. Строка заказа (`order_items.ticket_id`) переставляется на новый билет. Деньги строки не меняются. Место **не** освобождается: никаких вызовов `CancelTicketTx`, `ReleaseSold*`, `ReleaseCapacity`.

Плюсы:

- **MACS и сайт получают только знакомые сообщения**: старый номер → `ticket.refunded` (не пускать), новый номер → `order.paid` с одним билетом (как приглашение). Порядок: сначала закрыть, потом открыть.
- Сканеры arena уже отказывают `transferred` и отозванному коду.
- История честная: старый билет со своим кодом и причиной остаётся в заказе. Видно, какой код ушёл в чужой ящик.
- Это частный случай переноса из спеки 45 («перенос на тот же сеанс и то же место»). Ядро пишем один раз: пакет перевыпуска, который спека 45 потом расширит сменой сеанса, категории и места.
- Сканы старого кода приклеиваются к старому билету. Новый билет чист.

Риски:

- **Номер билета меняется.** Покупатель видит в письме новый номер. Это даже понятнее («новый билет №N взамен №M»). Таблица `wp_order_links.ticket_system_ids` сайта сохранит старые номера — она справочная, правило в разделе 6.
- Больше кода: перестановка `order_items.ticket_id`, новая строка `tickets`, новая `delivery_jobs`. Каждое место, где «билет заказа» ищется по `order_items.ticket_id`, должно увидеть новый билет (движок возвратов, варианты возврата, экспорт, сводки). Проверяем тестами (раздел 8).
- Биллинг: сбор `ticket_cancelled` не должен считать `transferred` отменой, а `ticket_sold` — новой продажей (ключ — строка заказа). Тест обязателен.
- Сайт покажет старый билет как «REFUND» (у протокола нет другого слова). Пока сайт жив, для заказов сайта действие не даём (раздел 6).

### 3.3. Вариант C. Только сменить адрес и переслать (как сейчас)

Это то, что сделал администратор в случае 1.1. Старый код продолжает пускать. Задачу не решает. Отклонён.

### 3.4. Вариант D. Отозвать старый код и выдать приглашение на то же место

Обходной путь без кода: `POST /v1/tickets/{id}/cancel` с `refund_mode=none` плюс приглашение. Место освобождается и тут же занимается приглашением (гонка с покупателями), приглашение не продажа, в отчёте пробел, связи нет. Отклонён. Подходит только как ручной обход в крайнем случае.

### 3.5. Почему B

Владелец выбрал **вариант B** (Р-7). Оркестратор предлагал A. Против A три причины:

1. **MACS.** В протоколе нет сообщения «смени код у действующего билета». Есть только «этот номер больше не действует», и в варианте A оно закрыло бы и новый код. Вариант B обходится сообщениями, которые MACS и сайты уже понимают.
2. **Решение Р-6 (старый код уже отсканирован).** В варианте A вход по старому коду остаётся на том же билете: `used_at` стоит, возвраты по билету закрыты, сводки считают его вошедшим, а MACS может не пустить новый код как «уже вошёл». В варианте B новый билет чистый: он пускает на вход, как решил владелец.
3. **Журнал.** В варианте B старый билет со своим кодом остаётся в заказе. Видно, какой код ушёл в чужой ящик и был ли по нему вход.

Ядро B общее со спекой 45 (перенос на другой сеанс). Пишем его один раз.

Вариант A стал бы дешевле, только если бы MACS по повторному `order.paid` с тем же номером заменял код. Это не проверено, и мы на это не опираемся.

## 4. Поведение (вариант B, с решениями владельца)

### 4.1. Кто может (Р-1)

Владелец организации (`org_admin`), менеджер (`organizer`) и суперадмин платформы (с `X-Admin-Reason`). Проверка — право `ticket.update` в организации заказа: его держат именно владелец и менеджер. Агент — `403`. Ключ API организации — `403 reissue.api_key_forbidden`: действие меняет данные покупателя.

### 4.2. Что заменяется (Р-3)

Весь заказ: все его действующие билеты (`status = 'active'`). Выбора билетов нет. Все новые билеты уходят одним письмом на верный адрес. Билеты не `active` (отменённые, возвращённые) пропускаются и не мешают замене.

Администратор вводит:

- **новый адрес** — обязателен. Может совпадать со старым (ящик взломали, письмо переслали чужому): тогда меняются только штрихкоды;
- **причину** — `sent_to_wrong_address` по умолчанию, `forwarded_to_stranger`, `other`, и заметку до 500 символов. Причина обязательна (Р-10): она остаётся в журнале замены и в аудите, администратор видит её в истории заказа.

### 4.3. Когда нельзя

| Случай | Ответ |
|---|---|
| Заказ не `paid` / `partially_refunded` | `409 order.not_paid` |
| Заказ сайта, пока сайт жив (канал с активным `bil24_wp`) | `409 order.seller_site_order` |
| В заказе нет ни одного действующего билета | `409 reissue.nothing_to_reissue` |
| Билет на удержании проверки или с возвратом в работе | `409 reissue.ticket_not_reissuable` с номером и причиной |
| Сеанс отменён или уже закончился | `409 reissue.session_closed` |
| Приглашение без заказа | заменяется своими маршрутами `.../complimentary/{id}/reissue-*` (этап R-5). Отозванное приглашение (`409 reissue.invitation_not_issued`) не заменяется, его выдают заново |
| Предыдущая замена этого заказа ещё не отправлена (4.5) | `409 reissue.in_progress` |

Отказ по одному билету отклоняет всю операцию: ничего не меняется.

**Старый код уже отсканирован — замена НЕ запрещена (Р-6).** Новые билеты выпускаются и действуют. Старый билет закрывается как обычно. Экран проверки предупреждает заранее: «По билету №M уже был вход в 20:05. Новый билет тоже пустит на вход». Отдельных сообщений никому не шлём (Р-11, раздел 4.8).

### 4.4. Одна транзакция

Блокировки: строка заказа (`FOR UPDATE`), затем билеты в порядке `id`.

1. Проверить всё из 4.3 под блокировками.
2. Для каждого действующего билета:
   - старый билет → `status = 'transferred'`, `cancelled_at = now()`, причина `reissued`;
   - `RevokeTicketArtifactsTx(старый)`. Здесь ошибка **возвращается**, а не глотается: незакрытый код — это вся суть операции;
   - новый билет — тот же заказ, `checkout_session_id`, сеанс, категория, `seat_key`, `vip`, `holder_name`. Новый `system_ticket_id`, `ordinal = max + 1`, `holder_email` = новый адрес;
   - `mintTicketEAN13s(новый)`;
   - `order_items.ticket_id` → новый билет. Деньги строки не меняются;
   - место **не** освобождается: никаких `CancelTicketTx`, `ReleaseSold*`, `ReleaseCapacity`.
3. `orders.buyer_email` **пока не меняем** (Р-2, раздел 4.5).
4. Сменить `checkout_sessions.checkout_token` покупки. Старые ссылки «Скачать PDF» и страница заказа из чужого ящика перестают работать (Р-12).
5. `InsertDeliveryJob(новый билет, новый адрес)` для каждого нового билета и одна задача `ticket.deliver`. Письмо на заказ собирает их в одно.
6. Строка `ticket_reissues` со статусом `pending` (4.7), `order_events` `tickets_reissued`, аудит `v1.order.tickets_reissue`.
7. Outbox: на каждый старый билет `v1.ticket.reissued` (новое событие, в спеку 15 в том же PR), затем на каждый новый — `v1.scanner.ticket.issued`. MACS: старый номер → `ticket.refunded`, новый номер → `order.paid` с одним билетом, именно в этом порядке.

Повтор с тем же `Idempotency-Key` отдаёт первый ответ и ничего не пишет.

**Ловушка для R-2.** Сообщение «билет не действует» для MACS и сайта строится из проекции `orderexport.QueryTicket`, а она пропускает статус `transferred` (`orderexport/query.go`, `bil24wire/loader.go`). Без правки старый номер не дойдёт до MACS. R-2 добавляет `transferred` в эти выборки и тест на заглушке MACS.

### 4.5. Адрес покупателя меняется после отправки письма (Р-2)

Порядок такой: сначала новые билеты и письмо, потом адрес заказа.

- «Письмо отправлено» = почтовый релей принял письмо (`email_letters.status = sent`, ответ `250`). Ждать «доставлено» от Brevo нельзя: это событие может не прийти совсем.
- Когда обработчик письма (`delivery.order_letter.go`) получил `250` для письма, в котором есть новые билеты замены, в той же записи статуса он:
  - ставит `orders.buyer_email` = новый адрес;
  - перепривязывает заказ к клиенту нового адреса (Р-13): `customers.Resolve` по новому адресу в SAVEPOINT, затем `orders.customer_id` = найденный или созданный клиент. Старого клиента не удаляем и не меняем. Если перепривязка не удалась, адрес всё равно меняется, а ошибка пишется в лог;
  - отмечает строку `ticket_reissues` как `applied` со временем.
- Если письмо не ушло (релей отказал, все попытки исчерпаны) — адрес заказа **не** меняется. Строка журнала `send_failed`. На карточке заказа: «Новые билеты выпущены, письмо не ушло, адрес заказа не изменён» и кнопка «Отправить ещё раз» (та же замена, тот же адрес, без нового выпуска штрихкодов).
- Если письмо ушло, а потом Brevo сообщил «не доставлено» — адрес уже сменён и не откатывается. Карточка показывает статус письма как обычно (Р-9).
- Письма о переносе сеанса, отмене и возврате берут адрес из `orders.buyer_email`. Пока замена в состоянии `pending` (обычно секунды), они ещё уходят на старый адрес. Это допустимо.

### 4.6. Письмо и молчание на ошибочный адрес (Р-4)

Обычное письмо с билетами (`ticket`, 7 языков) с новыми номерами, новыми штрихкодами и новыми PDF (у новых билетов нет кэша). Сверху — объяснение, почему пришли новые билеты (Р-19). Поле `templates.Data.Reissue` с причиной замены. Текст объяснения пишется автоматически, администратор его не набирает.

Тема письма: «Ваши новые билеты: {мероприятие}» / «Your new tickets: {event}».

**Причина «отправлено не на тот адрес»** (`sent_to_wrong_address`, по умолчанию):

> Здравствуйте, {имя}!
>
> При покупке в адресе электронной почты была опечатка, поэтому первое письмо с билетами ушло на другой адрес. Вы обратились к организатору и подтвердили свои данные. Мы выпустили для вас новые билеты, они во вложении.
>
> Билеты из первого письма больше не действуют. На вход пустят только по новым билетам.
>
> Места и оплата не изменились. Номер заказа: {номер}.

> Hello, {name}!
>
> There was a typo in the e-mail address given at purchase, so the first letter with your tickets went to another address. You contacted the organizer and confirmed your details. We have issued new tickets for you, they are attached.
>
> The tickets from the first letter are no longer valid. Only the new tickets will get you in.
>
> Your seats and payment have not changed. Order number: {number}.

**Причины «переслано чужому» и «другое»** (`forwarded_to_stranger`, `other`):

> Здравствуйте, {имя}!
>
> По вашей просьбе мы выпустили новые билеты взамен прежних. Они во вложении.
>
> Прежние билеты больше не действуют. На вход пустят только по новым билетам.
>
> Места и оплата не изменились. Номер заказа: {номер}.

> Hello, {name}!
>
> At your request we have issued new tickets to replace the earlier ones. They are attached.
>
> The earlier tickets are no longer valid. Only the new tickets will get you in.
>
> Your seats and payment have not changed. Order number: {number}.

Правила текста:

- Имя — `holder_name` или имя покупателя из заказа. Без имени — «Здравствуйте!» / «Hello!».
- Ни старого, ни нового адреса в тексте нет. Заметка администратора в письмо не попадает: она только для журнала.
- Остальные пять языков (cs, de, es, fr, he) переводятся при реализации по тем же фразам. Тест проверяет, что блок есть во всех семи шаблонах `ticket.<язык>.tmpl` и в HTML, и в текстовой части.
- Текст следует стандарту `docs/text_style_standard_ru.md`: короткие фразы, без упрёка покупателю. «Опечатка» — нейтральный факт, не «вы ошиблись».

На ошибочный адрес не пишем ничего: ящик может не существовать, а письма на мёртвые ящики портят доставляемость.

### 4.7. «Мои билеты» и кабинет покупателя

Как сейчас (`internal/platform/mytickets`, спека 62 §7):

- Других «кабинетов» у покупателя нет. «Мои билеты» — это и есть кабинет: страница `/my-tickets/` сайта организатора поверх arena.
- Покупатель вводит адрес. Письмо со ссылкой уходит, только если у организации есть заказ с `orders.buyer_email ILIKE <адрес>` (источники `public_feed`, `bil24_gateway`, `checkout_api`, `complimentary`, заказ хоть раз оплачен).
- Ссылка даёт сеанс на 4 часа. **Каждый** запрос сеанса (`ListOrders`, `OwnsTicket` для PDF) снова ищет по `orders.buyer_email`. `tickets.holder_email` и `customer_identities` не используются. Другие адреса того же человека не подмешиваются.
- В заказе показываются все билеты покупки, с любым статусом, и человекочитаемый код `static_qr`.

Что поменять:

1. **Ничего в поиске.** Смена `orders.buyer_email` после письма (4.5) сама переносит заказ: по верному адресу он появляется, по ошибочному пропадает. Сеанс, уже открытый по ошибочному адресу, тоже перестаёт его видеть: поиск идёт на каждом запросе.
2. **Окно до смены адреса.** Пока замена `pending`, заказ ещё лежит под старым адресом. «Мои билеты» не должны показывать такой заказ ни под старым адресом, ни под новым: в `ListOrders`, `OwnsTicket` и `RequestLink` добавить условие «у заказа нет замены в состоянии `pending` или `send_failed`».
3. **Закрытые билеты.** Показывать старый билет как «заменён», без кода `static_qr` и без кнопки PDF. `OwnsTicket` и маршрут PDF отдают только `active`.
4. «Мои билеты» клиента не читают, но заказ всё равно перепривязывается к клиенту нового адреса вместе со сменой адреса (Р-13, раздел 4.5).

### 4.8. Вход по старому коду (Р-11)

Сообщений администратору нет: ни в Telegram, ни письмом, ни в ops-бот. Случай крайне редкий, его разбирают вручную.

Достаточно, чтобы приложение на входе показало статус:

- старый код после замены: «Билет заменён» (`reissued`), вход не разрешён. Так отвечают сканер arena и SCAN_TICKET. MACS получает старый номер как недействительный (4.4, шаг 7);
- если по старому коду вход был **до** замены, это видно на экране проверки перед заменой (4.3) и в журнале замены (`old_code_scanned_at`).

### 4.9. Журнал и аудит

- Новая таблица `ticket_reissues`, по строке на операцию, и `ticket_reissue_items`, по строке на билет. Таблицы только пополняются, кроме полей состояния письма. Удаление запрещено статическим тестом по образцу `email_letters_retention_test.go`.
  - Операция: `id`, `org_id`, `order_id`, `old_email`, `new_email`, `state` (`pending` / `applied` / `send_failed`), `applied_at`, `reason`, `note`, `old_code_scanned_at`, `actor_type`, `actor_id`, `via`, `idempotency_key`, `created_at`.
  - Билет: `old_ticket_id`, `new_ticket_id`, `old_barcode`, `new_barcode`.
  - Адреса здесь нужны: это доказательство, куда ушёл старый код.
- `order_events` `tickets_reissued`: номера «M → N» и замаскированные адреса. Видно в истории заказа в веб-ивент-центре и в боте.
- Аудит `v1.order.tickets_reissue`: число билетов, причина, был ли вход по старому коду. **Адресов в аудите нет** (то же правило, что у повторной отправки).
- Ответ сканера по старому коду: «билет заменён» (`reissued`), а не просто «отозван».

### 4.10. Адрес покупателя у платёжной системы

При оплате адрес покупателя ушёл и к провайдеру:

| Провайдер | Что передаём | Что провайдер шлёт на этот адрес | Можно ли сменить по API |
|---|---|---|---|
| Stripe | `customer_email` сессии Checkout и `payment_intent_data[receipt_email]`, если включены чеки провайдера (спека 51, Р-6) | чек об оплате, чеки о возвратах; по просроченной ссылке на чек Stripe шлёт новую ссылку на адрес исходной оплаты | **Да, частично.** `POST /v1/charges/{id}` с `receipt_email`. Stripe сразу шлёт новый чек на новый адрес, будущие чеки о возврате идут туда же. Адрес в самой сессии Checkout и `billing_details.email` не меняются: в кабинете Stripe останутся оба |
| AllPay (Vino) | `client_email` | собственный налоговый документ организатора (חשבונית / קבלה) | В API нет такого метода. Только вручную в кабинете AllPay, если он позволяет переслать документ (не проверено) |
| Flitt | `sender_email` | письмо Flitt об оплате | Метода нет |
| PayPlus | `customer.email` | письмо и документ PayPlus | У PayPlus есть «update customer» по идентификатору клиента PayPlus. Arena этот идентификатор не хранит. Не проверено |

Что уже случилось, не исправить: чек об оплате ушёл на ошибочный адрес в момент покупки. В нём нет штрихкода, только сумма и продавец. Опасности для входа нет.

Варианты:

- **П-1. Провайдера не трогаем.** Arena — источник правды для писем о билетах. Журнал замены хранит оба адреса. Минус: чеки Stripe о будущих возвратах и документы AllPay уйдут на старый адрес.
- **П-2. Stripe: сменить `receipt_email` через API.** После смены адреса заказа (4.5), вне транзакции, ключом организатора. Только если у организации включены чеки провайдера. Иначе Stripe пошлёт чек, который организатор отключил. Неудача не мешает замене: она пишется в журнал и видна на карточке. Делается через возможность модуля `payments.ReceiptEmailUpdater`: ядро не называет провайдера.
- **П-3. Подсказка администратору.** Для провайдеров без API карточка заказа говорит: «У AllPay остался старый адрес. Документ об оплате можно переслать в кабинете AllPay». Ничего не отправляем сами.
- **П-4. Положить в новое письмо ссылку на чек провайдера**, если он у нас сохранён (Stripe, `provider_receipt_url`, ссылка живёт 30 дней). Покупатель получает чек сразу, без запросов к провайдеру.
- **П-5. Для спора (чарджбэка).** В пакет доказательств (спека 51) добавить запись журнала замены: кто, когда, почему сменил адрес. Тогда расхождение «у Stripe один адрес, у нас другой» объяснено. Нужно при любом варианте.

Решение владельца (Р-17): **П-1 для всех, плюс П-2 для Stripe, плюс П-3 и П-5.** П-4 не делаем.

## 5. Отозванные коды и PDF (этап R-1, сделано)

Правила, которые нужны при любом варианте замены:

1. **PDF в письме.** Отозванный PDF не прикладывается. Билет рисуется заново с текущим штрихкодом. Новый PDF сохраняется только для `active` билета.
2. **PDF по ссылке.** `GET /v1/public/checkout/{token}/tickets/{id}/pdf` и PDF «Моих билетов» отдают PDF только действующего билета. Иначе `410 checkout.ticket_not_valid`. Страница статуса заказа показывает такой билет без кода и без ссылки на PDF.
3. **Приём сканов MACS.** Скан отозванного кода, который MACS всё же пропустил, сохраняется как факт, но `used_at` у билета не ставится, а в событии `v1.ticket.scanned` есть `barcode_revoked: true`. Записывать его как отказ нельзя: человек физически прошёл, это факт MACS.
4. **Офлайн-снимок.** Полный `GET /v1/scanner/snapshot` без отозванных кодов. Дельта отдаёт их со статусом `revoked`, чтобы устройство вычеркнуло код из кэша.
5. **`GET_TICKETS_BY_ORDER`** — менять не нужно. Проекция `orderexport` берёт билеты со статусами `active`, `cancelled`, `revoked`. Заменённый билет (`transferred`) в ответ сайту не попадает. Код отменённого билета отдаётся нарочно: по нему MACS и сайт узнают, какой код не пускать.
6. **Повторная отправка на другой адрес** (`resend-tickets`) уходит с тем же штрихкодом. Её оставляем как есть, доработки нет (Р-14).

## 6. Заказы сайтов и Vino после ухода с WordPress

- Пока у канала есть активный подписчик `bil24_wp`, заказ ведёт сайт. Arena отказывает `409 order.seller_site_order`. Сайт не узнает новый код: в его снимке `bil24_tickets` останется старый, и его кнопка «Отправить повторно» снова пошлёт старый PDF. Протокол Bil24 замены не знает.
- Когда сайт отключён (нет активного `bil24_wp`), заказ с `source = 'bil24_gateway'` ведёт arena: замена разрешена. Решаем по `ChannelHasSite`, а не по `source`. То же исправление нужно повторной отправке: сейчас она отказывает по `source` навсегда (Р-8: сайт отключаем, всё будет на новом сайте).
- `wp_order_links.ticket_system_ids` не переписываем: это справка «что было на WordPress». Связь «старый → новый» видна в журнале замены.
- Основное место действия Vino после переезда — веб-ивент-центр arena и бот.

## 7. Набросок API и экранов

### 7.1. API

```
GET  /v1/organizations/{org_id}/orders/{order_id}/reissue-options
     → { route: "arena" | "seller_site", order_email, buyer_name, buyer_phone,
         tickets: [{ ticket_id, number, seat, status, reissuable: bool, reason?,
                     scanned_at? }],
         pending_reissue?: { id, state, new_email } }

POST /v1/organizations/{org_id}/orders/{order_id}/reissue-tickets
     Idempotency-Key: <обязателен>
     { "email": "buyer@example.com", "reason": "sent_to_wrong_address", "note": "…" }
     → 200 { reissue_id, state: "pending",
             tickets: [{ old_ticket_id, old_number, new_ticket_id, new_number,
                         old_code_scanned_at? }],
             letter: "queued" }

POST /v1/organizations/{org_id}/orders/{order_id}/reissues/{reissue_id}/resend
     (письмо не ушло: та же замена ещё раз на тот же адрес, без новых штрихкодов)

GET  /v1/organizations/{org_id}/orders/{order_id}/reissues   (история, order.read)
```

Ошибки: `404 orders.not_found` (и для чужой организации), `400 reissue.idempotency_key_required`, `422 reissue.invalid_email`, `409` из 4.3, `403 reissue.api_key_forbidden`. Маршруты с `{org_id}` и `{order_id}` — строки в таблице проверки изоляции организаций.

### 7.2. Веб-ивент-центр (`apps/event-center`)

Кнопка «Заменить билеты» на карточке заказа рядом с «Отправить билеты повторно», видна при `can("ticket.update")`. Диалог `ReissueTicketsDialog`:

0. **Случай.** «С какого адреса пишет покупатель?» — «С адреса заказа» ведёт в повторную отправку на другой адрес (EC-13), «С другого адреса» — дальше по этому диалогу (раздел 1.2). Тот же вопрос задаёт и кнопка «Отправить билеты повторно».
1. **Адрес.** Новый адрес, рядом замаскированный старый. Для сверки — имя и телефон покупателя из заказа.
2. **Причина.** Список и заметка.
3. **Проверка.** «Все билеты заказа №… (2 шт.) перестанут пускать на вход. Покупатель получит новые билеты на b***r@example.com. Место и оплата не меняются. Адрес заказа сменится, когда письмо уйдёт. Отменить замену нельзя». Если по старому коду был вход — отдельная строка-предупреждение (4.3).
4. **Слово подтверждения** в `ConfirmWordDialog` (вид `reissue`, Р-5).
5. **Итог.** Новые номера, письмо в очереди, затем статус письма и «адрес заказа изменён» на карточке.

Для заказа сайта — объяснение без кнопки. Двойник-тест — живой спек `live/reissue.spec.ts`.

### 7.3. Бот (Р-5)

Кнопка «🔁 Заменить билеты» на карточке заказа, только в личном чате, владелец и менеджер. Диалог `bot_dialogs` вида `reissue`, нажатия `or:x:*` (внутри префикса заказов). Шаги: случай (раздел 1.2: «с адреса заказа» уводит в повторную отправку) → адрес (набрать) → причина → проверка → набранное слово. Правило то же, что у отмены сеанса: подтверждающее нажатие только открывает шаг слова, неверное слово ничего не меняет. Слово: ЗАМЕНИТЬ БИЛЕТЫ / REISSUE TICKETS / REEMITIR ENTRADAS, английское принимается на любом языке (`typed_words.go`, ключ `bot.reissue.word`). Слово отличается от слов отмены сеанса и заказа. Веб читает тот же ключ в тесте `confirmWords.test.ts`.

## 8. Тесты

1. Замена заказа из двух билетов: старые `transferred`, их коды и учётные данные отозваны, новые `active` с новыми EAN-13 через `mint.EAN13`, те же `seat_key`, `order_items.ticket_id` = новые.
2. Деньги и места: `orders.total`, `order_items.*`, `session_seats`, `inventory_ledger`, `ga_unit` не изменились. Свободных мест не прибавилось.
3. Письмо: одно на заказ, на новый адрес, с новыми кодами. PDF не из кэша старого билета.
4. Адрес заказа: до `250` прежний, после `250` новый, `orders.customer_id` — клиент нового адреса, старый клиент не изменён, строка журнала `applied`. Отказ релея — адрес прежний, `send_failed`, повтор отправки меняет адрес.
5. «Мои билеты»: во время `pending` заказ не виден ни по старому, ни по новому адресу. После `applied` виден по новому и пропал по старому, в том числе в уже открытом сеансе. Старый билет показан «заменён», без кода и PDF.
6. Старый код: SCAN_TICKET `-2`, `scanner/validate` `reissued`, офлайн-снимок отдаёт его как снятый, приём сканов MACS пишет отказ и не ставит `used_at`.
7. MACS (заглушка `macs/stub`): сначала `ticket.refunded` старого номера, потом `order.paid` нового.
8. Старый код уже отсканирован: замена проходит, новый билет пускает, `old_code_scanned_at` записан, ни одного сообщения в Telegram и ни одного письма администраторам.
9. Старый токен покупки: статус заказа и PDF отвечают 404. Новый токен работает.
10. Отказы из 4.3, каждый: ничего не меняется (снимок строк до и после).
11. Повтор с тем же `Idempotency-Key` — тот же ответ, одно письмо, один журнал.
12. Две параллельные замены одного заказа — одна проходит, вторая `409`.
13. Права: владелец и менеджер — да, агент `403`, ключ API `403`, чужая организация `404`, суперадмин без причины `400`.
14. Заказ сайта при живом `bil24_wp` — `409`. Тот же заказ после отключения подписчика — замена проходит.
15. Возврат после замены: варианты возврата видят новые билеты, старые не возвращаются.
16. Биллинг: сбор не пишет `ticket_cancelled` за `transferred` и второй `ticket_sold` за новый билет.
17. Сводки сеанса и экспорт: продано столько же, `transferred` считается отдельно.
18. Журнал: строки с адресами, аудит без адресов, `order_events` с номерами.
19. Бот e2e и веб-двойник: весь путь. Неверное слово ничего не меняет. Ошибочный адрес не получает ни одного письма.
20. Stripe (заглушка): после смены адреса заказа один запрос `POST /v1/charges/{id}` с новым `receipt_email`, только при включённых чеках провайдера. Ошибка Stripe не откатывает замену и видна на карточке.
21. AllPay, Flitt, PayPlus: ни одного запроса к провайдеру, на карточке подсказка о старом адресе.
22. Пакет доказательств для спора по заменённому заказу содержит запись журнала замены.
23. Первый шаг диалога: «с адреса заказа» ведёт в повторную отправку, штрихкоды не меняются.
24. Письмо замены: блок объяснения есть во всех семи языках, текст зависит от причины, адресов и заметки администратора в письме нет.

## 9. Решения

### 9.1. Решено владельцем 07.11.2026

| № | Решение |
|---|---|
| Р-1 | Заменять могут владелец организации, менеджер и суперадмин платформы |
| Р-2 | Адрес покупателя в базе меняется, но только после успешной отправки нового письма. Цели: письма о переносе и возврате идут на верный ящик, «Мои билеты» по верному адресу показывают заказ |
| Р-3 | Меняется весь заказ: все билеты получают новые штрихкоды и уходят одним письмом |
| Р-4 | На ошибочный адрес ничего не пишем |
| Р-5 | Подтверждение обязательно, в веб-ивент-центре и в боте. В боте — набранное слово, как у отмены сеанса |
| Р-6 | Если старый код уже отсканирован, новые билеты всё равно выпускаются и действуют |
| Р-7 | Вариант B: старый билет закрывается (`transferred`), новый билет выпускается на то же место в том же заказе |
| Р-8 | Заказы эпохи WordPress после отключения сайта заменяем: сайт отключаем, всё будет на новом сайте. Решаем по признаку «у канала нет живого сайта», а не по `source` |
| Р-9 | «Письмо отправлено» = релей принял письмо. Если Brevo потом сообщит «не доставлено», адрес заказа не откатывается |
| Р-10 | Причина обязательна. Она остаётся в журнале и в аудите, администратор видит её в истории заказа |
| Р-11 | Никаких сообщений о входе по старому коду. Приложение на входе показывает статус «Билет заменён», остальное разбирают вручную |
| Р-12 | Токен покупки при замене меняется |
| Р-13 | Заказ перепривязывается к клиенту по новому адресу (вместе со сменой адреса) |
| Р-14 | Повторную отправку на другой адрес оставляем как есть, доработки нет |
| Р-15 | Заказ из случая 1.1 не трогаем. Первое письмо на ошибочный адрес дошло, но риск мал |
| Р-16 | В чат продаж о замене не пишем |
| Р-17 | Адрес у платёжной системы (раздел 4.10): провайдера в общем случае не трогаем (П-1); у Stripe меняем `receipt_email` через API, если у организации включены чеки провайдера (П-2); для остальных провайдеров — подсказка на карточке заказа (П-3); запись о замене попадает в пакет доказательств для спора (П-5) |
| Р-18 | Покупатель пишет с адреса заказа и просит слать на другой ящик: только разовая повторная отправка. Кнопки «сделать этот адрес основным» нет |
| Р-19 | Письмо с новыми билетами объясняет замену автоматически: при покупке в адресе была опечатка, покупатель подтвердил свои данные, поэтому ему выпущены новые билеты, а прежние не действуют (текст в разделе 4.6) |
