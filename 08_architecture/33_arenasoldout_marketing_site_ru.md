## 0. Коротко

1. **WordPress витрине не нужен.** Всё, что про мероприятия, приходит из API Arena; остальное
   это статические страницы, формы и блог. Предлагаю **Astro (статическая сборка) + контент в
   git + Cloudflare Pages**, формы через Cloudflare Functions → n8n → Telegram владельцу, блог
   двусторонне связан с Telegram-каналом через n8n. WordPress остаётся жить на поддомене как
   тестовый магазин и стенд плагина (решение 03.10), старые адреса получают 301.
2. **Сайт должен говорить правду о коде.** Сегодняшний сайт описывает продукт эпохи Bil24
   («desktop applications», «Reporter app», «trusted agents», 0,50 $/€ за билет, white label
   45 €). Контент переписывается с нуля по инвентаризации платформы (раздел 4), с явным списком
   того, чего не обещаем (раздел 4.3).
3. **Дизайн: уровень Stripe, тема организатора.** Ни один билетный сайт из обзора не дотягивает
   до Stripe по исполнению; у них нет живого интерактивного демо, у нас оно уже есть: виджет
   `<arena-tickets>` со схемой зала. Это и есть главный визуальный приём hero. Три направления
   дизайна описаны в разделе 7, прототипы делаю как кликабельные HTML-артефакты.
4. **Чтобы делать дизайн, подключать нужно немного** (раздел 10): официальный плагин Figma
   (есть в каталоге, нужен ваш аккаунт Figma), плюс уже включённые frontend-design, design
   (критика, доступность, UX-тексты), Artifact-прототипы, встроенный браузер для скриншотов,
   n8n. Остальное из каталога (Fairmind, design-skills, Rayden) лишнее.
5. **Решения владельца получены 07.10** (раздел 12): языки EN/ES/CS/RU с языковым стандартом
   (3.6), все русские статьи с обязательными редиректами, тарифы старого сайта (4.4), согласие
   на кейсы есть, новый русскоязычный Telegram-канал, WordPress на `demo.`, Figma не нужна,
   витрина раньше плагина, тексты через Claude с заделом под Keystatic (3.8), хостинг
   Cloudflare Workers с гарантией переезда на свой сервер (3.7a). Открытых вопросов нет.

## 2. Нужен ли WordPress

Разбор по тому, что сайту реально нужно.

| Потребность | Откуда берётся без WordPress | Вывод |
|---|---|---|
| Описание продукта, сегменты, тарифы, юр. страницы | MDX-файлы в git, правятся в редакторе или через Claude; при желании git-CMS (Keystatic/Decap) с визуальной формой | WordPress не нужен |
| Мероприятия, организаторы, живые примеры | `GET /v1/public/pages/{org}`, `/{org}/{event}`, виджет `<arena-tickets>` с demo feed-токеном | WordPress не нужен, это и был его главный «довод» в старом сайте |
| Формы (контакт, демо, заявка организатора, партнёры) | Cloudflare Pages Function (или Worker) → Turnstile → вебхук n8n → Telegram владельцу + контакт в Brevo | WordPress не нужен; n8n уже стоит (`n8.andreevmaster.com`, проверено 07.10) |
| Блог со статьями, рубриками, многоязычием | Markdown в git (content collection `posts`), RSS, hreflang; старые статьи переносятся из WXR-экспорта скриптом | WordPress не нужен |
| Блог ↔ Telegram-канал | n8n: пост канала → markdown в репозиторий → пересборка; новая статья → пост в канал | WordPress не нужен |
| Редактор, которому нужна кнопка «Опубликовать» без git | Keystatic (редактирование MD/MDX в браузере через GitHub-приложение) или Decap CMS | Закрывается без WordPress, но нужно решение, кто правит тексты (раздел 12) |
| Комментарии к статьям | Нет (или обсуждение в посте канала по ссылке) | WordPress не нужен |
| Тестовый магазин, стенд плагина | Остаётся **тот же** WordPress, но на поддомене `demo.arenasoldout.com` (решение 07.10) | WordPress остаётся, но не как витрина |

Почему не «WordPress с новой темой» (вариант, который кажется дешевле):

- скорость и безопасность: сегодня главная 1,1 с TTFB после всех оптимизаций, Elementor
  тянет 8 семейств шрифтов, аудит 02.10 показал постоянные сканеры и xmlrpc-атаки на все
  сайты; статике на Cloudflare всё это безразлично;
- дизайн уровня Stripe в Elementor не собирается: нужны свои компоненты, анимация, живой
  виджет, bento-сетки; это код, а не конструктор;
- тексты всё равно переписываются целиком, то есть «сохранить контент» ничего не экономит;
- релизы витрины не должны зависеть от обновлений WordPress и плагинов, а витрина не должна
  стоять рядом с платёжной базой (аргументы из 31 §7 остаются в силе).

Почему не headless WordPress (WP как CMS, фронт на Astro): лишний сервер, лишний слой
кэша и ещё одна точка взлома ради редакторского интерфейса, который даёт Keystatic бесплатно.

**Рекомендация: статика. WordPress уходит на поддомен как магазин и стенд плагина.**

## 3. Целевая архитектура

```
                                 ┌──────────────────────────────┐
  Telegram-канал ───(n8n)──────► │  репозиторий avamb/arena-site │ ◄─── редактор (Keystatic) / Claude
  (посты → заметки блога)        │  Astro + MDX + переводы       │
                                 └──────────────┬───────────────┘
                                                │ push → GitHub Actions / Cloudflare Pages build
                                                ▼
   посетитель ──► Cloudflare Pages (arenasoldout.com, статика + Functions)
                   │   ├─ /api/forms/*  → Turnstile → n8n webhook → Telegram владельцу, Brevo
                   │   ├─ /start        → пока форма заявки; потом POST /v1/onboarding/signup (спека 32)
                   │   └─ 301-карта старых адресов WordPress
                   │
                   ├─ клиентские островки: <arena-tickets> (demo feed), калькулятор сбора,
                   │   витрина «идёт сейчас» из GET /v1/public/pages/… (api.arenasoldout.com)
                   │
                   └─ Umami (lead-parser) без cookie

  demo.arenasoldout.com (бывший сайт) — WordPress, тестовый магазин, стенд плагина, noindex
```

### 3.1 Стек

| Слой | Выбор | Почему |
|---|---|---|
| Генератор | **Astro 5**, режим `static`, content collections, встроенный i18n-роутинг, View Transitions | Ноль JS по умолчанию, островки только там, где нужна интерактивность; MDX для страниц; лучший Lighthouse среди вариантов; стандарт для маркетинговых сайтов |
| Островки | **Svelte 5** (тот же фреймворк, что виджет) для калькулятора, переключателей тарифов, живой витрины | Один язык компонентов с `apps/widget`; команда/агенты его уже знают |
| Стили | Tailwind 4 + дизайн-токены в CSS-переменных, общие с виджетом (`--arena-accent`, `--arena-radius`…) | Виджет на странице сайта должен выглядеть «своим» без доработок; токены задокументированы в `apps/widget/src/lib/tokens.ts` |
| Контент | MDX (страницы), MD с frontmatter (`posts`, `notes`, `changelog`, `cases`), переводы в `content/<lang>/…` | Переводы файлами, как решили 03.10; история в git |
| Редактирование | Keystatic (GitHub-режим) для владельца/редактора, Claude для массовых правок | Без сервера; визуальная форма у того, кто не хочет git |
| Формы | Cloudflare Pages Functions + Turnstile; тело → n8n webhook | Без cookie-баннера, без бэкенда, спам-защита без CAPTCHA-картинок |
| Хостинг | **Cloudflare Pages** (домен уже в Cloudflare) | Бесплатно, глобальный CDN, превью на каждый PR, Functions для форм; запасной вариант: образ nginx по образцу `apps/tickets-page/Dockerfile` в Dokploy на lead-parser |
| Аналитика | Umami (уже на lead-parser) | Без cookie, значит без баннера согласия; GTM/пиксели только если решим рекламировать сайт |
| Поиск по блогу | Pagefind (статический индекс на сборке) | Работает без сервера |
| OG-картинки | Генерация на сборке (satori/resvg) на каждую страницу и статью | Превью ссылок в Telegram/WhatsApp — у tickets-page этого нет, у сайта должно быть |

Репозиторий: отдельный `avamb/arena-site` (релизный цикл витрины не связан с API; доступ
редакторам без доступа к платформе). Из монорепо берём только токены виджета (копией с
проверкой в CI, что не разошлись) и ссылку на сборку виджета с jsDelivr или с
`tickets.arenasoldout.com/widget/v1/`.

### 3.2 Что нужно от платформы (новое, небольшое)

1. **Демо-организация с вечным событием** для живого виджета на сайте: организация «Arena Demo»
   (или существующая «Arena Test Promotions»), канал со Stripe test, событие с залом и GA,
   сеансы, которые автоматически сдвигаются вперёд (cron-задача или скрипт seed раз в неделю),
   холды с коротким TTL. Виджет в hero принимает `feed-token` этого канала.
2. **Витрина «идёт сейчас»** на сайте: либо курируемый список slug'ов организаторов в
   контенте сайта (ничего не меняем в API, читаем `GET /v1/public/pages/{slug}` на клиенте или
   на сборке), либо новый публичный маршрут `GET /v1/public/showcase` с избранными событиями
   (флаг `events.showcase` ставит суперадмин). Начинаем с курируемого списка.
3. **`/start`** (решение 08.10): анкета-заявка с черновиком живёт на этой странице и работает на платформе,
   без n8n. Спецификация `34_onboarding_applications_ru.md`: маршруты и поля (приложение A), страницы сайта
   (раздел 9), бэклог APP. Сайт рисует анкету по `GET /v1/onboarding/form-schema`; до готовности бэкенда строится
   против описания договора с заглушкой.
4. **Пульс платформы** (необязательно): публичная цифра «билетов продано за 30 дней,
   событий сейчас в продаже» из `GET /metrics` через маленький агрегатор; добавлять, когда
   числа станут аргументом.

### 3.3 Блог и Telegram-канал

Два типа материалов, чтобы короткие посты канала не превращали блог в кашу:

- `posts` — длинные статьи (старые перенесённые и новые), со слагом, рубриками, языком,
  обложкой;
- `notes` — короткие заметки, приходящие из Telegram-канала (лента «Что нового»), с ссылкой
  на исходный пост и его медиа.

Решение 07.10: канал заводится **новый, ведётся на русском**. Значит, `notes` рождаются как
RU-материалы и показываются на всех языковых версиях сайта с пометкой языка; перевод заметок
подключаем позже отдельным решением. Для канала нужен бот-администратор (можно отдельный
токен, не продажный и не ops-бот).

Связка через n8n (бот в канале с правами администратора):

1. **Канал → сайт.** Триггер Telegram (channel_post) → фильтр по тегу (`#blog` или без фильтра
   для всех) → скачать медиа в R2 → собрать markdown (`notes/<дата>-<id>.md`) → коммит в
   репозиторий через GitHub API → сборка Cloudflare Pages (≈1–2 минуты). Правка поста в канале
   (`edited_channel_post`) обновляет файл.
2. **Сайт → канал.** При публикации новой статьи (`posts`, коммит в `main` с новым файлом)
   GitHub Action вызывает вебхук n8n → пост в канал с обложкой и ссылкой.
3. Долгие статьи, написанные в Telegram как Telegraph (`telegra.ph`), тоже можно забирать
   (API Telegraph открыт), но проще писать их в репозитории.

Лента «история платформы» (просьба владельца): отдельная коллекция `changelog` (дата,
заголовок, что изменилось, ссылки), страница `/changelog` и блок «Последние обновления» на
главной. Записи в неё пишутся при каждом заметном релизе (у нас уже есть привычка писать
AGENTS.md и заметки памяти, из них это делается за минуты). Первые записи: переход с Bil24 на
собственный бэкенд, Telegram-бот ивент-центра, оплата Stripe/Flitt на счёт организатора, письма
при переносе сеанса, чтение афиши AI, испанский язык.

Старые статьи (75 записей: en 30, ru 43, es 1, no 1; все датированы 2024 годом):

- все сохраняются, адреса сохраняются или получают 301 на новый формат
  (`/blog/<slug>` и `/ru/blog/<slug>`);
- каждая получает плашку «Из архива: написано в 20xx, когда платформа работала на
  предыдущем ядре. С 2026 года платформа полностью переписана — что изменилось» со ссылкой на
  статью-манифест и на `/changelog`;
- заголовок и аннотация на новой карточке статьи; внутри текст не правим (кроме битых ссылок
  и картинок). Статьи, которые описывают несуществующие функции, получают дополнительную
  строку «эта возможность устроена иначе, см. …»;
- технически: экспорт WXR → скрипт в markdown (есть готовые конвертеры), картинки в R2 или в
  репозиторий, проверка каждой ссылки.

### 3.6 Языковой стандарт (решение 07.10: любой язык добавляется без переделки)

Контракт, который закладывается в каркас с первого дня:

1. **Коды языков** по BCP-47 в нижнем регистре (`en`, `es`, `cs`, `ru`, позже `he`, `de`,
   `fr`, `it`, `pl`, `uk`…), те же, что у платформы (`internal/platform/i18n/locales`,
   `PAGE_LOCALES` tickets-page, `SupportedLocales` письма). Один файл `site.config.ts`
   перечисляет языки с полями: код, название на самом языке, направление (`ltr`/`rtl`),
   локаль для `Intl` (даты, числа, валюты), включён ли в меню, язык по умолчанию.
   **Добавить язык = одна строка в этом файле + папка с переводами.**
2. **Маршруты**: язык по умолчанию без префикса (`/pricing`), остальные с префиксом
   (`/es/pricing`); slug'и страниц переводимые (`/es/precios`) через карту slug'ов в
   конфиге страницы; `hreflang` и `x-default` генерируются автоматически из конфига.
3. **Контент**: `content/<lang>/<collection>/…` зеркалит структуру языка по умолчанию.
   Отсутствующий файл перевода = страница показывается на EN с плашкой «ещё не переведено»
   и `noindex` на этот URL, а не 404. Строки интерфейса (кнопки, меню, формы) в
   `i18n/<lang>.json` с fallback на `en`, как в боте (go-i18n fallback).
4. **CI-проверки**: у каждого переведённого файла совпадает набор полей frontmatter и
   набор `{{плейсхолдеров}}` с оригиналом (тот же приём, что для toml бота); отчёт «какие
   страницы не переведены на какой язык» публикуется в PR.
5. **RTL** с первого дня: `dir` на `<html>` из конфига, логические CSS-свойства
   (`margin-inline`, `padding-inline-start`), проверка макета на `he` в прототипе, даже если
   иврит включается позже.
6. **Типографика**: один переменный шрифт с подмножествами latin, latin-ext, cyrillic,
   greek; для иврита отдельное подмножество подключается конфигом. Никаких шрифтов,
   у которых нет кириллицы и чешских диакритик.
7. **Даты, числа, валюты** только через `Intl` с локалью из конфига (`en` → `en-GB`,
   24 часа, как уже сделано на tickets-page); никаких захардкоженных форматов.
8. **Перевод**: оригинал пишется на EN; Claude переводит diff при каждом изменении
   оригинала (скрипт показывает, какие файлы устарели по хэшу оригинала во frontmatter:
   `source_hash`); владелец или носитель вычитывает.
9. **Блог**: язык статьи в frontmatter; статья может существовать на одном языке (RU-архив),
   карточка показывает флаг языка; `notes` из Telegram рождаются на RU и переводятся только по
   решению.
10. **Поиск** (Pagefind) строит индекс по языкам отдельно.

### 3.7 Что такое Cloudflare Pages и сколько это стоит (ответ на вопрос владельца)

Cloudflare Pages это хостинг статических сайтов на сети Cloudflare, через которую
`arenasoldout.com` уже и так проходит. Вы подключаете репозиторий GitHub, Cloudflare сам
собирает сайт при каждом push и раздаёт файлы с 300+ точек присутствия; каждый pull request
получает свой адрес предпросмотра. Небольшой серверный код (наши формы) выполняется в Pages
Functions, это Cloudflare Workers внутри того же проекта.

Плюсы для нас: бесплатный тариф без оплаты трафика; домен уже в Cloudflare, значит DNS,
TLS, WAF и кэш те же, что у API; ничего не стоит на наших серверах, нечему падать и нечего
обновлять; превью на каждый PR; откат к любому предыдущему деплою одной кнопкой; статика не
делит ресурсы с продажами и платёжной базой.

Бесплатный тариф (проверено 07.10): безлимитные запросы и трафик к статике, 500 сборок в
месяц (одна одновременно), до 20 000 файлов по 25 МБ, 100 своих доменов на проект;
Functions делят с Workers лимит 100 000 запросов в день и 10 мс процессорного времени на
запрос. Для витрины с несколькими формами в день это с запасом: платить не нужно. Платный
Workers Paid ($5 в месяц) понадобился бы только при более чем 100 000 отправок форм в день.

Минусы: сборка идёт на машинах Cloudflare (ограничение 500 в месяц, у нас будет 30–60);
Cloudflare с 2025 года развивает хостинг статики в основном внутри Workers (Workers Static
Assets) и рекомендует новые проекты делать там; Pages продолжает работать и поддерживаться,
а переход между ними это смена настроек деплоя, не сайта. Если хотите остаться полностью на
своём железе, запасной вариант: образ nginx по образцу `apps/tickets-page/Dockerfile` в Dokploy
на lead-parser, бесплатно, но на общем сервере с четырьмя WordPress-сайтами и стендом.

**Pages или сразу Workers (вопрос владельца 07.10).** Cloudflare Workers это их основная
платформа для кода на краю сети; с 2025 года Worker умеет сам раздавать папку статических
файлов (Workers Static Assets), и Cloudflare прямо говорит, что Workers «поддерживает
большинство сценариев Pages и даёт больше», а новые проекты советует делать там. Для нашей
витрины это выглядит так: один проект, в котором папка сборки Astro раздаётся как статика
(запросы к статике бесплатны и не считаются в лимит 100 000 в день, трафик не меряется), а
обработчики форм `/api/*` живут в том же Worker. Поддерживаются те же файлы `_redirects` и
`_headers`, сборка из GitHub (Workers Builds) с адресом предпросмотра на ветку, версии с
откатом и постепенным раскатыванием, у Astro есть официальный адаптер `@astrojs/cloudflare`.
Сверх Pages: настоящие логи и метрики Workers Observability (у Pages Functions логи были
слабым местом), cron-триггеры (например, еженедельный сдвиг дат демо-события, раздел 3.2),
Durable Objects, очереди, KV — на будущее, если витрине понадобится что-то серверное
(статус-страница, «пульс платформы»). Минусы: чуть больше конфигурации (`wrangler.jsonc`),
продукт моложе, и готовые инструкции в интернете чаще про Pages.

**Рекомендация меняется: строим сразу на Workers Static Assets**, не на Pages. Это снимает
будущий переезд, даёт логи и cron, а для статики стоит столько же: ноль. Если что-то в
Workers Builds окажется неудобным, папка сборки та же самая и переносится в Pages или в nginx
за час.

**Cloudflare Pages против nginx на своём сервере (вопрос владельца 07.10).**

| | Cloudflare Pages | nginx в Dokploy на lead-parser |
|---|---|---|
| Доступность | Нет своего origin, нечему упасть; не зависит от OOM и перезапусков lead-parser (аудит 17.09: 219 OOM за 30 дней) | Делит сервер с 4 WordPress-сайтами, n8n, стендом; падение хоста = падение витрины |
| Скорость | Файлы всегда на ближайшей к посетителю точке | Через оранжевое облако кэш тоже работает, но промахи и HTML идут в Фалькенштайн; нужен ручной сброс кэша при деплое |
| Деплой | push → сборка → превью на каждый PR → откат одной кнопкой | GitHub Actions → образ → Deploy в Dokploy, как tickets-page; превью PR нет |
| Обслуживание | Нулевое | Обновления образа nginx, место на диске, логи, сертификат (Traefik) |
| Логи запросов | Сырых access-логов на бесплатном тарифе нет (Logpush платный); есть Cloudflare Web Analytics (без cookie) и логи Functions с короткой историей | Полные access-логи nginx с `CF-Connecting-IP`, можно смотреть ботов и 404 построчно |
| Редиректы | Файл `_redirects`: до 2000 статических и 100 динамических правил; наша 301-карта (~400 строк) укладывается; сверх лимита есть Bulk Redirects на уровне аккаунта | `map` nginx без лимитов |
| Формы | Pages Functions (Workers): код специфичен для Cloudflare; минимизируем, оставляя логику в n8n (функция 30 строк: Turnstile + пересылка) | Любой обработчик, но его надо хостить и защищать самим |
| Переносимость | Сборка Astro это обычная папка файлов: переезд на nginx занимает час | То же в обратную сторону |
| Лишний домен | `project.pages.dev` дублирует сайт: ставим `noindex` и canonical для этого хоста (превью-деплои Cloudflare сам закрывает заголовком `X-Robots-Tag: noindex`) | Нет |
| Данные | Персональные данные только в отправках форм, они и так шли бы через Cloudflare (домен проксируется); DPA Cloudflare покрывает GDPR | То же: трафик уже идёт через Cloudflare |

Аналитика и отслеживание действий **не зависят от хостинга**: Umami, GA4/GTM, Meta Pixel,
Clarity это скрипты в странице и работают одинаково там и там. Разница только в сырых логах
сервера (см. таблицу). Для сквозной атрибуции «сайт → tickets.arenasoldout.com → оплата» нужен
не хостинг, а передача UTM в ссылки на страницы продаж и событие виджета `arena:order_paid` в
ту же аналитику; это бэклог SOC (источник заказа), а не вопрос витрины. Отправку формы можно
дополнительно фиксировать серверно (Function → Umami API), чтобы заявка считалась даже при
блокировщике рекламы.

SEO **тоже одинаково**, потому что Astro отдаёт готовый HTML со всем текстом (в отличие от
SPA tickets-page): hreflang, canonical, карта сайта, JSON-LD, OG-картинки и настоящие коды
404 живут в сборке, а не в хостинге. Что действительно влияет и что надо сделать правильно в
любом варианте: (1) сохранить завершающий слэш старых адресов WordPress (`/about/`), то есть
Astro `build.format: 'directory'` и согласованный `trailingSlash`, иначе каждый старый адрес
получит лишний прыжок редиректа; (2) закрыть дубликат `pages.dev`; (3) очередь IndexNow /
Crawler Hints и правила для AI-краулеров настраиваются на зоне Cloudflare и действуют в обоих
вариантах; (4) скорость: у Pages TTFB ниже во всём мире без усилий, у своего сервера нужно
настроить кэширование HTML и сбрасывать кэш при деплое. Разница в ранжировании от этого
небольшая, но в пользу Pages.

Итог: по аналитике и SEO паритет; выигрыш Pages в надёжности и нулевом обслуживании, выигрыш
своего сервера в сырых логах и безлимитных редиректах. Логи нам заменяет Umami, редиректы в
лимит укладываются.

### 3.7a Решение 07.10: Workers, с гарантией переезда на свой сервер без переделки

Владелец: пробуем Workers, но всегда держим возможность перекинуть всё на свой сервер.
Правила, которые делают переезд сменой одного места деплоя, а не переделкой:

| Слой | Правило | Как проверяется |
|---|---|---|
| Сборка | Astro только в режиме `static`: результат это папка `dist/` с обычными HTML/CSS/JS, никакого серверного рендера на запрос. Адаптер Cloudflare лишь упаковывает папку, сайт от него не зависит | CI собирает `dist/` один раз и из него делает ОБА артефакта: деплой в Workers и образ nginx |
| Редиректы | Один источник правды `redirects.yaml` (старый адрес → новый, код, язык). Скрипт генерирует из него `_redirects` для Cloudflare и `redirects.conf` для nginx | Тест прогоняет каждую строку карты против обоих выходов |
| Заголовки (CSP, кэш, безопасность) | То же: `headers.yaml` → `_headers` и nginx-сниппет | Тот же тест |
| Формы | Обработчик написан на веб-стандартных `Request`/`Response` через Hono (один и тот же код исполняется в Workers, Node, Bun, Deno). В репозитории две точки входа: `worker.ts` для Cloudflare и `server-node.ts` для контейнера. Сам обработчик тонкий: проверка Turnstile (обычный HTTP-вызов, работает откуда угодно) и пересылка в вебхук n8n | Один набор тестов обработчика; e2e-прогон форм против Worker и против контейнера |
| Состояние | На витрине его нет: ни KV, ни Durable Objects, ни D1. Заявки, подписки и демо-событие живут в n8n, Brevo и платформе | Ревью PR: любое новое Cloudflare-хранилище требует отдельного решения |
| Расписания | Сдвиг дат демо-события и прочие cron-задачи ставятся в n8n (у него есть расписания), а не в cron-триггер Worker | — |
| Секреты и переменные | Одинаковые имена (`TURNSTILE_SECRET_KEY`, `FORMS_WEBHOOK_URL`, `UMAMI_*`) что в `wrangler secret`, что в окружении Dokploy | `.env.example` один на оба варианта |
| Образ nginx | `Dockerfile` по образцу `apps/tickets-page` (non-root, healthcheck, кэш-политика) собирается в CI **на каждый push**, даже пока не используется, и проходит смоук: главная 200, редирект 301, заголовки на месте | Job `parity` в CI падает, если образ разошёлся с Workers-деплоем |
| Домен и сеть | Домен остаётся проксированным Cloudflare в обоих случаях: WAF, кэш, TLS, правила для ботов не меняются. Переезд = переключить `arenasoldout.com` с маршрута Worker на A-запись lead-parser | Runbook переезда в `docs/ops/` с проверочным списком, учение раз в квартал на `staging`-поддомене |
| Аналитика | Umami, не привязана к Cloudflare | — |

Чего сознательно **не** используем из Cloudflare, чтобы не привязаться: Cloudflare Images,
Email Routing внутри кода, D1/KV/R2 для сайта (R2 остаётся только для медиа платформы и
бэкапов, это уже так), Cloudflare Access для редактора, Smart Placement. Если такая
потребность возникнет, сначала проверяем, есть ли независимый аналог (n8n, платформа,
контейнер).

### 3.8 Готовность к редактору (решение 07.10: сначала тексты через Claude, Keystatic потом без переделки)

Чтобы потом подключить Keystatic (или аналог) одним файлом `keystatic.config.ts`, каркас
строится так с первого дня:

- весь контент только в `content/` (MD/MDX/YAML), ни одной строки текста в компонентах
  Astro; компоненты получают данные из коллекций;
- у каждой коллекции (`pages`, `posts`, `notes`, `changelog`, `cases`, `faq`,
  `pricing`, `people`) есть zod-схема (Astro content collections), которая один в один
  превращается в поля формы редактора;
- секции маркетинговых страниц описываются как структурированные блоки во frontmatter
  (`sections: [{type: hero, title, …}, {type: bento, items: […]}]`), а не свободным MDX с
  компонентами, чтобы редактор видел поля, а не код; свободный MDX остаётся только для
  статей блога;
- картинки в `content/**/images` рядом с материалом (Keystatic так умеет), не в `public/`
  вразнобой;
- репозиторий на GitHub, ветка `main` защищена, правки редактора идут через PR с превью
  Cloudflare, значит ничего не ломается молча.

При этих правилах подключение редактора это установка пакета, конфиг коллекций и выдача
прав GitHub редактору; структура сайта не меняется.

### 3.9 Стандарт рынков и платёжных провайдеров (решение 08.10: провайдеры и страны добавляются без переделки)

Владелец 08.10: кроме Stripe и Flitt у платформы уже есть **AllPay** (израильский шлюз:
Isracard, Leumi Card, Bit, рассрочка «ташлумим»), и это важно для продаж в Израиле;
провайдеры будут добавляться дальше, потому что планируется выход на Балканы (Сербия,
Черногория, Босния), в Южную Америку (все страны) и в Швейцарию, где своя платёжная система,
а не Stripe. Значит, сайт не может нести в текстах «ваш Stripe или Flitt»: провайдеры и
рынки становятся данными, как языки в 3.6.

**Что есть в коде на 08.10 (проверено):**

| Провайдер | Где работает | Статус для сайта |
|---|---|---|
| Stripe | hosted-чекаут виджета и страниц, вебхуки per-org | живой |
| Flitt | hosted-чекаут виджета (с 01.10, миграция 0120), EUR и GEL | живой |

На сайте AllPay показывается как провайдер платформы («Израиль: AllPay», живой для продаж с
сайта на WordPress); обещание «в виджете» появляется после задачи «AllPay в hosted-чекауте по
образцу Flitt» (redirect-оплата, подписанный callback, `payment_provider_configs`), которую
ставим до запуска нового сайта.

**Правила стандарта:**

1. **Данные, не прилагательные.** `content/data/providers/*.yaml`: `id`, `name`, `regions[]`
   (ISO-3166), `currencies[]`, `methods[]` (card, bit, installments…), `hosted_checkout:
   true|false`, `status: live|api|planned`, `since`. `content/data/markets/*.yaml`: `iso2`,
   `name` (по языкам), `languages[]`, `currencies[]`, `providers[]`, `status: live|planned`,
   `vat_note`. Schemas на zod, как у остальных коллекций (3.8).
2. **Тексты без имён провайдеров.** В прозе всех языков пишется «ваш платёжный аккаунт»;
   список имён подставляется из данных компонентом `<Providers status="live"/>` (бейджи
   текстом, логотипы только по лицензии). Проверка в CI: `grep -E "Stripe or Flitt|Stripe и
   Flitt"` в `content/**` даёт пустой результат.
3. **Страница `/payments`**: карточки провайдеров по регионам из данных, у каждой статус
   («в виджете», «через API», «готовим»), поддерживаемые методы, валюты, «как подключить за
   день» (ключи в своём аккаунте, деньги на свой счёт, платформа денег не держит).
   Планируемые рынки показываются только здесь, отдельным блоком «Готовим» без дат и без
   названий провайдеров, которые ещё не подписаны.
4. **Главная называет только живое.** Строка в блоке «Деньги»: «Организаторы продают в
   Чехии, Испании, Франции, Грузии и Израиле» (страны из `markets` со `status: live`), без
   «скоро».
5. **Тариф по валютам из данных.** Блок тарифа (4.4) читает `pricing/*.yaml` с ценой за
   билет по валюте (EUR, USD, ILS, GEL, RSD, CHF…); новая валюта это файл, не правка
   страницы. Пока владелец не назвал цены для новых валют, показываются EU/US/World.
6. **Рынок = язык + валюта + провайдер + право.** Добавление страны это: файл рынка,
   провайдер (если новый, то адаптер в платформе по образцу Flitt: redirect-оплата,
   подписанный callback, `payment_provider_configs`), язык из 3.6, строка в `/payments`,
   запись в `/changelog`. Сайт не трогается.
7. **Сегменты по рынкам в формах.** В `/start` поле «страна» из `markets` (живые и
   планируемые) и «провайдер, который у вас уже есть»; ответ попадает в Telegram владельцу
   как сигнал спроса по рынку, это и есть недорогая разведка Балкан и Южной Америки.

Что НЕ делаем на сайте: не обещаем конкретные провайдеры для Швейцарии, Балкан и Южной
Америки, пока адаптер не в коде; не ставим флажки стран в таблицах (анти-слоп T10), регионы
текстом; не делаем геолокацию с автоподстановкой цены, рынок выбирается явно.

### 3.10 Сайт для агентов (решение 08.10: ChatGPT, Perplexity, Claude и Gemini читают сайт наравне с Google)

Владелец 08.10: организаторы всё чаще ищут не в Google, а спрашивают ChatGPT и других
агентов; сайт должен отдавать агентам структурированную информацию максимально быстро. Это
третий стандарт рядом с языками (3.6) и рынками (3.9): всё, что знает сайт, должно быть
доступно машине без рендера JavaScript, в одном месте и в одном формате.

**Принцип: один источник фактов, три представления.** Факты о продукте (возможности, тариф по
валютам, провайдеры, рынки, языки, лимиты, клиенты с согласием, даты изменений) лежат в
`content/data/**` (zod-схемы из 3.8). Из них на сборке генерируются: (а) HTML-страницы для
людей, (б) Markdown-двойники для агентов, (в) JSON-LD и машинные файлы. Руками ничего из
этого не пишется дважды, поэтому агент и человек всегда читают одно и то же.

**Что сайт отдаёт агентам (всё генерируется на `astro build`):**

1. **`/llms.txt`** (стандарт Answer.AI): кто мы одним абзацем, список ключевых страниц с
   одной строкой описания каждая, ссылки на Markdown-версии; **`/llms-full.txt`**: весь сайт
   одним Markdown-файлом (без блога-архива, с changelog). Обновляются каждой сборкой.
2. **Markdown-двойник у каждой страницы**: `/pricing` → `/pricing.md` (и ответ `text/markdown`
   на `Accept: text/markdown` через правило в `headers.yaml`; на nginx тот же файл). Блог и
   changelog тоже: статья это и есть Markdown, отдаём исходник.
3. **JSON-LD на каждой странице из тех же данных:** `Organization` (с `sameAs`, контактами,
   юрлицом), `SoftwareApplication` (категория Ticketing, `offers` по валютам из
   `pricing/*.yaml`), `Product`/`Offer` на `/pricing` (цена за билет, валюта, условия),
   `FAQPage` на страницах с вопросами, `HowTo` на `/start` и в «три шага», `Article` с
   автором и датами в блоге, `BreadcrumbList`, `WebSite` с `SearchAction` (Pagefind).
   Валидность JSON-LD проверяется в CI (schema-dts типы + тест на каждую страницу).
4. **`/facts`**: одна страница-таблица «что есть, чего нет, с какой даты» (возможности из
   бэклога с датой появления, тариф, провайдеры, рынки, языки, лимиты нагрузки, бэкапы) и её
   JSON `/facts.json`. Это страница, которую агент процитирует вместо пересказа маркетинга;
   список «чего не обещаем» (4.3) там явно, чтобы агент не додумывал.
5. **Каждая страница отвечает на вопрос в первых 60 словах.** Заголовки h2 формулируются как
   вопросы организатора («Сколько стоит билет с местом?», «Куда приходят деньги?»),
   под ними короткий прямой ответ, затем подробности. Сравнения и тарифы только таблицами,
   числа с единицами и валютой, даты в ISO, никаких чисел на картинках и в PDF.
6. **Семантический HTML без зависимости от JS:** контент в `main`/`article`/`section`
   с заголовками по порядку, табы и аккордеоны отрисованы в HTML полностью (JS только
   переключает видимость), виджет в hero имеет текстовое описание рядом (`<noscript>` и
   обычный абзац), таблицы это `<table>`, не div-сетки.
7. **Публичная OpenAPI и доки для агентов-разработчиков:** `/developers/openapi.yaml` (копия
   из монорепо на сборке), `/developers.md`, примеры запросов текстом; это прямой путь, которым
   агент-кодер организатора встроит виджет.
8. **Ленты:** `/changelog.atom`, `/changelog.json` (JSON Feed), `/blog.atom`; `sitemap.xml`
   с `lastmod` из git-даты файла, `hreflang` для всех языков (3.6).
9. **Роботы: агентам разрешено.** `robots.txt` явно разрешает GPTBot, OAI-SearchBot,
   ClaudeBot, Claude-SearchBot, PerplexityBot, Google-Extended, Applebot-Extended, Bingbot,
   CCBot (`Allow: /`, запрет только на `/_states` и черновики). **В Cloudflare для зоны
   проверить и выключить «Block AI bots» / AI Crawl Control** (у новых зон блокировка AI-ботов
   может быть включена по умолчанию) и не включать Bot Fight Mode (см. урок Lampyris: он
   режет и платёжные вебхуки). Сверять раз в квартал список ботов с актуальной документацией
   OpenAI/Anthropic/Perplexity, имена меняются.
10. **Скорость = статика на краю.** Astro static без client-JS для контента, Workers Static
    Assets отдаёт HTML из кэша Cloudflare с TTFB в десятки миллисекунд, Markdown и JSON с
    `Cache-Control: public, max-age=300, stale-while-revalidate=86400`, Brotli, шрифты
    самохостом с `font-display: swap`, картинки AVIF/WebP с размерами. Планка: Lighthouse 100
    по всем четырём, TTFB < 200 мс из Европы и Израиля (проверять с `curl -w` из
    lead-parser и из дома владельца).
11. **Измерение:** в Umami отдельный отчёт по рефералам `chatgpt.com`, `perplexity.ai`,
    `claude.ai`, `gemini.google.com`, `copilot.microsoft.com` и по UTM `utm_source=chatgpt`;
    в Cloudflare смотреть аналитику AI-краулеров (какие боты что читают); раз в месяц задавать
    пяти агентам одинаковые вопросы («билетная платформа с рассадкой для театра в Праге,
    деньги на свой Stripe», «как продавать билеты через Telegram», «AllPay билеты Израиль») и
    фиксировать, цитируют ли нас и что именно, в `docs/marketing/agent_answers_log.md`.
12. **Позже, не сейчас:** read-only MCP-сервер на том же Worker (инструменты
    `get_pricing`, `get_providers`, `search_docs`) и `/.well-known/` манифест для агентов,
    когда стандарт устоится; данные для него уже лежат в `facts.json`, так что это тонкая
    обёртка, а не переделка.

**Чего не делаем:** не прячем текст для агентов в скрытые блоки (это клоакинг, санкции и у
поисковиков, и у агентов); не плодим страницы под каждый запрос; не покупаем «GEO-сервисы»;
не пишем для агентов отдельный текст, отличный от текста для людей.

**CI-проверки этого стандарта:** `llms.txt` и `.md`-двойники сгенерированы для каждой
страницы из карты сайта; JSON-LD валиден на каждой странице; на каждой странице есть h1, первые
60 слов без маркетинговых прилагательных (тот же regex, что в анти-слоп проверке T21);
`robots.txt` содержит список разрешённых агентов; Lighthouse 100.

### 3.11 Светлая и тёмная тема (решение 08.10: тема устройства по умолчанию, статистика по темам)

Вопрос владельца 08.10: можно ли понять, какая тема включена на устройстве, чтобы сразу
отдать её, а статистику собирать по обеим. Можно: браузер сообщает системную настройку через
медиазапрос `prefers-color-scheme` (`light` или `dark`; все современные браузеры, iOS и
Android, включая режим «авто по времени суток», тогда значение меняется в течение дня).
Серверу статический сайт это знать не обязан, решение принимает CSS до первой отрисовки,
поэтому мигания нет.

Правила:

1. **Порядок приоритетов:** явный выбор посетителя на сайте (переключатель в шапке, хранится в
   `localStorage`) → тема устройства → светлая. Инлайн-скрипт в `<head>` ставит
   `data-theme` из `localStorage` до рендера; CSS: токены на `:root`,
   `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) {…} }` и
   `:root[data-theme="dark"] {…}`; `<meta name="color-scheme" content="light dark">`, чтобы
   системные элементы (скроллбары, поля) совпадали. Так сделаны все прототипы и оболочка.
2. **Не выдаём темы «по очереди» поверх настройки устройства.** Посетитель с тёмной
   системой, получивший светлый сайт, воспринимает это как сбой, а не как вариант; такой
   эксперимент портит и конверсию, и данные. Статистика по темам собирается наблюдением, не
   принудительной ротацией: доля посетителей с тёмной системой, доля переключивших тему
   вручную и в какую сторону, конверсия в `/start` по теме.
3. **Что пишем в Umami** (без cookies, один event на просмотр): `system_theme`
   (`matchMedia('(prefers-color-scheme: dark)').matches`), `theme` (что фактически показано),
   `theme_source` (`device` / `choice`); событие `theme_toggle` при переключении; слушатель
   `change` на медиазапросе фиксирует переход устройства днём/вечером. В Cloudflare/Umami
   этого нет из коробки, поэтому это наш маленький скрипт в базовом layout.
4. **Ротация допустима только внутри сегмента без сигнала:** если когда-нибудь захочется
   A/B-теста тёмной темы, чередовать можно лишь у посетителей, чья система светлая и кто не
   делал выбора, и только для дизайна, не для текста; решение отдельное, в этой волне не
   делаем.
5. **Виджет и билет живут по другим правилам:** виджет на чужом сайте следует токенам сайта
   организатора (`--arena-*`), а не устройству; страницы `tickets.arenasoldout.com` следуют
   устройству, как витрина; e-ticket PDF всегда светлый (печать); письма получают
   `color-scheme: light dark` в `<head>`, тёмный режим почтовых клиентов проверяется отдельно.
6. **Контраст в обеих темах проверяется в CI** (4.5:1 для текста, см. 3.8/QA), тёмная тема
   без неонового свечения (анти-слоп T20); токен акцента тёмной темы `#6F8CFF` выбран по
   контрасту 6.2:1 с тёмным текстом кнопки.

### 4.1 Позиционирование (из конкурентных документов, подтверждено кодом)

Arena это **инфраструктура организатора, не афиша и не маркетплейс**. Сильные стороны, которые
можно говорить с опорой на код:

- рассадка в ядре: схемы залов с версиями, импорт SVG, гибрид мест и GA, цены по категориям;
  публичный тезис «рассадка без доплаты» ждёт подтверждения владельца (К1);
- деньги идут на счёт организатора через его платёжный аккаунт (Stripe, Flitt, AllPay в
  Израиле; список провайдеров из данных, см. 3.9), платформа денег не держит;

2. **Полоса доверия:** только факты (35 стран с 2019, 800 заказов в минуту, 7 языков,

## 5. Дизайн

### 5.1 Что взять у Stripe и у билетных (из обзора 07.10)

1. Hero: один результат-заголовок, один подзаголовок, две кнопки («Начать» и «Посмотреть
   демо»), справа **живой виджет** со схемой зала вместо картинки; фон — фирменный градиент
   с медленной анимацией (как у Stripe), выключаемой по `prefers-reduced-motion`.
2. Полоса доверия: 2–3 настоящие цифры, логотипы клиентов (с согласия), бейджи GDPR/PCI.
3. Bento-сетка возможностей с настоящими скриншотами (админка, бот, схема зала, PDF билета).
4. Тариф в одну строку на главной и подробно на `/pricing` с калькулятором.
5. Страницы `/compare/*` для SEO и возражений.
6. Сегменты как отдельные посадочные с кейсом и цифрой.
7. Блок для разработчиков с кодом (3 строки встраивания) рядом с живым результатом.
8. Вход без трения: «карта не нужна», «или начните в Telegram».
9. Человеческий тон и конкретика, никаких «№1».

### 5.2 Три направления (прототипирую как кликабельные страницы)

| | A «Инфраструктура» | B «Сцена» | C «Продукт вперёд» |
|---|---|---|---|
| Идея | Stripe-подобная: светлый фон, градиентный меш, строгая сетка, код рядом с UI | Тёмная «сцена»: глубокий индиго/чёрный, свет прожектора, Playfair Display в заголовках, фото реальных залов | Белая страница, где главное — сам виджет и скриншоты; минимум декора, как у Luma |
| Шрифты | Inter (или Geist) везде, моно для кода | Playfair Display + Inter | Inter |
| Для кого сильнее | Разработчики, площадки, операторы | Театры, гастроли, культурные центры | Небольшие организаторы «не IT» |
| Риск | Слишком «финтех», холодно для театра | Темнота тяжелее для текста и SEO-страниц | Может выглядеть «бедно» без сильного продукта в кадре |

Рекомендация: **A как каркас, с акцентами B** (Playfair только в крупных цитатах и заголовках
сегментов «Сцена/Театр», тёмные секции для «ночных» сюжетов: Telegram, сканирование на входе),
живой виджет из C в hero. Решение 18.09 про Playfair + Inter сохраняется, но Playfair
становится акцентом, а не основным заголовочным шрифтом.

Цвет: индиго Arena Sold Out (`DefaultAccentColor` билета) как основной, градиент индиго →
бирюза → тёплый коралл (ссылка на оранжевый старого сайта) для hero, нейтральные серые.
Токены те же, что у виджета, чтобы виджет в hero не выглядел чужим. Тёмная тема по
`prefers-color-scheme` с первого дня (у Stripe её нет, у нас будет).

### 5.3 Как прототипируем

1. Мудборд и токены (цвета, шрифты, радиусы, сетка) одной страницей.
2. Главная в трёх направлениях как HTML-артефакты (мобильная и десктопная ширина).
3. Выбранное направление: главная + `/pricing` + одна страница сегмента + страница статьи +
   страница `/start` как прототип с настоящим виджетом (demo feed-токен).
4. Критика по чек-листу `design:design-critique` и доступность `design:accessibility-review`,
   потом в код Astro.

- Не строим каталог событий для покупателей на сайте (это tickets-page и, возможно, позже
  витрина; решение 27.09 «не афиша»).
- Не ставим GTM/пиксели до решения рекламировать сайт; без них нет и баннера.
- Не публикуем цены конкурентов без перепроверки.
- Не называем клиентов без их согласия.

   прототипов и фирменного стиля там нет; прототипы делаем HTML-артефактами, которые сразу

Search Console (чтение), токен бота для канала, аккаунт Umami.
