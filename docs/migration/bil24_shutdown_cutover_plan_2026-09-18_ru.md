# План недели: боевой запуск Arena до отключения сервера Bil24

Дата: 18.09.2026. Статус: **план, изменения не выполнялись.**
Вводная владельца: сервер Bil24 перестаёт работать примерно через неделю (точную дату и час — уточнить). До этого нужно провести реальные тесты и перевести Lampyris и Vino&Co на Arena. Основной тестовый сайт — arenasoldout.com, дополнительно staging Lampyris и staging Vino&Co.

## 1. Факты, на которых стоит план (проверено 18.09)

- `api.bil24.pro` и `api.tixgear.com` — **один и тот же сервер** 116.202.82.211 (PX62). По словам владельца (18.09), адрес TixGear уже не используется; на какой именно адрес сейчас смотрит прод Vino&Co, прочитать из базы сайта не удалось — **уточнить у владельца или в админке сайта**. В любом случае оба сайта зависят от одного PX62 и гаснут вместе. После отключения **отката на Bil24 не существует**.
- Стенд Arena = стек `arena-backend` на lead-parser, тег `99c64f1`, `APP_ENV=staging`, `OUTBOX_MODE=noop`, `TRUSTED_PROXY_COUNT=1`. Через неделю он де-факто становится продом. При этом: **бэкапа его Postgres нет**, хост ловит 219 OOM-kill за 30 дней, firewall отсутствует (см. `docs/ops/infra_audit_2026-09-17_ru.md`).
- Lampyris staging ↔ стенд: полный прогон закрыт 13.09 (создание GA-мероприятия → покупка → билет → MACS → возврат), окно оплаты 20 мин со Stripe manual capture проверено 14.09. - Импорт Arena переносит проданное: для мест с рассадкой `seatList.available:false` становится `unavailable` с сохранением ID Bil24 (`himports/seating.go`); для GA переносится остаток `availability`. **Сами билеты, проданные через Bil24, в Arena не попадают** — MACS их уже знает, но возврат такого билета через Arena не освободит место.
- Мероприятия с рассадкой сегодня размечаются в редакторе Bil24. **После отключения редактора не будет.** Уже импортированные планы залов в Arena переиспользуются для новых сеансов, поэтому все нужные залы надо импортировать, пока Bil24 жив.
- arenasoldout.com сейчас — сайт-витрина без WooCommerce и без набора плагинов продаж (`bil24-acf-sync`, `lampyris-ops`, cart-bridge, notification-receiver, ticket-mailer). Сделать его тестовым магазином = развернуть на нём тот же набор, что на Lampyris.

## 2. Принцип расписания

Переключение прод-сайтов — **не позже чем за 2 суток до отключения Bil24**, чтобы остался запас на исправления при ещё живом Bil24 (сверка данных, повторный импорт). Инфраструктурная перестройка из аудита сжимается до минимума, который защищает боевые продажи; остальное — после недели.

## 3a. Освобождение сервера Arena (lead-parser) от WordPress — пошагово

Решение владельца 18.09: на сервере, где живёт Arena, WordPress быть не должно. Сейчас там четыре сайта. По контрактной изоляции они уезжают на **два** новых сервера, а не на один:

| Сайт на lead-parser | RAM сейчас (WP + MySQL) | Куда |
|---|---|---|
| vinoandco.events (прод, клиент) | ≈ 1.0 + 0.5 ГБ — главный потребитель, его MySQL убивает OOM | **Сервер Vino&Co + туры** (новый CX33) |
| arenasoldout.com (свой, тестер) | ≈ 0.46 + 0.23 ГБ | **Сервер собственных сайтов** (новый CX33) |
| marinabakanova.com (свой) | ≈ 0.22 + 0.13 ГБ | сервер собственных сайтов |
| ndarchdesign (свой) | ≈ 0.1 ГБ | сервер собственных сайтов |

После переезда на lead-parser освобождается ≈ 2.7 ГБ RAM, исчезает основная причина OOM, и Arena остаётся с n8n, ботом, pr-top и MACS-кандидатом.

Порядок (каждый сайт — после approval):

1. **Заказ и подготовка (владелец + я):** два CX33 в Hetzner (fsn1), имена `wp-own-1` и `wp-vino-1` (без одинаковых hostname). Hardening: ключи, `PasswordAuthentication no`, Hetzner Firewall (22 по allowlist, 80/443 только с Cloudflare), fail2ban, unattended-upgrades, `daemon.json` с лимитом логов. Docker; подключение к текущему Dokploy на lead-parser как **remote server** (control plane переедет позже, сейчас не трогаем).
2. **Шаблон на каждом новом сервере:** Traefik (ставит Dokploy), общий MariaDB 11 LTS с лимитом 2 ГБ, Redis, шаблон compose сайта с `mem_limit`.
3. **Пилот — ndarchdesign** (самый безопасный): дамп БД + архив тома `wp_app` → импорт в MariaDB нового сервера → compose из шаблона → проверка по sslip-домену → смена origin-IP в Cloudflare → наблюдение. Откат = вернуть IP.
4. **arenasoldout.com** тем же способом (БД 751 МБ, uploads 471 МБ; окно ≈ 15 мин). Сразу после переезда — превращение в тестовый магазин (шаги 8 недели).
5. **marinabakanova.com** тем же способом (сейчас отдаёт 403 и через Cloudflare, и напрямую — разобраться до переезда, чтобы не перенести поломку).
6. **vinoandco.events** — в окно низкого трафика, с заморозкой заказов на 15 минут: финальный дамп, перенос `wp_app` (3.0 ГБ, включая локальные архивы Updraft 1.5 ГБ — их не переносить), кастомный образ собирается Dokploy на новом сервере из того же репозитория, перенос host-cron `wp-cron`, проверка checkout с AllPay/PayPal, смена origin-IP. **Сделать это до переключения Vino на Arena (Д5) минимум за сутки** — не менять сервер и бэкенд одного клиента в один день. Вебхук деплоя `vino-webhook.service` (порт 9876) переносится вместе с сайтом или заменяется деплоем Dokploy.
7. **Уборка на lead-parser** после 3–7 дней стабильной работы: остановить старые стеки (не удалять тома до конца недели), убрать мёртвый cron `84umlx`, позже — удалить тома, образы vino (7.7 ГБ) и `/home/dev/wp-dev`.

Привязка к дням недели: шаги 1–3 — Д0–Д1; arenasoldout.com — Д1; marinabakanova — Д2; vinoandco.events — Д2–Д3 (до импорта мероприятий и задолго до Д5).
