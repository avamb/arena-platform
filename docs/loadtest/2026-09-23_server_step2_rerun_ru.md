## 1. Что поднято

Те же два сервера в nbg1 с теми же адресами: копия `arena-loadtest-1`
(cpx22 → cpx32), генератор `arena-loadgen-1` (ccx13 сразу, чтобы лимит
общих ядер проекта не мешал Rescale). Тот же compose копии и тот же Traefik,
образ `4434b93` вместо `d84a4de`; свежая база с seed; тот же k6-набор.
Новое в инструменте: `capacity.mjs` на каждой ступени снимает
`pg_stat_activity` копии и считает ответы api по его логу (ssh с генератора
на копию), так что вердикт «транспорт, не arena» подтверждается фактами.

## 2. Метод

Ровно как 22.09 (§2 того отчёта): ступени по 3 минуты, 5 посетителей на
заказ в минуту с потолком 1000, те же пороги. Каждый опыт с виджетом на
cpx22 выполнен дважды: с пулом 20 (как прод на момент 22.09) и с пулом 60
(как прод сейчас), чтобы отделить эффект кода от эффекта настройки.

## 4. Что изменилось и почему

### 4.1. Чистый эффект кода (cpx22, пул 20 — как на проде 22.09)

| Опыт | 22.09 | 23.09 |
|---|---|---|
| лестница виджета до 400/1000 | 200 ok, на 300–400 конвой: 19 ok / 1 182 неудачных, p95 33 с | все ступени чисто, на 400 — 1 138 ok, p95 101 мс, p99 3,3 с |
| 300 заказов/мин, 1 000 посетителей | 16 ok / 734 неудачных, p95 31 с | 901 ok / 0, p95 112 мс |
| два сеанса × 200, 2 × 500 посетителей | 2 × 11 ok / 2 × 590 неудачных | 601 + 601, p95 86 / 94 мс |
| `pg_stat_activity` в разгар ступени | 18 бэкендов ждут строку сеанса, держатель — `idle in transaction` | 0 ждут, 0 idle in tx, 1–2 активных на каждой ступени |

Механизм вчерашнего провала — транзакция удержания держала строку сеанса и
между операторами брала из пула api второе соединение; когда толпа
читателей занимала пул, удержание ждало соединение, держа блокировку, и
следующие покупатели вставали за ним, пока пул не заполнялся ожиданиями.
В образе `4434b93` чтения цен, промо-лимитов и конфига оплаты идут либо
до открытия транзакции, либо через её же соединение (`WithTx`), второго
соединения внутри блокировки больше нет — и очередь на строку сеанса
исчезла вместе с ним, что снимки `pg_stat_activity` на каждой ступени и
показывают. Индекс 0109 в этих прогонах роли не играет (сеансы по 2–6
тысяч мест), он для 20–50-тысячных категорий.

### 4.2. Пул 20 против 60 на двух ядрах

Установившийся режим одинаков (api 26–30 %, postgres 55–75 %, 1–4 активных
бэкенда). Разница — в залпах: каждая ступень лестницы и каждый опыт
стартуют с одномоментным приходом 1 000 посетителей и первой волны
покупателей. При пуле 20 залп выстраивается в очередь за соединением
внутри api; при пуле 60 он проходит в Postgres целиком, 13–35 удержаний
встают за строкой сеанса уже в базе, postgres на 120–125 % двух ядер, и
p95 всего прогона получает хвост 0,8–0,9 с (§3.3, §3.4). Вчерашний
«хвост от CPU при пуле 60» был тем же залпом после перезапуска api.
На cpx32 залп поглощается четырьмя ядрами: ни одного ожидания
блокировки за всю лестницу 200/400/600/800 (§3.5). Итог: пул 60 —
правильная настройка для прода (4 ядра), но не универсальный рецепт
для маленького сервера.

### 4.3. Что не изменилось

cpx32 при пуле 60 — в пределах шума вчерашнего (p95 94/85/70/70 мс против
82/70/63/87); шлюз в обоих режимах — те же 220–340 мс пути, заданные
последовательностью команд плагина; Cloudflare — те же 70–110 мс сверху.
Ограничения метода те же, что 22.09 §5: один сеанс на продажу, толпа не
больше 1 000 (генератор), GA-сеансы по 2–6 тысяч мест.
