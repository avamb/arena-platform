# Нагрузочное тестирование arena — шаг 1, локальный стенд

Дата: 2026-09-13. Окружение: локальный docker compose на машине разработчика
(Docker Desktop, 16 ядер, 15 ГБ), образ API собран с master `5fca24d`.
Серверы (стенд, стейджинг, продакшн) не затрагивались.

Целевая нагрузка, согласованная с владельцем: **200 одновременных посетителей
и 50 заказов в минуту** на одно мероприятие в момент старта продаж.

Проверялись оба входа, через которые arena продаёт билеты:

- **Шлюз, совместимый с Bil24** (`/compat/bil24/json`). Через него продают
  переезжающие WordPress-сайты (Lampyris, Vino&Co).
- **Собственное публичное API** (фид → `checkout/start` → оплата → статус).
  Через него работает встраиваемый виджет.

Набор тестов и инструкция по запуску: `ops/loadtest/README.md`, раздел
«Sales-path suite».

## Итог в одном абзаце

Двойных продаж нет ни на одном входе, остатки в базе сходятся после каждого
прогона. Шлюз держит целевую нагрузку: 248 покупок за 5 минут, билеты выпущены
все. Но найдены два дефекта, которые блокируют реальные продажи: брошенные
корзины никогда не возвращаются в продажу, а виджет одной площадки не может
принять больше 100 запросов в минуту на всех покупателей сразу. Ещё три
дефекта серьёзны, но проявляются реже.

## Находки

Порядок — по влиянию на продажи.

### 1. Брошенные брони никогда не освобождаются — КРИТИЧНО

Если покупатель забронировал билеты и ушёл, билеты остаются заблокированными
навсегда. Мероприятие показывает «распродано», хотя ничего не продано.

- **Доказательство.** Сценарий `gateway.js SCENARIO=expiry`: 20 покупателей
  бронируют весь пул и уходят. Срок брони 120 с. Через 240 с новый покупатель
  получает «Category is sold out». Аудит: 20 броней в состоянии `draft`,
  срок истёк, `capacity_held = 20`, продано 0.
- **Причина.** Код освобождения есть (`hcheckout.ReservationProcessor.ProcessExpiredReservations`),
  но его не вызывает ни API, ни `arena-worker`: в `registerBuiltinHandlers`
  такой задачи нет. Периодическая `order.expire_sweep` закрывает только
  заказ и сама в комментарии ссылается на «существующий обработчик TTL
  броней», которого нет.
- **Масштаб.** Механизм броней общий, поэтому страдают оба входа. Скорее всего,
  именно этим объясняется «распродано» у категории Standard на тестовом
  мероприятии стейджинга Lampyris. На сервере это не проверялось.
- **Что сделать.** Зарегистрировать периодическую задачу в `arena-worker`,
  которая вызывает `ProcessExpiredReservations`. Покрыть интеграционным тестом
  «бронь истекла → остаток вернулся».

### 2. Лимит 100 запросов в минуту на весь виджет площадки — КРИТИЧНО для виджета

Публичное API ограничивает частоту запросов по токену фида: 100 в минуту.
Токен один на канал продаж, то есть на всех покупателей виджета сразу.

- **Доказательство.** Полный поток через собственное API (200 посетителей,
  50 заказов в минуту, у каждого посетителя свой IP): 15 884 из 16 543
  запросов получили 429 `feed.rate_limited`, прошли 6 покупок из 250.
  Гонка за 10 билетов: 100 из 200 покупателей получили 429 ещё до попытки.
- **Причина.** `newPublicFeedRateLimiter(100, 300)` в `httpserver/wire.go`,
  значения зашиты в код, настройки нет.
- **Что сделать.** Считать лимит по посетителю, а не по площадке, и сделать
  его настраиваемым. См. также находку 8 про доверие к X-Forwarded-For.

### 3. Покупатель виджета не видит оплаченный заказ — ВЫСОКИЙ, требует проверки на Stripe

После успешной оплаты заказ помечается оплаченным, бронь переходит в
проданные, билеты выпускаются. Но `checkout_sessions.state` остаётся
`pricing_confirmed`. Публичный статус (`GET /v1/public/checkout/{token}`)
поэтому отвечает `pending` и не отдаёт билеты.

- **Доказательство.** Все 6 оплаченных покупок полного прогона и все
  покупки малого прогона: заказ `paid`, билеты есть, чекаут `pricing_confirmed`.
- **Оговорка.** Оплату в тесте эмулирует вебхук платёжного намерения,
  настоящего Stripe локально нет. Нужно проверить, завершает ли боевой путь
  Stripe чекаут иначе.
- **Связанное.** Вебхук принимает `succeeded` только из состояния `processing`.
  Прямой переход `created → succeeded` подтверждается ответом 200 и молча
  игнорируется. Stripe для карт часто присылает сразу `succeeded`. Если боевой
  путь идёт через этот обработчик, оплата будет потеряна без ошибки.

### 4. Взаимная блокировка при бронировании через шлюз — ВЫСОКИЙ

Под параллельной нагрузкой бронь иногда падает с ошибкой базы
`deadlock detected`. Сайт получает код -99, «внутренняя ошибка, не повторять».

- **Доказательство.** 2 случая за 5 минут полного прогона (13,7 тыс. запросов),
  лог `RESERVATION: cart mutation failed ... 40P01`.
- **Причина.** `hcheckout.CreateGAHold` (создание новой корзины) сначала
  блокирует `inventory_ledger`, потом строку `sessions` (`seat_status_version`).
  `ExtendHoldTx`, `ShrinkHoldTx`, `CreateSeatedHold` берут те же строки в
  обратном порядке. Повтора при 40P01 нет. `writeCartHoldError` отдаёт -99
  вместо -1.
- **Что сделать.** В `CreateGAHold` поднять `IncrementSessionSeatStatusVersion`
  перед `ReserveCapacity`. Добавить короткий повтор при 40P01/40001. Отдавать
  -1 на инфраструктурные ошибки. Тест: параллельные создание и сокращение
  корзины на одном GA-сеансе.

### 5. Потолок производительности шлюза — СРЕДНИЙ

Каждая команда шлюза проверяет токен сайта через bcrypt, кэша нет.

- **Доказательство.** Даже простейшая команда отвечает не быстрее 50 мс,
  тогда как чтение фида собственного API — 5–8 мс. При 44 запросах в секунду
  API занимал 3–4 ядра, база — около 30 %. Замер bcrypt cost 10 на этой
  машине: 50–190 мс процессорного времени на вызов.
- **Влияние.** 50 заказов в минуту шлюз держит. В пике одновременных
  бронирований (гонка 200 покупателей) каждое бронирование ждало около 3 с.
  Все брони на одном сеансе к тому же выстраиваются в очередь на строке
  `sessions` (см. находку 4).
- **Что сделать.** Кэшировать успешную проверку токена в памяти
  (например, по SHA-256 токена с коротким сроком жизни).

### 6. Выдача доступа к шлюзу обнуляет срок брони канала — СРЕДНИЙ

`PUT .../channels/{id}/gateway-credential` сбрасывает
`sales_channels.reservation_ttl_override` в NULL. Бронь получает стандартные
20 минут вместо настроенного срока.

- **Доказательство.** Канал создан с 120 с, после PUT в базе NULL
  (воспроизведено вручную).
- **Причина.** В `UpdateSalesChannel` (`queries/channels.sql`)
  `reservation_ttl_override = $8` присваивается всегда, в отличие от
  остальных полей. Любой частичный вызов обновления канала стирает настройку.

### 7. Второй заказ того же покупателя закрывает первый — СРЕДНИЙ

arena держит один неоплаченный заказ на покупателя в сеансе, покупатель
определяется по email и телефону. `CREATE_ORDER_EXT` с тем же email истекает
предыдущий заказ, даже если у него своя действующая бронь. Оплата первого
заказа (`PAY_ORDER`) затем падает `invalid status transition: expired → paid`
и отдаётся сайту как временная ошибка.

- **Когда бывает.** Покупатель оформляет два заказа в двух вкладках. Деньги за
  первый уже списаны WooCommerce, а билетов нет и ручная проверка не
  запускается.
- **Доказательство.** Воспроизвелось в первом прогоне, где у тестовых
  покупателей был общий email. В тестах это исправлено.

### 8. Ограничитель частоты доверяет X-Forwarded-For — НИЗКИЙ, безопасность

`httputil.ExtractClientIP` берёт первый адрес из `X-Forwarded-For`, который
присылает сам клиент. Лимит по IP обходится подменой заголовка. Словари
счётчиков в ограничителе не очищаются, поэтому поток подменённых адресов
растит память.

### 9. Мелочи

- Старые сценарии `scanner.js` и `checkout.js` не могли авторизоваться:
  `shared/auth.js` слал поля, которые сервер отвергает. **Исправлено.**
- Workflow `.github/workflows/load-test.yml` ни разу не запускался.
- OpenAPI описывает создание канала полями `{name, type}`, сервер требует
  `payment_mode`, `provider`, `provider_account_id`.

## Ограничения шага 1

- Цифры скорости сняты на Docker Desktop под Windows. Они показывают порядок
  величин, а не боевые значения. Честные цифры даст шаг 2 на отдельной копии
  стенда.
- Настоящий Stripe не участвовал, оплата виджета эмулирована.
- Вебхуки на сайты и MACS не нагружались: воркер локально работает в режиме
  без отправки. Это отдельный сценарий.
- Пропускную способность собственного API без лимита измерить нельзя, пока
  лимит зашит в код.
