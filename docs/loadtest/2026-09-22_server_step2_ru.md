# Нагрузочный прогон на сервере — шаг 2 (22.09.2026)

Цель, поставленная владельцем: определить, какая инфраструктура нужна
для минимальной, средней и высокой нагрузки — ступенчато поднимать
нагрузку до предела, назвать, во что упирается стенд, и дать матрицу
серверов. Прод (`arena-platform-prod-1`, 178.105.217.195) не трогался.

## 0. Итог

- **Текущий прод (cpx32, 4 vCPU AMD, 8 ГБ) закрывает все три уровня с
  запасом**, если поднять пул соединений api: виджет — 800 заказов/мин в
  один сеанс при 1000 одновременных посетителей (путь p95 87 мс, api 40 %,
  postgres 1,2–1,4 ядра из 4); шлюз — 800 заказов/мин (p95 229 мс, api
  1,5 ядра, postgres 1,2). Для «высокого» уровня (1000 посетителей, 200
  заказов/мин) это запас ×4 по заказам; по посетителям выше 1000 наш
  генератор не заходит.
- **Минимальный и средний уровни держит и cpx22** (2 vCPU, 4 ГБ, €0,031/ч):
  виджет чист до 200 заказов/мин при 1000 посетителей (p95 172 мс), с
  пулом 60 — до 400; шлюз — до 400 заказов/мин.
- **Первым ломается не процессор, а транзакция удержания мест + пул
  соединений api (20).** Под толпой читающих посетителей транзакция,
  держащая строку сеанса, удлиняется, очередь на ней выедает пул, и всё
  встаёт до таймаута клиента — CPU при этом свободен. `DB_POOL_MAX_CONNS=60`
  на том же cpx22 превращает 11 покупок из 601 в 601 из 601. На cpx32
  прод-настройка (пул 20) держит 300 заказов/мин + 1000 посетителей, но
  рычаг тот же — поднять пул стоит и на проде.
- **Модель нагрузки решает больше, чем сервер**: шлюз с «одним
  GET_ALL_ACTIONS на посетителя» ломается на 50 заказах/мин, «как сайты
  пользуются шлюзом» (плагин с кэшем) — чист на 400 на той же машине; сеанс
  на 60 000 мест делает команды удержания в 8 раз дороже, чем на 2 000.
- Через Cloudflare (оранжевое облако) всё работает, +100–150 мс к пути
  покупки, адрес посетителя доходит правильно при `TRUSTED_PROXY_COUNT=3` и
  диапазонах Cloudflare в `trustedIPs` Traefik — прод-Traefik этого не
  делает (см. §6).
- Точка «8 vCPU» не снята: лимит общих ядер проекта Hetzner и отсутствие
  нужды — на 4 vCPU высокий уровень пройден с четырёхкратным запасом.

## 2. Метод

Лестница `capacity.mjs`: одна ступень = 3 минуты k6 на фиксированной
интенсивности заказов (`constant-arrival-rate`) плюс толпа читающих
посетителей (`constant-vus`, 5 посетителей на заказ в минуту, потолок
1000 — столько держит генератор на 2 vCPU). Ступени 10, 25, 50, 100, 200,
400 заказов/мин, пауза 45 с. Ступень «сломана», если: доля ошибок > 0,5 %,
p95 полного пути покупки > 1 с, есть неудачные покупки, оплаченные
билеты не показаны покупателю, или k6 не удержал темп (dropped
iterations — предел генератора, а не стенда). Отдельно считаются 5xx
(стенд) и транспортные ошибки (путь до стенда).

Полный путь покупки: виджет — список событий → событие → `checkout/start`
(hosted-сессия на заглушке) → подписанный вебхук
`checkout.session.completed` → опрос статуса до появления билетов; шлюз —
CREATE_USER → GET_ALL_ACTIONS → RESERVATION → GET_CART →
CREATE_ORDER_EXT → PAY_ORDER → GET_TICKETS_BY_ORDER.

Уровни нагрузки (черновик, ждёт подтверждения владельца):

| Уровень | Посетителей одновременно | Заказов/мин |
|---------|--------------------------|-------------|
| минимальный | 50 | 10 |
| средний | 200 | 50 |
| высокий | 1000 | 200 |

Пул мест на лестницу — 6 000 (большой зал; заказ берёт 1–3 билета);
причина именно такого размера — в §3.1.

## 3. Находки до лестницы

### 3.1. Стоимость GA-команд растёт с размером категории

Один и тот же cpx22, пустой стенд, 1 посетитель, 6 заказов/мин, медианы:

| Команда шлюза | пул 60 000 мест | пул 2 000 мест |
|---------------|-----------------|----------------|
| RESERVATION | 443 мс | 56 мс |
| GET_CART | 199 мс | 19 мс |
| CREATE_ORDER_EXT | 205 мс | 21 мс |
| GET_ALL_ACTIONS | 48 мс | 49 мс |
| путь покупки | 970 мс | 147 мс |

Команды, которые держат или считают места категории, читают все места
категории, а не только свободные — 30-кратный пул даёт 8–10-кратную
задержку. Для реальных залов (сотни — несколько тысяч мест) это
десятки миллисекунд; для стадионной GA-категории на 20–50 тысяч мест —
сотни. GET_ALL_ACTIONS от размера пула не зависит. Отдельная задача на
индекс/запрос (`session_seats` по `(session_id, tier_id, status)`), не
блокер запуска.

### 3.2. За настоящим прокси посетители сливаются в один IP

Traefik по умолчанию затирает клиентский `X-Forwarded-For`, генератор —
один адрес, и `PUBLIC_API_IP_RATE_LIMIT` (600/мин) резал виджет уже на 20
заказах/мин: 98 × 429, 2 неудачные покупки. На копии генератор внесён в
`forwardedHeaders.trustedIPs` Traefik и `TRUSTED_PROXY_COUNT=2`. Для прода
это напоминание: за Cloudflare без `trustedIPs` для его диапазонов api
видит только адрес edge-узла (в `~/.ssh`-заметке 2026-09-14 это уже
записано), и per-IP лимит превращается в общий.

### 3.3. Мелочи стенда

- Docker 29 отказывает API-клиентам ниже 1.40, Traefik просит 1.24 →
  `"min-api-version": "1.24"` в `daemon.json`.
- Образ `grafana/k6` не root → `results/` на генераторе с правом записи.

Ресурсы копии на ступени 200: api 24 %, postgres 54 %, Traefik 13–19 %

**Что сломалось на 400.** `capacity.mjs` по формальному признаку записал
«транспорт, не arena» (0 × 5xx на стороне k6, статус 0 = таймаут 30 с), но
лог api говорит обратное: за ступень api завершил 9 284 запроса, из них
8 203 дольше 5 с, максимум 30 с; 243 × 500 и 931 × 503 — k6 их уже не
дождался. Монитор: 20 из 20 соединений пула api заняты, 19 ждут
блокировку, самая длинная транзакция 13–28 с, CPU postgres при этом
22–55 %, api 5–27 % — процессор свободен. Postgres логирует отменённый
`UPDATE sessions SET seat_status_version = seat_status_version + 1`: это
та самая блокировка строки сеанса, которую по правилу порядка
блокировок берёт каждая транзакция удержания мест
(`hcheckout.createGAHoldTx`). Все заказы лестницы идут в ОДИН сеанс, и
при ~7 чекаутах в секунду очередь на его строке становится длиннее, чем
пул соединений api (20): следующие запросы — включая список событий и
вебхуки оплаты — ждут свободного соединения, пока клиент не отвалится
по таймауту (`context canceled` во всех 4 000 + 4 000 ошибках списка
тарифов и медиа, 932 отказа «payment config: failed to load the
organization» — это тоже ожидание соединения, а не платёжный конфиг).

Вывод по механике: предел виджета на этом сервере — **между 200 и 400
заказами в минуту в один сеанс**, и упирается он не в CPU, а в
последовательность транзакций удержания на строке сеанса плюс размер
пула соединений. Хвост p99 3,4 с на ступени 200 — начало той же очереди.
Сдвигается ли граница с сервером — покажут cpx32 и cpx42 (§4.3–§4.6);
если нет, это предел «на сеанс», и продажи нескольких событий
складываются, а один ажиотажный сеанс — нет.

блокировок нет, до 18 активных запросов. Команды (медиана / p95):

Здесь упор — **CPU базы**, и его создают не покупатели, а читатели
каталога: 250 читателей × один GET_ALL_ACTIONS (~50 мс CPU базы даже на

шлюза: WordPress-сайты зовут GET_ALL_ACTIONS с сервера, по расписанию и с
кэшем в метаданных товаров, а не по разу на каждого посетителя. Поэтому
§4.3 — та же лестница в режиме «как сайты пользуются шлюзом»: покупатели
по ступеням плюс 10 читателей каталога.

Проверка размера пула под нагрузкой (тот же сервер, пул 1 100, 50
заказов/мин, 250 читателей, 2 мин): путь p95 1 005 мс (медиана 183 против
410 на пуле 6 600), RESERVATION p95 297 против 803, GET_ALL_ACTIONS p95
463 против 657 — пул отвечает за команды удержания, читатели — за
остальное.

### 4.4. cpx22 — виджет: разбор провала на 400 и рычаг пула соединений

Отдельные трёхминутные ступени на том же cpx22, свежие пулы:

| Опыт | заказов/мин | посетителей | пул api | ok | неудачных | путь p95 | api / postgres CPU | итог |
|---|---|---|---|---|---|---|---|---|
| один сеанс, толпа | 400 | 1000 | 20 | 19 | 1182 | 33 с | 5–27 % / 22–55 % | конвой (§4.1) |
| один сеанс, без толпы | 400 | 10 | 20 | 963 | 0 | 78 мс | 9–15 % / 22–34 % | чисто |
| один сеанс, толпа | 300 | 1000 | 20 | 16 | 734 | 31 с | 4–15 % / 20–37 % | конвой |
| два сеанса, толпа | 2 × 200 | 2 × 500 | 20 | 2 × 11 | 2 × 590 | 30 с | — | конвой в обоих |
| два сеанса, толпа | 2 × 200 | 2 × 500 | **60** | 2 × 601 | 0 | 1,0–1,3 с (p99 7–8 с) | — | все покупки прошли, хвост от CPU |

Снимок `pg_stat_activity` в разгар конвоя (300 заказов/мин, 1000
посетителей): 18 бэкендов ждут `IncrementSessionSeatStatusVersion`
(`Lock:tuple`), цепочка блокирующих PID — это очередь на строку сеанса;
держатель блокировки — `idle in transaction` после
`InsertReservationGAItem`, `ClientRead`: он ждёт не базу, а код api. При
10 посетителях те же 400 заказов/мин проходят с путём 78 мс, значит,
удлиняет транзакцию удержания именно толпа читателей: их запросы
занимают пул соединений api (20), транзакция удержания между
операторами ждёт свободное соединение или планировщик, держа при этом
строку сеанса, а следующие удержания встают за ней и занимают
оставшиеся соединения. Пул заполняется ожиданиями, и всё — список
событий, вебхуки оплаты, `/healthz` базы — стоит до таймаута клиента.
Два сеанса по 200 при пуле 20 утонули вместе: пул один на всех, конвой
одного сеанса не изолирован от остальных.

С `DB_POOL_MAX_CONNS=60` (Postgres `max_connections` 100 хватает) та же
пара сеансов — 1 202 покупки из 1 202, без ошибок; остаётся только хвост
задержек, и это уже честный предел двух ядер. Для прода это самая дешёвая
правка из всех найденных: поднять пул api (и посмотреть на
`max_connections` базы). Настоящее лечение — укоротить транзакцию
удержания (всё, что не требует блокировки строки сеанса — резолв
покупателя, прайсинг, конфиг платежа — делать до неё) и не брать
второе соединение из пула внутри открытой транзакции.

### 4.5. cpx32 (тип прода: 4 vCPU AMD, 8 ГБ) — виджет

60 уже давали postgres 63–80 % и p99 5,2 с.

## 5. Матрица серверов

Что даёт каждый размер при **правильной настройке** (пул api 60,
`TRUSTED_PROXY_COUNT` по числу хопов, сеанс до ~6 000 мест):

| Сервер | Цена | Виджет (1000 посетителей) | Шлюз (WP-режим) | Во что упирается дальше |
|---|---|---|---|---|
| cpx22 — 2 vCPU, 4 ГБ | €0,031/ч (~€23/мес) | 400 заказов/мин чисто (p95 139 мс, p99 5 с) | 400 заказов/мин чисто (p95 228 мс) | CPU postgres (63–80 % на 400) и хвост p99 |
| **cpx32 — 4 vCPU, 8 ГБ (прод)** | €0,057/ч (~€42/мес) | ≥ 800 заказов/мин (p95 87 мс, p99 2,5 с), запас ×2 по CPU | 800 заказов/мин (p95 229 мс), потолок ~1 100 | генератор (1000 VU); CPU api на шлюзе |
| cpx42 — 8 vCPU, 16 ГБ | €0,111/ч (~€82/мес) | не мерилось (лимит ядер проекта); по CPU-профилю ≥ ×2 к cpx32 | — | — |

С **прод-настройкой как есть** (пул 20): cpx22 — 200 заказов/мин при 1000
посетителей (на 300–400 конвой); cpx32 — 300 при 1000 посетителей чисто
(898/898, p95 73 мс), выше не проверялось с пулом 20.

Уровни владельца против матрицы:

| Уровень | Посетителей / заказов в мин | Хватает |
|---|---|---|
| минимальный | 50 / 10 | cpx22 с любой настройкой |
| средний | 200 / 50 | cpx22 с любой настройкой |
| высокий | 1000 / 200 | cpx22 с пулом 60 (без запаса по p99); **cpx32 — с запасом ×4** |
| «ажиотаж» | 1000 / 400–800 в один сеанс | cpx32 с пулом 60 |

Ограничения матрицы: один сеанс на всю продажу (несколько событий
складываются, пока пул api не забит — §4.4); толпа не больше 1000
одновременных посетителей (генератор); пул мест 6 600 (для 20–50-тысячной
GA-категории — §3.1); всё с серым облаком, Cloudflare добавляет
100–150 мс.

## 6. Что исправить (по убыванию цены ошибки)

1. **`DB_POOL_MAX_CONNS` на проде поднять с 20 до 60** (Postgres
   `max_connections` 100, воркер держит ещё ~3). Самая дешёвая и самая
   действенная правка: она отделяет «медленно» от «встало». Проверить
   `mem_limit` базы 1 ГБ: с 64 соединениями postgres на копии занимал
   ~300 МБ.
2. **Укоротить транзакцию удержания** в `hfeed`/`hcheckout` checkout/start:
   резолв покупателя, прайсинг, pre-flight платежа — до
   `IncrementSessionSeatStatusVersion`; внутри транзакции — ни одного
   запроса через пул мимо `tx`. Это убирает саму возможность конвоя, а
   не только отодвигает его.
3. **Cloudflare перед прод-Traefik**: добавить диапазоны Cloudflare в
   `forwardedHeaders.trustedIPs` (Dokploy → Traefik config) и держать
   `TRUSTED_PROXY_COUNT` равным числу хопов (сейчас на проде 1 — значит,
   api видит адрес edge-узла Cloudflare, и per-IP лимит 600/мин делит на
   всех покупателей одного edge). Проверка та же, что в §4.7.
4. **GA-команды и большие категории** (§3.1): индекс/запрос по
   `session_seats (session_id, tier_id, status)` для выделения и подсчёта
   мест; критично только для категорий от ~10 000 мест.
5. `capacity.mjs`: вердикт «транспорт, не arena» верен только вместе с
   логом api — при конвое клиент рвёт соединение раньше, чем api ответит
   5xx (§4.1). Добавить в лестницу снимок `pg_stat_activity` и счёт
   `http.request.completed` из лога api на ступени.
