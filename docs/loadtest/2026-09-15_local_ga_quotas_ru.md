# Нагрузочный тест — квоты категорий GA (локально, 2026-09-15)

Проверка волн A и B плана `08_architecture/23_ga_category_quotas_plan_ru.md`
(коммиты ba44e0e, 15d1e34, ca3fe84, e10f081) под нагрузкой из
`ops/loadtest`. Стенд: локальный docker compose, образ API собран из этих
коммитов, локальная база `arena` мигрирована до 0101 (бэкап
`arena_pre0101.dump` снят до миграции; конверсия заняла 16 с).

Профиль: 200 посетителей, 50 заказов в минуту, длительность 3 минуты на
поток (в прошлом отчёте 5 минут — здесь важнее сравнение до/после
правок оператора, а не длина). Гонки: 200 покупателей за 10 мест одной
категории.

`quota_admin.js` каждые 2 с меняет количество VIP на ±150, каждые 10 тиков
закрывает VIP на 4 с, один раз добавляет категорию во время продаж. Это
новый класс риска в модели квот: правка количества берёт блокировку
строки сеанса, ту же, что и каждая бронь.

## Что подтверждено

- Категория никогда не продаёт сверх количества: в обеих гонках ровно 10
  билетов на 10 мест, у 190 покупателей честный отказ «распродано».
- Одновременные правки оператора не ломают продажи: ни одной ошибки 5xx
  и ни одного упавшего платежа на 290 покупок при 201 правке квот.
- После каждого прогона выполняется инвариант
  `sum(ticket_tiers.capacity) = count(session_seats ga_unit) = sessions.capacity_total = inventory_ledger.capacity_total (tier_id IS NULL)`.
- Закрытая категория для покупателя выглядит как «распродано» (решение 4),
  после открытия продажи продолжаются, билеты выпускаются.
- Категория, добавленная во время продаж, сразу продаваема, вместимость
  сеанса растёт ровно на её количество, чужие места не тронуты.
- Сжатие ниже занятого отвечает 409 `tier.quantity_below_used` с полом; в
  прогонах таких ответов 0, потому что качели ±150 не доходили до
  проданного.

## Находки

1. **Латентность под правками квот.** p99 HTTP через шлюз вырос с 1,29 с
   до 2,2 с (max 2,28 с) при операторе, который меняет количество каждые
   2 с. Причина ожидаемая: `SetQuantity` на 150 мест держит блокировку
   строки сеанса, брони ждут. Для реальной эксплуатации оператор меняет
   количество раз в час, не раз в 2 секунды; отдельной правки не требует,
   но стоит помнить, что массовое перекраивание квот на живом сеансе
   заметно покупателям.
2. **Админский JWT из фикстур не проходит на маршруты категорий**
   (`org.access_denied`): известная проблема org-scoped ролей
   (AGENTS.md, «Org-scoped user_roles role assignments never reach a real
   logged-in user»). `quota_admin.js` обходит её токеном
   `platform_superadmin` с заголовком `X-Admin-Reason`. Для реальной
   админки это не воспроизводится: там membership-строка есть.
3. Дефектов в модели квот нагрузка не выявила.

## Как повторить

```bash
docker compose -f docker-compose.yml -f ops/loadtest/bil24/docker-compose.loadtest.yml up -d --build --no-deps api worker
node ops/loadtest/provision.mjs
MSYS_NO_PATHCONV=1 docker run --rm -v "C:/Projects/arena_new/ops/loadtest:/lt" -e BASE_URL=http://host.docker.internal:8080 -e SCENARIO=race grafana/k6:0.54.0 run /lt/gateway.js
MSYS_NO_PATHCONV=1 docker run --rm -v "C:/Projects/arena_new/ops/loadtest:/lt" -e BASE_URL=http://host.docker.internal:8080 -e SCENARIO=flow -e DURATION=3m grafana/k6:0.54.0 run /lt/gateway.js &
MSYS_NO_PATHCONV=1 docker run --rm -v "C:/Projects/arena_new/ops/loadtest:/lt" -e BASE_URL=http://host.docker.internal:8080 -e DURATION=3m grafana/k6:0.54.0 run /lt/quota_admin.js
```

`--no-deps` нужен на этом хосте: `arena_postgres` создан вручную вне
compose (порт 45432, см. AGENTS.md), и compose иначе пытается его
пересоздать.
