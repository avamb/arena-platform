# Disputes, receipts and evidence

Chargebacks, the dispute package, provider receipts, seller and provider lines in letters, ticket access log. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **Payment disputes (chargebacks) live in `internal/platform/disputes` (spec `08_architecture/51_3_disputes_chargebacks_ru.md`, migration 0186), and NOTHING reaches a bank or a provider before the owner's press.** A dispute arrives three ways: a VERIFIED per-config webhook whose module normalizes it to `EventDisputeOpened`/`EventDisputeUpdated` with a `payments.Dispute` (Stripe `charge.dispute.*`, AllPay `type=chargeback|chargeback_revert`), dispatched by `hcheckout.processDisputeWebhook` before the payment state machine (a dispute of a payment the organization does not own is 200 `processed:false`, a recording failure is 500 so the provider redelivers); a dispute the organizer enters from a provider's letter (`POST .../disputes`, channel `manual`); later a Flitt report poll. `RecordProviderEvent` reads an API provider's dispute back through the config that verified the delivery before it believes the body, finds the payment by `provider_charge_ref` or `provider_payment_id` inside the org and provider, dedups by `(provider, provider_dispute_id)` and by provider event id in `payment_dispute_events`, and queues `dispute.build_package`. The build collects facts (order, tickets, letters and opens, `ticket_access_events` only when that table exists, scans, the checkout consent and stored terms, refunds, session changes), renders PDFs under a budget (Stripe 4.0 MB / 19 pages, e-mail answers 2 MB / 19 pages: pages are taken from the least important file first, then files dropped), stores them as `bytea` in `payment_dispute_files` (never in the media store, never a public URL), and for an API dispute saves the evidence at Stripe with `submit=false` only. `submit=true` (Stripe takes ONE answer) and `POST /v1/disputes/{id}/close` happen only from `POST .../submit` / `.../accept`, which are `dispute.respond` (owner and platform superadmin only; in `apikeys.ForbiddenScopeExact`; an organization API key is refused even `dispute.read` routes with 403 `dispute.api_key_forbidden`), are in `stepUpMoneyRoutes`, and run on a context detached from the request with a 2-minute budget. A provider error after the answer was sent is judged by re-reading the dispute (`submission_count > 0` counts as sent). Every Stripe call carries an idempotency key derived from the dispute and package version (`arena-dispute-<id>-...`). E-mail channel disputes (AllPay, PayPlus, manual) are answered by `dispute.send_email`: one letter per package to the provider (`Descriptor.DisputeEmail` or the organizer's address), Reply-To the first owner, the PDFs attached, a `[Copy]` to the owner, journaled as `email_sent` with hashes (not in `email_letters`: not a buyer letter); a letter that did not leave within an hour puts the dispute back to `draft_ready`. Stripe's test outcome (`evidence[uncategorized_text]=winning_evidence|losing_evidence`) is the `test_outcome` of the submit body and is refused for a live config. `dispute.watch` (every 5 minutes) expires past-due open disputes and tells the organization (sales chats via `AnnounceToOrg`, owners by e-mail; managers too one day before) on opening, 7/3/1 days before the deadline, on expiry and on close, the operator (ops bot, no buyer data) on opening and expiry; each notice is claimed in `payment_dispute_notices` BEFORE it is sent. Low-value advice (decision R-11) comes from `dispute_settings` (platform row `org_id IS NULL`, seeded USD/EUR 500, GBP 400, ILS 2000, CZK 12000 minor units). The payment-config check warns `dispute_events_not_subscribed` and `dispute_access_missing` for Stripe. A fixture that deletes an order, payment intent or organization must delete `payment_dispute_files`, `_packages`, `_events`, `_notices`, `payment_disputes` and the `dispute.*` worker_jobs first (`cleanupDisputes` in `httpserver/disputes_integration_test.go`); none of the FKs cascade. A new provider that can answer disputes through an API implements `payments.DisputeResponder` and sets `Capabilities.Disputes` (the contract test checks the pair). Tests: `disputes/disputes_test.go`, `disputes/email_integration_test.go`, `httpserver/disputes_integration_test.go` (Stripe stub: webhook → draft → submit → closed → notices).
- **Dispute traps found on the staging run (2026-11-02).** (1) A verified dispute event whose dispute the provider answers 404 for (`payments.ErrDisputeNotFound`, Stripe maps any 404 of `GET /disputes/{id}`) is acknowledged with 200 and records nothing: a 500 would make the provider redeliver for days. Every other read-back error stays 500. (2) Stripe's test cards open the dispute 2 seconds after the payment, so the package is built BEFORE the ticket letter leaves and says "no e-mail recorded"; a real dispute comes days later. `POST .../disputes/{id}/package` rebuilds it (new version, new Stripe draft). (3) The evidence reads two other changes only when their schema exists: `ticket_access_events` (PR #352, `to_regclass`) for `access_activity_log` and the downloads section, and `payment_intents.provider_receipt_*` (PR #359, `information_schema.columns`) for the provider's receipt number, link and archived copy fingerprint in the receipt file and the case summary. The archived receipt FILE is not attached (Stripe takes one `receipt` file and the copy may be HTML). `customer_purchase_ip` is the checkout consent's IP, else the IP of the first ticket access within an hour after the payment (`purchaseTimeIP`); with neither arena leaves the field out (Stripe may still show the IP it saw itself). (4) PR #359 conflicts with this change in `cmd/arena-worker/main.go`, the Stripe module's `Capabilities` and `contracttest.go`: keep both sides (`ProviderReceipt` and `Disputes`, both register calls, both contract checks). (5) A test org on staging without an `org_admin` cannot answer a dispute: `dispute.respond` and `payment_config.*` are owner-only. (6) Rules from the review of the branch (`review_rules_integration_test.go`): a deadline arena only estimated (`due_by_source='default'`, an e-mail dispute entered without the letter's date) never expires the dispute, only reminds; a past deadline is refused (422 `dispute.due_in_past`); a later deadline from the organizer reopens an EXPIRED letter dispute that was never sent, and a provider event that still waits for an answer reopens an expired API dispute (`providerTransition`, `applyProviderState` clears outcome, `closed_at` and the `due_*`/`expired` notices). A key without the right to read disputes records the verified event body instead of failing forever. `submit` takes the optional `package_version` the organizer looked at (the bot sends it) and answers 409 `dispute.package_changed` when a newer build exists; a send whose outcome stays unknown after the read-back (own timeout, detached from the request) is 503 `dispute.outcome_unknown`, never "nothing was sent". The `dispute.send_email` job sends only while the dispute is `submitted`, takes the letter text from the package unless the organizer edited it (the queue keeps no copy of buyer data), and the address entered after the build (`respond_to`) wins over the draft's. `accept` re-checks the state inside its transaction. A dispute first seen already closed claims its `opened` notice silently. A payment known only by its checkout id is found through the module's `ChargeRefResolver` (five newest succeeded payments without a charge reference).
- **The payment provider's own receipt, and the seller in buyer letters (spec 51 section 2, decision R-6, migration 0185).**
  - **The setting.**
    - The owner's switch is `organizations.provider_receipt_enabled` (default true). It is written by `PATCH .../seller-profile` with `provider_receipt_enabled`, and shown on the event center's "Organization data" screen.
    - `provider_receipt_forced` ("always send", in the admin console's Payments tab) is written ONLY by a platform superadmin with `X-Admin-Reason`. Anyone else changing it gets 403 `seller.provider_receipt_forced_superadmin_only`; repeating the stored value is allowed.
    - The setting is in effect when either flag is on. `hfeed.StripePaymentStarter.receiptEmail` then passes the buyer's e-mail as `HostedCheckoutRequest.ReceiptEmail`. A failed read of the setting also counts as "send".
    - Each module decides alone what to do with the e-mail:
      - Stripe sets `payment_intent_data[receipt_email]`;
      - PayPlus sets `sendEmailApproval`;
      - AllPay and Flitt ignore it (an AllPay receipt is the merchant's own tax document).
    - "Off" is not a guarantee: a Stripe account's own dashboard setting "email customers about successful payments" still sends. The screen says so.
    - The seller-profile PATCH now takes any non-empty subset of `contact_form_to_telegram`, `provider_receipt_enabled` and `provider_receipt_forced`. An empty body is 400.
  - **The archive.**
    - When a payment intent becomes `succeeded`, the webhook transaction queues `payment.receipt_archive` (`paymentreceipts.EnqueueTx`, in a SAVEPOINT, best effort). This happens only for modules with `Capabilities.ProviderReceipt`, which requires `payments.ReceiptFetcher` (the contract test checks it). An operator's `POST /v1/payment-intents/{id}/transition` to `succeeded` queues it too, in its own short transaction after the move.
    - The job runs `paymentreceipts.ArchiveDelay` (15 minutes) after the payment, because Stripe numbers a receipt only after it has mailed it. The payload carries `config_id`, the configuration that verified the webhook (per-config route), and the module is built from it through `refunds.WithProviderConfig`, never from the organization's preferred config.
    - arena-worker's handler reads the receipt through that module and stores it on the payment intent:
      - `provider_receipt_url`;
      - `provider_receipt_number`, which may still be empty: Stripe numbers a receipt after it mails it;
      - the copy in media, owner type `payment_receipt`, which is not uploadable (it is absent from `AllowedOwnerTypes`);
      - `provider_receipt_archived_at`.
    - Outcomes of `FetchReceipt`: `payments.ErrReceiptNotReady` retries; `payments.ErrReceiptNotFound` (the account does not know the payment) ends the job without a retry; `payments.ErrReceiptDownload` stores the link and number at once and retries the copy, so a copy that never arrives ends in the dead-letter queue, which the ops watchdog reports. A retry reuses a copy an earlier run already saved (`GetPaymentReceiptMediaID`), so it never leaves an orphan.
    - Stripe downloads only an https `pay.stripe.com` address (or the test stub's host), sends no API key, and follows at most three redirects, each only to an https host of `stripe.com`. It tries the unofficial `/pdf` first and falls back to the HTML page, so the copy may be `text/html`.
    - A `payment_receipt` media object is dispute evidence: `DELETE /v1/media/{id}` answers 409 `media.receipt_not_deletable`, and `/v1/media-files/{id}` serves it with `Content-Disposition: attachment`, `Content-Security-Policy: sandbox` and `nosniff`, so a provider's HTML page never runs on the API origin. A presigned S3 URL bypasses that route.
    - A fixture that pays a Stripe checkout must delete `payment.receipt_archive` jobs and `payment_receipt` media objects (see `hostedOrgFixture.cleanup` and the shop fixture).
  - **The letters.** Every buyer letter (ticket, invitation, change, cancel, refund, all 7 locales) has a footer that names the seller and the provider. The shop letters name the seller only:
    - the seller: "Seller: <organization's legal name, else its name>". The platform's name is never shown as the seller;
    - the provider: `Branding.PaymentProvider`, the module's `Descriptor.Title` of the order's succeeded payment intent, printed as "Payment processed by X". It is resolved at render time by `GetTicketPaymentProvider` / `GetOrderPaymentProvider`. An invitation, a free order and a selling-site order print no provider line.
    - The words are in `templates.sellerFooterWords`. A new buyer template must carry both `.Branding.SellerLabel` and `{{with .Branding.PaymentLine}}`.
  - **Refund letters.** The refund letter goes out for partial and full batch refunds alike (`TestRefundBuyerEmail_PartialRefundIsMailedWithSellerAndProvider`). These send no letter, as before:
    - refunds without a batch (the flat routes, the ticket-cancel route);
    - refunds made in the provider's dashboard.
- **Every buyer download and view of tickets is logged in `ticket_access_events` (migration 0184, spec 51 R-13) — the access log a chargeback answer quotes.** `hfeed/ticket_access.go` writes a `pdf_download` row for `GET /v1/public/checkout/{token}/tickets/{id}/pdf` (not repeated for the same ticket, IP, source and automation flag within a minute) and one `tickets_view` row when the status answer lists a paid order's tickets (deduplicated per checkout + IP + flag for ten minutes in SQL, the widget polls). **`likely_automated` marks a request that looks like a machine** (`ticketAccessLooksAutomated`: prefetch/preview headers, empty UA, a scanner/script fragment in the UA, or no `Accept-Language`) — corporate mail security (Safe Links, Mimecast, Proofpoint) opens every link of a letter at delivery, so an unmarked "downloaded from the e-mail" row would be false evidence; anything that quotes this log to a payment provider must leave those rows out or label them. The IP is stored in the clear on purpose (owner decision R-10) and is only the buyer's real address when `TRUSTED_PROXY_COUNT` matches the proxy chain. Recording is best effort: the write runs on `context.WithoutCancel` with a 2 s timeout, a failure is logged and the PDF still goes out. The e-mail link carries the checkout token, which also opens the order's status answer — deliberate, the letter already carries every ticket as an attachment. The ticket e-mail links each ticket's PDF with `?src=email` (`delivery/download_links.go`, `HandlerOptions.APIBaseURL` from `cfg.APIPublicBaseURL()` in arena-worker; empty = no links), because Brevo sees neither the attachment being opened nor the reader's IP. A new `source`/`action` value needs the migration CHECK too (`TestTicketAccessValues_MatchMigration`). No purge job yet: retention counted from the event date is a follow-up.
