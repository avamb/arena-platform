# Hall plan intake and plan verification

The hall plan intake (spec `08_architecture/64`, wave 1): an organizer sends the files of a hall plan, an administrator or (later) the generator builds a draft, the organizer approves it into a seating plan, a platform superadmin verifies the plan into a venue template. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **An intake has seven states and each is moved by one actor (`venueplan.CanTransition`, tables of migration 0216).** `received` (files stored, the worker job is queued), `generating` (the worker called the generator), `review` (the organizer checks the current draft), `operator` (an administrator builds or fixes the plan), and the final `approved`, `rejected`, `cancelled` (`closed_at` is set, nothing changes after). Create: a source SVG that passes `ImportSVG` and `ValidateForPlanType` becomes draft 1 (`source_svg`) and the intake starts in `review`; anything else stays `received` for the job `venue_plan.generate` (see the wave 2 items below). `answers` and `corrections-text` store the input and move `review -> operator` (the seams are nil). The administrator's `drafts` keeps `operator`, `return` moves `operator -> review`, `reject` moves `operator -> rejected`. Every administrator write but `claim` (`drafts`, `return`, `approve`, `reject`) needs the caller's own claim (`holdsClaim`): an intake nobody holds answers 409 `venue_plan_intake.not_claimed`, one another administrator holds 409 `venue_plan_intake.claimed_by_other`. Approve is allowed to the organizer in `review` and to the administrator in `review` or `operator`; `cancel` is the organizer's from any non-final state. A new draft that keeps the state is NOT a transition, only `current_draft` moves. Never write `state` outside `moveState`/`finishMove`: they hold the row lock (`LockVenuePlanIntake`) and the transition check.
- **Intake sources are private media of owner type `venue_plan_source`, with no public link and their own body limit.** The type is in the CHECK of `media_objects.owner_type` but NOT in `mediastore.AllowedOwnerTypes`, so `POST /v1/media` refuses it and `GET /v1/media-files/{id}` never serves it; the files are read only through `.../plan-intakes/{id}/sources/{source_id}` (an attachment with a sandbox CSP and `nosniff`, EXIF dropped except the orientation) and its admin twin (needs `X-Admin-Reason`; every admin download writes the audit event `v1.venue_plan_intake.source_download` with the reason, the source id and its sha256, never the content, before a byte is sent). A stored JPEG ends at the first EOI after the scan data (`stripJPEGMetadata`/`scanEnd`): whatever a phone appends after it, such as MPF pictures with their own EXIF, is dropped. The create route takes up to 80 MB, so `Deps.BodyLimitOverride` (`venuePlanUploadBodyLimit` in `mount_venue_plan.go`) lifts the global body limit for exactly the create route and the administrator's draft route; every other request answers 0. A new upload route needs its own line there. `POST /v1/media` itself is still under the global 1 MiB JSON body limit.
- **A draft SVG is validated before anyone sees it.** `ImportSVG` plus `ValidateForPlanType` run before the media object and the draft row exist; a refused SVG leaves no row and no media (`TestVenuePlanIntake_BadAdminDraftStoresNothing`, 422 `venue_plan_intake.draft_validation_failed` with the list in `details.errors`). The organizer reads a draft only as an SVG with a sandbox CSP.
- **Approve is ONE transaction with the plan, its version 1, the intake move and the billing fact, and the fact sits behind a SAVEPOINT.** The plan is `status=active`, `visibility=private`, `verification_state=unverified`; the SVG becomes media of type `seating_plan_svg`. `billingFact` opens the SAVEPOINT (`tx.Begin`) FIRST and runs its three reads and the write of the free `venue_plan_intake` fact (subject = intake id, rated 0 `free`) inside it: any error rolls back to the SAVEPOINT, an organization without a billing account is skipped and any other error is logged, so billing never aborts an approval (`TestVenuePlanIntake_BillingFactReadErrorKeepsTheTransaction`). The SVG is stored before the transaction; `locked` reports whether the commit really happened, and only then is the stored SVG kept (approve and the admin draft), a failed commit deletes it. An administrator's approve (with `X-Admin-Reason`) also writes an `approved` notice for the organizer's bot.
- **`operator_verified` is set ONLY by `POST /v1/admin/seating-plans/{plan_id}/verify` (`seating_plan.verify`, a platform superadmin, `X-Admin-Reason`).** Plan create and PATCH refuse it with 403 `seating_plan.verify_required`. Verify works on ANY active plan with a current version (also a plan whose `verification_state` is NULL, for example one imported by the Forzum library session), sets `visibility=operator_verified`, and makes the venue `review_status=verified`. `needs-fix` sends a template back to `private` with a note; copies made before keep working. The owner of a template may only PATCH it back to `private` (which resets it to `unverified`); any other visibility change answers 409 `seating_plan.template_visibility_locked`. A template is `visibility = operator_verified` AND `verification_state = verified` (`hseating.IsVerifiedTemplate`): the `plan-templates` list, the fork rule and the "a copy of a template is created active" rule all ask both. Rows that carry `operator_verified` from before this feature (state NULL) are therefore NOT templates until the verify route is run on them (`TestSeatingPlanVerify_OperatorVerifiedWithoutStateIsNotATemplate`).
- **Fork rules.** `POST /v1/seating-plans/{id}/fork` refuses a `private` plan of ANOTHER organization (404 `seating_plan.not_found`); another organization copies only a verified template (`GET .../venues/{venue_id}/plan-templates` lists them). A `venue_id` in the fork body must be the forking organization's own venue or a verified venue (`GetVenueSessionContext`, the rule of `plan-templates`), else 404 `venue.not_found` (`TestSeatingPlanVerify_ForkVenueOverride`). The copy is the caller's own, `private`, with `verification_state` NULL; categories and prices are its own and the source never changes (`TestSeatingPlanVerify_TemplateFlow`).
- **A new version on ANY write path resets a verified template; only a superadmin's version with a non-empty `X-Admin-Reason` does not.** The rule is ONE function, `gen.Queries.LockSeatingPlanForNewVersion(ctx, planID, keepTemplate)`: it locks the plan row and, when it is `operator_verified` and `keepTemplate` is false, sets `visibility=private` and `verification_state=unverified` in the caller's transaction. `POST /v1/seating-plans/{id}/versions` calls it (the audit row carries `verification_reset`), and so does the Bil24 import `upsertSeatingPlanVersion` when it adds a version to an existing plan (`TestImportSeatingPlanVersion_ResetsAVerifiedTemplate`). A new path that adds a version to an EXISTING plan must call it too (approve and fork make new plans). `keepTemplate` is true only for a platform superadmin whose request carries a non-empty `X-Admin-Reason` (`httputil.AdminReason`); a superadmin who is also a member and posts without it is answered like a member and the template is reset, a superadmin who is not a member still gets 400 `superadmin.missing_reason` (`TestSeatingPlanVerify_OwnerVersionResetsTheTemplate`, `TestSeatingPlanVerify_SuperadminMemberWithoutReasonResetsTheTemplate`).
- **Four events tell every platform administrator through the job `venue_plan.notify` (package `venueplan/notify`).** The kinds are `venue_created`, `intake_created`, `intake_escalated`, `plan_approved`; the payload is `{kind, intake_id, venue_id, reason, nonce}` and the nonce is made when the job is enqueued. `venueplan.Notifier` is implemented by `notify.Notifier`, set in arena-api with `SetVenuePlanNotifier`, and enqueues INSIDE the transaction of the intake route (`worker.EnqueueInTx`), so the job exists exactly when the change commits. `IntakeEscalated` sends for every reason, `no_generator` too: since wave 2 a new intake without a source SVG tells no administrator at create (`intake_created` is sent only for a source SVG), they hear of it when the generator job gives up. `venue_created` is enqueued by `hcatalog.HandleCreateVenue` (no transaction there: a short one of its own right after the insert, a failure only logs), by the Bil24 import `resolveVenue` and by the arena event-bundle import `resolveArenaVenue` (in the import transaction, only on a real insert, never on a dry run and never for a reused venue).
- **The notify handler sends nothing twice and tells no person.** It runs in ONE transaction: the dedup row of `venue_plan_notify_log` (key `kind:nonce`, `subject_id` is the intake id, or the venue id for `venue_created`, no foreign key) and `adminnotify.Fanout` (one `admin_notify.email` job per administrator, one `admin_notify.telegram` job per live bot link). A retried job finds the row and sends nothing; a concurrent run waits on the unique index. The message holds the organization name, the venue, the city, the file kinds and count, the reason in words and, for `organizer_request`, the organizer's own text; never a user name, e-mail, phone or Telegram id. No administrators at all is a warning and the job is done. The link is `<APP_PUBLIC_URL>/venue-plans/<intake_id>`, and `/venues` for `venue_created`. The handler is registered in `cmd/arena-worker` next to the admin_notify handlers, with Telegram on only when `EVENTS_TELEGRAM_BOT_TOKEN` is set; no new setting.
- **The bot claims organizer notices with `POST /v1/bot/venue-plan-notices/claim` (service token, batch 50), modelled on `web-login-notices/claim`.** `ClaimVenuePlanNotices` marks the rows claimed in the same statement that returns them, so a crash between the claim and the message loses one message and never repeats it. A notice whose creator has no live bot link is still claimed and comes with `telegram_user_ids: []`. The route is in the service-token group of `mount_bot.go` and in `flatRouteFamilies` (`flatPlatform`).
- **The answers loop is still an administrator's work: `venue_plan.render` and the question table have no writer.** `venueplan.Renderer` has an implementation since wave 2 (`generator.Client.Render`, `POST /render`), but arena-api does not get it (`WithRenderer` is not called), so answers and text corrections are stored and the intake goes to an administrator (reasons `answers`, `organizer_text`). `venueplan.TextInterpreter` has no implementation. Nobody writes `venue_plan_questions`. Migrations 0216 and 0217 are not merged: renumber them at merge time and move the migration-head pin.
- **Since wave 2 the generator builds the first draft: create leaves the intake `received` and queues `venue_plan.generate` (packages `venueplan/intake`, `venueplan/generate`, `venueplan/generator`).** A clean source SVG is still draft 1 at once (`received -> review`, `IntakeCreated`). Any other intake stays `received`; `intake.EnqueueGenerate` puts the job `{intake_id, attempt}` into the create transaction and NO administrator is told. Only arena-worker knows the generator (`VENUE_GEN_URL`, `VENUE_GEN_TOKEN`, role worker in `config/roles.go`, row in `deploy/DOKPLOY.md` §2.6); arena-api has no setting and never calls it. The handler always registers: without the two settings or without a media store it moves `received -> operator` with `no_generator`, so an intake never waits in `received`. `MoveState`, `CheckPlanSVG` and `SummaryOf` live in `venueplan/intake`; `hvenueplan` only has aliases, never write a second copy.
- **One function decides what a generator answer does to the intake: `generate.Decide` (table in its test).** `ok` + `PASS` + an SVG that passes `intake.CheckPlanSVG`: draft of author `generator` (model, report, generator version, preview PNG), `generating -> review`, notice `draft_ready`. `ok` + `QUARANTINE`: `operator` with `too_many_questions`, and a valid SVG is kept as the current draft for the administrator (an organizer must not approve a plan that silently lacks seats; this changes when the question loop exists). `ok` without an SVG (no seat has an identity, every vector PDF today): `too_many_questions`. `PASS` with an SVG the importer refuses: `draft_invalid`, nothing stored. `no_adapter`: `unsupported_format`, or `generator_failed` when a file report says `failed`. A failure that may pass (network, 5xx, 503, job `timeout`/`worker_crashed`/`internal_error`, poll deadline) is retried as a NEW `worker_jobs` row with a later `scheduled_at` (1 and 5 minutes, 3 attempts), the intake stays `generating`; 401/400/413 and `memory_limit` escalate at once. Every escalation calls `IntakeEscalated` (all reasons send now, `no_generator` too) and writes the organizer notice `escalated` (migration 0217); audit actions `generate_started`, `draft_generated`, `generate_failed` have a system actor.
- **What goes to the generator is chosen by `generate.SendKind` and `generate.Select`, and the generator is called outside any transaction.** `pdf`, `xlsx`, `jpeg`, `png` go as they are; `webp`, `heic`, `tiff`, `bmp`, `gif` go as their PNG copy; `xls`, `csv` and `svg` have no reader and are never sent; a file over 10 MB is not sent and files are dropped from the tail over 30 MB. Nothing to send is `unsupported_format` without a call. The outcome transaction locks the intake and writes only when it is still `received` or `generating`: an intake cancelled meanwhile keeps its state and the stored draft bytes are deleted.
- **An attempt of `venue_plan.generate` is a chain of short steps, one `worker_jobs` row each, and never holds the worker loop for more than one HTTP call.** arena-worker runs its jobs one after another, so a handler that waited for the generator blocked ticket delivery and letters for minutes. Step submit (payload without `gen_job_id`): pick the files, `received -> generating`, `generator.Client.Submit` (POST /generate, timeout 120 s), queue the step poll `generate.PollDelay` (3 s) later and return. Step poll: ONE `Client.Poll` (GET /jobs/{id}, timeout 30 s); still running or no answer (network, 5xx): one more poll row 3 s later, until `generate.Deadline` (4 minutes) after `submitted_at`, then a retryable failure with the code `deadline`; a 404 queues a submit row with `resubmitted` once (no second `generate_started`), a second 404 is a retryable failure `job.not_found`; done or failed goes through `Decide` as before. A cancelled context (the worker stops) is NOT a generator failure: the step returns the error, the worker runs the same row again, `attempt` does not grow. Log and audit only `error_code`, never the generator's `error.message`. `Client.Generate` (submit plus a polling loop, one at a time) is kept for tests and tools only.
- **A repeated step does nothing: every row carries `seq`, and a row whose intake already has a `venue_plan.generate` row with a higher `seq` is skipped (no migration, the check reads `worker_jobs`).** Every step enqueues its next row with `seq+1` in a transaction that holds `LockVenuePlanIntake` and checks `superseded` first; `finish` checks it under the same lock. So a row the worker gave back after a stale claim, run twice, makes ONE next row and asks the generator once (the cheap pre-check before the HTTP call skips it; two copies running at the very same moment may both call, only one writes). Every enqueue also sets the intake's `updated_at`, which the sweep reads. A row from before this change has no `seq` (0) and runs as a submit.
- **The sweep `venue_plan.generate_sweep` (every 10 minutes, `generate.ScheduleInitialSweep` at worker start, one pending row per database) sends an intake that stayed `received` or `generating` for 30 minutes without a step to an administrator.** It goes through the same `finish` (`operator` with `generator_failed`, notice `escalated`, `IntakeEscalated`, audit `generate_failed` with `error_code` `stalled`), and under the lock it rechecks that `updated_at` is still old, so a living chain is never taken. It covers a dead-lettered step, a lost row and a worker that was down for 30 minutes (then a waiting `received` intake goes to an administrator too). An administrator's claim also moves `updated_at`, it does not break a chain.
- **The bot sends the files of a plan as ONE intake and never builds a plan itself (`eventbot/plan_intake.go`, callbacks `pi:*`).** The wizard step `stSPlanFile` and the "Upload a seating plan" buttons (the date card of a seated date, the plan question of a venue WITH plans) collect Telegram file ids in a `planintake` dialog (documents and photos, 10 files, 20 MB each, 80 MB together; nothing is downloaded before "Done"), then `POST .../venues/{id}/plan-intakes` (multipart, `channel=telegram_bot`, the dialog's `Key` as Idempotency-Key). A wizard draft waiting for the intake keeps `Draft.PlanIntakeID` and is `Paused` on `stSPlanFile`; `Draft.IntakePlans` (outside `Scratch`, which is reset between steps) lists the plan versions that came from an intake, and the saved event offers `splitSeatsByPriceButton` for those dates only. The notice loop (`planNoticeLoop`, `NoticeEvery`) claims `venue-plan-notices/claim` and runs each chat inside `serial.do` (it may write the person's draft). The review is `planpreview.Render` (pure Go PNG of the draft SVG read by `seating.ImportSVG`) sent with `SendPhoto`, or the SVG with `SendDocument` when it cannot be drawn; a media message with buttons must be registered live by hand (`sendPlanPreview`), `post()` does it only for text. A button of the wizard screen whose data starts with `pi:` is sent WITHOUT the `wz:` prefix (`wizardKeyboard`). The old direct path (CreateSeatingPlan, UploadOwnedMedia, CreatePlanVersion from the bot) and the `bot.wz.plan_up_*` keys are gone. The review works in the person's CURRENT organization (`id.Current`): a notice of another organization finds 404 until they switch.
- **The world country table is `internal/platform/worldgeo` (`countries.tsv`, 249 ISO 3166-1 rows), and only a venue or an approved application creates a reference country from it.** Each row has iso3, the ISO 4217 currency, ONE of seven regions (AM, GE, CY, RU europe; KZ, AZ asia; TR, IL middle_east; EG africa) and the en/ru names; `TestTable_MatchesMigration0127` keeps it equal to the countries migration 0127 seeded (iso3, currency, region), so fix both together. `GET /v1/geo/world-countries` (public, `?lang=`/`?locale=`, ru gives Russian names, any other English) lists it with `in_reference`, `country_id`, `has_organizers` (`organizations.country`). `worldgeo.Ensure(ctx, tx, iso2)` inserts the missing `countries` row (slug from the English name, `-iso2` when taken, `ON CONFLICT (iso2) DO NOTHING` for a race) and the names through `worldgeo.UpsertI18nName`, the helper `hgeo` admin routes now share. Callers: `POST .../venues` with `country_iso2` + `city_name` (`hcatalog/venue_geo.go`: country, city by the rules of `POST .../cities`, venue, audit `v1.country.create`, `venue_created` and `country_created` jobs in ONE transaction; an organization API key gets 403 `venue.country_create_forbidden` before anything is written and 403 `venue.city_create_forbidden` when the city name is new, a key uses only a country and a city that exist, and a request without an actor counts as a key; the old `city_id` path keeps its after-insert notification) and `provisioning.CreateWorkspace` (`Workspace.CreatedCountry`, `onboarding.Approve` queues the job in the approval transaction). `POST .../cities` takes `country_iso2` only for a reference country (409 `city.country_not_in_reference`). Onboarding accepts any world country (an unknown code is `invalid`); the settings list or a country outside the reference makes `country_allowed` a WARN, which keeps automatic approval off. The notification is kind `country_created` of `venue_plan.notify` (payload `country_id`, `country_iso2`, `venue_id` or `org_id`; the dedup subject is the country id; link `/geo`; no migration was needed, `venue_plan_notify_log.subject_id` has no foreign key). `GET /v1/geo/countries/{iso2}/currency` falls back to the world table and `/timezones` to `worldgeo.FallbackZones` for the six territories the city data lacks (AQ, BV, HM, IO, TK, UM).
- **The venue directory is `GET /v1/organizations/{org_id}/venue-directory` (`hcatalog/venue_directory.go`, queries `gen/venue_directory.sql.go`), with the access of `shared-venues`.** Scope: own venues not archived plus verified active venues of other organizations; a venue's country is its city's country, else `venues.country`. Four SQL rounds, no N+1: countries (never filtered), quick-pick sources (the organization's own country and reference countries with organizers), cities (only with `?country=`) and venues (only with `country`, `city_id` or `q`; `total` from `count(*) OVER ()`, `q` is an escaped ILIKE). `has_own_plan` = the organization's active plan with a current version at the venue; `has_plan` adds a verified template (`visibility = operator_verified` AND `verification_state = verified`), the rule of `plan-templates`. The answer never carries contacts. The route has `{org_id}`, so it needs no `flatRouteFamilies` entry; `world-countries` is `flatPublic`.
- **The web reads `GET /v1/geo/world-countries` and `GET /v1/organizations/{org_id}/venue-directory` (both in `openapi.yaml`) only through `apps/event-center/src/lib/venues/directoryApi.ts`, and a country outside the reference is made only by the venue create.** Both routes are in `routes.ts` (`geoWorldCountries`, `venueDirectory`) and the matrix row "Площадки"; `pendingRoutes.ts` is gone. The server's wire names stay inside `serverSource`: `country_iso2` becomes the view model's `country`, `geo_lat`/`geo_lng` become `latitude`/`longitude`. The server's ordered `quick_pick` IS the quick row (`quickCountries(all, regions, quickPick)`), not "countries with venues". `venues` is filled when any of `country`, `city_id`, `q` is sent. Both routes take `locale` as an alias of `lang`. `autoSource` still answers a 404 or 405 with `fallbackSource` (an old stand image has no routes), built from `GET .../venues`, `/v1/geo/countries` and `/v1/geo/cities`: no regions, no `quick_pick`, `has_plan` unknown; it can be deleted once no stand is older than the routes. A country outside the reference: `POST .../cities` answers 409 `city.country_not_in_reference` for it, so `ensureCity` (wizard `save.ts`) skips the city call and the venue create sends `country_iso2` + `city_name` (never together with `city_id`, that is 400 `venue.city_conflict`), with `?locale`; the server makes country and city in the venue's transaction. An API key cannot do this (403 `venue.country_create_forbidden`), people can.
- **The venue chooser is ONE component for the screen "Venues" and the wizard (`components/VenueChooser.tsx`, rules in `lib/venues/chooser.ts`).** The wizard keeps the country of a chosen venue in the draft (`existingCountry`): a shared verified venue is not in `listVenues`, so without it a restored draft lost its currency. Live helpers pick through the chooser (`pickWizardVenue`, `pickWizardCountry` in `tests/smoke/live/wizardHelpers.ts`); a counter next to a city is shared by every spec that adds a venue there, so a spec checks that the counter exists, never its value.
- **The web intake (`lib/venuePlan`, `components/venuePlan`, screen `/o/$orgId/venues/$venueId/plan-intakes/$intakeId`) refuses a file before any request and keeps one Idempotency-Key per attempt.** The limits in `upload.ts` are the server's (`hvenueplan/sniff.go`, MiB). The draft and the sources are read with the bearer token and shown from blob addresses, never as markup. The card and the upload are keyed by venue, the review by `org:intake`. The twin `tests/smoke/live/venue-plan-intake.spec.ts` makes its own venues and files through the API; the cases that need a platform administrator (a returned draft, a rejection) or another organization's template are `test.fixme`: the live harness has no superadmin.
- **The admin queue is `/venue-plans` (nav "Seating plans") and it finds plans with no verification state by subtraction.** `GET /v1/admin/seating-plans` never lists a plan whose `verification_state` is NULL (the imported library). The filter "No status (imported)" reads the venues of one chosen organization, then `GET /v1/venues/{venue_id}/seating-plans` for each, and drops the plans the three stated lists hold. A server filter for NULL would replace it. People read "request", the code says intake.
- **A draft SVG of an intake is read by `seating.ImportAnySVG` (`domain/seating/svg_detect.go`): a Forzum `sbt` file goes to `ImportSBTSVG`, any other to `ImportSVG`.** The one check `checkPlanSVG` (`hvenueplan/create.go`) serves the intake creation, the administrator's draft upload and the approval, and the bot's preview (`eventbot/plan_intake.go`, `sendPlanPreview`) uses the same function, so a draft that the server accepts is also drawn for the organizer. The plan VERSION route (`POST /v1/seating-plans/{id}/versions`, `hseating/versions.go`) still calls `ImportSVG` only: a library plan is loaded as the converted `house.svg`, not as the Forzum source. The sbt importer does not apply `MaxCanvasDimension` (on purpose, `sbt_import.go`), so an sbt draft may have a canvas the authoring path would refuse. Found on the staging run of 2026-11-12: an sbt draft was refused with `price_category_unlabelled` fifteen times.
- **Only an ACTIVE plan is seen by the admin queue, by `has_plan` of the venue directory and by the bot ("this venue has no seating plan").** A plan is created in `draft`, and a version upload does not change the status. `ops/forzum-library/loader.py` therefore sends `PATCH /v1/seating-plans/{id}` `{"status":"active"}` after a successful version upload (`--keep-draft` turns it off) and a re-run activates a draft plan that already has a current version without a second upload. It never verifies: verification is the administrator's action. On staging 49 library plans stayed invisible as drafts until 2026-11-12. The bot's draft picture (`planpreview`) draws the stage, sector names and row names with a Latin-only font: a label with a non-Latin letter is skipped, the render never fails for it.

- **A generated draft names its category through the worker's `target_profile`, never the generator's PLACEHOLDER.** The default profile of the generator (`arena-authoring-v1.json`) names the one price category `PLACEHOLDER`; an approved auto-draft showed «Category «PLACEHOLDER»» in the bot wizard and in the categories of a session. `generate.submitStep` now sends the multipart field `target_profile` (`generator.WithCategoryName`, `generator.TargetProfile`: the default profile with only `category.name` replaced, it passes `validate_profile`): en «Standard», ru «Стандарт», es «Estándar», any other language en. The language comes from `generate.categoryName`: for a `telegram_bot` intake the `locale` of the author's live `bot_telegram_links` row (newest `updated_at`), else `users.preferred_locale` of the author, else `organizations.default_locale`, else en. SVG files uploaded as SVG skip the generator and are not touched; `Render` (the answers loop) sends no profile yet, so add one there when that loop gets a writer. If the generator's default profile changes (name, colour, legend), change `generator.TargetProfile` with it. The real-generator test checks the draft SVG and `seating_plan_versions.geometry` for `Standard` and no `PLACEHOLDER`.
