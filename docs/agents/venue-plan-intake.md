# Hall plan intake and plan verification

The hall plan intake (spec `08_architecture/64`, wave 1): an organizer sends the files of a hall plan, an administrator or (later) the generator builds a draft, the organizer approves it into a seating plan, a platform superadmin verifies the plan into a venue template. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **An intake has seven states and each is moved by one actor (`venueplan.CanTransition`, tables of migration 0216).** `received` (files stored), `generating` (wave 2, no writer yet), `review` (the organizer checks the current draft), `operator` (an administrator builds or fixes the plan), and the final `approved`, `rejected`, `cancelled` (`closed_at` is set, nothing changes after). Create: a source SVG that passes `ImportSVG` and `ValidateForPlanType` becomes draft 1 (`source_svg`) and the intake starts in `review`; anything else goes `received -> operator` with reason `no_generator`. `answers` and `corrections-text` store the input and move `review -> operator` (the seams are nil). The administrator's `drafts` keeps `operator`, `return` moves `operator -> review`, `reject` moves `operator -> rejected`. Approve is allowed to the organizer in `review` and to the administrator in `review` or `operator`; `cancel` is the organizer's from any non-final state. A new draft that keeps the state is NOT a transition, only `current_draft` moves. Never write `state` outside `moveState`/`finishMove`: they hold the row lock (`LockVenuePlanIntake`) and the transition check.
- **Intake sources are private media of owner type `venue_plan_source`, with no public link and their own body limit.** The type is in the CHECK of `media_objects.owner_type` but NOT in `mediastore.AllowedOwnerTypes`, so `POST /v1/media` refuses it and `GET /v1/media-files/{id}` never serves it; the files are read only through `.../plan-intakes/{id}/sources/{source_id}` (an attachment with a sandbox CSP and `nosniff`, EXIF dropped except the orientation) and its admin twin (needs `X-Admin-Reason`). The create route takes up to 80 MB, so `Deps.BodyLimitOverride` (`venuePlanUploadBodyLimit` in `mount_venue_plan.go`) lifts the global body limit for exactly the create route and the administrator's draft route; every other request answers 0. A new upload route needs its own line there. `POST /v1/media` itself is still under the global 1 MiB JSON body limit.
- **A draft SVG is validated before anyone sees it.** `ImportSVG` plus `ValidateForPlanType` run before the media object and the draft row exist; a refused SVG leaves no row and no media (`TestVenuePlanIntake_BadAdminDraftStoresNothing`, 422 `venue_plan_intake.draft_validation_failed` with the list in `details.errors`). The organizer reads a draft only as an SVG with a sandbox CSP.
- **Approve is ONE transaction with the plan, its version 1, the intake move and the billing fact, and the fact sits behind a SAVEPOINT.** The plan is `status=active`, `visibility=private`, `verification_state=unverified`; the SVG becomes media of type `seating_plan_svg`. `billingFact` writes the free `venue_plan_intake` fact (subject = intake id, rated 0 `free`) inside `tx.Begin` (a SAVEPOINT): an organization without a billing account is skipped and any other error is logged, so billing never fails an approval. An administrator's approve (with `X-Admin-Reason`) also writes an `approved` notice for the organizer's bot.
- **`operator_verified` is set ONLY by `POST /v1/admin/seating-plans/{plan_id}/verify` (`seating_plan.verify`, a platform superadmin, `X-Admin-Reason`).** Plan create and PATCH refuse it with 403 `seating_plan.verify_required`. Verify works on ANY active plan with a current version (also a plan whose `verification_state` is NULL, for example one imported by the Forzum library session), sets `visibility=operator_verified`, and makes the venue `review_status=verified`. `needs-fix` sends a template back to `private` with a note; copies made before keep working. The owner of a template may only PATCH it back to `private` (which resets it to `unverified`); any other visibility change answers 409 `seating_plan.template_visibility_locked`.
- **Fork rules.** `POST /v1/seating-plans/{id}/fork` refuses a `private` plan of ANOTHER organization (404 `seating_plan.not_found`); another organization copies only a verified template (`GET .../venues/{venue_id}/plan-templates` lists them). The copy is the caller's own, `private`, with `verification_state` NULL; categories and prices are its own and the source never changes (`TestSeatingPlanVerify_TemplateFlow`).
- **A new version posted by the OWNER organization resets a verified template; a superadmin's version does not.** `POST /v1/seating-plans/{id}/versions` locks the plan (`LockSeatingPlanForVerification`) and, when it is `operator_verified` and the caller is not a platform superadmin acting with `X-Admin-Reason`, sets `visibility=private` and `verification_state=unverified` in the same transaction as the version (the audit row carries `verification_reset`). A template must never change without a new verification; the superadmin's fix is the new version (`TestSeatingPlanVerify_OwnerVersionResetsTheTemplate`).
- **Four events tell every platform administrator through the job `venue_plan.notify` (package `venueplan/notify`).** The kinds are `venue_created`, `intake_created`, `intake_escalated`, `plan_approved`; the payload is `{kind, intake_id, venue_id, reason, nonce}` and the nonce is made when the job is enqueued. `venueplan.Notifier` is implemented by `notify.Notifier`, set in arena-api with `SetVenuePlanNotifier`, and enqueues INSIDE the transaction of the intake route (`worker.EnqueueInTx`), so the job exists exactly when the change commits. `IntakeEscalated` with reason `no_generator` enqueues nothing: in wave 1 every new intake without a source SVG goes to an administrator and `intake_created` already says so (keep the code path, wave 2 reasons send). `venue_created` is enqueued by `hcatalog.HandleCreateVenue` (no transaction there: a short one of its own right after the insert, a failure only logs), by the Bil24 import `resolveVenue` and by the arena event-bundle import `resolveArenaVenue` (in the import transaction, only on a real insert, never on a dry run and never for a reused venue).
- **The notify handler sends nothing twice and tells no person.** It runs in ONE transaction: the dedup row of `venue_plan_notify_log` (key `kind:nonce`, `subject_id` is the intake id, or the venue id for `venue_created`, no foreign key) and `adminnotify.Fanout` (one `admin_notify.email` job per administrator, one `admin_notify.telegram` job per live bot link). A retried job finds the row and sends nothing; a concurrent run waits on the unique index. The message holds the organization name, the venue, the city, the file kinds and count, the reason in words and, for `organizer_request`, the organizer's own text; never a user name, e-mail, phone or Telegram id. No administrators at all is a warning and the job is done. The link is `<APP_PUBLIC_URL>/venue-plans/<intake_id>`, and `/venues` for `venue_created`. The handler is registered in `cmd/arena-worker` next to the admin_notify handlers, with Telegram on only when `EVENTS_TELEGRAM_BOT_TOKEN` is set; no new setting.
- **The bot claims organizer notices with `POST /v1/bot/venue-plan-notices/claim` (service token, batch 50), modelled on `web-login-notices/claim`.** `ClaimVenuePlanNotices` marks the rows claimed in the same statement that returns them, so a crash between the claim and the message loses one message and never repeats it. A notice whose creator has no live bot link is still claimed and comes with `telegram_user_ids: []`. The route is in the service-token group of `mount_bot.go` and in `flatRouteFamilies` (`flatPlatform`).
- **Seams for the later waves are nil in wave 1.** `venueplan.Renderer` (generator `POST /render`, job `venue_plan.render`) and `venueplan.TextInterpreter` (text corrections, `ErrNotUnderstood`) are interfaces with no implementation: answers and text corrections are stored and the intake goes to an administrator (reasons `answers`, `organizer_text`). The state `generating`, the escalation reasons `generator_failed`, `draft_invalid`, `too_many_questions`, `unsupported_format` and the table `venue_plan_questions` have no writer yet. Migration 0216 is not merged: renumber it at merge time and move the migration-head pin.
