# Session sales state and alerts

Manual sales state of a session, sold-out and site alerts, notify-me-when-sales-open subscriptions. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **A session has ONE sales state for every channel (migration 0183, package `salesstate`, owner decision 2026-10-31).** The organizer sets `soon` or `sold_out` in `session_sales_states` (no row = open) through `PUT /v1/organizations/{org_id}/sessions/{session_id}/sales-state` (`session.update`, so the owner AND the managers); the hold gate refuses every NEW hold while a row exists (`hcheckout.ManualSalesStateRefusal` inside `CheckSessionSalesOpen`, REST 409 `session.sales_not_started` / `session.sold_out` with `details.sales_state`, gateway 101 `bil24.sales_soon` / `bil24.session_sold_out` with `salesState` merged into the envelope). Holds taken before keep going: CREATE_ORDER_EXT of a held cart, PAY_ORDER and the payment webhook do not run the gate (`TestCompatBil24_SalesState_StartedPaymentCompletes`). The state never rewrites places, sale windows or `sales_end_at`: "open" deletes the row and the sale comes back as it was. The EFFECTIVE state (`open`/`soon`/`sold_out`/`ended`/`cancelled`) is `salesstate.Effective` and nothing else — REST session list and single read (`sales_state`, `manual_sales_state`), the public feed session (`sales_state`, every tier `available: 0` and no seat links while a manual state is set), GET_ALL_ACTIONS (`salesState` in the sites' vocabulary `open`/`soon`/`soldout`/`ended` via `salesstate.Wire`, plus `arenaSessionId` and `salesStateManual` — true only for a state the organizer set by hand, so a site can mirror the hand state without mistaking an automatic sell-out for one — availability 0 while a manual state is set) and the organization events list (`ListEventSalesFacts` ignores a session with a manual state when deciding `selling`). A session without categories is `soon`, never `sold_out`; one whose categories own no place rows (pre-0101 ledger) stays `open`. `salesstate.Change` writes the journal row (`session_sales_state_changes`: actor, membership role, client from `X-Client-Channel`) and a `v1.session.updated` outbox row IN THE SAME transaction and keeps its id, so `site_sync` reads that row's delivery (`none` when no `bil24_wp` site sells the event). The WordPress sites get the change through the existing `event.changed` webhook and re-read the session: there is no dedicated wp-json endpoint for it. A repeated PUT of the current state answers 200 `changed:false` and writes nothing. Clients: the bot's session card (`eventbot/sessions_sales_state.go`: `ses:ss:<state>` opens the confirm screen, `ses:ssgo` writes with ONE press because the switch is reversible and emails nobody, `ses:ssck` re-reads `site_sync`) and the web event center's `SessionSalesState` block; the web twin (`tests/smoke/live/sales-state.spec.ts`) uses its own fixture event (`arena-e2e-seed --sales-state-op reset`), never the shared session, because a "sold out" there would refuse other twins' holds. Alerts (package `salesalert`, self-scheduling job `sales_state.watch`, every minute, registered in arena-worker): a session is told as sold out when "sold out" is set by hand, or when it has places, none is free AND no unpaid hold is left (`salesalert.IsSoldOut` — the storefront already says sold out with holds in flight, the organizer is told only when it is final); a "coming soon" is never a sell-out. `session_soldout_notices` holds a session while it is told and is deleted when a place comes back, so the next sell-out is told again; the notice row and the `sales_state.alert_email` job are written in one transaction BEFORE the chat message (a crash loses a chat line, never repeats it). A journal row whose outbox delivery is still missing after `StaleAfter` (15 min) while a `bil24_wp` site sells the event is told once (`site_alerted_at`). Messages go to the organization's OWN sales chats only (`salesnotify.AnnounceToOrg`, in the org's `default_locale` en/ru/es); the e-mail (`delivery.NewSalesAlertHandler`, template `sales_alert`, seven locales) goes to the owners AND managers for a sell-out, and to the owners only for a stale site and only when no chat took the message. The FIRST pass on a database (`sales_alert_watch_state` empty) records what is already sold out or stale and tells nobody, so a deploy does not flood the chats. `GET .../sales-state` answers `org_sales_chat`; the bot and the web say a sell-out goes by e-mail only when it is false.
- **"Notify me when sales open" (package `salesubscribe`, table `session_sale_subscriptions` in migration 0183, owner decisions 2026-10-31) is accepted ONLY while the session's effective state is `soon`.** That covers a "coming soon" set by hand AND the automatic one (a category whose sale window has not started). Clients:
  - the widget: `POST /v1/public/feeds/{feed_token}/sessions/{session_id}/sale-subscriptions`;
  - the WordPress sites: the gateway command `SUBSCRIBE_SALE`, an arena extension authenticated by the channel token, with `email`, `locale`, `pageUrl`, `consent` (flex bool) and `consentVersion`.
  
  Both call `Service.Subscribe` and answer the same success whether the address was new, pending or confirmed, so the endpoint never reveals which addresses are known. The consent is ONE ticked box; its version (`salesubscribe.ConsentVersion`, mirrored as `SALE_NOTIFY_CONSENT_VERSION` in `apps/widget/src/lib/saleSubscribe.ts`), the time and a salted client-address hash are stored, and another version is refused (`subscription.consent_outdated`). **Change both constants together whenever the consent text changes meaning.**

  Double opt-in:
  - the `sales_state.subscribe_confirm_email` job mints the token AT SEND TIME and stores only its SHA-256, so the link never sits in `worker_jobs`;
  - `GET /v1/public/sale-subscriptions/confirm?token=` confirms once and 303s to the page the buyer subscribed on with `arena_subscription=confirmed|invalid`.

  A widget's `page_url` is kept only when its origin is on the return-URL allow-list (`ReturnURLPolicy.AllowsOrigin`), so nobody can make arena mail a link to their own site. A site's `pageUrl` is trusted because the channel token authenticates it.

  The `sales_state.watch` pass (`salesubscribe.ClaimOpened`) queues one `sales_state.sale_open_email` per confirmed, not-yet-told address when a session becomes `open`. It marks `notified_at` in the same transaction, so nobody gets the letter twice. A new subscription of a confirmed address clears `notified_at` and waits for the next opening.

  The letter's language is the subscription's, then the organization's, then English. It links to the subscribed page, else the event page (`delivery.SaleBuyLink`). Both letters end with the owner-approved note that Unsubscribe stops EVERY letter to that address, tickets included (`saleUnsubscribeNotes` in the template tests).

  Rows are kept forever: the consent also covers invitations to later events.

  Limits are counted in the database: 20 subscriptions an hour per client address, 10 per e-mail.
