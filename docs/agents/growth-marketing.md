# Growth: reminders, marketing consent, smart price

Unpaid-order reminder, marketing tick and double opt-in, smart price presets. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **The unpaid-order reminder and the marketing tick (spec 51-1, migration 0190, owner answers 2026-11-02) are two packages and one rule each.** `cartreminder`: the self-scheduling `checkout.reminder_sweep` (every minute, arena-worker) picks widget orders (`source='public_feed'`, `pending_payment`, total > 0, a buyer e-mail) created 15 minutes ago or more whose hold still has 8 minutes, unless `org_growth_settings.cart_reminder_enabled` is false (no row = on), and claims each with ONE `checkout_reminders` row (order id is the key) plus the `checkout.reminder_email` job in one transaction, so an order gets at most one reminder whatever the sweep does. The letter handler (`delivery.NewCartReminderHandler`) decides again with `cartreminder.Decide` (paid, expired, under 5 minutes left, no open payment page, a newer order of the same address for the session, switched off), then TAKES the reminder before sending (`cartreminder.Claim`: `sent_at` set only when nothing was sent or skipped; `Release` gives it back when the relay refuses), so a retried or reclaimed job can never mail it twice; never move that write after the send. It is a buyer-order letter (`email_letters` kind `checkout_reminder`). Both letters follow white label (spec 53): the reminder by the session's brand, the marketing confirmation by the organization's own period, with the platform line inside `{{if not .WhiteLabel}}` and the brand as sender. Its link is `GET /v1/public/checkout/{checkout_token}/resume`, never the provider page: the route 303s to the payment page while the order is unpaid and the window open, else to the buyer page stored in `checkout_sessions.return_url` (checked by `ReturnURLPolicy` again) with `checkout_token`, else to the tickets base. `marketing`: a tick at checkout (never pre-ticked) is `marketing_consent {accepted, text_version}` in `checkout/quote` and `checkout/start`; `text_version` must equal `marketing.TextVersion`, mirrored as `MARKETING_TEXT_VERSION` in `apps/widget/src/lib/marketing.ts` (a widget test reads the Go constant) — change both whenever the tick text changes meaning, an older one answers 422 `marketing.consent_outdated`. The widget sends its OWN constant, never the version the feed names, so an older cached widget is refused instead of being recorded as having shown the newer text. State is `marketing_subscriptions` (one row per organization and address, pending/confirmed/withdrawn), evidence is the insert-only `marketing_consents` journal with the real IP and browser; `customer_consents` is not used. Double opt-in: the `marketing.confirm_email` job mints the token at SEND time and stores only its hash. The confirmation link works like the withdraw link: GET only shows a page with a button (`LookupConfirm`), POST confirms, because a mail scanner's click must not stand as the buyer's consent with the scanner's address in the journal. The withdraw link is `/v1/public/marketing/withdraw?token=`: GET only shows a page, POST (multipart, the JSON content-type guard lets it through) withdraws, because mail scanners open links; the word "unsubscribe" must not appear in any buyer template (`TestTransactionalTemplates_CarryNoUnsubscribe`). The reward is the promo code in `org_growth_settings.consent_promo_code_id` (live, `max_uses_per_customer = 1`, checked on save): `hfeed.pickDiscount` takes the larger of it and a typed code, a typed reward code without the tick is `promo.not_applicable`, and an address that already used it gets 422 `marketing.discount_used` at start (the quote has no e-mail); the widget then sends `discount: false` with the next press and the consent is still recorded. `pickDiscount` counts the reward's uses with `CountPromoCodeUsesInFlight` (the count `hcheckout.ReservePromoUseTx` takes inside the order transaction: redemptions plus paid or live orders), so a reward whose `max_uses` is held by live orders is simply not applied, in the quote and the start alike. A use taken between that check and the order is refused inside the transaction and answered as the tick's own `marketing.discount_used` / `marketing.discount_unavailable` (`rewardRefusal`), never as a plain promo error: the widget would otherwise drop a typed code that is not the problem and send the same request again. An address the order accepts but `marketing.NormalizeEmail` refuses drops the tick before the hold (`dropUnmailable`), so the consent never fails the checkout. GDPR erasure calls `marketing.ForgetEmailTx` before `AnonymizeUser`, in its own transaction (`GDPRProcessor.forgetMarketing`), so a retry after a failure finds the same rows. Organizer side: `GET|PUT …/growth-settings` (`promo.read` / `org.update`), `GET …/marketing-subscribers[.csv]` (`order.read`, API keys refused; the CSV carries every row in batches of 1000 and answers 413 `export.too_many_rows` above 50000 before the first byte, never a cut file) and the event center screen `/o/$orgId/growth`. Integration tests must scope the sweep with `cartreminder.SweepOrgs` (an unscoped sweep claims other packages' orders in the shared database and leaves `checkout.reminder_email` jobs nobody handles) and delete their `checkout.reminder_email` / `marketing.confirm_email` jobs (`growthCleanup` in `growth_integration_test.go`). The widget prices the pay button with the tick through `lib/marketingQuote.ts` (`checkout/quote` with `marketing_consent`, shown only for the cart and code it was asked about, never blocks paying); `marketing.Purge` (called from `worker_jobs.cleanup`) deletes withdrawn subscriptions 3 years after withdrawal and never-confirmed ones 3 years after the tick, with their journal, and never a confirmed one. Twin test: `apps/event-center/tests/smoke/live/growth.spec.ts`, fixture `--growth-op reset`. Not built: the WordPress plugins, a bot screen.
- **"Smart price" is a preset written through the event-bundle import, never a second price engine (spec `08_architecture/51_4_2_smart_price_ru.md`, migration 0189 `smart_price_rules`, owner decisions 2026-11-02).** `internal/domain/pricing/smartprice` is the one pure computation (step prices rounded UP to a whole currency unit, linear from the start price, capped); `himports/smart_price.go` turns a preset into what already exists and posts it through `prepareImport` + the arena executor in one transaction:
  - `by_sales` = a category CHAIN (`nextCategoryIndex` + `sellLimit`), the steps named "Name · 2", "Name · 3"... and the hall keeps its places (the head carries the whole chain, successors start closed with none; `gaquota.RebalanceStep` and `tier.chain_sweep` hand places on as for any chain). A seated category never takes it (422 `smart_price.seated_by_sales`).
  - `by_days` / `last_days` = a `priceSchedule` on the category.

  Routes (`.../organizations/{org_id}/sessions/{session_id}/smart-price`, `tier.read` for the list, `tier.update` for preview/enable/stop): the preview writes nothing; enable refuses a category already in a chain, one with future price windows, a free one and a second active preset (409/422, codes `smart_price.*`); stop freezes the price (later chain steps take the current price, no place moves; future windows are removed). **A price set by hand ends the preset** (`gen.OverrideSmartPriceRulesForTier(gen.SmartOverride{...})`, called inside the transaction of the tier PATCH, the price-schedule PUT, pricing-bulk and every ordinary arena import: `smartPriceGuard` in `executorFor` compares the preset categories before and after the import and skips imports marked `importPlan.SmartPriceWrite`): status `overridden`, and nothing rises afterwards. Chain steps after max(edited step, step selling now) take that step's price, so the step buyers pay now never changes unless it is the one edited; an import keeps step prices it changed itself (`PricesBefore`). A base price PATCH (`ScheduleTyped` false) removes every future window; a schedule written by hand (PUT, pricing-bulk, import: `ScheduleTyped` true + `Before`) removes only the future windows that equal the ones stored before the edit — the web and the bot re-send the WHOLE schedule when they change the window in force now, so the preset's untouched windows come back and must go, while a window the person typed stays — and the window in force runs on to the next window left, or open-ended. A rise by tickets sold refuses a category with a running or future window (`smart_price.schedule_exists`: the head would be dearer than the steps after it). **Enable and stop are planned from a read-only snapshot, so the write re-checks it:** the write transaction first runs `LockSmartSession` (sessions row, then the session's categories in id order) and compares `SmartSessionFingerprint` with the snapshot's; on a difference it reads and plans again, up to `smartAttempts` (3), then answers 409 `smart_price.changed`. The fingerprint leaves sales and holds out on purpose (they move no place between categories); anything the bundle re-posts (session times, event, category fields, windows, chain links, place counts, presets) must stay in it, or a colleague's edit made meanwhile is written back. The buyer feed shows a smart chain as ONE card under the head's name (`hfeed/public_feed_price_steps.go`: future steps of every chain are hidden, past steps of a smart chain too) with `price_step.remaining_at_price` (real free places of the selling step) and `next_price`; the widget line is `lib/priceStep.ts` (7 languages, nothing when the feed says nothing). Clients: web `SmartPriceSection` on the category card (rules in `lib/smartPrice.ts`, twin `live/smart-price.spec.ts`, seed `--smart-price-op reset|sell`), bot `eventbot/smart_price.go` inside the categories dialog (`ct:sp|ss|sd|sl|sn|se|sx|sz:<tier>`, turn on only from the preview on screen, stop only from its own question; e2e `bot_e2e_smart_price_integration_test.go`). Not built: parallel categories in one preset, "change the rule", a sales-chat message on a new step.
