# Refer a friend

Personal referral codes, cashback refunds, shop referral, review rules, cashback in reports. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **"Refer a friend" server core (spec 52, migration 0191, `internal/platform/referral`, steps RF-1/2/5).** A personal code is a `promo_codes` row with `origin='referral'` (new columns `origin`, `referral_program_id`, `referrer_order_id`, `referrer_shop_order_id`; the shared `PromoCodeRow` is NOT widened, `gen.GetReferralPromoMeta` reads them) issued idempotently by `referral.IssueCode` (unique partial index on `referrer_order_id`, code `ANNA-7K2Q`). `referral.RecordFriendOrderTx` runs in `hcheckout.FulfillCompletedCheckoutTx` under a SAVEPOINT (`recordReferralRewardTx`), writes one `referral_rewards` row per friend order (self-referral, other currency, cap and zero amount end it without money) and enqueues `referral.payout` in the same transaction. The payout is a partial MONEY-ONLY refund of the referrer's own payment through the refund engine: `BatchInput.Origin='referral_cashback'`, `CancelTickets=false`, `NotifyBuyer=false`, key `referral-<reward id>`; the cap and the split over tickets are decided inside the engine's transaction under `LockPayment` by the new `BatchInput.Prepare` hook (it replaces `Items`, never runs on a replay). A scan of the ticket does NOT stop such a refund (R-RF3): `scanBlocksBatch` in `create.go` and `refundIgnoresScanSQL` in `scanned.go` (claim, `ScannedTicketForRefund`); a referral refund that CANCELS tickets is still blocked. `billing.collect`'s `ListCollectRefunds` skips `origin='referral_cashback'`. `referral.payout_sweep` (self-scheduling, 10 min, `cmd/arena-worker/referral.go`) requeues stuck due rewards, reads back `sent` ones, records `friend_reversal` (friend order refunded or, when `payment_disputes` exists, disputed), calls `Notifier.FriendReversed` (nop until the Telegram/e-mail one is wired: `ErrNotWired` leaves it unmarked), PAUSES a code with two reversals (`promo_codes.status='paused'`) and deactivates the code of a refunded or cancelled referrer order. The programme's status does NOT stop a reward already recorded (spec 3.1). A fixture that deletes orders must delete `referral_rewards`, then `promo_codes`, then `referral_programs` first (plain FKs, no cascade). Tests: `referral/*_test.go`, `referral_integration_test.go`, `refunds/engine_referral_cashback_integration_test.go`.
- **The "Refer a friend" routes (spec 52) live in `httpserver/hreferral` and `hfeed/public_referral.go`, over the core in `internal/platform/referral`.** Org routes under `/v1/organizations/{org_id}/events/{event_id}/`: `referral-program` GET (`promo.read`; no programme is 404 `referral.program_not_found` whose `error.details` carries `capability` and `warnings`), PUT (replaces the settings, 201 on a new programme, 200 on a change; first enable needs `accept_terms`, else 422 `referral.terms_not_accepted`; channels that cannot return part of a payment are 422 `referral.provider_unsupported`) and `/pause` `/resume` `/end`, `referral-program/summary`, `referral-rewards` (keyset `cursor`, never a buyer e-mail, phone or name). Every write needs `promo.update` AND `refund.create` AND `refund.approve` (`alsoRequire` in `mount_referral.go`, so the owner and manager pass, an agent does not), runs under the advisory lock `arena.referral.program:<event>` and writes an audit row `v1.referral_program.*`; the event is loaded inside the path organization (`GetEventOrgForMaterials`, 404 `event.not_found`). Capability (`hreferral/capability.go`) judges the event's published channels (else the organization's non-site channels) through the payment module registry (`Capabilities.PartialRefund`; a channel with a gateway credential is a selling site and never qualifies); an event with no channel yet is advisory only. Public `GET /v1/public/checkout/{checkout_token}/referral` issues the code with `referral.IssueCode`, same rate limiter as the order status route, every miss is the same 404 `referral.not_available`. checkout/start (not quote) refuses the buyer's own code with 422 `promo.own_referral_code` (`referral.IsSelfReferralBuyer`: e-mail or phone of the referrer's order or customer) and a paused, ended or out-of-period programme's code with `promo.not_active` BEFORE the hold; the Bil24 gateway path does not check the programme status yet. Promo code LISTS, usage and the redemptions list without a code id show `origin='manual'` only, get-by-id still reads a referral code. `refund-options` carries `referral_cashback_paid` for a friend order whose reward is `sent` or `paid`. The integration test is `referral_routes_integration_test.go`; on the shared database a GA hold sometimes answers 409 `reservation.over_capacity` for any code (`TestPublicQuote_EqualsStartTotal_AndLeavesNothingBehind` fails the same way), so it accepts that answer for the friend's checkout.
- **"Refer a friend" for the organizer's SHOP (spec 52 sections 0 R-RF6 and 3.5, same migration 0191) reuses the tables and the engine, with five differences.** (1) A shop programme is `referral_programs.scope='shop'` (one live per organization, `event_id` NULL); the routes are the event ones under `/v1/organizations/{org_id}/shop/referral-program[/pause|resume|end|summary]` and `.../shop/referral-rewards`, the SAME handlers (`hreferral/target.go`: a `target` is an event or the shop), the same rights (`promo.read` / `promo.update` + `refund.create` + `refund.approve`), the capability judged from the shop settings' sales channel, else the organization's non-site channels. (2) A shop code is a `promo_codes` row with `referrer_shop_order_id` and the SENTINEL `gen.NoSessionID` (nil UUID) in `applies_to_session_ids`, so the ticket checkout, the Bil24 gateway and `promo-validate` can never treat it as a club code; it is read only through `gen.GetReferralShopPromoByCode`. (3) `POST /v1/public/shop/{org_slug}/checkout` takes `promo_code`: `referral.CheckShopPromo` (in `shop.placeOrderTx`, before the total) refuses with 422 `promo.not_applicable` / `promo.own_referral_code` / `promo.not_active` / `promo.exhausted`; the discount is `referral.ShopDiscount` = floor percent of the GOODS subtotal (never the delivery fee) and goes to the existing `shop_orders.discount` (total = subtotal - discount + shipping_fee is a DB CHECK) plus the new `shop_orders.promo_code_id`; there is no `promo_code_redemptions` for a shop, uses are counted over `shop_orders` (paid-like statuses and live pending holds) under `LockShopPromo`. (4) `shop.markPaidTx` calls `referral.RecordFriendShopOrderTx` inside a SAVEPOINT (`recordReferralTx`); the cashback is `referral.payoutShop`: a partial refund of the referrer's shop payment through the engine, `Origin='referral_cashback'`, key `referral-<reward id>` stored in `refunds.idempotency_key` + `shop_order_id`, written under `LockPayment`. `SumShopPaymentRefunds` "accepted" EXCLUDES cashback and the engine skips `projectOrder` for it, so the referrer's order keeps its status, `refunded_minor` and letters. (5) The buyer's code after payment is `GET /v1/public/shop/checkout/{order_token}/referral` (404 `referral.not_available` for everything else, `Cache-Control: private, no-store`, link from `shop_domain` else `SHOP_PUBLIC_BASE_URL/<slug>`); the catalog settings carry `referral_active`. The notifier moved to `referral/referralnotify` because `shop` imports `referral` and `salesnotify` imports `shop`; `referral` itself must never import `salesnotify`. The shop-page reads `?promo=` into sessionStorage (`lib/referral.ts`) and shows the promo field only while `referral_active` or a code came with the link. A fixture that deletes shop orders deletes `referral_rewards`, nulls `shop_orders.promo_code_id`, then deletes `promo_codes` and `referral_programs` first (`referralShopCleanup`). Known gap: `salesnotify.AnnounceToOrg` skips shop-only Telegram chats, so a shop-only organization hears about a friend's reversal by e-mail only. Test: `httpserver/referral_shop_integration_test.go`.
- **"Refer a friend", second review (migration 0191 edited in place): a code is issued only for a payment that can return a part of itself, and the "could not return" letter has an explicit rule.** `referral.IssueCode`/`IssueShopCode` answer `ErrNotEligible` (the buyer's page: 404 `referral.not_available`, like `ErrNoSessions`) unless the order's succeeded payment intent names a provider whose module has `Capabilities.PartialRefund` (`referral/partial.go`, `CanPartialRefund`, read from `app/payments` registry). A fixture that issues a code needs a succeeded `stripe` payment intent for the referrer's order (the referral unit fixture's fake module is named `stripe` for that reason). `RecordFriendOrderTx` and its shop twin write `not_possible` `provider_unsupported` (no letter) when the referrer's provider changed after issue. `LetterKindFor(state, reason, providerCode)` sends the "unavailable" letter only for `provider_declined` or the provider's own failure code (reason == provider code) of a refund that really reached the provider (`refundView.Attempted` = `provider_attempts` > 0; otherwise `refund_not_sent`); every platform decision (`no_refundable_ticket`, `refund.*`, `payment_not_succeeded`, `no_payment`, `provider_unsupported`, `currency_mismatch`, `manual_review`, ...) sends nothing, add a new reason to `TestLetterKindFor_PlatformReasonsSendNothing`. A reward announced as paid that later ends in such a refusal gets ONE correction letter (`CashbackEmailPayload.Correction`, `referral_rewards.correction_sent_at`), never while the refund waits in `manual_review`. A code's pause is final (no route switches it on): no text may promise it. The shop catalog answers `referral_friend_discount_pct` beside `referral_active`; the shop checkout previews the discount with `referralDiscountMinor` (same floor as `ShopDiscount`) and says the payment page is final. The widget's open promo field no longer counts `origin = 'referral'` codes (`promo_codes_available`).
- **"Refer a friend", rules from the first review (spec 52).** (1) A refund with `origin='referral_cashback'` is never retried (`refunds.Retryable` false, the retry route answers 409 `refund.not_retryable`); the general retry carries `Origin` into the new batch. (2) A personal code is visible ONLY to the widget checkout (`GetPromoCodeByCodeCIAnyOrigin`, hfeed quote/start) and to the shop checkout: `GetPromoCodeByCode`/`GetPromoCodeByCodeCI` read `origin='manual'` only, so the Bil24 gateway, the REST checkout and `promo-validate` answer a referral code as unknown. A new surface that looks a code up must pick one of the two on purpose. The marketing tick's reward code (`marketing.SaveSettings`, `LoadOffer`, spec 51-1) is read by id and must be `origin='manual'` too: a referral code is limited to one use per buyer, so it passes the reward check and every subscriber would get the friend's discount and pay its owner a cashback. (3) Percentages are a snapshot on the code (`promo_codes.referral_cashback_pct`, `referral_cap_pct`), filled at issue: the reward and the buyer's screen read the code, never the current programme. (4) A refund in `manual_review` gives the reward reason `manual_review` and keeps the provider's code in `referral_rewards.provider_code`; the sweep reads it back and moves the reward to `paid` or `not_possible` when the operator closes the refund. (5) Session, event and report numbers of "refunds" leave `origin='referral_cashback'` out, but since 2026-11-03 the cashback is its own figure and comes off net, and sales-link revenue is net of it (see the "cashback in the sales reports" entry); a shop order is `refunded` when ordinary accepted refunds plus cashback cover its total, and a cashback alone never changes its status. (6) The friend count of a code is decided under a row lock of the promo code (`lockedFriendCount`), extra friends get `capped`/`max_friends`. (7) Down of the referral migration RAISES while cashback refunds exist: they must never become ordinary refunds. (8) Every referral percentage is taken from `referral.ItemsBase(subtotal, discount)` (owner decision 2026-11-03): the friend's tickets or shop goods after the discount, never `total` (no service charge `orders.charge`, no delivery, no fee or tax), and the referrer's cap uses the same base on their own order; a new place that computes a cashback or a cap must call it.
- **"Refer a friend" cashback in the sales reports (owner decision 2026-11-03, migration 0195).** The cashback is money the organizer returned to a referrer out of the referrer's own payment, so it is NOT a refund to a buyer and NOT left out of the money: `ListSessionSummaryRefunds` selects and groups by `r.origin`, `horders.foldMoney` keeps `referral_cashback` rows out of the `refunds` groups and out of `money.refunded`, counts succeeded ones into `money.cashback` / `money.cashback_refunds`, and `net = paid - refunded - cashback`. Session `sources` and `SalesLinkOrdersAggregate` revenue subtract it too, so they add up to the net. The post-event report writes a `referral_cashback` line (`AggregateReferralCashbackForEvent`, category CHECK widened by 0195, `reporting.CategoryReferralCashback`); the `refunds` line still leaves it out. The order card answers `referral` (`horders/referral.go`, `queries/order_referral.sql`, best effort, null when the order has no part): `cashback[]` of a referrer's order (one per friend order, `paid_at` = latest succeeded cashback refund of the reward or its batch) and `used_code` of a friend's order. Clients: bot `bot.ec.refunds_line` / `bot.ec.sum_money` (`Cashback`/`CashbackCount`, empty = part left out) and `bot.ord.ref_*` (`eventbot/order_referral.go`), web `figures.cashback` in `SalesFigures` and `components/OrderReferral.tsx`, admin-web session overview. A new money figure that reads `refunds` must decide on purpose whether a cashback row belongs to it. Live twin: `tests/smoke/live/referral-cashback.spec.ts` with `arena-e2e-seed/referral_cashback_fixture.go` (own event "E2E Cashback Show").
