# Venue SVG generator (apps/venue-svg-generator)

The Python service that turns a hall plan into a hall model, an authoring SVG and a preview PNG.

- **The service contract and the hall model live in ONE file, `apps/venue-svg-generator/HALL_MODEL.md`.** Section 7 is the HTTP contract that arena-worker calls (`POST /generate`, `GET /jobs/{id}`, `POST /render`, `POST /schematic`, `POST /apply-operations`). Change the code and that file in the same commit. The model is `seating-json-v2`; the adapters still write their own private `seating-json-v1` shapes and `hall_model/convert.py` converts them.
- **The service refuses to start without `VENUE_GEN_TOKEN`.** Every route except `GET /healthz` needs `Authorization: Bearer`. Tests set `VENUE_GEN_ALLOW_NO_TOKEN=test-only` (in `service/tests/__init__.py`); never put that variable into the Dockerfile or compose. The CI smoke step and the compose service pass the token through the environment.
- **Run the generator tests from the app folder, not with a path argument.** `python -m pytest` inside `apps/venue-svg-generator` reads `testpaths` from `pytest.ini`; `pytest apps/venue-svg-generator` from the repository root also collects `benchmark_v1`, which imports a git-ignored package and fails at collection.
- **The Go contract test reads committed fixtures.** `internal/domain/seating/venue_gen_authoring_test.go` imports `arena_export/testdata/*.svg` with `ImportSVG` and `ValidateForPlanType`. After a change of the exporter, the schematic layout or the service render path, regenerate them with `VENUE_GEN_REGEN_FIXTURE=1 python -m pytest arena_export` (the run rewrites the old v1 fixture with other line endings: restore it with `git checkout` when its content did not change) and run the Go test.
- **A seat without a full identity never becomes a seat in the authoring SVG.** Identity is section, row label and number, unique, not blank, not `observed`. Unavailable seats are drawn as decor. A schematic hall is `QUARANTINE` until the caller sets `confirmed: true`, and every applied operation sets it back to false.
- **No client file and no profile bound to a client file's SHA-256 goes into the service.** `m2_fixtures/` and the `results/` folders of the old M2 checkout stayed behind on purpose. Test data is built in code.
- **On the staging stand the generator is a standalone container, not a service of the stand's compose.** `arena-venue-generator` on `lead-parser`, network `arena-backend-2lzrkj_default`, names `venue-generator` and `venue_gen`, port 8090, no host port and no Traefik router; token and run script are in `/opt/arena-venue-gen` on the server. The limit is 1024 MB (`--memory` = `--memory-swap`), `oom_score_adj` 500. Keep `VENUE_GEN_JOB_MEMORY_MB` at 2048: it caps VIRTUAL memory, and at 900 a real PDF with a 250 MB peak fails with `memory_limit`. The health route is `/healthz`. The api and worker images have no shell: test from `docker run --network container:<worker>`. Measurements, rollback and update steps: `docs/ops/venue_generator_staging_install_2026-11-12_ru.md`. The worker of the stand calls it only when its environment has `VENUE_GEN_URL=http://venue-generator:8090` and `VENUE_GEN_TOKEN` (job `venue_plan.generate`, see `venue-plan-intake.md`).
- **What the generator really reads today (2026-11-13), as the intake sees it.** XLSX: a layout the autodetect finds gives `PASS` and a draft for the organizer. Vector PDF: seats and numbers, never row labels, so no seat has an identity and `authoring_svg` is null. JPEG and PNG: the raster adapter needs a per-file colour profile (`raster_profile`), the worker has none to send, so the answer is `no_adapter` with `raster_profile_required`. A scanned PDF has no seat candidates. XLS and CSV have no reader. Everything but the first case goes to an administrator with the exact reason; the structural lane (`POST /schematic` after a vision model read the image) is what closes the gap.
