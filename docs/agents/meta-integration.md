# Meta integration (spec 66)

Connection of an organizer's Meta business (Facebook Login for Business, BISU token), the encrypted token, CAPI through the connection. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **The Meta token is the first secret encrypted at rest: `internal/platform/secretbox`, key `META_TOKEN_ENC_KEY` (2026-11-22, M1).** AES-256-GCM, value `<keyid>:<base64url(nonce||ciphertext)>`, AAD = the organization id bytes, so a sealed value copied into another organization's row does not open. The key spec is `v2:<b64>,v1:<b64>`: the first key seals, every key opens (rotation: put the new key first, keep the old one until every row was re-sealed or reconnected). Without the key the feature is OFF (`cfg.MetaEnabled()` needs `META_APP_ID`, `META_APP_SECRET`, `META_LOGIN_CONFIG_ID` and a key that parses); a token is never stored in plaintext. Losing the key means every organization has to connect again. `config` imports `secretbox`, never the other way round.
- **One connection per organization: `org_meta_connections` + `org_meta_assets` (migration 0219).** `access_token_enc` is wiped on disconnect, deauthorize and a 190 answer (`MarkTokenInvalid` sets it NULL, so a disconnect after a 190 no longer calls Meta); a CHECK keeps an active row with a token. `meta_user_id` is the app-scoped id from `/me` and the ONLY key the Meta callbacks (`signed_request`) carry. Only one selected asset per kind (partial unique index). The token is never returned by a route, written to a log or to audit (`v1.org.meta.connect/select/disconnect`).
- **The login is the server redirect `dialog/oauth?config_id=…&response_type=code`, the event center does NOT load the Facebook JS SDK.** The JS SDK popup would need a looser CSP (`connect.facebook.net`) and COOP `same-origin-allow-popups` for the WHOLE app while the refresh token sits in localStorage, and a popup opened after an awaited request is blocked. There is no JS mode at all (removed 2026-11-23): the `state` has no mode and the exchange always sends `META_OAUTH_REDIRECT_URL`; without that address the feature is off. The `state` is HMAC-signed with a key derived from the app secret, lives 10 minutes and names org and user. `META_OAUTH_REDIRECT_URL` is required in production on the api only, never on the worker (`capMetaLogin`).
- **The public callback NEVER exchanges the code (login CSRF): it checks the state's signature and expiry and redirects to `EVENT_CENTER_PUBLIC_URL/o/{org}/ads/meta?meta=finish#code=…&state=…`.** Code and state go in the FRAGMENT, never the query (no server log, no Referer). The page wipes the fragment at once (`history.replaceState`) and posts them ONCE to `POST /v1/organizations/{org_id}/integrations/meta/finish` (org.update + membership, API key refused); `finish` refuses with 403 `meta.state_mismatch` unless `state.org` is the path org AND `state.user` is the JWT actor, re-checks `org.update` in the DB, then exchanges and saves. Errors of `finish` are JSON envelopes `meta.<reason>`; the callback answers only redirects (`?meta=error&reason=denied|no_code`, root for `state_invalid`/`disabled`) except 503 `meta.event_center_unconfigured`. The code exchange is a GET with `client_secret` in the query (as Meta documents it); `metaconnect` reduces every transport error to a text without the URL and never copies Meta's error message.
- **A Meta `signed_request` older than 24 hours or more than 5 minutes ahead is refused (`ParseSignedRequest(raw, secret, now)`).** A missing `issued_at` is refused too.
- **A Meta connection that cannot be read never blocks GA4.** `PGStore.Settings` puts an `ActiveDataset` error (database or key) into `Settings.MetaErr` and still returns the manual GA4 credentials; only the meta delivery retries, it never falls back to the manual pixel.
- **Which Graph edges list ad accounts and pages is not confirmed for a BISU token: `META_ASSET_EDGES` decides.** Default: pixels `{business}/owned_pixels`, `{business}/client_pixels`; ad accounts `{business}/owned_ad_accounts`, `{business}/client_ad_accounts`, `me/adaccounts`; pages `{business}/owned_pages`, `{business}/client_pages`, `me/accounts`. An edge that fails with 10, 100 or 200-299 is skipped, the connection is still saved. Check on the first live login (spec 66 §4.1а) and narrow the list.
- **CAPI takes the connection first, the manual `org_conversion_settings` token second (`conversions.PGStore.WithMetaBox`).** The test event code and GA4 always come from `org_conversion_settings`. Only Graph code 190 with the connection token moves the connection to `error` (once, `MarkTokenInvalid` returns `changed`) and fails the delivery without retries; 10/200-299 fail only that delivery and write `last_error`, the connection stays active. The manual-token path keeps its old behaviour. Every event carries `partner_agent: arenasoldout`. The Graph version is `META_GRAPH_VERSION` (default `v25.0`) for both paths; v21.0 stops working on 2027-01-21.
- **`META_GRAPH_BASE_URL` is a test seam and is refused in production**, like `STRIPE_API_BASE_URL`. It replaces only the host; the version is appended to it.
- **A broken Meta connection tells its owners once, in the transaction of the break (`conversions.PGStore.MarkMetaTokenInvalid` -> `adminnotify.NotifyMetaConnectionBroken`).** Only the call that moves the row `active -> error` (190 with the connection token) queues jobs: one `admin_notify.email` (payload `kind: meta_connection_broken`) per owner and one `admin_notify.telegram` per non-revoked `bot_telegram_links` row of that owner, through the event-center bot. An owner is `adminnotify.OwnerRecipients`: an ACTIVE membership whose MEMBERSHIP role holds `org.update` (a global role does not count), not deactivated, of a live organization; manager and agent are never told. A second 190 while in error changes nothing and queues nothing; a reconnect followed by a new 190 tells them again. A failed queue rolls the break back, so the next 190 tries again. The worker sets the link and Telegram with `WithOwnerNotice(EVENT_CENTER_PUBLIC_URL, EVENTS_TELEGRAM_BOT_TOKEN != "")`; without the token only e-mails go. The text (Russian only, like every adminnotify letter) names the organization and `/o/{org}/ads/meta`, never a token or Meta's message.
- **Meta's app webhook is `GET|POST /v1/integrations/meta/webhook`, only `business_integration_uninstall` is acted on.** GET answers `hub.challenge` (text) when `hub.mode=subscribe` and `hub.verify_token` equals `META_WEBHOOK_VERIFY_TOKEN` (constant time, api only, secret); an empty token refuses (403). POST checks `X-Hub-Signature-256` = `sha256=<hex HMAC-SHA256 of the RAW body with META_APP_SECRET>` before parsing (64 KB limit, 401 on mismatch); the business id is `value.business_manager_id`, else `value.business_id` (string or number, not confirmed by a live call), and every connection with that `meta_business_id` is revoked, token wiped, assets deleted, audit `v1.org.meta.uninstall` (system actor). Other fields and an unparsable signed body still get 200 (Meta retries anything else); only a database failure answers 503. Feature off: 404 `meta.disabled`. The address and the verify token are entered in the Meta panel (Webhooks -> Application) after the release.
