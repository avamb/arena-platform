# Product analytics and sales funnel

Behaviour events, rollup, CRM export, UX dashboards, bot analytics, buyer sales funnel. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **`analytics.rollup` (stage A5 of spec 50, `internal/platform/analytics/rollup*.go`, hourly, cursor in `analytics.state`) is idempotent by RECOMPUTING, and READ-ONLY on every business table.** Joins (`linkIdentities`: find every person holding any of the identities / the CRM contact / the user, merge into the OLDEST, move identities, delete the younger, all in one transaction) come from `email_click.props.aid`, `onboarding_applications` (`aid` column since migration 0194, e-mail as `email_sha256`, approval -> user, bot confirmation -> `TGHasher`) and new identifiers in events. Then EVERY person is recomputed from raw events: sessions are synced by deterministic id (uuid v5 of person+surface+start), the profile is written only when a value differs so `changed_at` moves only on a real change. Because of that, ages and 30-day windows are counted in whole UTC days (the score changes once a day, never hourly). `analytics.TGHasher` (`tghash.go`) is the ONE implementation of the `tg` identifier, keyed by the dedicated `ANALYTICS_TG_HASH_SECRET` (same value on arena-worker and arena-bot, never JWT_SIGNING_SECRET: the worker does not receive that); unset = the tg join is skipped and each binary warns once. A run holds the session-level advisory lock `analytics.RollupLockKey` on one dedicated connection (a second run is skipped) and `ErasePerson`/`ForgetEmail` take the same lock; only CONFIRMED applications link or count (`/v1/onboarding/applications` is public); a link that would join two different users or CRM contacts is refused and counted (`MergeConflicts`); only people with new events, a join or a user/e-mail identity are recomputed each hour, everybody once per UTC day; sessions older than the oldest kept raw event are never deleted. Erasure: `analytics.ErasePerson` (events of all the person's identifiers, the person row, application `aid`) and `analytics.ForgetEmail` (called by `onboarding.purgeRow` BEFORE it blanks the address). `gmv_30d` is the only milestone that is not a time (currency -> minor units). The integration tests live in `internal/platform/onboarding/analytics_rollup_integration_test.go` because they drive the real application lifecycle, and the rollup walks EVERY person of the database: run them on a scratch database only.
- **The CRM link of the analytics (stage A6) is two handlers in `hanalytics/admin_crm.go` (`CRMHandler`), mounted TWICE: for a human superadmin as `POST /v1/admin/analytics/contact-codes` and `GET /v1/admin/analytics/profiles` (superadmin.read), and for the n8n sync as `POST /v1/service/analytics/contact-codes` and `GET /v1/service/analytics/profiles` behind `httputil.RequireStaticBearer(ANALYTICS_SYNC_TOKEN)` (unset -> 503 `analytics.sync_not_configured`, wrong -> 401; production needs >= 32 characters and a value different from `BOT_SERVICE_TOKEN`).** The service token exists because a human JWT lives 15 minutes and an organization API key can never hold `superadmin.*`; it opens ONLY those two routes, and the audit row is actor type `service`, empty `actor_id`, `metadata.actor_label` `n8n_crm_sync`. The export serves only profiles with `changed_at` <= the start of the last FINISHED rollup run (`analytics.LastFinishedRollup`), `next_cursor` is an exclusive keyset that is ALWAYS present, the explanation (`analytics.ExplainProfile`) is built from the stored profile and sessions (price-page visits are not stored per visit, so their share shows as `price page and other`), and `may_create_contact` is true only for a person with an organizer application or a CRM contact (an account-only manager must never get a CRM card created). Contact codes: `analytics.EnsureContactCodes` returns the OLDEST existing code of a Twenty person id (so every mailing carries one stable `cid`), mints new ones with `crypto/rand` (10 characters of the sales-link alphabet) through INSERT ... ON CONFLICT DO NOTHING and redraw, serialized by `pg_advisory_xact_lock(5050002)` and audited (`v1.admin.analytics.contact_codes.issue`) on the same transaction; a writer without `DurableInTx` makes it 503. Profiles: `analytics.ExportProfiles` is a keyset page ordered by `(changed_at, person_id)` with an INCLUSIVE `changed_since` on purpose - the rollup stamps every profile of a run with the run's START time and commits them one by one, so an exclusive bound loses rows that commit after a reader saw the first of them; clients must write idempotently. The e-mail is resolved at query time (`users.email`, else the newest non-purged `onboarding_applications` row whose SHA-256 matches an `email_sha256` identity) and never stored in `analytics`; `activity_explanation` is NOT stored either - `explainPerson` rebuilds the score items from raw events and the stored milestones with the same pure functions as the rollup. The routes are mounted even without a pool (503) so the OpenAPI drift test sees them. `timeline_url` is `APP_PUBLIC_URL` + `/analytics/people/<person_id>` (the page itself is stage A8). `analytics.Querier` (`querier.go`) is the ONE read interface of the package (Exec/Query/QueryRow). Twenty custom field names must be camelCase (`arenaStage`, not `arena_stage`). The n8n workflow and the field script live in the `avamb/arena-crm` repository (`ops/n8n/arena_analytics_to_twenty.json`, `ops/twenty/create_arena_analytics_fields.py`).
- **The UX dashboards of the admin console (spec 50 A8) are READ-ONLY views over `analytics.flow_daily`, `analytics.events`, `analytics.sessions` and `analytics.profiles`: `GET /v1/admin/analytics/flows|errors` and `.../people/{person_id}/timeline` (`hanalytics.AdminHandler`, `mount_analytics_ux.go`, `superadmin.read`, no `X-Admin-Reason`), queries in `internal/platform/analytics/ux.go`.** Days are UTC days like `flow_daily`; the previous period is the equal-length range ending the day before. The routes are mounted whenever auth is on and answer 503 without a database (never wrap a nil `*pgxpool.Pool` into the `Querier` interface). The timeline continues with an opaque `cursor` (`<unix micro>.<event id>`), returns profile and sessions on the first page only, and recomputes the score explanation (`ExplainScore`) from the person's events at request time. `analytics.ux_digest` (`ux_digest.go`, registered in `analytics_jobs.go` with the worker's ops notifier) is self-scheduling for Monday 09:00 Europe/Madrid (`NextDigestTime`, embedded tzdata): the next run is queued BEFORE the work, guarded by `NOT EXISTS ... status = 'pending'` (NOT 'claimed' too, or the running job would block its own successor), and the message carries counts and dictionary names only. admin-web: nav entries `analytics_flows` / `analytics_errors`, the person page `/analytics/people/$personId` is in `NON_NAV_ROUTE_IDS`; strings live in `lib/i18n/analyticsStrings.ts` (ru + en). The period is capped at 180 days (the previous period must stay inside the 13-month raw retention), a timeline `limit` above 200 is 400, and a failing query is 500 (503 only for a missing database). Integration tests seed the month AFTER the current one, whose `analytics.events` partition already exists, so they never touch real data.
- **The bot's behaviour events (spec 50 stage A4) go through `botAnalytics` (`eventbot/bot_analytics.go`, `wizard_analytics.go`) and only ever carry constants, never text.** `Options.Analytics` is an `analytics.Tracker` (arena-bot passes the process's `analytics.Writer`, closed before the pool at shutdown; nil = off, every method is a no-op). Identity is the linked platform user (`id_kind=user`, `bot_telegram_links.user_id`) else `analytics.TGHasher.Hash(telegramID)` (`id_kind=tg`, keyed with `ANALYTICS_TG_HASH_SECRET` through `Options.AnalyticsTGHashSecret`, empty = bot analytics off, the raw id is never stored); `org_id` is the draft's organization, else the link's current one. The who-is-this answer is cached 30 s: call `b.an.forget(tg)` wherever a link or the current organization changes. `bot_update` is written inside the sender's lane right after the rate limiter (a refused update writes nothing) and carries the step from `bot_dialogs` (`<kind>:<step>`) or the open draft. `wizardApply` records `wizard_step` / `wizard_input_error` / `wizard_exit` (cancel / keep / drop) from `trackWizard`; `wizardSave` writes `wizard_exit done`; `draft_sweep.go` writes `wizard_exit expired` and `draft_reminder`. A refused wizard answer is reported through `d.reject("err_x", note)`, which stores the message key on `Draft.rejected` (never persisted); the code comes from `wizardReasonCodes`, and `TestWizardReasonCodes_CoverEveryErrKey` fails when a new `bot.wz.err_*` key has no code. The time on a step is `Draft.StepSince` (Unix seconds, in the draft JSON, no schema bump). **`analytics.Sanitize` reads numbers the way JSON decodes them: pass `float64`, not `int`, or the prop (`seconds`) is dropped silently.**
- **The buyer sales funnel is `sales_funnel_daily` (migration 0193) fed by `POST /v1/public/funnel` and read by `GET /v1/organizations/{org_id}/events/{event_id}/funnel` under `report.read` (spec 50, stage A7).** Only the first three steps (`view`, `session_open`, `seats_chosen`) are counters; `checkout_start`, `payment_open`, `paid` are counted LIVE from `orders` / `checkout_sessions` / `payment_intents` (`gen/sales_funnel.sql.go`) and must never be written by the beacon (`salesfunnel.ParseStep` refuses them). The server steps count BUYERS, not attempts (key: customer id or lower e-mail or the order id, x session x venue-zone day), so a retried checkout cannot push a share past 100 %; the window's own steps come from `GetFunnelServerTotals` (a buyer once), NOT from summing the grouped rows. Revenue is `orders.total` of ever-paid orders minus SUCCEEDED refunds reached through the order, its ticket or its payment intent (same reach as the session summary), per currency. Every orders/reservations query keeps the sargable `created_at >= $from::date - 1 AND created_at < $to::date + 2` beside the zone-aware date test so `orders_org_created_idx` can be used. The beacon copies the page-statistics beacon (`pagestats.CleanUTM`, suspect UA, venue-zone day, 200-pair cap, `CheckPageTrack` limits) and answers 204 for EVERYTHING except an unreadable JSON body (400): an unknown event, session, page, step or surface, a body that names both contexts or neither, and a surface that does not fit the addressing (`feed_token` is surface `widget` only, `page` is `hosted_page` or `tickets_page`) are all uncounted 204s that tell nothing; 429, 503 (never 502). `session_id` is NULL for `view`, so the primary key uses the STORED generated column `session_key` and `ON CONFLICT` names plain columns. The same visitor's identical step is dropped for the UTC day by `salesfunnel.Deduper`, a salted SHA-256 held in memory only; it lives on the `Server` (`funnelDedupe`, passed through `WithFunnelDeduper`) because `feedHandler()` builds a fresh `hfeed.Handler` per request. A site on the Bil24 gateway protocol (channel with `settings.gateway.token_hash` or the legacy `gateway_token_hash`) has no browser steps: its carts and orders are in the response's `gateway` block, which starts at `seats_chosen`, and are excluded from the main funnel. With `?session_id=` the `view` step has `count: null`. The response carries `sessions` (id, start, status, zone of THAT session's venue) for the screen's picker, and the screen computes its 7/30/90-day presets in the venue's day (`dayInZone`). Frontends: the widget always files under surface `widget`; `funnel="hosted_page"|"tickets_page"` only tells it the Arena page around it counts the `view` (the hosted event page sends it from `main.ts`; a promoter-page card sends it once when the card first scrolls into view, `observeOnce`, because the page mounts a widget per card on load). A session counts as opened only on a buyer action (session chip, seat tap, GA area or quantity), never on load. The funnel read test server must be `productionIntegrationServer` (sign-in wired), the beacon and checkout one `buildHostedCheckoutServer` (`sales_funnel_integration_test.go` uses both). A sales-link `ref` in a fixture must use `attribution.CodeAlphabet` (no `i`, `l`, `o`) or `Clean` drops it silently.
