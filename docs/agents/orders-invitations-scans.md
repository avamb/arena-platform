# Orders, invitations and door scans

Order lists and cards, resend, invitations (bot and web), MACS and door scan events. Also guest lists, ticket reissue, revoked codes and legacy Bil24 tickets. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **An invitation is priced by arena, not by the selling site.**
  CREATE_ORDER_EXT's `complimentary` flag (arena extension, decoded from
  true/1/"1"/"true") keeps each ticket's face value, discounts the whole
  subtotal, drops the service charge and writes the order with source
  `complimentary`, total 0 — so PAY_ORDER expects 0 and the export (MACS,
  webhooks) shows `totalPrice 0` with discount reason «Приглашение». A
  same-cart re-send cannot flip the flag (answers `-2`
  `bil24.order_kind_changed`): an order never changes its source.
- **The org orders list takes ONE `q` and classifies it in `horders.classifyQuery` (EC-04), and the order card builds `delivery` / `payment` / `unpaid_reason` from rows, never from the order status alone (EC-05).** Precedence of `q`: exactly 13 digits = barcode (`barcodes.external_ref`, every authority, to the ticket's order; a legacy `ean13.PlatformCode` is also decoded back to its `system_ticket_id`), up to 12 digits or `#`-prefixed = `orders.system_id`, `@` = exact case-insensitive e-mail (`buyer_email` or a customer identity), a 7-15 digit phone-like value = normalized digits (leading `+`/`00` stripped) matched exactly or by a 9+ digit suffix, else the pg_trgm similarity. A 13-digit value and a 7-12 digit number are ALSO tried as phones (SQL ORs the matchers), so never "fix" that into an exclusive switch. `tab`: `paid` = paid, partially_refunded, refunded, `unpaid` = pending_payment, expired, cancelled, abandoned, manual_review, `recent` (default) = all; every status is in exactly one group and an unknown tab is 400 `orders.invalid_tab`. `session_id` / `event_id` of another organization are 404 `orders.<name>_not_found`, like an unknown id. The default `limit` stays 50 (the admin console depends on it), the bot sends `limit=5`. On the card, per-ticket `delivery` comes from `delivery_jobs`, `payment` is the latest `payment_intents` row (null when the order has none), `unpaid_reason` is a function of the order status and that intent (`payment_failed`, `payment_abandoned`, `awaiting_payment`, `hold_expired`, `cancelled`, `manual_review`; empty when paid) and `barcode` is the stored credential with the `orderexport` legacy fallback. Tests: `horders/search_test.go`, `httpserver/orders_event_center_integration_test.go` (its barcode expectation goes through `ean13.PlatformCode`, never a hard-coded check digit). An exact `orders.system_id` hit ($10) is ORDERED FIRST in `SearchOrdersByOrg` (a 10-digit number is also a phone tail, and a newer order whose phone ends in it would otherwise lead the list; `TestEventCenterOrders_ExactOrderNumberListedBeforePhoneSuffix`), and the phone-identity lookup compares `value_normalized IN ('+'||digits, digits)` so it uses the (kind, value_normalized) unique index instead of regexp-scanning every organization's phone identities. The SQL lives twice (`queries/orders.sql` and the hand-kept constants in `gen/orders_search.sql.go`): edit both.
- **"Resend an order's tickets" (EC-13, `htickets/order_resend.go`) requeues EVERY active ticket and relies on the order-letter claim to make ONE e-mail; a one-time address lives on the delivery job, never on the order.** `POST /v1/organizations/{org_id}/orders/{order_id}/resend-tickets` (`ticket.update`, the path param is `order_id`, not `id`) calls `RequeueDeliveryJob(ticket, address)` for each ticket with `status='active'` (a refunded ticket is `cancelled`, so it is skipped) and enqueues one `ticket.deliver` worker job per ticket, all in ONE transaction with the `tickets_resent` row of `order_events` and the audit event (`v1.order.tickets_resend`, metadata only `tickets` and `different_address` — never an address, in either place). `ClaimPendingDeliveryJobsForOrder` folds jobs of the same order AND the same `recipient_email` into one letter, which is why every ticket must be requeued to the SAME address (the order's `buyer_email`, else the first active holder's). A typed address gets `delivery.Payload.RecipientExpiresAt` (now+24h): the handler (step 4b) skips a job that starts after it and marks it `skipped`, so a worker outage never mails a stale address; the delivery job keeps the typed address afterwards, so a later resend to "the same address" must read the ORDER, not the job. The seller-site decision is `sessionchange.ChannelHasSite` alone (an active `bil24_wp` subscriber on the channel, the same test as the session-change route) -> 409 `order.seller_site_order`, nothing queued; since spec 63 R-5 (decision R-8) `orders.source='bil24_gateway'` no longer refuses by itself, so a former site order is resent once its site is switched off. A paid order means status `paid` or `partially_refunded`. Branding is copied into the payload by `applyOrgBranding` (the older admin per-ticket resend sends none, so its letter falls back to platform defaults). Bot: the dialog is `bot_dialogs` kind `resend` and its presses are `or:r:<what>` — inside the Orders prefix so they do NOT end the orders dialog, while `handleCallback` deletes the resend dialog on every other press (an address typed after leaving would otherwise be taken for the dialog's). The button is added to the card by `withResendButton` only in a private chat. Tests: `htickets/order_resend_test.go`, `httpserver/orders_resend_integration_test.go`, `delivery/order_resend_integration_test.go`, `eventbot/resend_test.go`, `httpserver/bot_e2e_resend_integration_test.go`.
- **The order card has one line per letter the buyer got, and every letter goes through ONE renderer (`eventbot/order_letters.go`, owner decision 2026-10-13).** `ticketLetterStatus` folds `OrderDetail.delivery` (pending/processing = queued; skipped, disabled and `none` count for nothing), `refundLetterStatus` reads `OrderDetail.refund_letter`, and `letterLine` renders `bot.ord.letter_<tickets|refund>_<state>` with the time of the latest step in the venue's zone and the address (private chat only). States: none, off (refund, no letter asked), queued, partial_queued, sent, delivered, opened, partial (some sent, the rest failed), failed. The server feeds only queued/sent/failed today; when the e-mail provider's delivery events arrive, only the fold needs to learn `delivered`/`opened` (`letterRank`), the texts exist. A failed or partly failed ticket letter renames the card's resend button (`or:r:s:<order>`, the EC-13 route) to `bot.ord.letter_retry_btn`, and the orders list marks the row with `⚠️📧` from `OrderListItem.delivery_state` (`horders.listDeliveryStates`, one `ListOrdersDeliveryCounts` query per page; the legend explains it). Server side (`horders/letters.go`, `gen/order_letters.sql.go`): `delivery[].recipient_email` per ticket, `refund_letter` (`off`/`queued`/`partial`/`sent`/`failed` over the order's batch refunds that are not failed or rejected; a refund without a batch never mails and is not counted). The sale notification of the sales bot cannot show a failed letter: it is sent before the letter is. Tests: `eventbot/order_letters_test.go`, `horders/letters_test.go`, `httpserver/bot_e2e_order_letters_integration_test.go`.
- **Invitations from the bot (EC-12, migration 0136) are NOT orders, and one guest is one issuance.** The admin complimentary flow (`htickets/complimentary.go`, `POST .../complimentary`) writes `complimentary_issuances` + `tickets.complimentary_issuance_id`, never an `orders` row (`source=complimentary` orders exist only on the Bil24 gateway's `complimentary` flag), so a bot invitation has NO order number: the result shows the ticket number (`tickets.system_ticket_id`) and the list is keyed by issuance. The bot (`eventbot/invite.go`, `invite_list.go`, dialog kind `invite`, keys `bot.inv.*`, presses `iv:*`) issues ONE call per guest with `qty 1` and the batch id `tg-<operation>-<index>`, so each guest can be annulled alone and a retry, a double press or a bot restart replays the guests already issued (the API answers the first result with `idempotent_replay` and sends no second letter); a fresh operation id is minted whenever the confirmation screen is rebuilt, never reuse one for different guests. The number of guests must EQUAL the quantity (guests may come in several messages, a message with ONE bad line is refused whole, an e-mail may appear once per operation), at most 50 tickets per operation (the API refuses more with 400 `complimentary.qty_too_large`, a recipient that is not an address with `complimentary.invalid_recipient`, more guests than tickets with `complimentary.too_many_recipients`). A seated date is refused in the bot (no seat on the ticket would leave the seat on sale), only general-admission categories are offered. The guest's NAME lives in `tickets.holder_name` (request field `recipient_names`, aligned with `recipients`) and wins over the order's buyer name in `GetTicketPresentationByID`, so the PDF and the letter print it. `GET .../complimentary` is now a PAGE (`limit` 1-100, `offset`, `state` valid/revoked/used, `session_id`; answers `issuances` with event, date, category, tickets and a derived `state`, plus `total` and `has_more`); "used" is a ticket with `used_at` or a scanned barcode, and `HasScannedTicketsForIssuance` uses the same definition, so the list never calls "used" a ticket the revoke would annul. The revoke route is flat (`POST /v1/complimentary/{id}/revoke`): the shim loads the issuance and answers a non-member 403 (not 404), and its manual-review refusal is now the standard error envelope (`error.code`), it used to be a bare string the bot could not read. Annulling in the bot needs the typed word (`bot.inv.revoke_word`, ANNUL / АННУЛИРОВАТЬ / ANULAR, English accepted everywhere) and the screen says Arena does not tell the guest. Guests' e-mails are shown and typed only in the private chat (every entry checks `chatID == from.ID`) and are never logged. Tests: `invite_test.go` (parser, texts), `httpserver/bot_e2e_invite_integration_test.go` (the seed needs REAL places: `session_seats` of kind `ga_unit` stamped with the tier and an `inventory_ledger` row, a category without them answers 409 `tier.sold_out`).
- **A bot invitation can be revoked and resent, and "takes part in nothing else" is code, not a feeling (EC-16, migration 0137, 2026-10-10).** `DELETE /v1/organizations/{org_id}/bot-invitations/{id}` (`membership.revoke`) sets `bot_invitations.revoked_at` (the row stays, `AcceptBotInvitation` skips it) and `POST .../{id}/resend` (`membership.grant`) mints a NEW code, a fresh 7 days and a new `bot.invitation_email` job in one transaction, at most one per 10 minutes per invitation (`last_sent_at`, 429 `bot.invitation_resend_too_soon` + `Retry-After`; a fresh invitation counts as just sent). Both are owner-only (the manager role holds neither permission), audited (`v1.bot.invitation.revoke/resend`), and another organization's row is the route's own 404 `bot.invitation_not_found`. **The membership the invitation inserted is removed ONLY when all of these hold** (`hbot.removeUnusedMembership`, in this order, the first failing one is the `kept_reason`): not accepted (`accepted`), the invitation or an earlier one of the same person created it (`bot_invitations.membership_created`, `member_before`: a person who was already a member is never removed - a second invitation to someone the first one brought in records created=false, so the check asks about EVERY invitation of the pair), no other live invitation (accepted, or unexpired and not revoked) holds them (`other_invitation`), they have not started working through the bot - no active `bot_telegram_links` row with this `current_org_id` and no `bot_drafts` row of this org (`in_use`), the membership still has the role the invitation gave it (`role_changed`: the owner changed it on purpose), and an owner is not the last `org_admin` (`last_owner`). An accepted invitation only has its row voided; the person stays and the remove-member flow takes them out. The user account is never deleted. `GET .../bot-team` carries `invitation_state` (`accepted`/`waiting`/`expired`), `invitation_id`, `invitation_expires_at` and `resend_available_at` (only while the ten-minute window is open) - additive, `invitation_pending` is unchanged. Migration 0137 backfills `membership_created` where `memberships.joined_at = bot_invitations.created_at`. Bot: the owner's Team screen (`eventbot/team_invitations.go`) shows "Resend e-mail" and "Revoke invitation" per waiting/expired person (`team:rs:<user>`, `team:ri:<user>[:yes]`, looked up afresh on every press so a stale button ends in a note); the revoke confirmation is a stateless second button, not a `bot_dialogs` row. **The manager (`organizer`) sees the Team screen READ-ONLY (U-8, owner decision V-11, 2026-10-16, no server change: `membership.read` was always his):** the main menu carries the Team row for him (always `team`, never the "+ Team member" shortcut), `showTeam` lists members with their roles and invitation states and a `bot.team.readonly_hint` footer, and the buttons come from the pure `teamMemberControls` / `teamFooterControls` (`readOnly` = `isTeamReader`), so he gets none but the way back; EVERY `team:*` press with data from him (an old button, a forged payload) is refused in `teamCallback` with `bot.team.readonly` before any handler runs and changes nothing, an agent still gets `bot.team_owner_only` and no menu row. A new Team action must be added to `teamMemberControls` / `teamFooterControls`, never as a hand-built button. Tests: `httpserver/bot_invitation_manage_integration_test.go`, `bot_e2e_team_invitations_integration_test.go`, `bot_e2e_team_readonly_integration_test.go` (owner, manager, agent), `eventbot/team_readonly_test.go`.

- **MACS posts its door scans back through `POST /v1/macs/scan-events` (task M1, migration 0154, `httpserver/hmacsscan`, spec 17 "Scans from MACS").** No JWT and no `{org_id}`: `X-MACS-Subscriber-Id` names a `webhook_subscribers` row of kind `macs` (`gen.GetMACSSubscriberByID`) and `X-MACS-Signature: sha256=<hex HMAC-SHA256 of the raw body>` is checked against ITS `signing_secret`, the secret arena signs its own MACS webhooks with; unknown, inactive, secret-less and wrong-signature all answer the same 401 `macs.invalid_signature`. The subscriber IS the organization: tickets are resolved (`ResolveMACSScanTicketBySystemID` / `ResolveMACSScanTicketByBarcode`, both filtered on the subscriber's org and `FOR UPDATE`; a barcode falls back to the legacy `ean13.PlatformCode` decode) only inside it, so a foreign ticket is rejected per scan as `scan.ticket_not_found` and never read or locked. Idempotency is `(subscriber_id, external_scan_id)` (UNIQUE, NULL for arena-scanner rows); the old `(credential_code, scanned_at)` index still catches the same physical scan under another id, and both answer `duplicate` with nothing written. Each scan is ONE transaction: the `scan_events` row (`source='macs'`, `scanner_label`, `external_scan_id`, `subscriber_id`; `rejected`/`duplicate` stored as `denied`), `MarkTicketUsedAtIfUnset` for the first admission of an ACTIVE ticket (an admission of a cancelled ticket is recorded but never stamps `used_at`; no `first_admitted_at` column, run decision R-6), the `v1.ticket.scanned` outbox row through `PGEventsWriter.Append` on the tx, and for a first admission an audit row `v1.ticket.admitted` with `actor_type='macs_subscriber'` and the subscriber uuid as `actor_id`. Scans are processed in `scanned_at` order, so a late offline batch stamps its earliest admission; across batches `used_at` is never moved back. **A MACS admission blocks every refund of the ticket** (decision M1): MACS is the gate of the WordPress clients and `refunds/scanned.go` counts every admitted `scan_events` row of the ticket's own organization whatever its `source`, so nothing in the refund engine changed; a MACS `denied` scan blocks nothing. Arena's own scanner callback is untouched (it still emits `v1.ticket.scanned` in a separate short transaction and writes no `source`, which defaults to `arena_scanner`). The session and event summaries carry `entered.by_source` (`ListSessionSummaryAdmissions`, one query in `summary_core.go`). Limits: 500 scans, 1 MiB, 120 batches a minute per subscriber in process memory. Catalog rule: every outbox event type a PR starts emitting goes into spec 15 (`08_architecture/15_webhook_event_catalog.md`) in the same PR; M1 added the missing `v1.order.paid`, `v1.order.cancelled`, `v1.ticket.cancelled`, `v1.ticket.scanned`, `v1.refund.blocked_scanned`, `v1.refund.scan_exception_granted`. A fixture that creates MACS scans must delete `scan_events` by `subscriber_id` BEFORE the subscriber (plain FK, no cascade). Tests: `hmacsscan/handler_test.go`, `httpserver/macs_scan_events_integration_test.go`.
