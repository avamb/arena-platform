# Merchandise shop

The organizer's shop: checkout, stock, orders, letters, courier, Shopify import, paid module and delivery steps. Add a new trap here as a `- **Title.** ...` item and one title line for it under this topic in the AGENTS.md index.

- **`cmd/arena-shop-import` loads a Shopify export into one organization's shop and is idempotent only because of its keys (`docs/ops/shop_import.md`).** Product = slug (the lower-cased Shopify handle, Cyrillic kept), variant = SKU then option values then title, picture = SHA-256 of its bytes, customer = `customers.Resolve` identity, page = slug from the `--pages-map` file. Settings are written ONLY when the organization has no `shop_settings` row, and `CreateProduct` makes a default row, so the settings step runs before the first product and an organizer who created a product by hand first gets none. A re-run never overwrites the stock of an existing variant (the shop's own number is the truth, `--sync-stock` opts in), keeps stored variants and pictures the CSV does not list, and leaves a product alone with `--only-new`. Money goes from major to minor once, on the decimal string (`ParseMinor`, a value with more decimals than the currency is refused, never rounded). Descriptions and pages pass `CleanHTML` (Shopify cleanup, `h1` -> `h2`) and THEN `shop.SanitizeBody` with the shop profiles, the very function the API write path uses: a text it refuses fails that product or page in the report, and the pictures and tables it removes are counted (a description loses pictures and tables, a page keeps them, and every kept `<img>` still hosted by Shopify is warned about). New products are `kind='physical'`, `Option1..3 Name` become `option1_name..option3_name` (Shopify's `Title`/`Default Title` placeholder is not an option), and the settings row leaves `enabled=false` and `max_line_qty=24` to the shop (only a superadmin opens the shop). ALL customers are migrated by default: `customers_export.csv` next to `--products` is picked up without a flag (`--skip-customers` opts out). E-mail marketing `yes` becomes a `customer_consents` row (kind `marketing`, `given_at` = import time because the export has no timestamp, source `import:shopify`), `no` records nothing, and SMS/WhatsApp `yes` land in `customer_attributes` (`marketing_consent_sms|whatsapp`) because `customer_consents` has no channel and a `marketing` row would read as e-mail consent. Orders are only parsed and summed, `shop_orders` with source `shopify` is not written yet. The tool IS in the arena image (`/app/arena-shop-import`, Dockerfile) because the stands keep media in a docker volume and the api image has no shell: run it there as a one-off `docker run --entrypoint /app/arena-shop-import` on the stand's compose network with the api container's own env (`MEDIA_LOCAL_ROOT` and `MEDIA_SIGNING_SECRET` must EQUAL the api's) and the media volume mounted, recipe in `docs/ops/shop_import.md`. An image still `<img>`-linked to cdn.shopify.com or the old domain's `/cdn/` is reported as "still points at the Shopify CDN" and must be re-hosted before the domain switch. An integration test that drives `run()` must register `pool.Close` with `t.Cleanup` BEFORE its row cleanup (a `defer pool.Close()` runs first and the cleanup then fails on a closed pool, leaking an organization into the scratch database).
- **The merchandise shop (migration 0172, `internal/platform/shop`, `httpserver/hshop`, spec `08_architecture/47`) pays through the TICKET payment rails, so keep both in step.** A shop order owns a `payment_intents` row with `checkout_session_id` NULL and `shop_orders.payment_intent_id` pointing back; the hosted page comes from the same `hfeed.PaymentStarter` with `HostedCheckoutRequest.ShopOrderID` set, and `processPaymentWebhook` hands an intent without a checkout session to the shop on the WEBHOOK transaction (`hcheckout.ShopPayments`, wired only when the server has a raw pool): succeeded runs `FulfillPaidOrderTx`, failed runs `MarkPaymentFailedTx`. The provider is `shop_settings.sales_channel_id`, else the first live channel (oldest first) that passes `CheckPaymentConfigured`. Stock: `shop_variants.stock` is the shelf; the hold is DERIVED (`gen.ShopHeldSQL`), never a counter. **Every stock decision locks the variant rows in id order in ONE statement and reads the held quantity in a SECOND one** (`LockShopVariantsForCheckout`; `LockShopOrderVariants` then `ShopOrderShortages`, which leaves the order's own hold out; `LockShopProductVariants` locks and returns stock only, no held quantity): under READ COMMITTED a held subquery inside the locking statement keeps its old snapshot and every queued buyer got the last unit (`TestShop_LastUnitRace`). **Every payment, on time or late, re-checks free stock under the variant locks** (whether the hold was live is decided in SQL on the transaction clock, the clock `ShopHeldSQL` uses, never on Go's `time.Now()`): the order is paid only if its goods are free after every OTHER live hold, otherwise it is parked in `manual_review` (paid_at set, nothing taken, `v1.shop.order.manual_review`, ops watchdog alert); shipping a parked order takes the goods then, and only if they are free (409 `shop.out_of_stock`). Every hold release (cancel, sweep, abandon, failed payment) locks the order's variants in id order BEFORE its journal, whose foreign key would otherwise take KEY SHARE locks in hash order and deadlock a two-variant checkout; PlaceOrder runs under `txretry`. Cancel closes the hosted page through the optional `payments.HostedCheckoutExpirer` (Stripe), and the expiry sweep skips a `processing` payment. A refund is a plain `refunds` row on the order's payment intent (no order or ticket), written under `refunds.LockPayment` BEFORE the order's row lock; only SUCCEEDED refunds count, and they reach the order through the refund engine's `Options.ProjectPayment` hook (`shop.Service.ProjectPaymentTx`, wired in arena-api AND arena-worker), never on read. The refund route needs `shop.manage` + `refund.create` + `refund.approve` and, like cancel, sits in `stepUpMoneyRoutes`. The storefront opens only with `shop_settings.enabled` (platform superadmin, like `shop_domain`). Product kinds (section 1b): a `digital` product sells a `shop_digital` media file (never a `shop_product` picture, both ways), never tracks stock, and a cart without physical lines takes no address and no shipping (`delivery_kind` none); the files are served only by `GET .../checkout/{order_token}/downloads` of a paid order. body_html is sanitized to the rich-text subset on write. The public routes put the static segments `by-host`, `checkout`, `pages` beside `{org_slug}`, so an organization whose slug is one of those words has no storefront. Integration tests: `httpserver/shop_integration_test.go`, `shop_review_integration_test.go` (fresh scratch database; checkout phones are randomized because customer identities are globally unique).
- **Shop notifications (lane L5, migration 0173).** `sales_notification_subscriptions.kinds text[]` (`tickets`, `shop`, CHECK; old rows `{tickets}`) says what a chat hears; one chat is still one row (the unique index is on org + chat), so the logistics group is a row with `{shop}` created by SQL (`docs/ops/shop_notifications_ru.md`, no admin route). `salesnotify.Route` sends ticket triggers only to chats that hear `tickets` and the shop's `v1.shop.order.paid` / `.refunded` (claimed as `shop_paid:<order>` / `shop_refund:<order>:<refunded so far>`) only to `shop`; `AnnounceToOrg` (contact form) skips shop-only chats. The message field order is `shop.CourierFields` - the ONE list the courier text and the Telegram message share, change it there. The buyer's e-mails are the `shop.order_email` worker job (`kind` received/shipped), queued by `shop.enqueueOrderEmailTx` behind a SAVEPOINT inside `markPaidTx` / `Ship` (a paid order is never lost over a letter) and rendered by `delivery.NewShopEmailHandler` (registered in `cmd/arena-worker/shop_sweep.go`) from `templates` kinds `shop_order_received` / `shop_order_shipped` (7 locales, `Data.Shop`). It remembers the send in `shop_orders.metadata.email_<kind>_sent_at`, prints only `shop_settings.contact_email` (never the organization's), links the storefront result page (`<shop_domain or SHOP_PUBLIC_BASE_URL/<slug>>/checkout/result?checkout_token=<token>`), lists digital lines (`shop_order_items.product_kind`) as links to that page (never a signed URL) and leaves the address and shipping fee out when `delivery_kind = none`; a digital-only order gets no `shipped` letter and a `manual_review` order no letter at all (`v1.shop.order.manual_review` reaches only the shop Telegram chats, key `shop_review:<order>`, the operator alert is the ops watchdog's). A test fixture that pays a shop order must sweep `worker_jobs` of type `shop.order_email` (see `newShopFixture` cleanup).
- **Shopify orders are imported as order HISTORY, never as sales (`arena-shop-import --orders`, 2026-11-07).** `orders_import.go` writes `shop_orders` with `source='shopify'`, key `external_ref` = the Shopify name (`#1872`), original created/paid/shipped/cancelled times, no payment intent, no stock move, no letter, no delivery step; a re-run adds new orders and refreshes status, refunded amount and the four times of known ones. Shopify's `Subtotal` is ALREADY after the discount (total = Subtotal + Shipping; lines - discount + shipping = total on all 872 orders of the Einat export), so the import stores subtotal = sum of the lines and an order whose numbers do not add up FAILS instead of being rounded to fit. The file has no SKU: lines are matched to variants by `Product - Variant` (or `Product`), unmatched lines (removed products) stay as text. Four places treat `source='shopify'` as a record and a new shop action that touches a parcel, a buyer or money MUST do the same: `SetFulfillmentStep`, `Ship`, `ResendEmail` and `Refund` answer 409 `shop.order_historic` (`shop.ErrOrderHistoric`), and the `to_ship` tab and its count (`shopOrderViewCondition`, `countShopOrders` in `gen/shop_orders.sql.go`) leave such orders out, as a second line of defence: owner decision 2026-11-07 is that the 224 paid orders Shopify never marked fulfilled are STORED AS SHIPPED at their payment time (`metadata.shipped_assumed`, refunded ones are left alone). The list search also finds an imported order by its old number (`#1872` or `1872`). The event center card hides the action buttons for it (`HistoricOrderNote`, key `shop.order.historic`). Customers are tied through `customers.Resolve` in a savepoint; marketing consent comes only from the customers file. Take the orders export on the day of the switch, after products and customers. Tests: `orders_import_test.go`, `orders_import_integration_test.go` (needs DATABASE_URL; the cleanup in `integration_test.go` deletes `shop_orders` first).
- **A shop page can remember its old address: `shop_pages.legacy_slug` (migration 0174).** `GET /v1/public/shop/{org_slug}/pages/{slug}` resolves slug first, then legacy_slug (lower-cased, NFC) and always answers the canonical `slug`; the list `GET /v1/public/shop/pages/{org_slug}` carries `legacy_slug` too and the storefront (`apps/shop-page` `getPage`) matches either. `arena-shop-import` fills it from a `pages__<handle>.html` file name (or the mapping's `legacy_slug`) when it differs from the slug, and a re-run fills it for pages imported earlier. `shop.SanitizePageBody` keeps a root-relative `<a href="/pages/contact">` (one leading slash, no `//`): dropping it left the partners page button dead (H-01), and the storefront's `fixContentLinks` puts its own base in front. The importer also drops the `Default Title` option VALUE of a single-variant product (E-07), not only its option name.
- **Shopify-parity work on the shop event center (2026-10-29, A-02/A-07/A-08/A-10/A-11).** The product card has ONE Save (`ProductForm.saveAll`: PATCH details, PUT variants, then the picture alts, stopping at the first refusal and naming what was already stored), guarded by `UnsavedChangesGuard` (TanStack `useBlocker` with STABLE callbacks, or it re-registers on every render; a move the form makes itself sets `allowLeave.current` first). The products list edits stock in place through `ShopStockCell`: saves of one product are queued per product id and rebuild the whole variants body from the NEWEST cached copy, with `expected_stock` for every variant (`stockUpdateRequest`). The order list's tabs are the API's `view` (`to_ship|unpaid|shipped|refunds`, ANDed with `status`) and `GET .../shop/orders/counts`; to_ship = paid or partially_refunded, delivery_kind <> none, shipped_at NULL. `shop_orders.staff_note*` (migration 0175) is staff only: it is in `orderJSON`, never in the public checkout status or the buyer letters, and its text is never copied into the audit row. `POST .../orders/{id}/resend-email` re-queues `shop.order_email` with `resend:true` (the worker then ignores the `email_<kind>_sent_at` marker), one request per order per minute from an in-memory limiter on the Handler (a refused request is released, a 429 is not). Traps met: two siblings with the same React `key` (card actions and note) render the section twice; a vitest `beforeEach(() => mock.mockReset())` returns the mock, which vitest calls as teardown, so use braces; the python/heredoc tool breaks on backticks in TS, write such scripts with the Write tool.
- **Shop courier address (2026-10-29).** A shipped shop order needs a postal code (422 `shop.postal_required` / `shop.invalid_postal`: Israel exactly 7 digits, elsewhere 3-12 characters, checked in `shop.requireShipping`, so a digital-only cart is unaffected). `shop.CourierFields` prints name, phone, street, entrance/floor, city, postal, country (street before city) and builds the Google Maps / Waze links from street + city + postal + country WITHOUT line 2. The shop Telegram messages (`salesnotify/shop.go`) speak the organization's `default_locale` through `salesnotify.shop.*` keys (en/ru/cs/he/es, `shop_text.go`, English fallback), print no courier form for `delivery_kind none` and carry NO events-bot footer. A new shop message text goes into all five catalogs: `TestShopTexts_EveryLocaleHasEveryKey` reads the files, because a missing key falls back to English silently.
- **The shop admin's saves are optimistic, and each one names the version it was written against (audit SA-04/12/13/18, 2026-10-30).** PUT .../shop/products/{id}/variants: a row of an existing variant with NO `expected_stock` keeps the stored stock whatever `stock` it carries (`VariantInput.KeepStock`, set by `hshop.toVariantInputs`; the import tool sets it too for every stored variant unless `--sync-stock`, so a sale during an import is never written back over), the event center sends `stock` + `expected_stock` only for a row whose stock the person edited, and `expected_variant_ids` (the ids it loaded) makes the server answer 409 `shop.variants_changed` instead of silently deleting a variant a colleague added (`ReplaceVariantsChecked`). PUT .../shop/settings takes `expected_updated_at` (the `updated_at` string the GET printed, compared at microsecond precision, 409 `shop.settings_changed`). The currency of a shop with a live product or any order is locked (409 `shop.currency_locked`, `ShopHasProductsOrOrders`), and a currency the sales channel's payment module cannot charge is 422 `shop.currency_unsupported`: modules state their currencies in `payments.Capabilities.Currencies` (AllPay: ILS, USD, EUR), the shop reads them through `Service.WithCurrencies` wired in `mount_shop.go`. Both checks run only when the currency or the channel changes, so an unrelated settings edit of an old shop is never blocked. The orders list is read with POST .../shop/orders/search (filters in the body, `from`/`to` RFC 3339), the web sends the days of the SHOP's time zone (`dayStartIso`), and a refund carries one `Idempotency-Key` per operation (kept by the web while the amount and reason stay the same and the answer is lost).
- **Shop orders after the 2026-10-30 audit (SA-01..SA-37, migration 0179).** (1) `POST .../shop/orders/{id}/refund` REQUIRES an `Idempotency-Key` (400 `shop.idempotency_key_required`). The key is stored on the refund it created (`refunds.idempotency_key`, unique per organization, plus `refunds.shop_order_id`), not in `refund_batches` (that table is ticket-only: it references `orders`). `shop.Service.Refund` looks the key up under the payment lock BEFORE any status or budget check, so a repeat answers the first refund (`replayed: true`, `Drive` is called again and is a no-op for an answered refund) even after the order was fully refunded; the same key with another order or amount is 409 `shop.idempotency_key_reused`. The handler runs the work on a context detached from the request with the ticket routes' budget (`refundWorkCtx` in `hshop/org_orders.go`, 2 min plus a write deadline), so a dropped connection never leaves a half-driven refund. Test fixtures: `shopFixture.do` adds a fresh key to every POST ending in `/refund`, `doKeyed` names it. (2) A payment parked in `manual_review` (amount mismatch, an untrusted status) parks its shop order too: `shop.MarkPaymentReviewTx` (called from `hcheckout.applyShopPayment`) moves a pending order to `manual_review` with `metadata.review_reason = payment_manual_review`, releases the hold, writes `v1.shop.order.manual_review` and queues no letter; a later `failed` payment expires such an order (`paymentReviewParked`). It also stamps `paid_at` (the status helper does that for every manual_review), so `paid_at` does not prove money arrived for those orders. (3) Shipping a `partially_refunded` order that was not yet shipped re-runs `syncRefundsTx`, so the refund status survives; `delivery_kind = none` is 409 `shop.order_not_shippable`. (4) `shop.sweep` queues its next run BEFORE it works and `PGScheduler.ScheduleNext` inserts only when no pending run exists (a retried run must not start a second chain). (5) Shop letters go through `delivery.sendRecorded` with `emailstatus.NewLetter.ShopOrderID` (`email_letters.shop_order_id`, kinds `shop_received/shop_shipped/shop_refunded`, `order_id` stays NULL, so the ticket order card does not list them). (6) `POST .../shop/orders/search` takes the list's filters in a JSON body, so a buyer's name or e-mail stays out of proxy and Cloudflare logs; `from` is included, `to` is excluded, both RFC 3339 with a zone or `YYYY-MM-DD` (UTC midnight). `next_offset` is present only when another page exists (`ListOrdersPage` reads one row more). (7) GDPR erase of a user (`ForgetUserShopOrders`, run before `AnonymizeUser`) blanks buyer and delivery details of the user's finished shop orders (found by e-mail, statuses shipped/cancelled/expired/refunded or `shipped_at` set); an order still to be handled keeps its address and is not retried later; the letters in `email_letters` are evidence and stay. (8) `shop.FormatMinor` and the Telegram money format follow the currency's exponent (`shop.CurrencyExponent`: JPY 0, KWD 3); the logistics message cuts the goods list to 3800 characters with a "N more lines" line.
- **The shop checkout is guarded three ways, all in the database or at the edge, none in process memory (audit SA-05/SA-34, migration 0177).** (1) `SHOP_TURNSTILE_SECRET` (+ `SHOP_TURNSTILE_SITE_KEY`) switch on a Turnstile test: the catalog `settings.captcha_site_key` appears only while the secret is set, `POST .../checkout` then needs `captcha_token` (422 `shop.captcha_required` / `shop.captcha_failed`, 503 `shop.captcha_unavailable` when Cloudflare cannot be asked) and the test runs BEFORE any stock is held; it reuses `honboarding.TurnstileVerifier` with no Action/Hostnames restriction (storefronts live on the organizers' own domains). (2) One client key — an IPv4 address or an IPv6 /64 (`httputil.ClientKey`) — may hold `shop.MaxPendingPerClient` (3) live unpaid orders per shop, counted over `shop_orders.buyer_ip_hash` (salted sha256, never the address) under an advisory lock taken AFTER the e-mail lock; the checkout budget keys on the same `ClientKey`. An integration test that places many orders must NOT share one address: `shopFixture.do` gives every checkout POST a random `RemoteAddr` unless `f.remote` is set. (3) A digital line stores `shop_order_items.media_id` (the file bought, not the product's current one) and `download_count`; the downloads route signs every link first, then `ConsumeDownload` counts each atomically, 20 links per line and 30 days from `paid_at`, then 410 `shop.download_expired`. The public catalog never publishes `sku`, and `available` is `min(stock - held, max_line_qty)`.
- **A shop order parked in `manual_review` has a cause in `shop_orders.review_reason` (migration 0180), and the two causes are different orders of business** (second audit pass SB-01, SB-02, SB-04). `late_payment_no_stock`: the money was taken, the hold had ended and the goods are gone (`paid_at` set, buyer sees `paid`, Telegram says "Paid"). `payment_unconfirmed`: the provider's report is not trusted (amount mismatch, SA-09), the money may not have arrived (`paid_at` stays EMPTY, `PublicStatus` is `pending` with no payment page and no `expires_at`, the status answer carries `review_reason` and a localized `review_message`, Telegram says "not confirmed" and never "Paid"). Write the park only through `SetShopOrderReview(reason, moneyTaken)`: `SetShopOrderStatus` stamps `paid_at` for `paid` only and clears `review_reason` when the order leaves `manual_review`. An unconfirmed order follows its PAYMENT: when the payment intent becomes `succeeded` (provider webhook or the operator's `POST /v1/payment-intents/{id}/transition`, which now runs `applyShopPayment` on the same transaction for an intent without a checkout session) `FulfillPaidOrderTx` pays it like any other, or parks it again as `late_payment_no_stock` when the goods are gone; `failed` ends it `expired`. `Ship` of an unconfirmed order still answers 409 `shop.payment_unconfirmed` until the intent succeeded. A `late_payment_no_stock` order is settled by `POST .../shop/orders/{id}/resolve {action: fulfil | refund_and_cancel}` (`shop.manage` + `refund.create` + `refund.approve`, step-up, `Idempotency-Key` required; `fulfil` re-checks the stock and calls `markPaidTx`, a repeat of the same key answers `replayed`; `refund_and_cancel` is a full `Refund` with the same key and the order ends `refunded` when the provider confirms, it is NOT set to `cancelled`). An unconfirmed order answers resolve 409 `shop.order_not_resolvable`. The review announcement is claimed per `shop_review:<order>:<reason>`, so the second parking of one order is announced again.
- **A digital download is counted when the FILE is served, not when links are listed (SB-05).** `GET /v1/public/shop/checkout/{token}/downloads` signs nothing and counts nothing: each `url` it returns is the absolute address of `GET .../downloads/{item_id}` (built from `Options.APIBaseURL` = `apiPublicURL()`, falling back to the request host), `expires_at` is the end of the 30-day window. The item route (`HandlePublicCheckoutDownload`) checks the order (`DownloadOf`), signs the media URL FIRST, then `ConsumeDownload` (one atomic `download_count < 20` update) and answers 302 with `Cache-Control: no-store`; a failed signing costs the buyer nothing. The shop-page needs no change: it renders the `url` as a link.
- **The shop letters' unsubscribe note speaks of orders, not tickets (SB-10).** `shop_order_{received,shipped,refunded}.<locale>.tmpl` end with "the letters about your orders will no longer reach you" in all seven languages; the ticket letters keep the ticket wording. - **A shop order parked in `manual_review` because its PAYMENT waits for a human (`metadata.review_reason = payment_manual_review`, SA-09) is shipped only after its payment intent succeeded** (second audit pass SB-01): `Ship` answers 409 `shop.payment_unconfirmed` otherwise; a stock-short parking (`stock_short`, money taken) ships as before. - **The shop's courier text has ONE builder, `salesnotify.FormatShopCourierText`, and it shares `writeCourierForm` with the Telegram announcement (C-05/E-06/E-11, 2026-10-30).** `GET .../shop/orders/{id}/courier-text` (hshop `HandleCourierText`) loads `shop.Service.CourierSourceFor` (order, items, `organizations.default_locale`, `shop_settings.country_iso2`) and renders it: order number first, name, phone, street, address line 2, city, postal code, the country ONLY when it differs from the shop's (named in the organization's language), map links, goods as `name × qty`, total in the locale's money format, buyer's note. - **The shop is a paid module since migration 0198 (spec `08_architecture/61_shop_module_and_bot_ru.md`).** `org_module_periods` (module `shop`) says from which UTC day to which day an organization has it; only a platform superadmin writes it (`/v1/admin/organizations/{org_id}/modules/shop`, `/v1/admin/org-modules/{id}/end|reprice`, audited with the reason), and like white label a start or reprice is refused before today and an end before yesterday, because charged months are never rewritten. `orgmodules.ShopMode` is `full` (a period covers today), `orders_only` (no period, but the org has a paid or an open shop order: list, card, ship, refund stay reachable FOREVER, owner decision 2026-11-05) or none; every `/v1/organizations/{org_id}/shop/*` route goes through `shopFull` or `shopOrders` in `mount_shop.go` and answers 404 `shop.module_not_enabled` otherwise, also to a superadmin. `/v1/me` and `GET /v1/organizations` carry `modules` and `shop_mode` from ONE batched `orgmodules.States` query. - **Shop delivery steps and the sales bot receiver (spec 61 sections 7a, 7b, migration 0199).** Every delivery step of a shop order goes through `shop.SetFulfillmentStep` (row lock, history row in `shop_order_events`, outbox `v1.shop.order.fulfillment_changed`, the shipped and delivered letters at most once); never UPDATE `fulfillment_step` or `status='shipped'` directly. - **The Shopify order import never rewrites a KNOWN order that the file describes differently (F-SH-01, 2026-11-12).** The idempotency key is only (org, source, external_ref = the order name), so a new export that reuses `#1001` for another order used to count as "unchanged". `storeOrder` now compares the Shopify id, the total, the buyer's e-mail and the number of lines (`existingOrder.conflicts`); a difference is the outcome `conflict`: counted in the report ("N in conflict with the file"), one `problems` line names WHICH fields differ (never their values), the stored order is left as it is and the run does not fail. A status or date change of the SAME order is still a refresh ("updated"). Test: `TestShopImport_OrderHistory` (conflict step), `TestExistingOrder_ConflictsNamesWhatDiffers`.
- **The storefront (apps/shop-page) cannot answer 404 for a product or page handle that does not exist (F-SH-05, 2026-11-12).** nginx knows only the route SHAPES (`$shop_known_route`), not the catalog, so `/products/<anything>` is 200 with the SPA shell. The app marks the not-found page `<meta name="robots" content="noindex">` (`missing` in `renderRoute`, not for the "try again" page), which is the standard cure for a soft 404. A true 404 status would need the catalog at the edge: not done.
