# Web event center: screens

Per-screen rules of apps/event-center: Team, Organization data, session change, status, categories, wizard, poster, billing usage. Verbatim items of the former single AGENTS.md. Add a new trap here as a `- **Title.** ...` item and put one title line for it into the index in AGENTS.md.

- **The web "Resend tickets" action (4-1) reads the order card's `letters[]` first and falls back to `delivery[]`, and its twin test needs paid orders the base seed lacks.** `apps/event-center/src/lib/letters.ts` is the port of `eventbot/order_letters.go`: statuses come from the e-mail provider's events (`letters[]`), the older `delivery[]` fold only when no ticket letter is recorded, and a proxy open is delivery, never reading. The live harness runs NO worker, so a resend leaves the delivery job pending and the card says "in the queue"; the spec therefore accepts `sent` or `queued` before the first resend (an earlier role's resend changes the shared base). `cmd/arena-e2e-seed/resend_order_fixture.go` adds a channel and two paid one-ticket orders (fixed ids, `orders.source` must be one of `bil24_gateway|public_feed|checkout_api|complimentary`, the `bil24_gateway` one is the seller-site refusal) and puts the delivery job back to `sent` on every run. Two live runs on one machine (a sibling session) collide on the harness ports: set `ARENA_LIVE_API_PORT`, `ARENA_LIVE_READY_PORT` and `ARENA_LIVE_UI_PORT` to free values.

- **The web Team screen (4-5, `apps/event-center/src/screens/TeamScreen.tsx`) has no server-side "last owner" guard to lean on: `DELETE .../members/{user_id}` removes any `org_admin` row, the caller's own included.** Only the invitation REVOKE knows `last_owner`. The screen is therefore the guard: it never offers Remove on your own row (`canRemoveRow`, like the bot's `!self`), and since only a caller holding `membership.revoke` sees the buttons, the organization always keeps the owner who is looking at it. Resend and Revoke are offered only for a waiting or expired TELEGRAM invitation (`isRevokable`): a `web` invitation is written already accepted, so the API answers 409 `bot.invitation_channel_unsupported` to a resend. The generated `RevokeMembershipRequest.role` enum lacks `org_admin` although the server accepts it, so `removeMember` sends its own `{role: string}` body (the row's `membership_role`). `GET .../bot-team` lists only owners and managers: an agent is never in the list, and has no `membership.read` either. The 4-5 twin drives it all through `--team-op reset|age|expire|inspect` of `cmd/arena-e2e-seed` (`team_fixture.go`): it moves an invitation's `last_sent_at` back instead of waiting ten minutes, and the harness has no worker, so a letter is checked as a queued `worker_jobs` row, not as a delivered mail.

- **The web "Organization data" screen (`/o/$orgId/org-data`, task 4-7) sends ONLY what changed and never the operator's switches.** `buildOrgPatch` (`apps/event-center/src/lib/orgData.ts`, a port of `sellerinfo`) diffs the form against the last stored organization: an emptied optional field is `null`, an untouched one is left out, and the tax number and its type always travel as a pair (PATCH `/v1/organizations/{id}` refuses one without the other). A page's public contact goes through `PATCH .../seller-display` with `public_contact` only: the web shows `seller_hidden` (operator) and the legacy `show_seller` and writes neither. The screen is gated by `can("org.update")`, so the manager and the agent get an explanation and no call is sent. The live twin (`tests/smoke/live/org-data.spec.ts`) resets and reads the fixture through `arena-e2e-seed --org-data-op reset|inspect|hide` (`org_data_fixture.go`: the org starts with NO legal data and gets its own hosted channel `E2E Org Data Page`). The fixture org has two hosted channels (this one and the 4-2 cancel channel), so a spec must pick its card by `data-channel-name` and must not expect the whole-profile status to be "complete" while the other channel has no public e-mail.

- **The web Team screen (4-5, `apps/event-center/src/screens/TeamScreen.tsx`) was built when no server-side "last owner" guard existed (`DELETE .../members/{user_id}` removed any `org_admin` row, the caller's own included); since U-4 the API answers 409 `membership.last_owner` (see the U-4 entry below) and the screen is only a second line: it never offers Remove on your own row (`canRemoveRow`, like the bot's `!self`), and since only a caller holding `membership.revoke` sees the buttons, the organization always keeps the owner who is looking at it. Resend and Revoke are offered only for a waiting or expired TELEGRAM invitation (`isRevokable`): a `web` invitation is written already accepted, so the API answers 409 `bot.invitation_channel_unsupported` to a resend. The generated `RevokeMembershipRequest.role` enum lacked `org_admin` although the server accepts it (U-4 added it), so `removeMember` sends its own `{role: string}` body (the row's `membership_role`). `GET .../bot-team` lists only owners and managers: an agent is never in the list, and has no `membership.read` either. The 4-5 twin drives it all through `--team-op reset|age|expire|inspect` of `cmd/arena-e2e-seed` (`team_fixture.go`): it moves an invitation's `last_sent_at` back instead of waiting ten minutes, and the harness has no worker, so a letter is checked as a queued `worker_jobs` row, not as a delivered mail.

- **The web move/cancel of a session (task 5-2, `apps/event-center` `SessionChange`/`SessionMovePanel`/`SessionCancelPanel`, rules in `lib/sessionChange.ts`) is the web twin of the bot's Sessions dialog and writes ONLY through the dry run `GET .../sessions/{id}/change-impact` and ONE `PATCH .../events/{event_id}/sessions/{id}`.** A move needs one press, a cancellation (`status: "cancelled"`, never a delete) the typed SESSION word (`confirmWords.cancel_session`), and the cancel screen says before and in the dialog that letters go out but nothing is refunded. `contact_missing` shows the contact form inside the change (`PUT .../events/{event_id}/contact`, needs `event.update`) and re-runs the dry run; `site_route_unsupported` blocks with the server's honest text. The wall clock typed by the person is read in the VENUE's zone by `zonedToInstant` (a time lost to a clock change is refused on the screen, an hour that happens twice is its FIRST occurrence: it tries both offsets around the day and takes the earlier valid instant; a single-offset guess returned the second one). The message to buyers is counted in code points (limit 1000) like the API. Twin test: `tests/smoke/live/session-change.spec.ts` with `cmd/arena-e2e-seed/session_change_fixture.go` (own event with five sessions; `reset` DELETES and re-inserts them because a raw `UPDATE sessions SET start_at` is what the session-change guard forbids, and clears the organization's `contact_email`). The harness runs no worker, so a letter is checked as a queued `session.change_email` job. Playwright ports: arena-api also listens on its port + 1 (metrics), so never set `ARENA_LIVE_READY_PORT` to `ARENA_LIVE_API_PORT + 1`. A contact `<input type="email">` inside a form needs `noValidate`, or the browser's own bubble hides the screen's error. `--session-change-op reset` also clears the SHARED organization's `contact_email` / `contact_phone` (the dry run must say `contact_missing`), so it is safe only with Playwright `workers: 1` (the live config's setting) and would break a spec of another task that runs in parallel and relies on that contact. The panels never drop the buyers' message: when the dry run's answer is not in state at the moment of the press, the panel asks it again before the `PATCH`.

- **The web "Status" block of the event card (5-1, `EventStatusBlock`) takes its buttons from `lib/eventStatus.ts`, a copy of `ValidEventTransitions` that `eventStatus.test.ts` checks against `domain/catalog/event_state.go`; the API has no route that lists the allowed moves.** Publish acts at once, "Take off sale" and "Archive" are one `ConfirmPressDialog`, Delete is `delete-impact` through `DryRunConfirm` and then the `delete_event` typed word; a refused delete (`blocked`) offers the archive instead, never the word. An archive is final through the API, so the twin fixture (`event_status_fixture.go`, `--event-status-op reset`) puts its three events back with SQL on every run. Live-harness trap: do NOT export `JWT_SIGNING_SECRET=x` (the secret from the integration-test recipe) before `test:e2e:live`: it overrides the harness default and arena-api never becomes healthy, so the run dies after 240 s with only "Timed out waiting from config.webServer". A spec that records the writes of a page must skip `/v1/auth/*` (login and refresh are POSTs). Widget: `lib/consent.ts` (rules, `forceConsent` shows the box after an unannounced 422) + `lib/consentI18n.ts` (7 languages), the box lives in `BuyerForm.svelte`, the pay button waits for it, the tick is never stored. Tests: `hfeed/checkout_consent_test.go`, `hseller/consent_rule_test.go`, `httpserver/checkout_consent_integration_test.go`, widget `lib/consent.test.ts` and `tests/consent.e2e.ts`.

- **The web sales-end and doors editor (task 5-3, `SessionSaleTimes.tsx`, `lib/saleTimes.ts`) converts a clock time on the VENUE's wall clock into an RFC 3339 instant itself, and refuses to draw without the venue zone.** The session list item carries no zone; it comes from the summary's `venue_timezone` (`order.read`), so a person without it sees "no time zone on file" instead of an editor that would guess UTC. A time that falls in the hour skipped when the clocks go forward is refused (`wallToInstant` round-trips it), doors after the start are refused on the screen before any call and by the API as 400 `session.doors_after_start`; one PATCH names ONE time (`sales_end_at` or `doors_open_at`, null clears). The twin uses its own event and date (`cmd/arena-e2e-seed/sale_times_fixture.go`, `--sale-times-op reset|inspect`). Live-harness trap: a full `test:e2e:live` run once lost arena-api halfway ("exited early with code 4294967295", every later spec ECONNREFUSED) while another session shared the host — rerun before chasing it, and give each run its own `ARENA_LIVE_*` ports.

- **The web categories card (5-4, `apps/event-center` `CategoryCard`, rules in `lib/categories.ts`, twin `tests/smoke/live/categories.spec.ts`) is the bot's categories dialog on one page.** A write is one PATCH of one key (`is_open`, `capacity`, `sale_window_start|end`, null removes an edge) and a price goes where the bot sends it: the price window in force NOW when the schedule covers it (`GET` then `PUT price-schedule`, read afresh inside the press), else `price_amount`. A window edge is the VENUE's calendar day: the first day starts at its midnight, the last day is inclusive and stored as the midnight after (`windowEdgeInstant`, DST safe); the session list carries no time zone, so the zone comes from the session SUMMARY (`order.read`) and the window controls are hidden when it is missing. The card offers by `categoryCaps` (port of `categoryCapsFor`): a chain category keeps only its price, a seated one has no quantity, free/pwyw no price. The seed's `--categories-op reset|inspect` rebuilds the five categories and reads places and window prices. API codes the bot never mapped are in `API_ERROR_STEMS` (`tier.invalid_fixed_price`, `tier.invalid_capacity`, `tier.price_windows_overlap`...): the bot's `tier.invalid_price_amount` constant matches no code the server emits. **A shared Go build cache can corrupt on this host** (`could not import ... (can't find export data (bufio: buffer full))` on every package): a private `GOCACHE` (an absolute path outside the repo) builds it; the live harness inherits the variable.

- **The web event wizard (6-1a, `apps/event-center`) checks a draft with `?dry_run=true`, at most once a second (the stub date and category of 6-1a are gone since 6-1b, see the next entry).** `lib/wizard/validation.ts` `createScheduler` is the one caller pattern: it waits `quietMs` (700) after typing, starts at most one request per `minGapMs` (1000), keeps one in flight and drops an answer for an older payload (the check holds a transaction like an import). `lib/wizard/bundle.ts` `buildBundle` is the one place a draft becomes a bundle (6-1b compares it with the bot's `BuildBundle`). The check answers 500 for an age outside `events_age_rating_check`, so the age is an allowlist in the client (`AGE_OPTIONS`). A new venue is only DESCRIBED (venueName + zone + cityName + 2-letter countryName): nothing creates it before the save of 6-1c. The wizard is behind the build flag `VITE_FEATURE_WIZARD=1` (Dockerfile build arg, off by default). Trap found: `buildPath` filled only `{name}` placeholders of letters and underscores, so `{iso2}` went to the server as literal text (400 `geo.invalid_iso2`) - digits are allowed now (`routes.test.ts`). A Python `open(p)` without `encoding="utf-8"` on this Windows host reads UTF-8 files as cp1252 and can corrupt non-ASCII text on write-back: use the Edit tool.

- **The web wizard's dates and tickets (6-1b, `apps/event-center/src/lib/wizard`) make ONE bundle per date and are pinned to the bot by golden files.** `buildBundles(draft)` gives one `ImportEventBundleRequest` per date (the import takes one date per call, key `web:<org>:<draft>:<n>`); each date sells its own tickets or "the same as the date before" (`effectiveTickets`, the bot's U-5), in the bot's three modes (single with `priceSchedule`, parallel, sequence with `nextCategoryIndex`/`sellLimit`/windows). The golden files are `apps/backend/internal/platform/eventbot/testdata/wizard_bundles/*.json`: each holds typed answers (`input`, strings as a person types them: "18,90", "19.00", "1 200") and the bundles the bot's `BuildBundle` makes for them. `wizard_golden_test.go` rebuilds them from the bot's own parsers and compares (`ARENA_REGEN_WIZARD_GOLDEN=1 go test ./apps/backend/internal/platform/eventbot -run TestWizardGolden` rewrites the files), and `bundle.golden.test.ts` builds a draft from the SAME input and compares `buildBundle` after reducing both sides: null, "", 0 and false equal an absent field EXCEPT on `nextCategoryIndex`, `sellLimit`, `priceSchedule`, `doorsOpenTime`, `promoterId` (a pointer on the wire: absent keeps, zero clears). The `venue` block is not compared (a new venue is only described in the web, 6-1a). A rule changed in one place breaks the other's test on purpose. Parsers are ported in `parse.ts` (`parseTime`, `parsePriceMinor`, `parseCount`, `salesEndOffset`, `doorsOffset`), the zone arithmetic in `zones.ts` (the same two-step lookup as Go's `time.Date`, RFC 3339 with "Z" for a zero offset, an inclusive last day ends at the next midnight). Traps: (1) the platform reads an EMPTY start time as 00:00 (`ParseLocalStart`), so the wizard asks for the time itself (`wizard.err.timeRequired`) or an organizer who forgets it sells a midnight show; (2) a price schedule on a FREE category (price 0) is refused by the check as `import.invalid_price_schedule` at `/categoryList/N/priceSchedule`, which the wizard shows against the date's whole set of tickets (`d.tickets`) because it cannot know the rule better; (3) the price must be typed (0 is a free ticket), an empty price is a client error, never "free"; (4) `checkRunner.ts` asks the dates of one run one after another and caches the answer to each bundle, so a change to one date costs one request, not N; the scheduler's pace (700 ms, 1000 ms gap) is unchanged and the payload of a run is the JSON of all bundles; (5) a field of a date has the key `<date key>.<suffix>` (`dateErrors.ts`) with the rows' own keys, never their positions, so removing a date does not move the errors of the next one; (6) `DateField` is heavy (a month grid), so `WizardDayPick` keeps it closed until asked: several days stand on one page (a date, a last day per step, a day per price change). Pay-what-you-want and a sale window per PARALLEL category are not in the bot's bundle and so not in the wizard. A stored draft of an older `DRAFT_VERSION` is dropped whole (version 2 added the dates).

- **The web wizard creates a DRAFT, off-sale, one-date GA event with ONE explicit POST (6-1c, `apps/event-center/src/lib/wizard/save.ts`, twin `tests/smoke/live/create-event.spec.ts`).** It is the same route as the check (`POST .../imports/event-bundle` without `dry_run`), gated by `import.bil24_session` (owner and manager; the agent gets 403) and by the build flag: `VITE_FEATURE_WIZARD` defaults to `1` in the event-center Dockerfile (both stages), build argument `0` is the rollback, a bare `vite` run without it stays off (`features.test.ts` pins the Dockerfile default; `wizardGate` is the one routing function of menu, list button and screen). `publish:false` makes a `draft` event and a `draft` session (`import_arena.go`), nothing is published into a channel. `externalRef` (`web:<org>:<draft id>:1`) is the idempotency key: a repeat edits the session it made (200, `created:false`), so after a lost answer (network error, timeout, 5xx = `unknown` outcome) the draft stays and the retry button re-sends the SAME key; there is no other reconciliation read. A 4xx is `rejected` (draft kept, the dry-run is asked again to show every field), 401/403 is `denied`. `createSaver` returns the in-flight promise for a second click, the form is a disabled fieldset while saving, and only the saved draft id is removed from localStorage (`clearDraftIfSaved`). LIMITS of this release: one date per event (the import is atomic per session and a second date needs the first answer's event id, so a draft with more dates is blocked, never split) and an existing venue only (no venue creation). The Playwright `live` run needs a private `GOCACHE` and `npm ci --ignore-scripts` works around an esbuild postinstall failure on this host (`ERR_INVALID_ARG_TYPE`).

- **The web event poster (7-1, `apps/event-center`, twin `tests/smoke/live/poster.spec.ts`, CSP proof `tests/smoke/container/poster-csp.spec.ts`) is two server writes that are never reported as one: `POST /v1/media` (multipart, answer `{media_object:{id}}`, `media.write`) and a PATCH of the event with ONLY `poster_media_id` (`event.update`; never `clear_session_overrides`, so a date's own poster survives).** The server does not look into the bytes (it stores the client's `content_type`; sniffs only `application/octet-stream`), so the web accepts JPEG/PNG only, proven from the first bytes, structure and a real browser decode, at most 5 MiB (`POSTER_MAX_BYTES`; server cap 32 MiB) — no WebP. `src/lib/api/http.ts` `call` takes a `form` (FormData) through the same token refresh, channel header and timeout as JSON (never set `Content-Type` by hand: the boundary is the browser's). The wizard uploads, creates the draft with its own idempotency key, then attaches; an attach failure keeps `poster.mediaId`/`poster.eventId` in the version-3 draft (a version-2 draft is still read) and retries the PATCH only, never the bundle. Previews and the shown poster are blob addresses (`img-src` gained `blob:` and nothing else); the signed address is fetched once, only from the API origin, and never stored. Uploaded-but-unattached and replaced media are never deleted (no cleanup exists). The live harness needs a media storage: it sets `MEDIA_BACKEND=local`, `MEDIA_LOCAL_ROOT=.live/media` and `API_PUBLIC_URL`. A `route.abort()` test of an attach lets the real create through; a "lost answer" test uses `route.fetch()` then `abort()`.

- **The session-change and refund cards are KEYED by organization and entity (`SessionChange` by `org:event:session`, `RefundOrder` by `org:order`), and the live resilience specs depend on it.** Client-side navigation between two pages of the same route keeps a component mounted when the target is already in the query cache, so an open panel, a typed message, a dry run in flight and a held refund Idempotency-Key survived the move (found when the two branches were merged; without the key `session-change-resilience.spec.ts` "another organization" and `refund-resilience.spec.ts` "another order" fail). A refund 5xx or lost answer is UNKNOWN: the retry is the same body with the same key, and the stub shows ONE provider call. Release gates that the local harness cannot prove (real mail provider delivery, Stripe TEST mode) are listed in `apps/event-center/tests/README.md`; the worker + local SMTP catcher relay run proves only the worker and the SMTP path. Use `ARENA_LIVE_READY_PORT` other than `ARENA_LIVE_API_PORT + 1` and an own Stripe port when several runs share a host.
