# Posters, formatted text and the Telegram mini app

Poster reading, media envelope, formatted texts (richtext, editor), mini app sign-in and pages. Verbatim items of the former single AGENTS.md. Add a new trap here as a `- **Title.** ...` item and put one title line for it into the index in AGENTS.md.

- **The bot reads a sent poster with a vision model, and everything it
  reads is a BUTTON, never a value.** `internal/platform/posterread`
  (Anthropic Messages API, `poster_facts` tool with `tool_choice: auto`, or Gemini, see the provider bullet, image only — no
  buyer data, no keys) is read by `arena-api` since 3-3 (`POSTER_LLM_API_KEY` there, see the last bullet
  of this list; model `POSTER_LLM_MODEL`, default `claude-sonnet-5`; empty key = off,
  the wizard asks as before). The reading lands in `Draft.Hints`
  (`wizard_hints.go`); `Render` prepends a "From the poster: …" button
  (`hintButtonData`) to every question `hintValue` answers, and `apply`
  turns the press into the typed text or the choice payload. A poster may
  arrive at the FIRST question (`stEvName` accepts `WizInput.Poster` and
  stays), and the poster step then offers `keep`. The model call blocks that
  person's lane (not other accounts) for up to 45 s ("Reading the poster…" is sent first).

- **Every `/v1/media` answer wraps the object in `media_object`, and its
  `signed_url` is absolute.** Until 2026-09-30 no poster sent to the Telegram
  bot ever reached an event, for four reasons stacked on one path: the bot
  decoded `POST /v1/media` and `GET /v1/media/{id}` at the TOP level (empty
  id, empty signed URL — no error, the bundle just went out without
  `bigPosterUrl`); `GET /v1/media/{id}` answered the local backend's
  host-relative `/v1/media-files/...` path, which `sideLoadPoster` refuses
  ("only http(s) poster urls"); Go's `multipart.CreateFormFile` labels the
  part `application/octet-stream`, which `hmedia.CreateMedia` stored as the
  content type; and the side-load trusted that header and skipped the
  "non-image". Now `hmedia` absolutizes a relative signed URL onto
  `Config.APIPublicBaseURL()` (`WithPublicBaseURL`, read per request) and
  sniffs an untyped upload (`http.DetectContentType`), the side-load sniffs
  the fetched bytes when the header is not `image/*`, and the bot sends a
  `content_type` field and reads the envelope. The wizard e2e
  (`bot_e2e_wizard_integration_test.go`) now sends a real 1000×1250 PNG
  through the stub Telegram (`getFile` + `/file/bot<token>/<path>`) and
  asserts `events.poster_media_id`; it needs `Options.Media` on the test
  server and `srv.cfg.AppPublicURL = api.URL`, because the import fetches the
  signed URL from the API itself. An event read back for "Edit" knows the
  poster only by id, so the kept-poster question uses the
  `bot.wz.ask_poster_have_nosize` text, never "0×0".

- **Poster reading is a route of arena-api, and the model key lives ONLY there (3-3, 2026-10-15).** `POST /v1/organizations/{org_id}/media/{media_id}/poster-facts` (`hmedia/poster_facts.go`, mounted in `mount_media.go`, `event.update` inside the path organization, so the owner and the manager but not the agent) reads the media object's bytes and calls `internal/platform/posterread` (unchanged); `POSTER_LLM_API_KEY`, `POSTER_LLM_MODEL` and `POSTER_LLM_BASE_URL` belong to the api role in `config/roles.go` and `deploy/DOKPLOY.md` §2.6, a bot that still holds the key only logs the "set but unused" warning. The media must carry the PATH organization (`obj.OrgID`), a foreign or org-less id is the route's own 404 `media.not_found`, and only a JPEG or PNG of at most 5 MiB is read (422 `media.poster_unsupported_type` / `media.poster_too_large`). No model key = 503 `media.poster_reader_not_configured`, a failed model call = 503 `media.poster_read_failed` (never 502, Cloudflare replaces it, and the model's own error text is logged, never returned). The model call runs on its own 45 s deadline detached from the router's 30 s request timeout, and the connection's write deadline is moved past it (like the refund routes), or a slow reading would be cut. **The daily limit is `POSTER_READS_PER_ORG_PER_DAY` (default 50, `0` = off) per organization, a sliding 24 h window counted by `ratelimit.SlidingWindow` in the MEMORY of one arena-api process** (spec 40 row 3-3 names `ratelimit`; there is no table to count in and the wave-A rule forbids a migration): a restart resets it and with N replicas the ceiling is N times the value, which is acceptable for a cost brake, not for a security limit. Only a request that passed the organization guard, the media checks and the type/size checks takes a slot, a refused one never does; a failed model call keeps its slot (the call may have been billed). The route counts through `SlidingWindow.Take` (a quota: a 429 is NOT recorded), never `Allow`, which records refused attempts too and would let an organization that keeps sending posters after the cap push its own window further out. The bot (`eventbot/arena_client_poster.go`, `ArenaClient.PosterFacts`, a 60 s client) uploads the poster as before and then asks the api (`readPosterHints`); `Options.PosterReader` is gone. It sends "Reading the poster…" only when the call takes more than 1.5 s, so an api without the key answers silently (the bot then pauses reading for 10 minutes) and the wizard asks every question by hand; the wizard always offers "fill in from a poster" now, because the bot cannot know whether the api holds the key. **Rollout order: arena-api with the key first (check that the route answers 404/422, not 503), then arena-bot of the same release, then delete the key from the bot's environment.** Tests: `hmedia/poster_facts_test.go` (stub reader), `httpserver/poster_facts_integration_test.go` (real router, real `posterread` against a stub Messages API, cap, organization isolation, and the bot e2e `TestBotE2E_PosterHintsComeFromTheAPI`), `config/roles_test.go`. The route is in `orgIsolationAuditedSafe` of the org-isolation sweep.

- **Poster reading has two providers and a fallback (2026-10-25), and a forced `tool_choice` is gone from it.** `POSTER_LLM_PROVIDER` = `anthropic` (default, key `POSTER_LLM_API_KEY`, model `POSTER_LLM_MODEL`) or `gemini` (key `GEMINI_API_KEY`, model `POSTER_GEMINI_MODEL`, default `gemini-3.8-flash`); `POSTER_LLM_FALLBACK_PROVIDER` (empty = none, must differ from the primary) is tried once when the first reader fails or times out, and the first one gets only 3/5 of the remaining deadline so the second has time (`posterread.WithFallback`, skipped when under 8 s remain). A provider without its key does not count: a keyed fallback then serves alone, with neither the route answers 503 as before (`httpserver/poster_facts_shims.go`, `posterProviders`). The Anthropic reader sends `tool_choice: {"type":"auto"}` because Claude 5.5 models answer 400 `tool_choice: type "tool" and "any" are not supported for this model`; a reply without a `poster_facts` call is still an error. The Gemini reader (`posterread/gemini.go`) posts to `{base}/v1beta/models/{model}:generateContent` with the key ONLY in `x-goog-api-key`, the image as `inlineData`, `responseMimeType: application/json` and a `responseSchema` made from the same schema as the tool (upper-case types); thinking tokens count against `maxOutputTokens` (8192), a non-STOP finish reason is an error. `POSTER_GEMINI_BASE_URL` is a test seam that production accepts only at its default (shared rule 17b in `config.Validate`). Both readers log one `posterread: model call` line with provider, model, token counts and duration, never poster text. The text-formatting route (`textformat`) still forces its tool for haiku; a 400 whose message names `tool_choice` sets `APIError.ToolChoiceRejected` and `htextformat` logs an ERROR line naming `TEXT_FORMAT_LLM_MODEL` as a config problem. `cmd/arena-poster-bench` is an operator tool (not in the Dockerfile) that scores `provider:model` specs against a `truth.json`.

- **"Format a text" is a route of arena-api and the CODE, not the model, decides what is kept (spec 44 RT-04, `internal/platform/textformat`, `httpserver/htextformat`, `mount_texts.go`).** `POST /v1/organizations/{org_id}/texts/format` (`event.update` inside the path organization, `{text, kind: description|email_note|session_message, locale}` -> `{html, ai_applied, reason?, prompt_version}`) asks Claude (forced tool `format_text`, model `TEXT_FORMAT_LLM_MODEL`, default `claude-haiku-5-5`, the poster key `POSTER_LLM_API_KEY` and base URL `POSTER_LLM_BASE_URL`, own 25 s deadline plus `SetWriteDeadline`) to add only tags and `textformat.Verify` keeps the answer only when `richtext.Words(Sanitize(answer)) == richtext.Words(FromLegacy(text))` (`**x**` markers are markup, so they count as removed), every link target is written in the text and is the link's own visible text (else unwrapped by `richtext.Constrain`), a paragraph has at most 3 emphasised fragments and the limits of the profile hold. **Every failure after validation is a 200 with `html = richtext.Normalize(text, "text", profile)` and `ai_applied:false` plus a `reason`** (`not_configured`, `quota`, `timeout`, `model_error`, `no_text`, `empty_output`, `invalid_markup`, `text_changed`, `limits`): never a 502/503, clients look only at `ai_applied`, saving never breaks because of the model. A text over the visible limit of its kind (4000/2000/1000 characters) is 422 `text.too_long` and one with forbidden characters 422 `text.invalid`, both BEFORE any slot or model call; an unknown kind is 400. Caps `TEXT_FORMATS_PER_USER_PER_DAY` (100) and `TEXT_FORMATS_PER_ORG_PER_DAY` (500), `0` = off, are two `ratelimit.SlidingWindow`s in the memory of one process, taken with `Take` right before the model call and only when both have room (a failed call keeps its slot). **Logs hold the reason, `prompt_version`, lengths, kind and org id and NEVER the organizer's text or the model's answer** (`textformat.APIError` carries only the status and the API's error type, not its message). Change `PromptVersion` with every prompt edit. A test points `POSTER_LLM_BASE_URL` at a stub Messages API (`httpserver/text_format_integration_test.go`, `htextformat/handler_test.go`, `textformat/*_test.go`); the route has `{org_id}` in its path, so it needs no line in `flatRouteFamilies`.

- **Formatted texts have ONE write path, `eventtext` -> `richtext.Normalize`, and a format flag that covers the translations (spec 44, RT-02, migration 0168).** `events.description_format` and `event_email_notes.note_format` are `'text'` (old marks) or `'art'` (HTML subset); every writer of `events.description`, the `i18n_text` rows of namespace `event.description` and `event_email_notes.note` calls `eventtext.NormalizeDescription/NormalizeNote(input, format)` and stores `'art'` (REST create/patch `hcatalog/events.go`, `event_email_note.go`; bundle `himports/import_description.go`, `import_email_note.go`; `arena-bil24-import` via `catalogimport.DescriptionART`). The flag is per EVENT: a writer that stores ART into an event whose flag is still `'text'` must first run `eventtext.UpgradeDescriptions` in its transaction (it converts the base text and the other translations, rows being overwritten excepted), otherwise old translations are read as HTML. `gen.InsertEvent`, `UpdateEvent`, `SetEventImportMetadata` and `UpsertEventEmailNote` take the format as their last argument; tests that seed raw text pass `"text"`. The flag is NOT in the shared `scanEventRow` SELECTs (reading is RT-03). The event-bundle READ names the stored format next to each text (`descriptionFormat`, `emailNoteFormat`), so a read bundle posted back keeps the stored texts byte for byte; a bundle with `source=bil24` and no `descriptionFormat` is read as `art` (WordPress sites send HTML), `source=arena` as `text`. The buyer letters read the note through `eventnote.Build(note, format)` (`richtext.Render`; the format travels in `gen.TicketPresentationRow.EmailNoteFormat`, `delivery.Payload.EventEmailNoteFormat` and `eventnote.TestPayload.NoteFormat`; a missing one reads as `text`), and the test letter validates its draft with `eventtext.NormalizeNote` like the save. A refused description or note is 422 everywhere (REST and bundle). The bot keeps `DraftEvent.DescriptionFormat` next to the description (REST `description_format`): ART goes back as `art`, an untouched old text is not re-sent, typed text is plain `text`; screens use `richtext.ToTelegramHTML` or `PlainText`, never raw tags. A literal `<b>` in a `text` write is visible text, never a tag; only the first 5 bare `https://` addresses of a note become links (a 6th is plain text, not an error), so `too_many_links` is an `art` refusal.

- **`cmd/arena-richtext-backfill` converts the rows still marked `'text'` (RT-02).** `--dry-run` is the default (the same code in a transaction that is rolled back), `--apply` writes one transaction per event or note that first copies the old value into `richtext_backfill_backup(run_id, entity, row_id, locale, ...)`, `--rollback <run_id>` restores old values and format (a dry run without `--apply`; a text written since the run, or a translation added since, keeps its whole event as it is), `--org` scopes a run to one organization (integration tests always use it, so they never convert someone else's rows), `--limit N` with the cursor `--after <event_id>` (the run prints the next one; rows left as they are never block it), `--report file.md` (ids, locales, lengths and reasons only; `--show-text` puts the texts in, only into the `--report` file, created 0600), `--html-as-art`, `--purge-backup-older-than <days>`; `--rollback` honours `--org`. A text of the old kind that holds HTML tags of the white list is left as it is with the reason `literal_tags` unless `--html-as-art` is given, a row changed under the run is skipped (`changed_while_running`) and the run goes on. A text that fails `Normalize` (too long, rejected characters) is NOT changed, and neither are the other texts of its event, because the flag covers them. Config is loaded like `arena-migrate` (`config.RoleMigrate`, `DATABASE_URL`; the role is listed in `tests/staticanalysis/cmd_config_role_test.go`).

- **Every reader shows a stored description through `eventtext.ViewDescription(stored, format)` (spec 44, RT-03a/b).** REST event reads add `description_html`/`description_text`/`description_legacy` (+ `email_note_format`), the public page and feed add `description_html`/`description_text`, the Bil24 `GET_ALL_ACTIONS` sends `richtext.Render` HTML; `description` stays the raw stored value. The format is the event's flag (read in one batch: `ListEventDescriptionFormats`, or `e.description_format` joined into the hosted-page resolution); a format that could not be read leaves the views null, it is never guessed from the tags. The hfeed snapshot tests (`*_ExistingFieldsUnchanged`) list the exact key sets, so a new public field means editing them. Front ends rebuild only whitelisted nodes (`tickets-page/src/lib/richtext.ts` with DOMParser, `admin-web/src/lib/richtext.ts` with its own tokenizer because admin-web's vitest runs in Node without jsdom) and the admin edit form loads `description_legacy` and sends `description` only when the person changed it. The shared corpus `richtext/testdata/richtext_legacy.json` is read by the Go, tickets-page and admin-web tests.

- **HTML from sites keeps its paragraphs and survives the gateway (spec 44, final review).** `richtext.AutoParagraph(html)` gives WordPress `wpautop` layout to an HTML text that has no block tag and no `<br>` (found with the html tokenizer, never a regex): a blank line is `</p><p>`, a newline is `<br>`; otherwise the text is returned as it is. `Normalize(.., "art", ..)` and `Render(.., "art", ..)` both run it first. `richtext.LooksLikeHTML` (tokenizer: a tag of the white list, `b`, `i`, `h1`-`h6`, `div`, `span` or `br`) is the one test of "this `text` row is really HTML a site wrote": the Bil24 gateway (`hbil24/cmd_catalog.go`) renders such a row as `art` until the backfill has converted it, and the backfill uses the same test for `literal_tags`. `arena-bil24-import` reads descriptions as `art` by default (`--description-format text|art`, `Bil24SnapshotEvent.DescriptionFormat`). The bot never re-sends an untouched description, in any format (it loads without a locale, so what it holds may be an `en` translation), drops U+202A-U+202E from typed text, and shows a refused description (`import.invalid_description`, `error.details.reason`) as `bot.wz.err_description*` texts (the bot catalog has en, ru and es only, cs and he fall back to en). The event-bundle import errors for texts carry `error.details.reason`. The PATCH metadata audit row is written after `Commit`. Release steps: `docs/ops/rich_text_release_runbook_ru.md`.

- **The bot formats a typed text in a loop of its own, and the draft never holds an unapproved text (spec 44 RT-05, `eventbot/textfmt*.go`).** At the wizard's description question `wizardText` hands the text to `descriptionTyped` instead of `Wizard.Apply`: `tfCheck` refuses what the server would refuse (4000 VISIBLE characters, forbidden characters) before a model call is spent, `ArenaClient.FormatText` calls `POST .../texts/format` (own 32 s timeout, `WithFormatTimeout` for tests), `tfDecide` re-proves the answer (`richtext.Words` equal to the typed text's, every href typed by the organizer) and falls back to the plain ART in EVERY failing case (call error, `ai_applied=false`, changed word, invented link), and the preview goes to `bot_dialogs` kind `textfmt` (`tf:s|p|a|c` buttons). Only the button hands the ART to the wizard through `WizInput.Art`; `setTypedDescription` (poster hints, tests) now stores `FromLegacy` ART marked `art` too, so a draft never carries the old notation. A restart of the bot ends the old message's buttons (feed.go) but keeps the dialog row: the organizer types the text again. The preview is never one message with 4096+ characters: `tfScreens` sends the text alone and the question with the buttons after it (`tgSplit` cuts between paragraphs, never inside a tag). A new text kind joins by `tfKind` (+ its `richtext.Profile`), not by a copy of the loop. The e2e `TestBotE2E_DescriptionIsFormattedAndPreviewedBeforeItIsSaved` drives the real route against a stub Messages API (cap 8 calls per person per day, bot timeout 3 s).

- **"Text in the letter" on the bot's event card is the same loop with `kind=email_note` (spec 44 RT-06, `eventbot/textfmt_note.go`).** Callbacks `tf:n|e|d|dy|t:<event id>` (screen, change, delete?, delete, test letter) share the `tf` prefix and the `textfmt` dialog with the description preview: `tf:e` stores step `await` with `tfDialog{Kind: email_note, EventID}`, the typed text becomes a preview, and the buttons `tf:s|p` PATCH `email_note` + `email_note_format: "art"` (`ArenaClient.SetEmailNote`, `null` clears). The screen reads the text from the event LIST (`eventOf` — only the list route hydrates `email_note`; the single-event route does not) and shows it through `ToTelegramHTML`. The bot says in plain words that the letter adds the greeting and the date itself: Arena has no `{name}`/`{date}` substitutions (owner decision 2026-10-24, spec 44 §9.3) and a text in the bot must not suggest any. The test letter goes to the caller's own address through `POST .../email-note/test` (a 422 `event.email_note_empty` and a 429 get their own lines). The button shows for `canViewSales` roles (owner, manager, operator) — the API's `event.update` decides in the end. Tests: `bot_e2e_textfmt_note_integration_test.go` (event list → card → screen → five model outcomes → test letter job → delete with confirmation).

- **Sign-in codes have a purpose, and `miniapp` is the Telegram mini app editor (spec 44 RT-12a, migration 0169).** `web_login_codes.purpose` is `'web'` (default, "Open in browser": 72-hour session, "signed in" notice, a new code takes back only the person's open `web` codes) or `'miniapp'` (`POST /v1/bot/web-login-codes` with `purpose`, `kind` description or email_note, `event_id`; `purpose` and `kind` are plain strings in openapi.yaml, an inline enum renamed existing constants (`Description`, `EmailNote`, `SessionMessage`); the API builds `<EVENT_CENTER_PUBLIC_URL>/tg/edit#code=..&kind=..&event=..`). Exchange is still `POST /v1/auth/web/link`: a miniapp code opens a session of channel `event_center_tg`, `idle_seconds` 1800, and `sessionEnd` caps it at `session_started_at + MiniappSessionAge` (30 min), so a refresh never extends it, and the access token is cut to the same end (`accessTTL(end, now)` = min(15 min, end - now), on the exchange AND on refresh, where the new end is computed BEFORE the JWT is minted; a refresh after the end is 401 `auth.refresh_token_expired`); a mini app session is NOT tracked in the concurrent-session store (`trackNewSession`/refresh skip `isMiniappSession`), so it never evicts the person's web or admin sessions, and requests made with its token are audited with `via=telegram_miniapp` (`audit.stampVia` reads `actor.Channel`, the header cannot claim it); its access token carries `chn=event_center_tg` and `isWebRequest` treats it like the web (money routes still ask for the password). `ClaimWebLoginNotices` filters `purpose = 'web'`, so no notice; `RevokeOpenWebLoginCodes` (sign out everywhere) takes back every purpose and `RevokeWebRefreshTokens` ends both web channels; platform roles are refused at issue and at exchange. Bot: `BOT_MINIAPP_EDITOR_ENABLED` (default off) -> `Options.MiniappEditor` -> `miniappRow` (`eventbot/textfmt_miniapp.go`) puts a CALLBACK button `bot.tf.edit_btn` (`tf:m` under the description preview, `tf:m:<event id>` on the email-note screen, only when the edit wizard has an event id, never in create mode, private chats only). The code is drawn LAZILY: a screen draw asks for nothing, the press (`tfMiniappCallback`) issues one `miniapp` code and edits the pressed message in place (same rows, that button becomes a `web_app` button with the fresh https link of <= 2048 bytes, plus the note `bot.tf.edit_note` "the link works for 5 minutes"); a later press on a fresh screen issues a new code, `bot.tf.edit_failed` answers a refusal, and the preview's no-markup fallback sends the keyboard WITHOUT that row. Rollback: turn the flag off, then roll back the API, the migration last (its Down revokes open `miniapp` codes and marks their notices as sent). nginx: `location ^~ /tg/` + named `@tg_index` (`rewrite ^ /index.html break;`) with `security-headers-tg.conf.template` (no X-Frame-Options, `frame-ancestors` = Telegram web clients); `try_files $uri /index.html` there would re-match `= /index.html` and send DENY. CI: `apps/event-center/scripts/check-headers-tg.sh`. The vendored `public/vendor/telegram-web-app.<8 hex>.js` is pinned by name and sha256 (README of event-center, `tgEdit.test.ts`); the page `/tg/edit` is the editor since RT-12b (next entry).

- **The mini app page `/tg/edit` (spec 44, RT-12b) edits the description with ONE PATCH and trusts nothing in its link.** `TgEditScreen` exchanges the code (once per page: a `useRef` memo, because StrictMode runs the effect twice and a code works once), then `openTgEdit` (`lib/tgEditEvent.ts`) looks the `event` of the fragment up in the events list of EVERY organization of the person; a 403/404 list, an event no list holds and a person without `event.update` all answer the same `tgEdit.noAccess`, a network failure is NOT "no access". The description is saved by `saveDescription`: `PATCH .../events/{id}` with `description` + `description_format: "art"` and nothing else (name, poster, dates, categories and translations are untouched; the server only converts still-plain translated descriptions to ART word for word, `UpgradeDescriptions`). The event-bundle the wizard edit posts would send the WHOLE event back (sessions, categories, windows) and skips sessionless events, so it is the wrong tool for one text. The letter text is the unchanged `EmailNoteSection` (`onSaved` closes the window only after Save, not after the test letter or Delete). **The events list returns a LOCALIZED description** (`COALESCE(d_loc, d_en, events.description)` for `lang` en/ru), so an event that has an `en` translation row shows the translation as `description`, and an editor that PATCHed it back wrote the translation over the canonical text. Every event route (list, get, create/patch answers) therefore also carries `description_base` (the raw `events.description`, read by `ListEventDescriptionBases` beside the format flag in `hydrateDescriptionFormats`) and `description_translated` (the shown text is another one); an editor reads and writes the BASE: the mini app (`descriptionBaseOf`, its list is asked with no language and a key with no locale, so a language switch neither reloads it nor replaces the draft) and the bot (`eventDescriptionBase` in the fingerprint and in the wizard's `LoadEventDraft`). A server that predates the field sends neither and `description` is then the only text. A description still marked `text` that holds literal HTML tags (a WordPress site wrote it, `richtext.LooksLikeHTML`, TS twin `looksLikeSiteHtml`) is NOT opened in the mini app: the converter would show the tags as words and Save would store the words; the page says to edit it on the site and Save stays disabled. `Telegram.WebApp.close()` is called only when `platform !== "unknown"`: the real script defines `Telegram.WebApp` in an ordinary browser too, where `close()` does nothing. `env(safe-area-inset-*)` is always defined (0px), so its fallback never applies: the Telegram insets are a separate `max(..., var(--tg-safe-area-inset-*))` term. The theme is `var(--tg-theme-*, <app colour>)` on `.tg-page`, set by the Telegram script with the CSSOM (allowed by `style-src 'self'`). **Bot side (`eventbot/textfmt_editor.go`):** the press of «Править в редакторе» stores a fingerprint of the stored text (as ART, so a legacy row rewritten with the same words is no change) in the dialog (`Editor`, `Seen`; the letter screen has no dialog, so it opens one of step `editor`); the next press under that preview or screen, or the next typed text, re-reads the event: a changed text says `bot.tf.editor_saved` ONCE, draws the saved text and does NOT carry out the press (a «Save as shown» would write the old preview over the editor's text); a typed text is only preceded by the note; a failed read says nothing and blocks nothing. The fingerprint is of `richtext.Normalize` of the BASE text (never raw `FromLegacy`), a second press of the button after a save asks first (note, no new link, `Seen` never overwritten), a lapsed dialog of step `editor` does not swallow a typed line, and after a description save `tfEditorSyncDraft` writes the saved ART into the wizard's edit draft and its `Loaded` copy and refreshes the loaded `updated_at` ONLY when name, age, promoter and poster still equal `Loaded` (otherwise «changed elsewhere» stays: somebody else edited too). Twin test: `tests/smoke/live/tg-edit.spec.ts` plays the bot with `BOT_SERVICE_TOKEN` (the harness sets it, `arena-e2e-seed` links the three people to Telegram accounts `9100000001..3`, `tgedit_fixture.go`); the Go proof is `bot_e2e_miniapp_save_integration_test.go`.

- **One editor for every formatted text: `apps/rich-editor` (spec 44, RT-10).** A framework-free library on Tiptap 2 (exact versions), ESM for `apps/event-center` (`"@arena/rich-editor": "file:../rich-editor"`, `dist/` must be built: the event-center Dockerfile builds it at `/rich-editor` before its own `npm ci`) and IIFE `ArenaRichEditor` for WordPress. `src/profiles.ts` is a copy of the Go profile table and `tests/profiles.test.ts` READS `richtext.go`; `getHTML()` is built by a port of the Go sanitizer (`src/model.ts`, `src/sanitize.ts`, `src/href.ts`), never `editor.getHTML()`, and `tests/corpus.test.ts` runs every `art` of `richtext_legacy.json` through the editor (an exception needs a written reason). Changing a profile, a tag or a link rule in `richtext/*.go` means changing the port in the same PR. - **The Telegram Mini App signs in with its launch data at `POST /v1/auth/telegram-miniapp` (task S3b), and arena-api holds only a DERIVED key.** Body `{init_data}` = `Telegram.WebApp.initData` unparsed. `hauth.VerifyInitData` (pure, `telegram_initdata.go`) applies Telegram's rule: `data_check_string` = every field but `hash` (the third-party `signature` field IS part of it), sorted, `name=value` joined by newline; `hash` = hex HMAC-SHA256 of it under `TELEGRAM_MINIAPP_SECRET_KEY`, which is `HMAC-SHA256(key="WebAppData", message=bot token)` as 64 hex characters (config refuses any other shape in every environment; arena-api never holds the bot token, so it cannot speak as the bot; how to derive it in PowerShell: `deploy/DOKPLOY.md` section 2.6, api only). The signature is checked BEFORE the age, so `auth.telegram_init_data_expired` (genuine, older than 5 minutes or more than a minute ahead) is never an oracle for a forger, who always gets `auth.telegram_init_data_invalid` (401) for malformed data, a repeated field, more than 24 fields, more than 4096 characters or a wrong hash. Then it binds to the person the bot linked (`bot_telegram_links` by Telegram id; unknown or revoked = 403 `auth.telegram_not_linked`, nothing is created or linked here), refuses a deactivated account (403 `auth.user_deactivated`) and any platform role (403 `auth.web_link_superadmin`), and issues the SAME 30-minute session as a `purpose='miniapp'` code of `/v1/auth/web/link` (`newMiniappSession`: channel `event_center_tg`, never refreshed past minute 30, not counted in the concurrent-session limit, `chn` claim so money routes still ask for the password, audit `v1.auth.telegram_miniapp_login` with `via` and the Telegram id, never the launch data). Unset key = 503 `auth.telegram_miniapp_not_configured`. 30 requests per client address per 15 minutes (a success resets it; memory of one process). Metric `arena_auth_telegram_miniapp_login_total{outcome}` with a CLOSED outcome set (`observability.RecordTelegramMiniappLogin` folds anything else into `error`). Known limits: NO single-use or replay cache (the same signed data works again until it is 5 minutes old, on purpose: a page reload reuses it, and a one-time store would need a table); the session is the 30-minute one, so a long edit ends at minute 30 and the page must be reopened from Telegram for FRESH launch data (the page's own `initData` is stale after 5 minutes); nginx `frame-ancestors` for `/tg` stays with the web side. **Where the page goes after sign-in (`next`):** the answer carries `next`, the event-center path to open (`hauth/telegram_next.go`). Source 1 is the SIGNED `start_param` of the launch data (base64url without padding of the path, because Telegram allows only `A-Za-z0-9_-` there; a direct Mini App link `t.me/<bot>/<app>?startapp=<b64>` carries it, an inline `web_app` button does NOT), source 2 is `next` in the request body (a path the page read from its own URL, untrusted); the signed one wins. Both pass `SafeMiniappNext`: only `/o/<uuid>(/segment)*[/][?query]` (segments and query from `[A-Za-z0-9._~=&-]`, `.`/`..` segments, `//`, backslash, `%`, `#`, absolute or scheme-relative URLs all refused, 300 characters max); anything else is `""` and the sign-in still succeeds, never an error. The check keeps the address inside the event center only: whether the person may open that organization is decided by the screen and the API. Tests: `hauth/telegram_next_test.go`, `telegram_miniapp_next_integration_test.go`.
