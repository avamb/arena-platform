# Страница продаж и редактор материалов Event Center

Дата: 18.10.2026. Задача для Claude через существующий direct SDK runner.
Основание: запрос владельца — доработать PR #164 до полноценной страницы продаж и обеспечить управление каждым публичным материалом в Event Center.

## Проверенная исходная ситуация

- PR #164: отображение галереи, видео, карты-ссылок, «Где ещё купить», фотоотчёта в tickets-page. Открыт, конфликтует с master. Описанные автором проверки не заменяют повторную приёмку текущей интеграции.
- PR #181: аналогичные блоки в widget, атрибут `materials="hidden"`; открыт, конфликтует. Его описание прямо отмечает риск двойного отображения материалов в tickets-page.
- PR #171: редакторы в Telegram-боте; открыт, конфликтует. Это заготовка поведения, не доказательство наличия редактора в вебе.
- PR #183: статистика. Отдельная задача; не делать обязательной зависимостью выпуска материалов и не сливать автоматически.
- Сервер текущей линии релиза уже содержит gallery/videos в `mount_event_materials.go`, partner-links/map-point/photo-report и копирование в `mount_materials_extras.go`.
- Публичные page/feed ответы содержат gallery, videos, partner_links, map_point, report_photos (`hfeed/public_materials.go`). Фотоотчёт скрывается сервером до окончания последнего сеанса мероприятия.
- В проверенном исходнике Event Center (линия PR #195, 78ffb67; production merge 820393174209cba99da6c76e541435c25f07f662) вызовы этих редакторов не найдены. В типе публичной страницы есть venue_names, но нет полноценного адреса площадки. Адрес продавца — другая сущность, его нельзя использовать вместо адреса мероприятия.

Перед изменениями сверить актуальный origin/master и головы PR. Не считать локальный корневой checkout актуальной базой: в нём пользовательские изменения.

## Результат для организатора и покупателя

Организатор открывает мероприятие в Event Center, добавляет материалы, сохраняет их, открывает публичную страницу и видит те же данные. После перезагрузки редактора данные остаются. Изменение или удаление отражается на публичной странице. Материалы необязательны; пустые блоки скрыты. Существующее решение об афише (загрузка первой либо осознанный пропуск) сохранить.

### 1. Полноценная страница продаж

Сохранить афишу, название, описание, даты, выбор билетов, покупку, данные продавца и действующие юридические ссылки. Органично встроить новые секции; на мобильном экране покупка остаётся доступной. Не менять checkout, платежи, цены или правила публикации мероприятия/сеанса.

### 2. Галерея

До 6 изображений: загрузить через существующий media API, изменить подпись, порядок, удалить. Показать загрузку, ошибки формата/размера, превышение лимита. Использовать существующие разрешённые форматы и ограничения media API, не выдумывать новые.
Публично: адаптивная сетка, подписи/alt, увеличение, закрытие Escape, навигация клавиатурой, возврат фокуса. Ошибка отдельной картинки не ломает покупку.

### 3. Видео

До 4 ссылок: добавить, просмотреть, удалить, переставить. Использовать серверную нормализацию YouTube/Vimeo/Rutube и https-ссылок; изменение существующего URL реализовать совместимо с имеющимся API, не обещать несуществующий PATCH.
Публично: внешние embed-запросы только после клика. Allowlist источников, согласованный CSP страницы и документация CSP для встраиваемого виджета. Неизвестный разрешённый https-источник — обычная ссылка. При ошибке плеера остаётся ссылка на оригинал. Не ослаблять sandbox/CSP ради прохождения теста.

### 4. Где ещё купить

До 3 партнёрских ссылок: название продавца, URL, порядок, редактирование, удаление. Показать переход к другому продавцу явно, не выдавать его за checkout Arena. Партнёры здесь — другие продавцы билетов, не спонсоры и не рекламные логотипы.
Проверка URL на сервере и клиенте; запрещены javascript/data и другие опасные схемы. Внешняя вкладка защищена noopener. Текст безопасно экранируется.

### 5. Где проходит мероприятие: адрес и карта

Название площадки, страна/город и почтовый адрес — из реальной площадки сеанса. Не путать с юридическим адресом продавца. Существующая форма редактирования площадки должна позволять сохранить эти сведения; если переход/поле отсутствует, добавить минимальный интерфейс или явную ссылку на него с проверкой полномочий.
Точка мероприятия: координаты и подпись, сохранить/изменить/удалить через существующий map-point API. В первой версии достаточно кнопок Google Maps/OpenStreetMap и текстового адреса; интерактивная карта и платный геокодер не обязательны. Не определять адрес или координаты догадкой и не загружать сторонние карты автоматически.
Проверять диапазоны координат; одна отсутствующая координата не равна 0. Валидная точка 0,0 разрешена. При отсутствии координат показывать имеющийся адрес без ложного маркера.
Если сеансы на разных площадках, показывать адрес выбранного сеанса либо явный список площадок/дат; не привязывать все даты к первой площадке. Один event-level map_point не должен ошибочно представляться точкой всех разных площадок.
Добавлять поля public API только при доказанном отсутствии нужных данных. Тогда обновить OpenAPI, Go/TS генерацию, совместимость старых ответов и тесты. Не публиковать частные контакты и адреса организации.

### 6. Фотоотчёт

До 30 фото: загрузка, подписи, порядок, удаление. В редакторе ясно показать, когда он станет публичным. Серверное скрытие до окончания последнего сеанса сохранить; часы браузера не являются защитой. Обработать отсутствие end_at согласно существующему серверному правилу, не придумывать новое.

### 7. Связь с Event Center и виджетом

В карточке мероприятия отдельный раздел «Материалы страницы продаж» с перечисленными редакторами и ссылкой на публичный результат, когда он действительно доступен. Owner/manager с event.update могут изменять, event.read — чтение. Проверять фактические permissions, не только названия ролей. Без права — read-only; попытка прямого API-вызова также запрещена. Чужая организация не читается и не изменяется.
Один источник данных — существующий API. Не хранить материалы исключительно в localStorage, константах или демо JSON. Подписи, состояния загрузки, пустоты, ошибки и подтверждение удаления локализовать в существующих языках соответствующего приложения.
Не внедрять новые материалы в неслитый PR #171 как обязательную зависимость; его сценарии использовать как ориентир паритета. Персональные тексты писем (#182) не входят в эту задачу.
Внешний widget должен уметь показывать тот же набор материалов (#181 как источник существующего кода). В tickets-page блоки не дублируются: атрибут materials="hidden" выставлен во всех соответствующих местах монтирования, включая страницу промоутера. Решение проверить совместно, не просто скопировать компоненты двух PR.

## Приёмка: реальные сохранения и публичное чтение

1. Создать локальное тестовое мероприятие; через настоящий Event Center и локальный API добавить фото, видео, ссылку продавца, точку. Перезагрузить редактор; проверить сохранение и public response. Пройти публичную страницу и внешний widget в браузере.
2. Изменить подпись/порядок/ссылку/точку, удалить материал; проверить конечный результат после перезагрузки, без stale cache и двойных секций.
3. Проверить лимиты 6/4/3/30 и серверный отказ при превышении, invalid URL, XSS-текст, чужой media_id/ивент/организацию, read-only роль и прямые запрещённые запросы. Ошибки не должны отображаться как успешное сохранение.
4. Адрес без координат, координаты без адреса, некорректная точка, 0,0, несколько площадок/сеансов. Пустые данные не превращаются в придуманный адрес/место.
5. До окончания последнего сеанса public API и страница не показывают фотоотчёт; после — показывают. Сценарий с несколькими сеансами и часовыми поясами.
6. Desktop/mobile, длинные подписи/названия продавца, клавиатура, модалка фото, отсутствие горизонтального переполнения. Сделать локальные скриншоты, без секретов и персональных данных.
7. Интеграция с реальным локальным backend обязательна: моки покрывают отказы, но не заменяют проверку «редактор → API → public page/widget». DB-тесты — integration tag, отдельная scratch DB, без изменения общей базы/production.
8. Typecheck/unit/build затронутых фронтендов, необходимые Go/integration tests, codegen drift, контейнерный CSP smoke, meaningful live E2E. Не называть старые результаты авторов PR новыми проверками. Отдельно указать, проверялись ли настоящие внешние видеоплееры; mock iframe не доказывает их воспроизведение.
9. Регрессия текущего выбора билетов/перехода к checkout без реальной оплаты, афиши и публикации. По завершении независимая проверка Codex, только после неё статус готовности к выпуску.

## Порядок и ограничения Claude

Использовать существующий direct SDK runner, модель claude-sonnet-5-5 для реализации. Начать с краткой сверки данных и зависимостей, затем код, проверки и отчёт. Не создавать новую orchestration-инфраструктуру.
Работать в отдельном worktree от свежего master; сохранить корневые пользовательские изменения. Использовать #164/#181 как исходные реализации, переносить нужный код с сохранением происхождения; не сливать вслепую старые ветки с общими файлами. Существующие PR не закрывать и не переписывать без необходимости.
Разрешённый код: tickets-page, widget, event-center; минимальные backend/API/codegen изменения для доказанных пробелов; релевантные тесты, docs и конфигурация заголовков. Исключить биллинг, сканер #185, массовые изменения стиля, другие проекты, SSH и production/staging.
Не менять secrets, billing-настройки или credentials. API-ключ только через Windows Credential Manager, Workspace header сохранить. Лимит первого edit-запуска до $8 в рамках ранее разрешённого общего бюджета $80; до запуска учесть фактические накопленные расходы и зарезервированные бюджеты. При отсутствии доступного остатка не запускать. Retries 0; старые latch/отчёты не сбрасывать. Не использовать Claude Max. В этой записи платный запуск не выполнялся.
