# Org-isolation audit of master 4fbf2ff (read-only static analysis by an agent, 2026-10-10). VERIFY EVERY CLAIM with a failing test before fixing.

Facts for everything: `applyAuth` (httpserver/mount_v1.go ~93) only runs auth + RBAC + the superadmin marker. The permission checker has NO org awareness: it unions the roles of ALL the caller's memberships, so an `org_admin` (owner) of org B holds `X.read/.update` for every org. Event and session UUIDs are exposed by public feeds and hosted pages, so "needs a UUID" is a weak barrier. Paths below are relative to `apps/backend/internal/platform/httpserver` ("hs/") unless they start with adapters/ or migrations/. Reference fixes: `hcatalog/tier_org.go` (`requireSessionInOrg`, `requireEventInOrg`, PR #23) and its test `tier_org_isolation_integration_test.go`; `orgread` package; `RowOrgAccess` (PAY-00) with `refund_org_isolation_integration_test.go`.

## CRITICAL (fix first)
H1. Membership grant / list / revoke ignore {org_id} entirely: privilege escalation to platform superadmin.
Routes: POST/GET `/v1/organizations/{org_id}/members`, DELETE `.../members/{user_id}`, GET/POST `/v1/admin/organizations/{org_id}/members`, PATCH/DELETE `/v1/admin/organizations/{org_id}/members/{membership_id}`.
Evidence: mount_iam.go:166-178 and mount_admin.go:142-158 gate only by `membership.read/grant/revoke`. hiam/memberships.go:88 (grant), :194 (list), :235 (revoke) have no org check (no requireOrgMembership; shims iam_shims.go:101-111 add none). hiam/admin_memberships.go:144, :424, :534 only check an X-Admin-Reason header is non-empty (`requireAdminReason`, hiam/superadmin.go:121). `org_admin` holds membership.grant/revoke/read (migrations 0011_memberships.sql:94-100, 0116_bot_team_permissions.sql). `validMembershipRoles` (hiam/memberships.go:50) ACCEPTS `platform_superadmin` and `org_admin` for any caller. `GetActiveRolesForUser` (adapters/postgres/queries/memberships.sql:59-79) unions `memberships.role` into the actor's roles; `DBChecker.SuperadminOrgBypass` (platform/permissions/rbac_checker.go:227) treats a `platform_superadmin` membership as full superadmin.
Exploit: owner of ANY org POSTs {"user_id": <self>, "role": "platform_superadmin"} to /v1/organizations/<any org>/members and becomes superadmin on the next request. Variants: grant `org_admin` in a competitor org, DELETE a competitor's owner membership, list any org's members (e-mails and names on the admin route).
Fix shape: caller must be a member (with grant/revoke authority) of the PATH org or a real platform superadmin (the `superadmin.read` marker); a non-superadmin caller may grant only org-level roles (an allow-list: organizer, agent, org_admin?; NEVER platform_superadmin, platform_operator, network_operator, external_ticketing_operator); revoke/list likewise scoped; the membership row must belong to the path org on PATCH/DELETE by membership_id. Also check whether a DB trigger or CHECK could forbid platform_superadmin memberships (0011 is documented to allow it); consider whether `platform_superadmin` memberships should exist at all and how real superadmins are granted today (seed/SQL/user_roles) so you do not lock the operator out.
H2. Org-level admin routes accept an owner token for ANY org; owner can self-verify KYB.
Routes: POST `/v1/admin/organizations`, PATCH `/v1/admin/organizations/{id}`, GET `/v1/admin/organizations/{id}/sender-dns`, POST `/v1/admin/organizations/{id}/archive`.
Evidence: gated by `org.create/update/delete` only (mount_admin.go:119-131); `org_admin` holds all (migrations 0009_organizations.sql:86-87). Handlers (hiam/admin_orgs.go:48, :148, :299) call only `requireAdminReason` (header non-empty). hiam/admin_orgs.go:198 `validateLegalUpdate` writes kybStatus but never calls `kybChangeAllowedForOwner` (guard exists only at hiam/orgs.go:474), so `TestOrgKYB_OwnerCannotSelfVerify` does not cover this route.
Exploit: owner of org B PATCHes /v1/admin/organizations/<A> with any X-Admin-Reason: renames A, changes legal data and sender e-mail; archive takes A's storefront offline; PATCH <B> kyb_status=verified opens live payments; POST creates organizations without onboarding approval.
Fix shape: these are SUPERADMIN-only routes (require the superadmin marker `auth.HasSuperadminOrgAccess`/`superadmin.read`), unless an owner legitimately uses a route (check admin-web usage in apps/admin-web first and keep owner-facing behaviour via the non-admin `/v1/organizations/{id}` routes which already have requireOrgMembership + KYB guard).
