# Веб-ивент-центр: сравнение с ивент-центром сайтов и планом бота, план доведения (14.10.2026)

> Это приложение: сравнение функций (разделы 1–4) и список серверных задач. Порядок работ и решения владельца от 14.10 — в `event_center_unified_plan_2026-10-14_ru.md`; разделы 5–7 ниже заменены им.

Основа: `08_architecture/37_web_event_center_ru.md` (спека веба и матрица паритета, раздел 11), `docs/plans/telegram_event_center_status_and_plan_2026-10-13_ru.md` (сравнение «сайт → бот»), `docs/plans/event_center_logic_for_bot_2026-09-28_ru.md` (полная логика мастера сайтов), код плагина `lampyris-ops` (вкладки «Ивенты», «Заказы», «Возвраты», «Сводка») и приложение `apps/event-center`.

## 1. Короткий ответ

1. Это не потерянные коммиты. Все ветки веба (`web-r1`, `web-center-*`, `event-center-password-links`) влиты в master, непросмотренных PR нет. Веб построен ровно до этапа **R1 (только чтение)**, как записано в спеке: этапы R2…R5 в плане стоят «после» серверных задач A2…A6, их ещё никто не начинал.
2. Бот уже закрывает весь ивент-центр сайтов и больше (сравнительная таблица 13.10). Веб отстаёт от бота: в нём нет ни одного действия, которое что-то меняет.
3. Точный образец для веба есть: форма мастера сайта (PHP + JS) и записанные правила (`event_center_logic…`), которые бот уже повторил. Чтобы веб не стал третьей версией этих правил, их нужно один раз вынести на сервер (A3).

## 2. Что есть в вебе сейчас (R1, на проде с 14.10)

Вход (пароль, ссылка из бота, «забыли пароль», новый пароль и приглашение по письму), выбор организации, список мероприятий с цифрами, карточка мероприятия, карточка сеанса (категории только на чтение), CSV мероприятия и сеанса, образец билета, список заказов с поиском (в теле запроса) и карточка заказа со статусом писем, ссылка на бота уведомлений, языки en/ru/es, установка как приложение (PWA), диалог повторного пароля (механизм готов, экранов с деньгами нет).

## 4. Серверные задачи, без которых экраны не собрать

| № | Задача | Размер | Нужна для |
|---|---|---|---|
| S1 | WEB-LIST: цифры продаж пачкой для списка мероприятий (сейчас до 10 запросов на экран) | S | быстрый список |
| S2 | WEB-ORDER-EVENT: имя мероприятия и время сеанса в `GET …/orders/{id}` | S | карточка заказа, возврат |
| S3 | A2: приглашение в команду с каналом `web` или `telegram` (организатор без Telegram получает письмо со ссылкой в веб) | M | команда |
| S4 | A3: «план мероприятия» — один серверный слой правил мастера (проверка полей, дат, цепочек и ступеней, афиши, значения по умолчанию, чтение мероприятия обратно в форму). | S5 | A4: чтение афиши на сервере. Ключ модели не может быть в браузере; сейчас он только у бота | M | мастер |

| S8 | WEB-AUTH-1: сессия не в `localStorage`, а в httpOnly-cookie с прокси и защитой от подделки запроса (или явное решение владельца оставить как есть) | M–L | деньги (R5) |

Что уже есть и ничего не требует: вход по ссылке, повторный пароль, поиск в теле, права организации `GET …/me`, все маршруты R3–R5 бота (промокоды, пригласительные, команда через `bot-team`, возвраты, очередь, категории, сеансы, статус, `change-impact`, данные организации).

## 5. План (заменён общим планом)

Принцип «точно как на сайтах и в боте» (без отступлений): на каждый экран весь тот же набор правил, что у бота, и тот же сценарий проверки.

1. **Правила переносятся целиком:** отдельные слова подтверждения для необратимого (отмена заказа, отмена сеанса, удаление, аннулирование), «сначала сухой прогон, потом одно нажатие» (`change-impact`, `delete-impact`), календарь с подтверждением даты, «контакт организатора для писем» при `organization.contact_missing`, понятные тексты при блоке сайтов (`session.change_site_unsupported`), права на каждый экран по `GET …/me`, тексты по стандарту (`docs/text_style_standard_ru.md`).
2. **Проверка:** для каждой функции бота есть e2e. Каждый экран веба получает близнеца: тот же сценарий через настоящий API (Playwright против живого бэкенда), и строка матрицы паритета не получает фазу «готово», пока близнец не зелёный. Тест сверки с OpenAPI уже существует.
3. **Порядок и зависимости:**

| Этап | Что | Зависит от | Размер |
|---|---|---|---|
| 0 | S1, S2, строка «Данные организации» в матрице, добор R1 по замечаниям живого использования | — | 1–2 дня |
| 1 | **R3**: повторная отправка, отмена неоплаченного, промокоды, пригласительные, команда (S3), промоутеры, данные организации | S3 | 4–5 дней |
| 1′ | Параллельно, на сервере: S4, S5, S6, S7 (код бота `wizard*.go` не трогает никто другой в это время) | — | 5–6 дней |
| 2 | **R4**: статус мероприятия, перенос и отмена сеанса, конец продаж и «вход с», категории | R3 (общие компоненты) | 4 дня |
| 3 | **R2**: мастер и правка, копия, афиша | S4–S7 | 6–8 дней |
| 4 | **R5**: возврат по заказу, очередь «Возвраты», повтор | S8 (или решение) | 5 дней |
| 5 | Материалы и письма ивента, XLSX | hosted-страница (HP-1…3) | по решению |

Оценки в рабочих днях одной сессии разработки без учёта независимой проверки (по правилу владельца деньги, права и публичные маршруты проходят проверку перед слиянием). Календарно с проверками ориентир 5–6 недель.

4. **Выкладка:** каждый этап — отдельный PR (или стопка PR, нижний не удалять до перенацеливания верхнего), после слияния выкат веба одним `application.deploy` приложения `event-center`; серверные части выкатываются с бэкендом, миграции в порядке номеров.

## 6. Риски (заменены общим планом)

1. Правила мастера в трёх местах → расхождения (как «кодген-дрейф»). Лекарство: S4 до R2.
2. A3 меняет боевой код мастера бота, которым пользуются сейчас: делать чистым переносом с теми же тестами, без изменения поведения, и прогнать на стенде.
3. Деньги в браузере: токен в `localStorage` при XSS даёт доступ. Сейчас смягчено строгим CSP и повторным паролем перед деньгами; полное решение — S8.
4. Ключ модели чтения афиши придётся дать api (сейчас только у бота) — это пересекается с разделением секретов по контейнерам: решить вместе.
5. Заказы сайтов как продавцов (перенос, отмена, возврат) остаются заблокированными и в боте, и в вебе до волны 2 плана бота. Веб обязан показывать то же честное объяснение.

2. Порядок этапов 1–4 по умолчанию такой, как в таблице (сначала повседневное, потом мастер, деньги последними). Нужен ли мастер раньше?
3. S8 (сессия в cookie с прокси) делать до денежных экранов или принять текущую защиту?
4. Ключ чтения афиши на api: согласны дать его api, когда будем разделять секреты?
5. Материалы и письма ивента (фото, видео, свой текст письма, просьба об отзыве) — в этот план или отдельной волной после hosted-страницы?
