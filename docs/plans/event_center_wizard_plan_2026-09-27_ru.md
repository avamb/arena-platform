# Ивент-центр: заведение мероприятий на сайтах — план (27.09.2026)

Цель: организатор заводит и правит мероприятия в ивент-центре своего WordPress-сайта
(вкладка «Ивенты» плагина `lampyris-ops`), Arena остаётся источником истины для продаж.
Сначала staging Vino&Co и staging Lampyris, потом прод. Волна 1 — без рассадки (GA),
волна 2 — с рассадкой по существующей схеме зала.

## Решения владельца 27.09

- Один мастер мероприятий для Vino и Lampyris (общий код `lampyris-ops`); на Lampyris к нему
  остаются шаги страницы сайта, туров и промоутеров.
- Несколько дат одного мероприятия — сразу в волне 1 («+ дата» копирует категории).
- Всё отрабатывается на staging (агент делает и проверяет сам), затем переносится на прод.

## Что есть сейчас (разведка 27.09)

- Вкладка «Arena» (`class-lops-arena.php`, одинаковая на Vino и Lampyris main): только создание
  через `POST /v1/organizations/{org}/imports/event-bundle`; одно событие = один сеанс; площадка
  вводится текстом; 3 пустые категории; цена `step=0.01`; одно окно продаж на сеанс; список —
  только созданные этой вкладкой; «редактирование» из локальной копии формы, не из Arena.
- Lampyris дополнительно имеет мастер мероприятий (WP-страница, туры, промоутеры) без Arena.
- Arena: event-bundle идемпотентен по `externalRef` (повторная отправка = правка), умеет площадку
  по id; НЕ умеет окна продаж по категориям, график цены, цепочку категорий, рассадку.
  Отдельные REST-методы (площадки, события, категории, график цены, схемы залов, привязка схемы)
  есть, ключу API нужны соответствующие scope.
- Сайты staging ходят в ПРОД-Arena через свои тестовые организации/каналы (Vino fid 8,
  Lampyris fid 2). Изменения Arena добавочные: пока их не используют, поведение прода не меняется.

## Волна 1 — мероприятия без рассадки

### Arena
1. **Цепочка категорий.** У категории «следующая категория»; когда её окно продаж закрывается,
   фоновая задача переносит свободные места в следующую и открывает её (лимит зала неизменен,
   места под незавершённой оплатой не трогаются). Заменяет разовый скрипт Ашдода.
2. **event-bundle:** у категории — своё окно продаж, `priceSchedule` (дата → цена), ссылка на
   следующую категорию, порядок; ответ отдаёт id категорий.
3. **Чтение для формы:** площадки организации со страной и городом, справочник стран/городов,
   текущее состояние события/сеанса/категорий (цены, графики, продано/свободно). Выдать ключам
   staging-организаций нужные scope.

### Плагин (общий код для обоих сайтов)
4. **Один вход «Ивенты»:** все мероприятия, поиск, фильтр «предстоящие / прошедшие»,
   кнопка «+ Мероприятие»; вкладка «Arena» убирается, слово Arena из интерфейса организатора тоже.
5. **Форма мероприятия:**
   - площадка: страна → город → площадка из списка; по умолчанию последняя выбранная;
     «+ новая площадка» — только если нужной нет;
   - цена — целое число в валюте, без копеек-степпера;
   - сразу одна категория, остальные — кнопкой;
   - выбор ценовой модели: «Цепочка категорий» (название, цена, количество, до какой даты
     продаётся → места переходят к следующей) или «Одна категория, цена по графику»
     (количество + строки «с даты — цена»);
   - несколько дат мероприятия: «+ дата» копирует категории.
6. **Правка:** карточка мероприятия открывает текущее состояние из Arena; сохранение =
   повторная отправка пакета с тем же `externalRef`.
7. **Мелочи из разговора с клиентом:** дата и время создания заказа рядом с номером;
   флаг «письмо не доставлено» снимается, если Brevo позже доставил; старые заказы Bil24
   не порождают вечных карточек.
   Если письмо не доставлено и доставить его нельзя (постоянный отказ: адреса нет, домен
   блокирует Brevo, ящик переполнен и повторы Brevo исчерпаны), карточка пишет это прямо и
   подсказывает администратору связаться с покупателем другим способом: показывает телефон
   покупателя с кнопками «позвонить» / WhatsApp, причину отказа человеческими словами
   («ящик переполнен», «почтовый сервер получателя не принимает наши письма») и предлагает
   отправить билеты на другой адрес или скачать PDF, чтобы переслать его в мессенджере.

### Проверка на staging (делаю сам)
- Создание GA-мероприятия через форму на staging Vino и staging Lampyris → проверка в Arena →
  синхронизация каталога сайта → тестовая покупка (AllPay dev / Stripe test) → возврат.
- Цепочка категорий с окнами по 5 минут: переход мест и цены на сайте.
- Правка цены/количества/даты уже продающегося мероприятия.

### Прод
- Бэкенд Arena раскатывает владелец (правка тега образа + Deploy); плагин — пуш владельца +
  Deploy сайтов. Потом Ашдод переводится на цепочку, таймер снимается.

## Волна 2 — с рассадкой по существующей схеме

- В форме: у площадки со схемой — «Рассадка: без мест / по схеме зала», список схем площадки.
- Категории схемы (из легенды) сопоставляются с ценовыми категориями мероприятия
  (по умолчанию 1:1 с названиями из схемы), цена задаётся на категорию.
- Arena: привязка схемы к сеансу через пакет (`seatingPlanId` + сопоставление категорий),
  повторная отправка не пересоздаёт места, если схема не менялась.
- Ограничение: цепочка категорий переносит только места без номера; у мест по схеме повышение
  цены делается графиком цены (место остаётся своим).
- Проверка: тестовое мероприятие на staging в зале со схемой (Lampyris: Palác Akropolis,
  Vino: Ашдод), покупка места, скан.
