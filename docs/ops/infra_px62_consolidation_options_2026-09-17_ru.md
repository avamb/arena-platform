### Спецификация PX62-NVMe (по каталогу Hetzner, линейка снята с продажи ~2021)

Intel Xeon E-2176G (6 ядер / 12 потоков, 3.7–4.7 GHz, 2018 г.), 64 GB DDR4 ECC, 2 × 960 GB NVMe Datacenter, 1 Gbit/s. Обычно ставится с software RAID 1 (`md`), но фактическая раскладка — UNKNOWN. Дополнительный **480 GB 3D XPoint** = Intel Optane DC P4800X, отдельное PCIe-устройство; Hetzner ставил его как опцию под нагруженные БД.

### UNKNOWN / NEEDS ACCESS — обязательно выяснить до любого решения

- Раскладка дисков и RAID: `lsblk`, `cat /proc/mdstat`, `df -h`, `mount`, что именно лежит на XPoint (data dir БД? WAL/redo? кэш? логи? ничего?).
- ОС, версия Java, как запущено приложение (systemd/Tomcat/Docker), где его данные и логи.
- СУБД (PostgreSQL/MySQL?), размер, где data dir, есть ли репликация.
- Реальная нагрузка: CPU/RAM/IO за неделю (`sar`, `iostat`), свободное место.
- Reverse proxy и место терминации TLS (nginx/Apache/Java напрямую), что слушает 8443.
- Бэкапы: что и как уходит на BX21 (rsync/borg/pg_dump?), retention, был ли restore.
- Firewall: Hetzner Robot Firewall и/или ufw/iptables, allowlist по IP для SSH.
- Есть ли Docker, cron-задачи, дополнительные сервисы (почта, очереди, Redis).
- Кто администрирует сервер сейчас, есть ли документация, где хранятся секреты, Stripe-ключи.
- Есть ли зависимость Beget-хоста (сайт/кабинет) от API на PX62 и наоборот.

## 2. Что мешает превратить PX62 в общий сервер прямо сейчас (блокеры)

0. **Платформа несовместима с нашим стеком.** Все наши проекты — Linux (Ubuntu 24.04 / Debian 13) + Docker/Compose + Dokploy + Traefik: WordPress (образ `wordpress`, Apache+PHP), MySQL 8.4, Redis, n8n, arena-api (Go, образ из GHCR), MACS (Python/Next.js + MongoDB), боты. Ничего из этого не запускается на Windows Server напрямую. Чтобы «поставить наше» на PX62, пришлось бы:
   - создать под Hyper-V **отдельную Linux-ВМ** (Ubuntu 24.04, Gen2, например 6–8 vCPU / 32–48 GB / 300+ GB VHDX на NVMe), внутри — Docker + Dokploy как remote server, Traefik;
   - решить сетевой вопрос: у сервера один IPv4, который уже занят Windows-хостом и ВМ Bil24 (443/8443). Либо проброс портов 80/443 с Windows-хоста в Linux-ВМ (тогда Bil24 должен уйти с 443, либо перед всеми стоит один reverse proxy), либо **дополнительный IPv4 в Robot** (≈ €1.70/мес + разовая плата, с MAC-адресом для ВМ);
   - взять на себя обслуживание Windows-хоста: лицензия Windows Server (у Hetzner — платный аддон, в текущем счёте не показана — уточнить, кто платит), обновления, RDP-поверхность, Hyper-V-бэкапы (Windows Server Backup/чекпоинты), которые не совместимы с restic/Dokploy-бэкапами;
   - принять двойную виртуализацию: Docker в Linux-ВМ под Hyper-V — работает, но с накладными расходами на IO/сеть и без прямого доступа к NVMe (VHDX поверх NTFS или pass-through-диск).
   Итог: PX62 в текущем виде — это **Windows-сервер чужого проекта**, а не Linux-хост, который можно «взять под себя». Единственный путь сделать его нашим — переустановить на Linux целиком, что уничтожает Bil24 и требует его полного переноса (тогда проще взять новый, дешевле и мощнее).
1. **Нет доступа и нет знаний о системе.** Получить root можно через Hetzner Robot (rescue-режим → сброс пароля/добавление ключа), но это вмешательство в чужую рабочую систему без понимания, что и как там сломается. Сначала — доступ по договорённости с текущим админом, инвентаризация, потом что-либо ещё.
2. **Неизвестное использование XPoint-диска.** Если на нём data dir БД или WAL, его удаление = миграция БД на NVMe и остановка платформы. Удалять «вслепую» нельзя.
3. **Java-платформа со Stripe = обработка платежей.** Совмещение с чужими WordPress, n8n и ботами на одном ядре расширяет blast radius инцидента (в audit уже есть ransom-note в одной из БД и открытые порты). Клиентские магазины со Stripe (lampyris, minimaldeco) + Bil24 Stripe на одной машине — концентрация платёжной поверхности.
4. **Возраст и цена железа.** Xeon E-2176G 2018 г. за €87.65 при том, что новый EX44 (i5-13500, 14 ядер, 64 GB, 2×512 NVMe) стоил ≈ €44, AX41-NVMe ≈ €42, AX42 (Ryzen 7 PRO 8700GE, DDR5 ECC) ≈ €49 (+€39 setup) до переоценки 15.06.2026 — уточнить в Robot. «Legacy-цена» PX62 не выгодна: это ~2× переплата за более слабый и старый сервер без гарантии, что NVMe 2018–2019 гг. не на исходе ресурса.
5. **Единственный IPv4 и уже занятые 443/8443.** Чтобы посадить рядом Traefik/Dokploy, Bil24 придётся перевести за общий reverse proxy — изменение конфигурации живой платёжной системы.
6. **Нет Dokploy/Docker (предположительно).** Всё, что мы умеем деплоить, живёт в Dokploy-парадигме; на PX62 её нет — придётся устанавливать поверх неизвестной ОС.
7. **Беспорядок на текущих серверах ещё не разобран** (бэкапы, OOM, ransom-note). Переезд «в одну коробку» перенесёт этот беспорядок, а не решит.

## 3. Варианты

Базовая стоимость сегодня: облако ≈ €50/мес (4 сервера) + PX62-контур €147.55 + SSL ≈ €12.5/мес ≈ **€210/мес** суммарно, без рабочих бэкапов и мониторинга.

### A. PX62 — главный общий сервер для всего

Архитектура:

```
Internet → Cloudflare (для наших доменов) / прямой DNS (bil24.pro)
        → один IPv4 PX62
        → Traefik (Docker) на 80/443
            ├─ Bil24 Java (host-процесс или контейнер), api.bil24.pro
            ├─ WP-стеки (compose на сайт: WP + MariaDB/MySQL + Redis)
            ├─ arena-backend, MACS, боты, pr-top, umami
            ├─ n8n + Postgres + Redis
            └─ staging-стеки
        Dokploy (локально, на этом же хосте)
        Бэкапы → BX21 Storage Box (borg/restic + Dokploy S3-совместимый или SFTP)
```

Ресурсы: 6C/12T, 64 GB — по RAM хватит на всё (сейчас суммарно используется ~15 GB), по CPU — впритык при пиках WooCommerce + n8n + Java (сравнимо с 3 сегодняшними VPS вместе). 2×960 GB NVMe — достаточно (все тома сейчас ~70 GB).

| Стоимость | €100.25/мес (PX62 + IPv4 + BX21, без XPoint) или €147.55 с XPoint; облако отменяется (−€50). Итого **≈ €100–148**, экономия €60–110/мес относительно сегодня |
| Производительность | достаточно для текущей нагрузки; один NVMe-массив на всё; без резерва CPU под рост |

| Безопасность | Docker-изоляция достаточна для *своих* доверенных проектов при лимитах/сетях/non-root, но не эквивалент VM; Bil24-платежи и клиентские магазины делят ядро и proxy |

С учётом Hyper-V/Windows Server схема выше реализуема только как «Linux-ВМ внутри Windows-хоста чужого проекта» — это добавляет слой виртуализации, лицензию и администрирование Windows, и всё равно оставляет один физический SPOF.

### D. Убрать PX62, Bil24 переезжает на облачный VPS, остальное — Option 2 аудита

## 4. Ответы на поставленные вопросы

- **Достаточно ли Docker-изоляции?** Для собственных доверенных стеков — да, при обязательных: лимиты памяти/CPU, отдельные сети, non-root, read-only где можно, без `docker.sock` в приложениях, отдельные БД/учётки/тома. Это защита от «соседского» OOM и утечки данных по ошибке, но не от эксплуатации ядра. Платёжные системы (Bil24 Stripe, магазины) и «экспериментальные» AI/боты лучше не держать на одном ядре — это ровно та причина, по которой бриф хотел разделить контуры.
- **Что должно оставаться на отдельных серверах?** Dokploy control plane; WordPress-магазины клиентов; Bil24 (пока жив); всё остальное — по вкусу.
- **Ёмкость.** Сегодняшняя суммарная реальная нагрузка ≈ 15 GB RAM, ~3–4 vCPU в пике. PX62 (64 GB) вместил бы всё с запасом по памяти; облачный набор из Option 2 даёт 32–40 GB суммарно и растёт добавлением worker'ов.
- **Восстановление при отказе физического сервера.** Dedicated не имеет snapshot-ов; спасение — только собственные бэкапы на BX21/Object Storage + написанный и **проверенный** сценарий пересборки. У облака есть snapshot/rebuild за минуты. Именно поэтому один dedicated под всё без отработанного restore — самый рискованный сценарий из четырёх.
- **Выгодна ли legacy-цена PX62?** Нет: €87.65 за 6 ядер 2018 г. против ≈ €44–49 за 14–16 современных ядер. Даже если нужен именно dedicated — выгоднее новый EX44/AX42 или Server Auction, чем удерживать PX62.
- **XPoint за €47.30.** Экономически — снимать хочется, но при трёх ВМ с Veeam вероятность, что на Optane лежит VHDX базы данных (ради чего его и ставят), высокая. Снятие диска = остановка ВМ, перенос VHDX на NVMe-массив, перенастройка Veeam-цепочки (инкременты привязаны к дискам/путям), возможно — перепривязка лицензий, если они смотрят на конфигурацию железа. Решение принимает только разработчик Bil24 после чек-листа §8.1; без его подтверждения «на XPoint ничего критичного нет» диск не трогать.
- **Платный SSL (≈ €150/год).** На Windows-стеке Let's Encrypt тоже работает (win-acme/Certify для IIS, или на reverse proxy перед Java), но замена затрагивает ВМ сервера приложения, Java-keystore и, возможно, сканеры/мобильные клиенты с pinning. Wildcard оплачен до 27.02.2027 — вопрос к разработчику к концу 2026: есть ли техническая причина держать AlphaSSL; если нет — перевести на LE при плановом обслуживании, а не сейчас.
- **Veeam.** Это плюс: у Bil24 есть настоящая система бэкапов ВМ. Нужно только подтвердить, что репозиторий Veeam **вне** PX62 (на BX21) и что restore проверялся; если репозиторий на том же сервере — при отказе железа бэкапы уйдут вместе с ним.

## 5. Риски миграции (для C и D)

| Риск | Смягчение |
|---|---|
| Получение root на PX62 через rescue без ведома текущего админа ломает работающие процессы/скрипты | Только по договорённости; сначала read-only инвентаризация из §8 руками админа |
| Неизвестный формат/размер БД Bil24, зависимость от Optane | Дамп + тестовое восстановление на временном CX33 до переключения DNS |
| Stripe: webhooks/секреты/IP-ограничения привязаны к старому origin | Инвентаризация Stripe Dashboard; тестовый платёж на новом хосте до переключения |
| `api.bil24.pro` без Cloudflare (прямой A на Hetzner) — при переезде TTL DNS имеет значение | Заранее снизить TTL до 300 с, либо завести зону в Cloudflare |
| Сканеры/мобильные клиенты Bil24 могут иметь захардкоженный IP/порт 8443 | Спросить админа; держать старый сервер параллельно 1–2 недели |
| Beget-хост (сайт/кабинет) может обращаться к API по IP | Проверить конфиги на Beget |
| Закрытие Bil24 «в какой-то момент» обесценивает усилия по переносу | Если закрытие в горизонте ≤ 6 мес — выбрать B (ничего не трогать) и просто снять XPoint/SSL; если > 6 мес — D |

## 6. Рекомендация (обновлена 17.09.2026 после ответа разработчика Bil24)

**Итог: PX62 — не кандидат ни на консолидацию, ни на перенос. Это закрытая Windows/Hyper-V-система из трёх ВМ с аппаратно привязанными лицензиями и своим Veeam-бэкапом; она живёт ровно до тех пор, пока живёт Bil24, и умирает вместе с ним.** Наша инфраструктура строится независимо от него — по Option 2 аудита (`infra_audit_2026-09-17_ru.md`, §10), бюджет ≈ €52–57/мес.

Что остаётся по PX62:
- **Вариант B до закрытия Bil24** — единственный рабочий сценарий. Никаких «возьмём сервер под себя».
- Рычаги экономии на PX62 только три, и все требуют решения разработчика Bil24: (а) XPoint-диск, если он не под базой и не в цепочке Veeam; (б) не продлевать AlphaSSL после 02.2027, если нет pinning-зависимостей; (в) дата закрытия Bil24 — в этот день отменяются PX62 + IPv4 + XPoint + BX21 (−€147.55/мес).
- До закрытия стоит получить от разработчика: где репозиторий Veeam, когда был последний успешный restore-тест, и хотя бы read-only учётку в Hetzner Robot (SMART-статус дисков 2018–2019 гг., Robot Firewall).
- Windows-лицензия Hetzner (если оформлена как аддон) в присланном списке расходов отсутствует — уточнить, кто и сколько за неё платит; это может быть ещё €20–40/мес поверх €147.55.

Первоначальный пошаговый план (сохранён для истории):

1. **Сейчас (0–2 недели):** вариант **B как переходный** — PX62 не трогаем, параллельно выполняем фазу 0–1 аудита по облаку (бэкапы, firewall, ротация паролей). Через Hetzner Robot проверить: включён ли Robot Firewall, есть ли Backup Space/BX21 привязка, состояние SMART-мониторинга дисков (Robot показывает).
2. **Получить от текущего администратора Bil24** результаты чек-листа §8 и доступ (свой ключ). Без этого решение по XPoint и по переезду не принимать.
3. **Если Bil24 живёт ещё ≥ 6 месяцев → D**: перенос Bil24 на CX33/CX43 в общий Dokploy (remote server), затем отмена PX62 + XPoint + IPv4; BX21 либо оставить как единое бэкап-хранилище (SFTP/restic для всех серверов), либо заменить на BX11/Object Storage. Целевой бюджет ≈ €60–80/мес на всю инфраструктуру.
4. **Если Bil24 закрывается в ближайшие месяцы → B до конца, потом просто удалить PX62.** Переносить умирающую платформу бессмысленно.
5. **Если очень хочется один мощный хост под apps/n8n/AI** — брать **новый** EX44/AX42 (≈ €44–49) как Apps-worker в Option 2, а не наследовать PX62; legacy CPX31 lead-parser тогда можно отменить. Клиентские WP и control plane всё равно держать отдельно.
6. **Вариант A не рекомендую** ни при каком сценарии: он повторяет ошибку lead-parser (всё на одном хосте), только на более дорогом и старом железе, и с учётом Hyper-V/Windows Server — ещё и на чужой платформе, которую наш Linux/Docker-стек не использует.
7. **Про Bil24 внутри Hyper-V при варианте D.** Раз Bil24 — это ВМ, перенос упрощается: вместо миграции приложения по частям можно **экспортировать ВМ целиком** (VHDX) и запустить её на Linux-хосте под KVM/QEMU (конвертация `qemu-img convert -O qcow2`) на облачном CX43 с вложенной виртуализацией — Hetzner Cloud её поддерживает, либо на новом дешёвом dedicated (AX41/EX44). Если ВМ Bil24 сама на Windows Server — нужна лицензия и остаётся Windows-администрирование, но уже только для одной ВМ, а не для всего парка; если внутри ВМ Linux — ещё проще, ставим её как обычный сервер. Первый вопрос разработчику: **какая ОС внутри ВМ Bil24 и сколько ВМ всего на хосте.**

## 8. Read-only чек-лист для администратора PX62 (выполнить и прислать вывод)

### 8.1 Хост Windows Server / Hyper-V (PowerShell от администратора)

```powershell
Get-ComputerInfo | Select-Object OsName, OsVersion, CsTotalPhysicalMemory, CsNumberOfLogicalProcessors
Get-VM | Select-Object Name, State, ProcessorCount, MemoryAssigned, Uptime, Generation, Version
Get-VM | Get-VMHardDiskDrive | Select-Object VMName, Path, ControllerType
Get-VM | Get-VMNetworkAdapter | Select-Object VMName, SwitchName, IPAddresses, MacAddress
Get-VMSwitch | Select-Object Name, SwitchType, NetAdapterInterfaceDescription
Get-Disk | Select-Object Number, FriendlyName, Size, PartitionStyle, HealthStatus, OperationalStatus
Get-PhysicalDisk | Select-Object FriendlyName, MediaType, BusType, Size, HealthStatus
Get-StoragePool -IsPrimordial $false -ErrorAction SilentlyContinue | Get-VirtualDisk | Select-Object FriendlyName, ResiliencySettingName, Size
Get-Volume | Select-Object DriveLetter, FileSystemLabel, FileSystem, Size, SizeRemaining
Get-NetNat; Get-NetNatStaticMapping -ErrorAction SilentlyContinue
Get-NetTCPConnection -State Listen | Select-Object LocalAddress, LocalPort, OwningProcess | Sort-Object LocalPort -Unique
Get-NetFirewallProfile | Select-Object Name, Enabled, DefaultInboundAction
Get-ScheduledTask | Where-Object State -ne Disabled | Select-Object TaskName, TaskPath
Get-WBSummary -ErrorAction SilentlyContinue        # Windows Server Backup
Get-VM | Get-VMSnapshot | Select-Object VMName, Name, CreationTime
Get-Counter '\Processor(_Total)\% Processor Time','\Memory\Available MBytes','\PhysicalDisk(_Total)\Avg. Disk Queue Length' -SampleInterval 5 -MaxSamples 6
```

Что смотреть: сколько ВМ и какая ОС в каждой; где лежат VHDX (на NVMe-массиве или на XPoint-диске); тип RAID (Storage Spaces / контроллер / нет); NAT-правила и как проброшены 443/8443; есть ли резервное копирование ВМ и куда (BX21?); здоровье дисков.

### 8.2 Внутри ВМ Bil24 (если Linux)

