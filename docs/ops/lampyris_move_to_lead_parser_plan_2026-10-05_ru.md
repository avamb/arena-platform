## 3. Подготовка (за день-два, сайт работает)

### 3.1. Шаги 1 и 2: `performance_schema` и бинарные логи

Что делает `lampyris-db-prepare.sh apply`:
1. Отказывается работать, если нет свежего (моложе 26 ч) бэкапа базы в `/var/backups/wp-sites/lampyris` или если подключена реплика.
2. `SET PERSIST binlog_expire_logs_seconds = 259200` (3 суток вместо 30) и `SET PERSIST_ONLY performance_schema = OFF`. Настройки пишутся в `mysqld-auto.cnf` внутри тома и переезжают вместе с данными, compose не меняется.
3. `FLUSH BINARY LOGS`, затем `PURGE BINARY LOGS TO <текущий>`: удаляются все старые логи (сейчас 6 файлов, 4,27 ГБ). Реплик и восстановления «на момент времени» нет, бэкапы делаются дампом.
4. Перезапускает контейнер БД (**сайт без базы ~20–40 секунд**), ждёт `healthy`, печатает состояние и проверяет, что WordPress достучался до базы и сайт отвечает.

Ожидаемый результат: каталог MySQL 5,0 ГБ → ~0,5–0,6 ГБ, память БД ~810 МБ → ~570 МБ.

Запуск (из PowerShell, в тихий час):

```powershell
Get-Content C:\Projects\arena_new\ops\wordpress\lampyris-db-prepare.sh -Raw | ssh lampyrisevents 'tr -d "\r" | sh -s apply'
```

Отчёт без изменений: то же без `apply`. Только проверка сайта и базы: `sh -s alive`.

Необязательно, по образцу остальных сайтов (02.10): `SET PERSIST innodb_log_buffer_size = 16777216` (сейчас 64 МБ) и `SET PERSIST max_connections = 60` (сейчас 151, процессов Apache 20). В скрипт не включено.

## 4. Новый стек на lead-parser (сайт ещё на старом месте)

Создаём **новый** compose, а не переназначаем старый: тогда откат остаётся одним переключением DNS, а старый стек нетронут.

1. Панель Dokploy (tRPC, как для iltabia): в проекте `lampyris` создать compose `wordpress-lp` на сервере `lead-parser`, источник github `avamb/lampyrisevents`, ветка `main`, `./docker-compose.yml`, `isolatedDeployment=true`, автодеплой **выключен**.
2. Окружение: те же ключи и значения, что у старого compose. **Перед Deploy проверить, что значения читаются как обычный текст**, не как `enc:v1:` (так Marina лишилась пароля БД и лежала час). Пароль БД должен остаться тем же, что в старом томе, иначе WordPress не войдёт.
3. Файловый mount `files/uploads.ini` с тем же содержимым.
4. Домены `lampyrisevents.com` и `www.lampyrisevents.com`, Let's Encrypt. Пока DNS указывает на старый хост, сертификат не выдастся (403), это ожидаемо, см. шаг 6.
5. Deploy (первая сборка образа). Он создаст тома и пустую базу. Затем остановить все три контейнера: нужны только созданные тома.
6. AppName нового compose получит случайный суффикс. Имена контейнеров далее: `<appName>-wordpress-1`, `-wp_db-1`, `-wp_redis-1`, имена томов `<appName>_wp_app`, `_wp_data`. Записать их, они нужны ниже как `NEW_WP`, `NEW_DB`, `NEW_APP_VOL`, `NEW_DB_VOL`.

## 5. Прогревочное копирование (сайт работает)

Между серверами нет ключа. Временный: сгенерировать `ed25519` на lampyrisevents, добавить публичную часть в `authorized_keys` на lead-parser с комментарием `lampyris-move 2026-10-05`, после переезда убрать с обоих концов.

На lampyrisevents:

```sh
rsync -aHAX --numeric-ids --info=progress2 /var/lib/docker/volumes/lampyrisevents-wordpress-ozgyu1_wp_app/_data/  root@78.46.176.249:/var/lib/docker/volumes/<NEW_APP_VOL>/_data/
rsync -aHAX --numeric-ids --info=progress2 /var/lib/docker/volumes/lampyrisevents-wordpress-ozgyu1_wp_data/_data/ root@78.46.176.249:/var/lib/docker/volumes/<NEW_DB_VOL>/_data/
```

Копия базы «на горячую» не годится как итоговая (файлы в движении), она нужна, чтобы финальный проход в окне был коротким. После шага 3.1 это ~0,6 ГБ вместо 5 ГБ.

## 8. После переезда

На lead-parser:
- В `crontab -e` root добавить `* * * * * docker exec --user www-data <NEW_WP> php /var/www/html/wp-cron.php >/dev/null 2>&1`.
- В `ops/backup/wp-sites-backup.sh` (встроенная таблица `SITES`) добавить строку `lampyris|<NEW_WP>|<NEW_DB>|<NEW_APP_VOL>` и раздать скрипт на lead-parser. Файла `/etc/wp-sites-backup.sites` на lead-parser нет, поэтому берётся встроенная таблица. Проверка свежести `backup-check.sh` уже знает `lampyris` и менять не нужно.
- Убрать временный ключ.

На lampyrisevents:
- Убрать из crontab строку `wp-cron` для старого прод-контейнера.
- В `/etc/wp-sites-backup.sites` убрать строку `lampyris` только после первой успешной ночи нового бэкапа (R2 хранит оба набора в одном префиксе, дубликата не опасаться).
- Старый стек держать остановленным (`docker stop`, не `down -v`) 14 дней, потом удалить тома `lampyrisevents-wordpress-ozgyu1_*` (освободит ~7,5 ГБ).
- В панели у старого compose выключить автодеплой и пометить как «старый».

В репозитории: `AGENTS.md` и заметка в памяти о новом месте, id нового compose и appName.

## 10. Риски и что не проверено

- Поведение API панели при создании compose (известная ловушка: `compose.create` дописывает случайный суффикс к appName, `compose.update` его не меняет, правится SQL в базе панели на arena-macs) и наличие автодеплоя у старого compose: проверить на месте.
- IP-ограничения у внешних сервисов (раздел 3.2): ключевой неизвестный.
- Сборка образа на lead-parser под рабочим трафиком.
- Чужой Traefik: на lead-parser один Traefik на все сайты, перезапуск контейнера WordPress не должен его затрагивать, но сертификат нового хоста просит именно он.
- Оценка ёмкости основана на моментальном замере в дневной час. Замер пиков трафика недоступен (журнал доступа Traefik выключен, токен Cloudflare без прав на аналитику, логи контейнера обнуляются при деплое). Нагрузку по заказам Arena оценил по базе.
- Ёмкость lead-parser под ПИКОВЫЙ день продаж Lampyris (например, старт крупного события одновременно с акцией Vino) не проверялась нагрузочным тестом.
