# Магазин: уведомления логисту и письма покупателю

Спека: `08_architecture/47_merch_shop_module_ru.md`, раздел 7. Миграция 0173.

## Что происходит при оплате

Оплаченный заказ магазина (`v1.shop.order.paid`) делает две вещи независимо друг от друга (письма покупателю бывают трёх видов: `shop_order_received`, `shop_order_shipped` и `shop_order_refunded`, см. ниже):

1. В той же транзакции, что помечает заказ оплаченным, кладётся задание `shop.order_email` (письмо `shop_order_received`). При «Отправлен» кладётся второе задание (`shop_order_shipped`), повторное нажатие «Отправлен» только меняет заметку и письма не шлёт. Письмо уходит из `arena-worker`, язык берётся из `shop_orders.buyer_locale` (нет такого шаблона — английский), Reply-To — `shop_settings.contact_email`. Адрес организации (`organizations.contact_email`) в письмо не попадает никогда.
2. Звено `salesnotify` в `arena-worker` шлёт сообщение в Telegram в чаты, у которых в `kinds` есть `shop` (заказ — строка по порядку формы курьера: имя, телефон, город, адрес 1, адрес 2, индекс, затем состав, доставка, заметка покупателя). Возврат (`v1.shop.order.refunded`) — отдельное короткое сообщение. Платёж, пришедший после конца брони, когда товара уже нет (`v1.shop.order.manual_review`, заказ ждёт решения организатора), — сообщение «Shop order needs your attention» (ключ `shop_review:<order id>`), покупателю письма нет. Операторский алерт об этом шлёт ops watchdog, а не это звено.

### Третье письмо: возврат (`shop_order_refunded`)

Когда возврат заказа переходит в `succeeded` (из ивент-центра, `POST .../shop/orders/{id}/refund`, или по вебхуку/`refund.sweep` позже), refund engine сводит его в заказ (`shop.Service.ProjectPaymentTx` / `SyncRefunds` → `syncRefundsTx`, статус `partially_refunded` или `refunded`). В той же транзакции, где сумма возвращённого выросла и пишется `v1.shop.order.refunded`, кладётся задание `shop.order_email` с `kind = refunded` и `refund_id` (`enqueueRefundEmailTx` в `internal/platform/shop/email.go`, под SAVEPOINT: письмо никогда не ломает возврат). Заказ без адреса покупателя письма не получает.

- Одно письмо на один возврат. Повтор (тот же возврат свёрнут в заказ ещё раз) заданий не добавляет, повторная доставка задания письмо не дублирует: воркер помнит отправку в `shop_orders.metadata` под ключом `email_refunded_<id возврата>_sent_at` (у остальных писем ключ без id). Частичный возврат, а затем остаток — два разных письма.
- Содержание: сумма этого возврата, сумма заказа, «возвращено всего» (строка только когда отличается от суммы этого возврата), состав заказа, ссылка на страницу заказа, контакт магазина (`shop_settings.contact_email`) и фраза, что деньги вернутся через платёжную систему на карту или способ оплаты покупателя, срок зависит от банка (даты не обещаем). Если возвратом (с учётом предыдущих) вернули весь заказ, письмо сообщает, что заказ возвращён полностью, и тема «Заказ № N возвращён»; иначе тема «Возврат по заказу № N» и сумма. «Всего возвращено» считается по возвратам, успешным к моменту этого возврата, поэтому запоздавшее или повторное письмо говорит то же, что первое.
- Шаблоны `shop_order_refunded.<locale>.tmpl` на всех семи языках (cs, de, en, es, fr, he, ru), оформление как у `shop_order_received`. Заказ в `manual_review` с возвратом тоже получает письмо (деньги ушли).
- Кнопка «Отправить письмо ещё раз» (`POST .../shop/orders/{id}/resend-email`, `{"kind":"refunded"}`) шлёт письмо о самом свежем успешном возврате; у заказа без успешного возврата ответ 409 `shop.order_email_unavailable`. Лимит прежний: один запрос в минуту на заказ.

Цифровой заказ (`delivery_kind = none`): в письме `shop_order_received` нет адреса и доставки, цифровые позиции — блок «Ваши файлы» со ссылкой на страницу результата, где кнопки скачивания (подписанные ссылки в письма не попадают). Письмо `shop_order_shipped` для такого заказа не отправляется. Каждое сообщение записывается один раз в `sales_notification_deliveries` (`shop_paid:<order id>`, `shop_refund:<order id>:<возвращено всего>`).

Бот тот же, что у продаж билетов (`SALES_TELEGRAM_BOT_TOKEN`), бот должен быть участником группы.

## Переменные окружения

| Переменная | Где | Зачем |
| --- | --- | --- |
| `SHOP_PUBLIC_BASE_URL` | `arena-worker` | Адрес витрины платформы. Ссылка на страницу результата заказа в письме: `<SHOP_PUBLIC_BASE_URL>/<slug организации>/checkout/result?checkout_token=<токен заказа>`. У организации с собственным `organizations.shop_domain` ссылка `https://<домен>/checkout/result?checkout_token=<токен>`. Пусто и домена нет — письмо уходит без ссылки. |
| `SALES_TELEGRAM_BOT_TOKEN` | `arena-worker` | Как для билетов. Пусто — Telegram-звено ничего не шлёт. |

Письма уходят только через настоящий почтовый sender (не `LogSender`), как и билеты.

## Группа логиста: строка в `sales_notification_subscriptions`

Подписок нет ни в API, ни в админке: это строки SQL. Один чат — одна строка (уникальность `org + chat_id`), поэтому «что слушает чат» задаёт массив `kinds`: `tickets` (продажи и возвраты билетов), `shop` (заказы магазина). Старые строки получили `{tickets}`.

Группа логиста организации (бот должен быть добавлен в группу заранее; id группы — число со знаком минус, супергруппа начинается с `-100`):

```sql
INSERT INTO sales_notification_subscriptions (org_id, name, chat_id, kinds)
VALUES ('<org uuid>', 'Логистика', '<chat id>', '{shop}');
```

Чат, которому нужны и билеты, и магазин:

```sql
INSERT INTO sales_notification_subscriptions (org_id, name, chat_id, kinds)
VALUES ('<org uuid>', 'Продажи', '<chat id>', '{tickets,shop}');
```

Изменить существующий чат:

```sql
UPDATE sales_notification_subscriptions
   SET kinds = '{tickets,shop}', updated_at = now()
 WHERE org_id = '<org uuid>' AND chat_id = '<chat id>';
```

Правила:

- `org_id NULL` — оператор: слышит магазины всех организаций (если в `kinds` есть `shop`).
- Переключатели `on_order_paid` и `on_ticket_refunded` работают для обоих видов: первый глушит сообщения об оплате, второй — о возвратах. По умолчанию оба включены.
- `allowed = false` отключает чат целиком.
- В `kinds` допустимы только `tickets` и `shop`, массив не пустой (иначе 23514).
- Чат только с `shop` не получает ни продажи билетов, ни сообщения контактной формы покупателя организатору (`AnnounceToOrg` идёт в чаты с `tickets`).
- Ошибка последней доставки (бота нет в группе и т.п.) видна в `last_error` строки.

## Проверка на стенде

1. Строка группы с `{shop}` (SQL выше), бот в группе.
2. Заказ через витрину, оплата в тестовом Stripe.
3. В группе одно сообщение «New shop order»; у покупателя письмо `shop_order_received`; повторная доставка вебхука второго сообщения и письма не даёт.
4. «Отправлен» в ивент-центре: письмо `shop_order_shipped` с заметкой отправления.
5. Возврат в ивент-центре (частичный, затем остаток): у покупателя два письма `shop_order_refunded` (второе «Заказ № N возвращён»), в `worker_jobs` по одному заданию `kind = refunded` на возврат.
6. Если сообщения нет: `SELECT last_error FROM sales_notification_subscriptions ...`, затем `SELECT * FROM worker_jobs WHERE job_type = 'shop.order_email' ORDER BY created_at DESC` для письма.
