# AutoForge backlog: перенос и отмена сеанса — письма покупателям, проверка афиши (волна SCN)

Updated: 2026-10-03
Status: **SCN-01..04 и SCN-09 реализованы 2026-10-03 (вариант 1: пока без сайтов-продавцов)**, остальное не начато.
Сделано: миграции 0121 (журнал, контакт) и 0122 (`session.update` менеджеру), пакет `sessionchange`, `change-impact`,
PUT контакта события, письмо Арены `session.change_email` (7 языков, новый PDF), бот «Сеансы: перенос и отмена».
Заказ с сайта-продавца (`webhook_subscribers` kind `bil24_wp`) пока блокирует перенос/отмену (`session.change_site_unsupported`) —
снимается SCN-05/06. Не сделано: SCN-05..08, SCN-10..13. Отступления от спеки: перенос только по `end_at` и правка вместимости
покупателю невидимы (письма нет); отмена всего ивента = отмена каждого сеанса.
Исходный статус документа: planning artifact. AutoForge исполняет записи features.db, а не этот файл;
импорт — отдельным скриптом при старте волны. Источник решения: владелец 2026-10-01 (обсуждение в сессии
после просьбы организатора «Учебный театр» перенести мастер-класс с 28.10 на 4.11).
Спецификация: `08_architecture/30_session_change_notifications_ru.md` — читать первой.

## Goal

Организатор переносит или отменяет сеанс, на котором уже есть оплаченные билеты, — и каждый покупатель
получает письмо **от того сайта, где покупал**, с новой датой и контактом организатора. Перенести или отменить
«без письма» нельзя ни из какого клиента. Афиша со старой датой или ценой не даёт опубликовать ивент.

## Owner decisions (не переобсуждать)

- Письмо пишет сайт-продавец (WordPress-сайты — сами, по событию от Арены); Арена пишет сама только заказам без
  сайта-продавца (страница продаж, виджет на чужом домене).
- «Перенести без письма» не существует: ни кнопки, ни ключа API. Блокировка на сервере, не в клиенте.
- Контакт организатора (адрес + телефон) обязателен на платформе; телефон можно скрыть. В письме: «напишите
  организатору, опишите ситуацию; организатор читает все письма». Возврат в письме не обещаем.
- Афиша: предупреждение + запрет публикации при явном несовпадении; у суперадмина есть «Афиша верна».
- Изменение для покупателя: дата, время, площадка, отмена сеанса.
- Отмена и перенос: организатору предлагается текст сообщения по умолчанию, он может править. Во всех клиентах:
  бот, ивент-центр на сайтах, админка.
- Просьбу про 4 ноября пока не трогаем (владелец говорит с организатором).

## Non-negotiable rules

- Guardrails `00_AGENT_GUARDRAILS.md`; ворота из `WAVE4_RUNBOOK.md` в каждой фиче: `go test ./...` без пайплайна,
  golangci-lint, gofmt на всех изменённых файлах включая integration-теги, admin-web test + type-check + build,
  codegen без дрейфа (openapi → types_gen.go → TS-клиент, регенерация после КАЖДОГО касания openapi.yaml), пин головы
  миграций, **push и проверка CI на именно этот коммит**.
- Письма покупателю — только через очередь задач; запись об изменении и постановка задач в одной транзакции.
- Данные покупателя (адрес, имя, телефон) не попадают в логи, метрики и URL.
- Любая новая запись `UPDATE sessions` с `start_at|end_at|venue_id|status` — только через `sessionchange`.
- Публичные маршруты за Cloudflare отвечают 503, а не 502.
- Билет по заказу, возвращённому вне Арены, не должен получать письмо — сначала отметить возврат (SCN-12).

## SCN-01. Контакт организатора обязателен

**Category:** Data / Organizations — MAJOR

Миграция: `organizations.contact_phone_hidden boolean not null default false`, `org_promoters.phone_hidden`
(то же). Правило контакта ивента: промоутер (если у него задан e-mail), иначе организация — **ждёт подтверждения
владельца (вопрос 1 спецификации §14)**. Адрес и телефон обязательны при создании организации и промоутера
(суперадминка, API, бот); для существующих — разовый отчёт «у кого нет контакта» (на проде 5 из 8 организаций без
e-mail). Публикация ивента и перенос/отмена сеанса с покупателями отвечают 422 `organization.contact_missing`.

Acceptance: создать организацию без адреса — 422; с телефоном и флагом «скрыть» — телефон не попадает в
ответы публичных страниц, письма и события; отчёт перечисляет пустые; тест на пин миграции; openapi + клиенты.

## SCN-02. Пакет `sessionchange` и журнал изменений

**Category:** Core / Catalog — BLOCKER

Таблицы `session_changes`, `session_change_notices` (спец. §10). Функция
`sessionchange.Apply(ctx, tx, old, new, notice)`: вид изменения (`date|time|venue|cancelled`, несколько сразу),
запись журнала, подбор заказов (`paid|partially_refunded` с действующим билетом, не пропуская приглашения),
выбор маршрута по каналу (`SubscriberByChannel`), постановка задач. Вызов из `hcatalog.HandleUpdateSession`,
`himports/import_arena.go`, `himports/import_exec.go`, отмены и мягкого удаления.

Acceptance: статический тест запрещает прямую запись времени/площадки/статуса сеанса вне пакета; транзакция с
изменением и постановкой задач атомарна (падение постановки откатывает перенос); сеанс без заказов —
запись без уведомлений; изменение вместимости или цены записи не создаёт.

## SCN-03. Сухой прогон `change-impact` и сообщение организатора

**Category:** API — MAJOR

`GET /v1/organizations/{org_id}/sessions/{session_id}/change-impact?start_at=&end_at=&venue_id=&status=`:
виды, число заказов и билетов, разбивка по маршрутам, наличие контакта, текст по умолчанию на языке организатора
(перенос и отмена — разные). Поле `notice.message` (до 1000 символов, обычный текст, экранируется) в PATCH сеанса и
в event-bundle (`changeMessage`). Тексты по умолчанию — ключи i18n (ru/en + остальные).

Acceptance: цифры совпадают с реальными заказами тестового сеанса; пустое сообщение допускается для переноса и
заменяется текстом по умолчанию; для отмены — то же; openapi с блочным YAML ошибок; описание каждого свойства.

## SCN-04. Письмо покупателю от Арены

**Category:** Delivery — MAJOR

Задача `session.change_email` на заказ, идемпотентна по `(change_id, order_id)`. Шаблоны `cs/de/en/es/fr/he/ru`,
перенос (с новым PDF, штрихкод прежний) и отмена (без PDF). Блок «Связаться с организатором», `Reply-To`
организатора, текст организатора под стандартным. Язык — `buyer_locale`.

Acceptance: интеграционный тест — перенос с двумя заказами со страницы продаж даёт два письма в заглушке
получателя; повторное сохранение не дублирует; в PDF новая дата и прежний штрихкод; отмена без вложения;
адрес не попадает в логи; ключи i18n во всех языках.

## SCN-05. Событие `order.session_changed` для WordPress-сайтов

**Category:** Gateway / Webhooks — MAJOR

`v1.order.session_changed` → `order.session_changed` в `bil24wire/dispatcher.go`, по одному на заказ с сайтовым
каналом; тело как `order.paid` (ticketList с обновлёнными данными) + блок `change` (спец. §6). Состояние
`delivered_to_site` при 2xx, повторы и мёртвая очередь как у остальных событий. Отмена — в дополнение к
`v1.session.cancelled`. Документировать в `docs/ops/bil24_gateway.md`.

Acceptance: тест с заглушкой подписчика: тело и подпись; недоступный сайт — перенос сохранён, состояние `failed`,
повторы идут; канал без сайта события не получает (его обслуживает SCN-04).

## SCN-06. Плагины WordPress: приём события и письмо покупателю

**Category:** WordPress plugins — MAJOR

Разведка в §13 спецификации: код сайтов — форк на общей основе, правки нужны в **двух** копиях (Lampyris, Vino&Co).
Приём `order.session_changed` в `mu-plugins/bil24-notification-receiver.php` (ID заказа в `data.id`);
идемпотентность по `change.id` в мете заказа (`_btm_last_change_id`); **обновление снимка**
`bil24_tickets[].actionEvent` из тела события (иначе повторная отправка и кабинет покажут старую дату);
письмо об изменении (`force=true`, новый шаблон, новый PDF, текст организатора, контакт организатора) и письмо
об отмене; строки на 9–10 языках; не трогать `_btm_sent_at`. Размеры: приём и снимок S, письмо об изменении M–L,
отмена M, переводы S–M, тесты и выкладка S–M.

Acceptance: на staging обоих сайтов перенос сеанса с оплаченным заказом даёт письмо с их домена и новой датой в
письме и PDF; повторная доставка события не шлёт второе письмо; «Отправить билеты повторно» после переноса
показывает новую дату; иврит на Vino читается (RTL); квота Brevo не превышается при пачке заказов; белый список
staging соблюдается.

## SCN-07. Факты афиши и `poster-check`

**Category:** Event center / Quality — MAJOR

Таблица `poster_facts` (по `media_id`), `POST /v1/organizations/{org_id}/events/{event_id}/poster-check`.
Читает `posterread`, сравнивает код (спец. §8): `block` — дата, время, цена не совпадают; `warning` — название,
площадка, город, возраст, не прочиталась. Нет значения на афише — не расхождение.

Acceptance: подставной читатель; таблица случаев (дата 28.10 против 04.11 = block, афиша без даты = ok,
сбой модели = warning); повторный вызов по той же афише не зовёт модель; ключ модели из `POSTER_LLM_API_KEY`.

## SCN-08. Ворота публикации по афише и «Афиша верна»

**Category:** Event center / Quality — MAJOR

Таблица `event_poster_checks`. Публикация (event-bundle с `publish:true`, публикация в канал) и правка
опубликованного ивента требуют вердикта `ok|warning|override` для текущих афиши и данных; устаревший
пересчитывается синхронно. `override` — только суперадмин (403 остальным), с причиной, в аудит.

Acceptance: ивент с афишей, где другая дата, не публикуется (422 `event.poster_mismatch`); после смены афиши или
данных — публикуется; `override` работает и пишется в аудит; организатор override не видит.

## SCN-09. Бот: сеансы как отдельный уровень, последствия, сообщение, афиша, отмена

**Category:** Telegram bot — MAJOR

Карточка ивента делится на два уровня (владелец 2026-10-01): **ивент** — название, описание, афиша, возраст, промоутер,
валюта; **сеанс** — дата и время, площадка, цены и категории, отмена. Сейчас в правке есть только «+ Дата» и «Цены и
категории»: нельзя ни изменить дату существующего сеанса, ни перенести, ни отменить его. Новая карточка: список
сеансов ивента (при одном сеансе — сразу его карточка), у сеанса кнопки «Дата и время», «Площадка», «Цены и категории»,
«Отменить сеанс». Строка по сеансу: продано / выдано, возвращено или отменено, действует, свободно, деньги.
Экран подтверждения изменения с цифрами из SCN-03, поле сообщения (по умолчанию/правка), единственная кнопка
«Перенести и уведомить» и «Отмена»; проверка афиши в мастере и в правке с кнопкой «Прислать новую афишу»;
отмена сеанса и ивента; сводка после рассылки (SCN-11). Тексты ru/en. Время по умолчанию при новой дате — время
предыдущей (сделано 2026-10-01, `7b3879d`).

**До SCN-02..05 «Дата и время» и «Отменить сеанс» для сеанса с оплаченными билетами в боте недоступны** (пишется
причина), для сеанса без продаж работают сразу: переноса без письма нет и временно тоже.

Acceptance: e2e через заглушку Telegram — перенос сеанса с проданными билетами: цифры, сообщение, без подтверждения
ничего не меняется; афиша с другой датой блокирует «Опубликовать изменения»; суперадмин видит «Афиша верна»; сеанс
без продаж переносится сразу; у ивента с несколькими сеансами выбирается нужный.

## SCN-11. Сводка доставки и тревога

**Category:** Ops — MINOR

«2 заказа: передано сайту 1, отправлено Ареной 1, ошибок 0» в боте и админке, «Повторить» для `failed`.
`ops.watchdog`: тревога на `session_change_notices` в `failed` дольше 30 минут и на мёртвую очередь события.

Acceptance: интеграционный тест состояний; тревога не содержит адресов покупателей.

## SCN-12. «Возврат вне системы»

**Category:** Orders / Refunds — MINOR

Кнопка в админке: отметить заказ возвращённым вне Арены (`refunds.settlement='external'`, билет гасится,
штрихкод перестаёт проходить). Нужна, чтобы тестовые и вручную возвращённые заказы не получали письма и не
считались проданными.

Acceptance: после отметки билет `refunded`, заказ не попадает в `change-impact`; запись в аудите; счётчик продаж
по сеансу уменьшается.

## SCN-13. Приёмка на staging и на проде

**Category:** QA — BLOCKER

Сценарии: (1) перенос сеанса с двумя заказами, один сайтовый, один со страницы продаж; (2) отмена с текстом
организатора; (3) афиша с другой датой блокирует публикацию, `override` её пропускает; (4) организация без
контакта получает 422; (5) недоступный сайт: перенос сохранён, повторы и тревога. Затем прод — по одному
организатору, с предупреждением владельцем.

Acceptance: все пять проходят на staging; журнал прогона в `docs/testing/`.
