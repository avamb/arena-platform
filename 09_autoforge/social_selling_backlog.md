# AutoForge backlog: продажи из Facebook и Instagram (волна SOC)

Updated: 2026-09-27
Status: planning artifact. AutoForge исполняет записи features.db, а не этот файл; импорт — отдельным
скриптом `09_autoforge/import_soc_social_selling_features.py` при старте волны. Голова очереди на момент
записи: 538 фич, priority 1095 — новая волна начинается с id 539, priority 1096.
Источник решения: владелец 2026-09-27 («запиши в бэклог, будем делать») по разбору вариантов продаж из
Facebook и Instagram; контекст — `docs/competitive/tickettailor_win_features_2026-09-27.md`.

## Goal

Человек видит рекламу или пост в Facebook/Instagram, нажимает ссылку и за минимальное число касаний
оплачивает билет; организатор видит, какая реклама и какой пост принесли продажу, а Meta получает
покупку для оптимизации рекламы.

Целевой путь покупателя: ссылка из рекламы → страница мероприятия уже с выбранными сеансом, категорией и
количеством → «Оплатить» → Stripe Checkout → билет. Два касания плюс ввод карты.

## Owner decisions (не переобсуждать)

- 2026-09-27: делаем в таком порядке — (1) ссылка сразу на оплату + сохранение источника + пиксель и
  серверное событие Meta; (2) Facebook-мероприятие с кнопкой «Билеты» и Instagram-стикеры — без разработки,
  инструкцией; (3) автоответ в Instagram «напиши БИЛЕТ» — второй этап.
- Покупка внутри Facebook/Instagram (Meta Shops checkout) и платёжные ссылки Stripe в обход arena — НЕ делаем:
  первое недоступно для билетов в ЕС, второе не держит места и не выпускает билеты.
- Организаторский UI живёт в ивент-центре (решение 2026-09-21). До его появления настройки пикселя и генератор
  ссылок делаются в суперадминке — владелец настраивает за организатора.

## Non-negotiable rules

- Guardrails `00_AGENT_GUARDRAILS.md`; все ворота из `WAVE4_RUNBOOK.md` в каждой фиче: `go test ./...` без
  пайплайна, golangci-lint, gofmt на всех изменённых файлах включая integration-теги, admin-web test +
  type-check + build, widget unit + e2e mock, codegen без дрейфа (openapi → types_gen.go → TS-клиент),
  пин головы миграций, **push и проверка CI на именно этот коммит**.
- Никаких персональных данных в логах, метриках и URL. E-mail и телефон уходят в Meta только
  нормализованными и SHA-256-хэшированными, только в серверном событии и только при наличии основания
  (SOC-05).
- Пиксель и любые сторонние скрипты на странице билетов грузятся только после согласия (SOC-05).
- Секреты Meta (access token CAPI) хранятся как секреты конфигурации организации и никогда не отдаются
  во фронт; в API — только признак «задан».
- Неизвестный или недоступный параметр ссылки никогда не ломает покупку: показывается обычный выбор билетов.
- Публичные маршруты за Cloudflare отвечают 503, а не 502 (AGENTS.md).

## SOC-01. Ссылка сразу на оплату: сеанс, категория, количество, промокод в URL

**Category:** Social selling / Checkout conversion — MAJOR

**Problem:** страница мероприятия понимает только путь и `?lang` —
`apps/tickets-page/src/lib/route.ts` (`/{org}/{event}`), `apps/tickets-page/src/main.ts:130`. Виджет
принимает `session-id`, но не категорию, количество и промокод (`apps/widget/src/ArenaTickets.svelte:5-12`).
Покупатель из рекламы начинает с выбора даты и категории — лишние касания на телефоне.

**Steps:**
1. Параметры страницы: `session` (UUID или целый system_id сеанса), `cat` (категория: UUID или system_id),
   `qty` (1–10, в пределах лимитов категории), `promo` (код). Страница передаёт их виджету атрибутами.
2. Виджет: новые атрибуты `category-id`, `qty`, `promo`. Если всё валидно и места есть — сразу экран
   с выбранной позицией и активной кнопкой «Оплатить»; промокод применяется через штатную проверку
   (`hcheckout.ValidatePromoForLines` → `CheckPromoLimits`), сумма показывается уже со скидкой.
3. Для рассадки `cat` открывает схему с подсвеченной категорией (места покупатель выбирает сам); `qty`
   игнорируется.
4. Любой невалидный, закрытый, распроданный или прошедший параметр → обычный выбор с короткой пометкой
   («Эта категория распродана, выберите другую»), без ошибки.
5. Параметры не теряются при возврате со Stripe (`checkout_token` уже переживает редирект — не ломать).

**Done when:** e2e (mock) — ссылка `?session&cat&qty=2&promo` открывает виджет на шаге оплаты с суммой со
скидкой; распроданная категория показывает выбор с пометкой; unit-тесты разбора параметров; скриншот
мобильной ширины 375 px.

## SOC-02. Источник заказа: UTM, fbclid и реферальная метка сохраняются в заказе

**Category:** Social selling / Attribution — MAJOR

**Problem:** в заказе нет источника. `orders.source` (миграция `0092_orders.sql:48`) описывает канал
продажи (`public_feed`, `bil24_gateway`…), а не рекламу; `widget_funnel_events` (0062) хранит только
тип события и токены. Организатор не видит, какой пост или объявление продали билет.

**Steps:**
1. Страница билетов при первом заходе читает `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`,
   `utm_term`, `fbclid`, `gclid`, `ttclid`, `ref` и хранит их в sessionStorage на 7 дней (last-touch),
   с областью по мероприятию, как `checkout_token`.
2. `POST /v1/public/feeds/{token}/checkout/start` принимает необязательный объект `attribution`; длины
   ограничены (256), неизвестные ключи отбрасываются, ошибка валидации никогда не ломает покупку.
3. Миграция: таблица `order_attribution (order_id PK, utm_*, fbclid, gclid, ttclid, ref, landing_url,
   first_seen_at)` — без PII; `fbc` вычисляется из `fbclid` по правилам Meta (`fb.1.<ts>.<fbclid>`).
4. Источник виден в карточке заказа (admin-web) и в `GET /v1/organizations/{org}/orders/{id}`.
5. Шлюз WordPress-сайтов не трогаем: там аналитика на стороне сайта.

**Done when:** integration — checkout/start с `attribution` создаёт строку, повторный запрос идемпотентен;
заказ без `attribution` работает как раньше; openapi + codegen обновлены.

## SOC-03. Meta Pixel организатора на странице билетов

**Category:** Social selling / Tracking — NORMAL

**Problem:** на `tickets.arenasoldout.com` нет пикселей (grep по `apps/tickets-page` и `apps/widget` на
pixel/fbq — пусто). Реклама в Meta не может оптимизироваться на покупки.

**Steps:**
1. Настройка организации: `meta_pixel_id` (цифры, валидация формата). Публичная выдача через
   `GET /v1/public/pages/{org}` только ID пикселя.
2. Страница грузит пиксель только после согласия (SOC-05). События: `PageView`, `ViewContent`
   (мероприятие), `InitiateCheckout` (нажата «Оплатить», value + currency), `Purchase` (возврат со Stripe
   с оплаченным `checkout_token`) с `eventID = "order-<orders.system_id>"` — тот же, что в SOC-04, для
   дедупликации.
3. Пиксель не грузится внутри виджета, встроенного в чужой сайт (у Lampyris и Vino&Co свои пиксели) —
   только на собственной странице билетов.

**Done when:** unit — без согласия скрипт не вставляется; с согласием события уходят с правильными
параметрами (моки `fbq`); e2e mock — `Purchase` один раз на заказ даже при перезагрузке страницы.

## SOC-04. Meta Conversions API: серверная покупка из arena

**Category:** Social selling / Tracking — MAJOR

**Problem:** во встроенном браузере Instagram/Facebook и на iOS пиксель теряет заметную часть покупок; без
серверного события оптимизация рекламы слепнет. В arena есть fan-out outbox с лёгкой ногой уведомлений
(`internal/platform/salesnotify`, реагирует на `v1.order.paid`) — образец для новой ноги.

**Steps:**
1. Настройка организации: `meta_pixel_id` (из SOC-03), секрет `meta_capi_access_token`, флаг
   `meta_capi_enabled`, необязательный `test_event_code` для проверки в Events Manager.
2. Пакет `internal/platform/metacapi`: нога outbox на `v1.order.paid` (и `v1.ticket.refunded` — не
   отправлять; Meta не принимает возвраты как событие, только фиксировать в логе счётчиком). Только ставит
   задачу в `worker_jobs` и всегда возвращает nil, как `salesnotify`, чтобы не задерживать вебхуки сайтов и
   MACS; дедуп по `order_id`.
3. Отправка `Purchase`: `event_id = "order-<system_id>"`, `event_time` = время оплаты, `action_source =
   website`, `event_source_url`, `value`/`currency` из `orders.total` (major units через общий конвертер),
   `user_data`: SHA-256 от нормализованных e-mail и телефона (E.164) — только при наличии основания
   (SOC-05), `fbc` из SOC-02, `client_ip_address` и `client_user_agent` из запроса checkout/start (сохранить
   на заказе, не логировать).
4. Ретраи с backoff, отказ после N попыток — строка в `ops_alerts` через существующий сторож; метрика
   с ограниченными метками (как `arena_payment_webhook_*`).
5. Только для заказов с `orders.source = 'public_feed'` (страница билетов и виджет); шлюз сайтов — нет.

**Done when:** integration со стабом Meta Graph API — оплата создаёт ровно одну отправку с правильным
`event_id` и хэшами; повтор вебхука оплаты не шлёт второй раз; отказ Meta не влияет на выпуск билетов и
вебхуки сайтов/MACS; секрет не появляется ни в одном ответе API и логе.

## SOC-05. Согласие на cookies и маркетинг на странице билетов

**Category:** Compliance — MAJOR (блокирует SOC-03/04 в ЕС)

**Problem:** на странице билетов нет баннера согласия; без него пиксель в ЕС ставить нельзя, а передача
хэшей в Conversions API требует основания.

**Steps:**
1. Лёгкий баннер согласия на странице билетов (без сторонних CMP): «Только необходимые» / «Разрешить
   аналитику и рекламу»; выбор хранится 6 месяцев; язык — язык страницы; RTL для иврита.
2. Выбор передаётся в checkout/start (`consent.marketing_tracking: true/false`) и сохраняется в заказе;
   SOC-04 отправляет `user_data` только при `true`, иначе событие без хэшей или не отправляется —
   **выбор режима — решение владельца** (см. «Открытые вопросы»).
3. Виджет, встроенный в чужой сайт, баннер не показывает: согласием управляет сайт.

**Done when:** e2e mock — до согласия нет запросов к `connect.facebook.net`; после отказа — тоже нет;
согласие видно в заказе; a11y-гейт axe зелёный.

## SOC-06. Генератор ссылок для рекламы и настройки Meta в админке

**Category:** Social selling / Organizer tools — NORMAL

**Problem:** организатору (пока — владельцу за него) негде собрать ссылку из SOC-01 с UTM и завести пиксель.

**Steps:**
1. В карточке мероприятия admin-web блок «Ссылки для рекламы»: выбор сеанса, категории, количества,
   промокода и UTM (источник: facebook / instagram / telegram / whatsapp / другое; кампания; объявление) →
   готовая ссылка, кнопка «Скопировать», QR-код PNG для афиш и сторис.
2. В настройках организации — раздел «Meta»: ID пикселя, токен Conversions API (ввод как у платёжных
   ключей: readOnly + «Заменить», без автозаполнения менеджером паролей), кнопка «Проверить» (тестовое
   событие с `test_event_code`), признак «последняя отправка ок / ошибка».
3. Всё через org-scoped API, чтобы потом перенести в ивент-центр без изменения бэкенда.

**Done when:** vitest на сборку ссылки и QR; e2e на сохранение настроек; токен после сохранения не
читается обратно.

## SOC-08. Проверка во встроенных браузерах Instagram и Facebook

**Category:** QA — MAJOR (приёмка волны)

**Problem:** Facebook и Instagram открывают ссылки во встроенном браузере; там обычно недоступен Apple Pay,
ограничен Google Pay, может теряться sessionStorage при переходах.

**Steps:** ручной прогон на iOS и Android из поста и из сторис (владелец): ссылка SOC-01 → оплата тестовой
картой → возврат со Stripe → билет на экране и в письме; пиксель виден в Events Manager, серверное событие
дедуплицировано. Результат — в `docs/testing/`. Если sessionStorage теряется — хранить UTM в `checkout_token`
на сервере (SOC-02 шаг 2 уже это позволяет).

**Done when:** протокол прогона с обеих платформ, найденные дефекты заведены отдельными фичами.
